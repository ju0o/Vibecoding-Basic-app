A01 · PRODUCT & BUSINESS

바이브코딩 응용·수익화반

이미 만든 프로젝트를 누군가 사용하는 상품으로 바꾸는 과정입니다. 기술보다 고객, MVP, 가격, 결제, 출시와 개선 판단이 중심입니다.

  • 대상: 기초반 프로젝트를 보유한 수강생
  • 최종 결과: 공개 가능한 작은 상품 또는 포트폴리오
  • 강사의 역할: 기능 추가보다 범위와 우선순위 코칭
X01 · AGENTIC WORKFLOW

AI 워크스페이스 심화반

MCP, Skill, Agent와 SubAgent를 연결해 반복 업무를 실행하는 작업 시스템을 만드는 과정입니다. 권한, 검증과 관찰 가능성이 중심입니다.

  • 대상: AI IDE와 파일 구조에 익숙한 수강생
  • 최종 결과: 실제 업무 한 사이클을 처리하는 AI 작업실
  • 강사의 역할: 자동화보다 작업 경계와 실패 복구 코칭
A01 · FOUR SESSIONS

응용·수익화반 4강 구성

네 번 안에 끝내려면 결제 코딩보다 “누가 왜 쓰는가”와 출시 가능한 범위를 반복해서 확인해야 합니다.

01

만들 것보다 팔릴 이유

고객, 상황, 문제, 기존 대안과 가치 제안을 한 문장으로 정리하고 인터뷰 질문을 만듭니다.

산출물: 고객 문제 정의서 + 가치 제안
02

MVP와 상품 구조

SaaS, 포트폴리오, 외주, 내부도구에 따라 필요한 화면과 관리자 기능, 완성 기준을 구분합니다.

산출물: 핵심 사용자 흐름 + MVP 제외 목록
03

가격과 결제 흐름

무료, 일회성, 구독 모델을 비교하고 가격표부터 결제 성공·실패·환불·고객지원 화면까지 설계합니다.

산출물: 가격 가설 + 결제 전후 화면 지도
04

출시와 첫 고객

소개 문구, 공개 URL, 측정할 행동, 피드백 수집과 다음 개선 우선순위를 정하고 작은 출시를 실행합니다.

산출물: 출시 체크리스트 + 2주 개선 계획
X01 · SIX SESSIONS

AI 워크스페이스 심화반 6강 구성

도구 연결부터 시작해 재사용 지침, 단일 Agent, 여러 Agent, 개인 작업실 순으로 복잡도를 한 단계씩 높입니다.

01

MCP와 외부 도구 연결

산출물: 개인 업무 Skill 1개

리서치, 구현, QA 역할을 분리하고 manager 방식과 handoff 방식의 차이를 실습합니다.

산출물: 개인 AI 작업실 구조

AI 운영체계 쇼케이스

실제 반복 업무 하나를 자동화하고 성공 기준, 실패 장면, 비용과 사람이 확인할 지점을 발표합니다.

산출물: 업무 자동화 데모 + 운영 문서
WHAT TO STUDY

강사가 먼저 공부할 내용

제품 이름과 명령어는 바뀔 수 있습니다. 아래 개념과 판단 기준을 먼저 익히면 도구가 바뀌어도 수업을 유지할 수 있습니다.

01 · PRODUCT

상품과 MVP

문제 인터뷰, 가치 제안, 핵심 사용자 흐름, MVP 제외 기준, 가격 가설과 전환 지표를 공부합니다.

설명 가능해야 하는 질문
  • 좋은 아이디어와 좋은 상품은 무엇이 다른가?
  • 기능을 어디까지 빼도 MVP인가?
  • 무료와 유료의 경계는 어떻게 정하는가?
02 · MCP

연결과 권한

MCP는 AI 앱과 외부 데이터·도구를 연결하는 표준입니다. 연결 성공보다 어떤 권한을 언제 허용할지가 중요합니다.

설명 가능해야 하는 질문
  • API와 MCP는 무엇이 다른가?
  • tool, resource, prompt의 역할은 무엇인가?
  • 쓰기 권한은 왜 단계적으로 열어야 하는가?
03 · SKILL

재사용 지침

좋은 Skill은 긴 프롬프트 저장본이 아니라 트리거, 입력, 절차, 산출물과 실패 기준을 가진 작업 규격입니다.

설명 가능해야 하는 질문
  • 프롬프트 템플릿과 Skill의 차이는?
  • 어떤 작업을 Skill로 만들면 안 되는가?
  • 검증 단계를 어디에 넣어야 하는가?
04 · AGENT

도구를 쓰는 실행 주체

Agent는 지침과 도구를 가지고 목표를 향해 여러 단계를 실행합니다. 종료 조건과 사람이 확인할 지점이 반드시 필요합니다.

설명 가능해야 하는 질문
  • 챗봇과 Agent의 차이는?
  • 언제 단일 Agent가 충분한가?
  • 무한 반복과 잘못된 도구 호출을 어떻게 막는가?
05 · TEAMS

역할 분담과 인수인계

SubAgent는 별도 맥락과 제한된 도구로 특정 작업을 처리합니다. 팀 수를 늘리는 것보다 경계와 결과 형식이 중요합니다.

설명 가능해야 하는 질문
  • manager와 handoff 방식의 차이는?
  • 병렬 작업이 오히려 느려지는 경우는?
  • 두 Agent가 같은 파일을 고치면 어떻게 하는가?
06 · OPERATIONS

관찰과 품질 관리

도구 호출, handoff, guardrail과 실패를 기록해 무엇이 잘못됐는지 볼 수 있어야 실제 업무에 사용할 수 있습니다.

설명 가능해야 하는 질문
  • 성공 여부를 무엇으로 평가하는가?
  • 로그와 tracing은 왜 필요한가?
  • 비용과 속도는 어디에서 측정하는가?
TEACHING PRINCIPLES

수업에서 반드시 지킬 네 가지

심화 수업일수록 화려한 자동화보다 권한과 검증을 먼저 보여줘야 수강생이 실제 업무에서 안전하게 응용할 수 있습니다.

01

읽기부터 시작

MCP와 Agent 도구는 먼저 조회만 허용하고, 결과를 확인한 뒤 쓰기와 실행 권한을 엽니다.

02

단일 Agent 우선

한 Agent로 설명 가능한 작업에 팀을 만들지 않습니다. 역할 충돌이 생길 때만 분리합니다.

03

검증 가능한 산출물

“잘 처리했다”가 아니라 파일, 표, 테스트 결과처럼 사람이 확인할 수 있는 결과를 요구합니다.

04

실패 장면 포함

성공 데모뿐 아니라 권한 거부, 잘못된 도구 선택, 불완전한 handoff를 복구하는 장면을 가르칩니다.

EXPECTED QUESTIONS

예상 질문과 답변 기준

답변은 특정 제품의 기능 홍보보다 개념의 경계와 선택 기준을 설명하는 방향으로 준비합니다.

MCP를 쓰면 API를 몰라도 되나요?

아닙니다. MCP는 연결 형식을 표준화하지만 실제 서비스가 제공하는 권한, 데이터 구조와 실패 응답은 여전히 이해해야 합니다.

Skill은 프롬프트 저장 기능인가요?

프롬프트가 일부일 수 있지만, 좋은 Skill은 언제 사용하고 어떤 입력을 받아 어떤 절차와 검증을 거쳐 무엇을 반환할지까지 포함합니다.

Agent를 많이 만들수록 더 잘하나요?

아닙니다. 역할과 결과 형식이 분명하지 않으면 중복 작업과 충돌이 늘어납니다. 단일 Agent로 시작하고 맥락 분리나 전문 역할이 필요할 때만 나눕니다.

Agent Teams는 사람 조직처럼 만들면 되나요?

비유는 가능하지만 실제 설계에서는 도구 권한, 입력과 출력 계약, 파일 소유권, 종료 조건과 실패 시 되돌아갈 주체가 더 중요합니다.

완전 자동화하면 사람이 필요 없나요?

고위험 작업, 돈과 개인정보, 외부 공개, 삭제 작업은 사람이 승인해야 합니다. 자동화의 목표는 사람을 제거하는 것이 아니라 반복 판단을 줄이는 것입니다.

어떤 업무를 첫 자동화 대상으로 고르나요?

반복 빈도가 높고 입력과 결과가 명확하며 실패해도 되돌리기 쉬운 업무가 좋습니다. 모호한 전략 판단이나 한번뿐인 작업은 첫 대상으로 적합하지 않습니다.
