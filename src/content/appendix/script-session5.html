TEACHER SCRIPT · SESSION 05 · 13 SLIDES

배포와 보안 그리고 데이터

수강생이 자신의 프로젝트를 localhost에서 GitHub, 안전한 배포 환경, 실제 공개 URL까지 이어 보도록 돕는 60분 운영 대본입니다.

수업 목표변경 기록, 비밀값, 데이터 권한, 배포 URL이 하나의 공개 과정이라는 점을 이해시킨다.
진행 방식핵심 단계는 버튼을 눌러 수동 진행한다. 배포 파이프라인만 시작 후 자동 진행을 허용하고 언제든 일시정지한다.
시간이론·시연 30분, 개인 프로젝트 적용 실습 30분. 서비스별 가격·한도·정책은 수업 전 공식 문서에서 다시 확인한다.
1

서비스를 세상 밖으로

SAY
“오늘은 코드를 더 예쁘게 만드는 시간이 아니라, 내 컴퓨터 안의 프로젝트를 실제 사람이 접속하는 서비스로 바꾸는 시간입니다. GitHub에 기록을 남기고, 비밀값을 분리하고, 공개 URL에서 다시 확인하는 흐름을 한 번에 보겠습니다.”
DO
LOCAL → GITHUB → SECURE → LIVE URL을 손으로 짚는다. 오른쪽 실제 GitHub·Vercel 화면은 ‘도구 이름’보다 ‘프로젝트가 이동하는 증거’로 보여준다.
ASK
“지금 여러분 프로젝트는 나만 보는 localhost인가요, 친구도 URL로 들어올 수 있는 상태인가요?”
2

내 컴퓨터와 공개 URL

SAY
“왼쪽과 오른쪽의 화면 디자인은 같습니다. 차이는 디자인이 아니라 실행되는 장소입니다. localhost는 내 노트북이 잠깐 서버 역할을 하는 상태입니다. 배포 뒤에는 배포 서비스의 서버가 같은 파일을 제공하고, 외부 사용자는 주소를 통해 접속합니다.”
DO
`공개 URL 만들기`를 눌러 중앙 실행 환경의 신호가 바뀌고 오른쪽 기기들이 연결되는 장면을 보여준다. 설명을 먼저 길게 하지 말고, 차단/허용의 변화가 보인 뒤 말한다.
오해 방지
배포는 도메인을 반드시 사는 일이 아니다. Vercel 같은 배포 서비스는 기본 공개 URL을 제공한다. 맞춤 도메인은 이후의 선택 작업이다. Firebase Hosting은 필요할 때 선택할 수 있는 별도 Hosting 경로다.
3

Git 명령어와 GitHub 확인

SAY
“명령어는 어려운 주문이 아니라 프로젝트의 상태를 바꾸는 말입니다. `git status`는 무엇이 바뀌었는지 확인하고, `git add .`은 이번 기록에 넣을 파일을 고르고, `git commit -m`은 변경 이유와 함께 저장 지점을 만들고, `git push`는 그 기록을 GitHub로 보내는 일입니다.”
DO
왼쪽에서 `status → add → commit → push`를 한 단계씩 누른다. 매 단계마다 가운데 터미널과 오른쪽 확인 위치를 함께 가리킨다. 특히 commit은 내 PC의 저장 지점이고, push가 끝난 뒤에야 GitHub의 Commits 탭에서 보인다고 분명히 구분한다.
ASK
“AI가 수정한 파일이 의도한 것인지 확인하려면 가장 먼저 어떤 명령어를 볼까요?” 정답은 `git status`다. “GitHub에서 그 기록을 보려면 마지막에 무엇이 필요할까요?” 정답은 `git push`다.
오류 복구
`nothing to commit`은 지금 기록할 변경이 없다는 뜻이다. `rejected`는 GitHub 쪽이 더 최신일 수 있으니, 바로 강제 push 하지 말고 `git pull`과 충돌 메시지를 먼저 AI와 확인한다.
4

GitHub에 남는 변경 기록

SAY
“GitHub에서는 세 가지를 구분해서 봅니다. Commits는 무엇이 바뀌었는지 남긴 기록, Releases는 검증해서 이름을 붙인 배포 기준점, Deployments는 실제 Production에 어떤 버전이 올라갔는지 보여주는 곳입니다. 모든 commit을 바로 배포하는 것은 아닙니다.”
DO
`다음 기록`을 눌러 Code → Commit → Push → Release 순서로 보여준다. Release 단계에서는 중앙의 `a8f21c3 → v1.0.0 → Production` 흐름을 가리킨다. “문제가 생겼을 때 무엇을 되돌릴지 알기 위해, 배포 버전에 이름을 붙입니다”라고 말한다.
릴리즈 구분
`v1.0.0`은 처음 공개할 수 있는 기준점, `v1.0.1`은 버그 수정처럼 작은 수정, `v1.1.0`은 이전 사용법을 크게 깨지 않는 기능 추가로 설명한다. 처음에는 숫자를 외우게 하지 말고, “배포할 버전에 이름을 붙여 되돌아갈 기준을 남긴다”만 이해시키면 된다.
ASK
“오늘 버튼 문구 하나를 고쳤다고 바로 모든 사용자에게 배포해야 할까요? 검토하고 확인한 버전만 배포한다면 무엇이 좋아질까요?”
5

GitHub 협업과 프로젝트 내려받기

SAY
“ZIP은 결과물을 한 번 받아볼 때는 편합니다. 하지만 수정한 것을 다시 올리고, 팀원의 변경을 받으려면 GitHub와 연결된 clone 방식이 필요합니다. 협업의 핵심은 누가 파일을 많이 갖고 있느냐가 아니라, 모두가 같은 기준점을 보고 안전하게 합치는 것입니다.”
DO
`clone → pull → checkout → push → PR → merge`를 순서대로 클릭한다. `pull`은 시작 전 최신 설계도를 받는 단계, `checkout`은 main을 건드리지 않는 내 공사 구간, PR은 준공 전 검수대, merge/release는 검증한 버전만 공개하는 단계라고 연결한다.
실습 연결
팀 실습은 시작 전 `git pull`부터 한다. 각자 같은 `main`을 직접 수정하지 말고, 작은 수정도 자기 branch에서 진행한 뒤 push한다. GitHub에서 Pull Request로 바뀐 파일과 이유를 검토한 뒤 main에 합치고, 확인한 버전에만 release를 붙인다.
오류 복구
충돌이 나면 “어느 파일, 어떤 두 변경이 충돌하는지, 유지할 문장이 무엇인지”를 AI에게 함께 전달한다. 충돌을 모른 채 덮어쓰거나 강제 push 하지 않는다.
6

브라우저에서 확인하는 공개 요청

SAY
“F12 개발자도구는 개발자만 쓰는 비밀 창이 아닙니다. 공개된 웹사이트를 보는 사람은 브라우저가 주고받는 요청과 내려받은 파일을 확인할 수 있습니다. 그래서 브라우저로 보내는 코드 안에는 진짜 비밀키를 두면 안 됩니다.”
DO
`다음 확인`을 한 번씩 눌러 F12 → Network → 요청 헤더 → 키 폐기 순서로 진행한다. 마지막 빨간 경고가 나오면 ‘삭제’가 아니라 ‘폐기 후 재발급’이라고 말한다.
예상 질문
Q. Firebase 웹 설정의 API key도 보이면 위험한가요? A. 프로젝트 식별용 공개 설정값과 결제·AI·서비스 계정 비밀키는 다르다. 실제 데이터 접근은 Security Rules와 인증 조건으로 한 번 더 막아야 한다.
7

비밀값과 배포 환경

SAY
“`.env.local`은 내 PC에서만 쓰는 실제 값입니다. `.gitignore`는 그 파일이 GitHub 기록에 들어가지 않도록 막습니다. 배포할 때는 같은 값을 Vercel이나 Firebase 같은 배포 환경의 설정 화면에 따로 넣습니다.”
DO
`다음 전달`을 두 번 눌러 비밀 상자가 local → gitignore → deployment로 움직이게 한다. `.env.example`은 실제 값이 아니라 변수 이름을 공유하는 견본이라고 짚는다.
오류 복구
배포 성공 뒤 로그인·AI 호출이 실패하면 가장 먼저 환경변수 이름, 배포 서비스의 Production/Preview 환경, 재배포 여부를 확인한다. 값 자체를 빔 화면에 노출하지 않는다.
8

데이터 접근 규칙

SAY
“데이터베이스는 창고이고, 보안 규칙은 창고 문을 여는 기준입니다. 로그인했다고 모든 데이터를 보는 것이 아닙니다. 비회원은 공개 정보만, 회원은 자기 주문만, 관리자는 운영에 필요한 정보만 다루도록 역할을 나눕니다.”
DO
비회원 → 회원 → 관리자를 차례로 누른다. 오른쪽 주문 카드의 설명과 허용/차단이 바뀌는 것을 보여준 뒤, 왼쪽 실제 Firebase 규칙 문서와 겹쳐 놓은 조건문을 연결한다.
ASK
“로그인한 학생 A가 학생 B의 주문 내역을 볼 수 있어야 할까요? 그 판단은 화면 버튼이 아니라 어디에서 막아야 할까요?”
9

Vercel과 Firebase의 역할

SAY
“Vercel과 Firebase 중 하나가 무조건 더 좋은 것이 아닙니다. Vercel은 GitHub의 웹 프로젝트를 빌드해서 공개 URL로 연결하는 데 강하고, Firebase는 로그인·데이터·파일 저장 기능을 연결하는 앱 플랫폼입니다.”
DO
Vercel과 Firebase 카드를 번갈아 누른다. 마지막으로 Vercel + Firebase 문장을 읽어, 화면 공개와 데이터 기능을 함께 쓸 수 있음을 설명한다.
주의
수업 중 서비스 가격, 무료 한도, 정책은 고정값으로 말하지 않는다. 계정 상태와 시점에 따라 달라질 수 있으므로 수업 전 공식 가격·문서를 재확인한다.
10

한 번의 release가 공개 URL이 되기까지

SAY
“배포는 파일을 여기저기 따로 올리는 일이 아닙니다. GitHub에서 검증한 release 하나를 선택하고, Vercel이 웹 build를 만들고, 필요한 환경변수와 Firebase 기능을 연결한 뒤 공개 URL을 엽니다. 그래서 무엇이 실제로 공개됐는지와 되돌릴 기준이 한 번에 남습니다.”
DO
기본은 `시작`을 눌러 release → build → 환경·기능 연결 → URL 순서를 자동 재생한다. 설명이 필요하면 `일시정지`, 특정 지점만 보일 때는 `다음`, 처음부터 재현할 때는 `초기화`를 사용한다. Vercel은 웹을 build해 URL로 공개하고, Firebase는 필요한 로그인과 데이터 규칙을 제공한다는 역할 구분을 계속 유지한다.
ASK
“URL이 만들어졌지만 화면이 하얗다면 release가 맞는지, build가 통과했는지, 환경변수와 Firebase 연결이 맞는지 순서대로 봅니다. 로그의 첫 오류부터 확인합니다.”
11

공개 전 최종 점검

SAY
“배포 성공이라는 초록 표시만 보고 링크를 보내지 않습니다. 사용자가 실제로 하는 로그인, 저장, 모바일 화면, 권한 확인을 공개 URL에서 다시 해봐야 합니다.”
DO
네 항목은 한 번에 모두 체크하지 않는다. 학생이 실제 URL에서 확인했다는 대답을 할 수 있을 때만 한 항목씩 누른다.
완성 기준
URL이 열린다는 것만이 아니라, 핵심 기능이 동작하고 비밀값과 데이터 접근 규칙이 의도대로 작동하는 상태다.
12

30분 실습

SAY
“지금부터는 제 화면을 보지 말고, 여러분 프로젝트의 공개 과정을 직접 진행해보겠습니다. 막히면 명령 하나만 보내지 말고, 실행한 명령과 첫 오류, 관련 파일, 원했던 결과를 함께 정리해서 AI에게 전달하세요.”
DO
30분 타이머를 시작한다. 10분 지점에는 GitHub 기록, 20분 지점에는 환경변수/배포 시도, 종료 5분 전에는 실제 URL 체크를 안내한다.
대체 화면
인터넷이나 계정 로그인이 막히면 학생은 `.env.example`, `.gitignore`, 배포 전 체크리스트를 먼저 작성한다. 강사는 미리 준비한 성공 배포 로그 화면으로 흐름을 유지한다.
13

다음 강의 예고

SAY
“다음 시간에는 완성한 프로젝트를 함께 보고 피드백합니다. 잘 만든 결과만 발표하는 시간이 아니라, 어떤 요청으로 어디가 바뀌었고 어떤 문제가 남았는지를 서로 배우는 쇼케이스입니다.”
과제 안내
공개 URL 또는 실행 화면, 오늘 바꾼 핵심 한 가지, 막힌 지점 한 가지를 기록해 둔다. 결과가 완성되지 않아도 작업 과정이 있으면 충분히 발표할 수 있다.
강사 리허설GitHub 로그인, Vercel 또는 Firebase 계정, 테스트 저장소, .env.example, 공개 URL, 실패 build 로그의 스크린샷을 수업 전 확인한다.
공식자료 재확인GitHub Docs, Vercel Docs의 Git deployment/environment variables, Firebase Authentication·Firestore Security Rules 문서를 수업 직전에 확인한다.
