TEACHER SCRIPT · SESSION 05 · 22 SLIDES

배포와 보안 그리고 데이터

수강생이 자신의 프로젝트를 localhost에서 빌드·GitHub·안전한 배포 환경·실제 공개 URL까지 이어 보도록 돕는 운영 대본입니다. 이론·시연만으로 약 60분, 이후 개인 프로젝트 적용 실습 30분.

수업 목표빌드와 배포, 변경 기록, 신뢰 경계와 비밀값, 데이터 권한, 공개 URL이 하나의 ‘공개 과정’이라는 점을 이해시킨다.
진행 방식핵심 단계는 버튼으로 수동 진행한다. 배포 파이프라인만 자동 재생 후 언제든 일시정지. 비유 슬라이드(책·컨베이어·집·건물)는 애니메이션을 먼저 보여주고 설명은 짧게 덧붙인다.
라이브 시연 창우측 상단 ‘라이브 시연’ 버튼 또는 단축키 T(터미널)·F(파일트리)·C(코드)로 가상 샌드박스를 띄운다. git·빌드·파일 구조를 VS Code 없이 즉석에서 시연한다. 실제 디스크에는 영향이 없다(Esc로 닫기).
시간이론·시연 약 60분(슬라이드 20여 장 × 평균 3분). 가격·무료 한도·정책은 수업 전 공식 문서에서 다시 확인한다.
1

서비스를 세상 밖으로 (커버)

SAY
“오늘은 코드를 더 예쁘게 만드는 시간이 아니라, 내 컴퓨터 안의 프로젝트를 실제 사람이 접속하는 서비스로 바꾸는 시간입니다. 빌드해서 올리고, 비밀값을 분리하고, 공개 URL에서 다시 확인하는 흐름을 한 번에 보겠습니다.”
DO
LOCAL → GITHUB → SECURE → LIVE URL을 손으로 짚는다. 배경의 실제 GitHub·Vercel 화면은 ‘도구 이름’보다 ‘프로젝트가 이동하는 증거’로 보여준다.
ASK
“지금 여러분 프로젝트는 나만 보는 localhost인가요, 친구도 URL로 들어올 수 있는 상태인가요?”
2

오늘의 지도

SAY
“오늘은 세 덩어리입니다. 배포는 공개, 보안은 보호, 데이터는 기억. 이 한 문장만 기억하면 오늘 길을 잃지 않습니다.”
DO
배포·보안·데이터 세 카드를 차례로 짚는다. 카드 설명을 그대로 읽지 말고 “이게 왜 ‘공유하기 전에’ 필요한지”로 연결한다.
TIP
슬라이드가 많아 지칠 때 이 지도로 돌아와 “지금은 보안 구간”처럼 현재 위치를 짚어주면 집중이 회복된다.
3

내 컴퓨터와 공개 URL

SAY
“왼쪽과 오른쪽은 같은 화면입니다. 차이는 디자인이 아니라 실행되는 장소예요. 내 노트북을 끄면 사라지고 방문자는 0명. 배포하면 서버가 대신 켜져 있어, 내 노트북을 꺼도 누구나 주소로 들어옵니다.”
DO
`공개 URL 만들기`를 눌러 신호가 바뀌고 오른쪽 기기들이 연결되는 장면을 먼저 보여준 뒤 말한다. ‘끄면 사라짐 → 꺼도 접속’의 대비가 핵심.
오해 방지
배포는 도메인을 반드시 사는 일이 아니다. Vercel 같은 서비스는 기본 공개 URL을 제공한다. 맞춤 도메인은 이후의 선택 작업이다.
4

배포는 빌드해서 올리는 과정 (책 비유)

SAY
“배포는 파일을 그대로 복사하는 게 아닙니다. 원고(코드)를 인쇄(빌드)해서 책(정적 파일)으로 만들고, 서점(서버)에 배본해서 독자(사용자)가 보는 일이에요. `npm run build`가 그 ‘인쇄’ 단계입니다.”
DO
원고 → 인쇄·제작 → 서점 배본 → 독자 이용 애니메이션을 한 바퀴 보여준다. 가운데 ‘인쇄=npm run build’가 켜질 때 강조한다.
TIP
“‘배포가 안 돼요’의 절반은 빌드 단계에서 막힙니다. 내 PC에서 `npm run build`가 먼저 통과하는지 확인하세요.” 원하면 라이브 시연(T)에서 `npm run build`를 쳐서 보여준다.
5

로컬과 서버는 다른 환경

SAY
“‘내 컴퓨터에선 되는데 배포하면 안 돼요’의 이유입니다. 내 PC는 환경변수가 이미 다 있고 경로·대소문자에 관대하지만, 배포 서버는 환경변수를 따로 넣어야 하고 리눅스라 대소문자에 엄격합니다.”
DO
왼쪽(LOCAL)·오른쪽(SERVER) 비교를 짚고, 아래 흔한 원인 3가지(환경변수 누락 / 대소문자 불일치 / 빌드에서만 나는 오류)를 하나씩 읽는다.
오류 복구
순서: 로컬에서 `npm run build` → 배포 서비스에 환경변수 채우기 → 배포 로그의 첫 빨간 줄 확인. 이 순서가 대부분을 해결한다.
6

Git 명령어와 GitHub 확인

SAY
“명령어는 어려운 주문이 아니라 프로젝트 상태를 바꾸는 말입니다. `git status`는 무엇이 바뀌었는지, `git add .`은 기록할 파일 선택, `git commit -m`은 이유와 함께 저장 지점, `git push`는 그 기록을 GitHub로 전송입니다.”
DO
왼쪽 레일에서 status → add → commit → push를 한 단계씩 누르고, 매번 가운데 터미널과 오른쪽 ‘확인 위치(GitHub 페이지)’를 함께 가리킨다. commit은 내 PC, push 뒤에야 GitHub Commits 탭에서 보인다고 분명히 구분.
라이브 시연
단축키 T로 터미널을 띄워 `git status` → `git add .` → `git commit -m "..."` → `git push`를 직접 타이핑해 보여줄 수 있다. ‘구현한 명령’의 결과는 F(파일트리)에서 시각적으로 확인.
오류 복구
`nothing to commit`은 기록할 변경 없음. `rejected`는 GitHub가 더 최신일 수 있으니 강제 push 대신 `git pull`과 충돌 메시지를 먼저 AI와 확인한다.
7

push 한 번이 자동 배포로 (컨베이어 비유)

SAY
“코드를 벨트(GitHub)에 올리면 공장(Vercel)이 자동으로 포장(빌드)해서 매대(URL)에 올립니다. 매번 손으로 옮기지 않아요. 그래서 자주, 작게 push하는 게 안전합니다.”
DO
컨베이어 벨트 위로 코드 상자가 BUILD 공장을 지나 공개 URL이 되는 애니메이션을 보여준다. 실패한 배포는 공개되지 않고 직전 버전이 그대로 유지된다는 점을 강조.
ASK
“버튼 문구 하나 고친 걸 매번 손으로 서버에 올려야 한다면? push 한 번으로 자동 배포되면 무엇이 편해질까요?”
8

주소(도메인)와 HTTPS

SAY
“배포하면 `my-project.vercel.app` 같은 무료 주소가 자동으로 생깁니다. 내 도메인을 사서 DNS로 연결하면 `my-shop.com`처럼 바꿀 수 있어요. 자물쇠(HTTPS)는 주고받는 내용을 암호화하고, 인증서는 자동으로 발급됩니다.”
DO
무료 주소 카드 → 내 도메인 카드 순서로 보여준다. 비유로 정리: 도메인은 간판, DNS는 내비게이션, HTTPS는 봉인된 택배.
주의
도메인 구매·DNS 연결은 기초반에선 ‘가능하다’ 수준만. 자세한 설정은 각 서비스 공식 문서를 수업 전 확인하고, 시연은 무료 주소까지만 한다.
9

프론트엔드는 모두에게 열려있다 (신뢰 경계)

SAY
“브라우저로 내려간 것은 누구나 열어볼 수 있습니다. 프론트엔드는 사용자 컴퓨터에서 실행되고 F12로 코드·요청이 다 보여요. 그래서 비밀값은 절대 프론트에 두면 안 되고, 서버에 둡니다.”
DO
왼쪽 OPEN(프론트)·오른쪽 CONTROLLED(서버) 비교를 짚는다. 이 슬라이드는 다음 F12 시연의 ‘왜’에 해당하므로 천천히.
ASK
“보안의 첫 질문은 항상 ‘이건 어디에서 실행되지?’ 입니다. 브라우저에서 실행되면 그건 이미 공개된 것일까요?” (그렇다)
10

브라우저에서 확인하는 공개 요청 (F12)

SAY
“F12 개발자도구는 개발자만 쓰는 비밀 창이 아닙니다. 공개된 사이트를 보는 사람은 브라우저가 주고받는 요청과 내려받은 파일을 볼 수 있어요. 그래서 코드에 진짜 비밀키를 박아두면 그대로 노출됩니다.”
DO
`결제하기` 또는 `다음 확인`을 눌러 F12 → Network → 요청 헤더 → 키 노출 → 폐기 순서로 진행한다. 비밀키가 코드에 보이는 장면에서 멈추고 “삭제가 아니라 폐기·재발급”이라고 말한다.
예상 질문
Q. Firebase 웹 설정의 API key도 보이면 위험한가요? A. 프로젝트 식별용 공개 설정값과 결제·서비스 계정 비밀키는 다르다. 실제 접근은 Security Rules로 한 번 더 막는다(14번).
11

비밀값과 배포 환경 (.env)

SAY
“`.env.local`은 내 PC에서만 쓰는 실제 값입니다. `.gitignore`가 그 파일이 GitHub에 올라가지 않게 막아요. 배포할 때는 같은 값을 Vercel·Firebase의 설정 화면에 따로 넣습니다.”
DO
`다음 전달`을 두 번 눌러 비밀 상자가 local → gitignore → deployment로 이동하는 걸 보여준다. `.env.example`은 값 없이 이름만 공유하는 견본이라고 짚는다.
오류 복구
배포 뒤 로그인·AI 호출이 실패하면 환경변수 이름, Production/Preview 환경, 재배포 여부를 먼저 확인한다. 값 자체를 화면에 노출하지 않는다.
12

공개해도 되는 값 vs 절대 안 되는 값 (집 비유)

SAY
“같은 ‘키’라도 성격이 다릅니다. 우리 집 주소(공개)는 알려줘도 되지만, 현관 비밀번호(비밀)는 절대 안 됩니다. 공개 API 주소·`VITE_` 붙은 값은 어차피 브라우저로 내려가도 되는 값, 결제 비밀키·DB 비밀번호는 노출 즉시 폐기해야 하는 값이에요.”
DO
PUBLIC·SECRET 두 카드를 비교한 뒤 집 그림(주소 표지판 vs 흔들리는 비밀번호 패드)으로 정리한다.
구분법
“이 값이 브라우저에 보여도 괜찮은가? 아니오면 무조건 서버 환경변수로.” 이 한 문장만 가져가면 된다.
13

인증과 인가 (건물 비유)

SAY
“로그인(인증)과 권한(인가)은 다른 질문입니다. 인증은 ‘너 누구야?’, 인가는 ‘넌 뭘 할 수 있어?’. 출입증으로 건물에 들어오는 것과, 갈 수 있는 층이 정해진 것은 달라요.”
DO
인증·인가 카드 비교 후 건물 그림(1F 내 정보 허용 ✓ / 2·3F 차단 ✕)으로 보여준다.
핵심
“로그인만 확인하고 권한 검사를 빠뜨리면, 로그인한 누구나 남의 데이터를 볼 수 있게 됩니다.” 다음 슬라이드(데이터 규칙)로 연결.
14

데이터 접근 규칙

SAY
“데이터베이스는 창고이고, 보안 규칙은 창고 문을 여는 기준입니다. 비회원은 공개 정보만, 회원은 자기 주문만, 관리자는 운영 정보만 다루도록 역할을 나눕니다.”
DO
비회원 → 회원 → 관리자를 차례로 누른다. 오른쪽 허용/차단이 바뀌는 걸 보여준 뒤, 왼쪽 실제 Firebase 규칙 조건문과 연결한다.
ASK
“로그인한 학생 A가 학생 B의 주문을 볼 수 있어야 할까요? 그 판단은 화면 버튼이 아니라 어디에서 막아야 할까요?” (서버·규칙)
15

데이터는 표처럼 쌓이고 네 가지로 다룬다 (CRUD)

SAY
“새로고침해도 사라지지 않는 정보는 데이터베이스에 ‘표’처럼 쌓입니다. 다루는 방법은 네 가지뿐이에요. 추가(Create)·조회(Read)·수정(Update)·삭제(Delete).”
DO
버튼을 직접 눌러 변화를 보여준다 — 추가는 ‘5 · 민준’ 행이 새로 생기고, 수정은 서연의 role이 수강생→관리자로 글자가 바뀌고, 삭제는 행이 접히며 사라지고, 조회는 데이터 변화 없이 훑기만 한다. 아래 상태 캡션을 같이 읽는다.
강조
‘조회는 데이터를 바꾸지 않는다’를 분명히. 화면의 거의 모든 기능이 결국 이 네 동작의 조합임을 한 문장으로 정리한다.
16

Vercel과 Firebase의 역할

SAY
“둘 중 하나가 무조건 더 좋은 게 아닙니다. Vercel은 GitHub의 웹 프로젝트를 빌드해 공개 URL로 연결하는 데 강하고, Firebase는 로그인·데이터·파일 저장을 연결하는 앱 플랫폼입니다. 함께 쓸 수도 있어요.”
DO
Vercel·Firebase 카드를 번갈아 누른다. 마지막 ‘Vercel + Firebase’ 문장으로 화면 공개와 데이터 기능을 함께 쓰는 그림을 정리한다.
주의
가격·무료 한도·정책은 고정값으로 말하지 않는다. 시점·계정에 따라 달라지므로 수업 전 공식 문서를 재확인한다.
17

에러와 로그 읽는 법

SAY
“배포가 실패하면 당황하지 말고 로그의 ‘빨간 줄’부터 봅니다. 에러 메시지는 혼내는 말이 아니라, 어디가 막혔는지 알려주는 이정표예요.”
DO
왼쪽 build.log의 빨간 Error 줄을 짚고, 오른쪽 5단계(멈춤 → 복사 → 질문 → 수정 → 재배포)를 읽는다. ‘질문’ 단계에서 상황+명령어+에러 전문을 함께 주는 게 핵심.
TIP
에러 한 줄만 던지지 말고 “무엇을 하려다, 어떤 명령에서, 어떤 에러가, 어느 파일에서” 났는지를 묶어서 AI에게 준다. 실습 막힘의 대부분이 여기서 풀린다.
18

무료 한도와 책임

SAY
“Vercel·Firebase 모두 개인 프로젝트는 무료 한도로 시작할 수 있습니다. 다만 무료가 무한은 아니에요. 방문자·저장량이 늘면 과금되고, 사용자 정보를 받는 순간부터는 책임이 생깁니다.”
DO
무료로 시작 · 비용 신호 · 개인정보 최소 · 백업 네 카드를 짚는다. ‘비밀번호는 직접 저장하지 말고 로그인 서비스에 맡긴다’를 강조.
주의
구체 한도 수치는 변한다. ‘무료로 시작 가능, 늘면 과금’ 수준만 전달하고, 정확한 값은 공식 문서로 안내한다.
19

한 번의 release가 공개 URL이 되기까지

SAY
“배포는 파일을 여기저기 따로 올리는 일이 아닙니다. 검증한 release 하나를 고르고, Vercel이 웹 build를 만들고, 필요한 환경변수·Firebase 기능을 연결한 뒤 공개 URL을 엽니다. 그래서 무엇이 공개됐고 무엇을 되돌릴지가 한 번에 남아요.”
DO
기본은 `시작`으로 release → build → 연결 → URL을 자동 재생. 설명이 필요하면 `일시정지`, 특정 지점만 보일 땐 `다음`, 재현은 `초기화`.
ASK
“URL은 생겼는데 화면이 하얗다면? release가 맞는지, build가 통과했는지, 환경변수·Firebase 연결이 맞는지 순서대로, 로그의 첫 오류부터 봅니다.”
20

공개 전 최종 점검

SAY
“배포 성공이라는 초록 표시만 보고 링크를 보내지 않습니다. 사용자가 실제로 하는 로그인·저장·모바일 화면·권한 확인을 공개 URL에서 다시 해봐야 해요.”
DO
네 항목을 한 번에 체크하지 않는다. 학생이 ‘실제 URL에서 확인했다’고 답할 수 있을 때만 한 항목씩 누른다.
완성 기준
URL이 열린다만이 아니라, 핵심 기능이 동작하고 비밀값·데이터 접근 규칙이 의도대로 작동하는 상태.
21

30분 실습

SAY
“지금부터는 제 화면을 보지 말고, 여러분 프로젝트의 공개 과정을 직접 진행합니다. 막히면 명령 하나만 보내지 말고, 실행한 명령·첫 오류·관련 파일·원했던 결과를 함께 정리해 AI에게 전달하세요.”
DO
30분 타이머 시작. 10분: GitHub 기록, 20분: 환경변수/배포 시도, 종료 5분 전: 실제 URL 체크를 안내한다.
대체 화면
인터넷·계정 로그인이 막히면 `.env.example`, `.gitignore`, 배포 전 체크리스트를 먼저 작성한다. 강사는 미리 준비한 성공 배포 로그 화면으로 흐름을 유지한다.
