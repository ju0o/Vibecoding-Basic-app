배포와 보안 그리고 데이터

현재 5강 슬라이드 구조에 맞춘 최종 강사 대본입니다. 수강생이 localhost의 프로젝트를 GitHub에 기록하고, 안전한 배포 환경으로 옮기고, 공개 URL에서 다시 검증하는 전체 흐름을 이해하도록 돕는 발표용 운영 대본입니다.

수업 목표배포는 공개, 보안은 보호, 데이터는 접근 규칙이라는 점을 연결해 설명한다. 특히 “브라우저에 내려간 것은 공개”라는 신뢰 경계를 확실히 심어준다.
권장 시간슬라이드 설명과 시연 55~65분, 이후 개인 프로젝트 적용 실습 30분. 버튼형 슬라이드는 자동으로 넘기지 말고 핵심 장면에서 반드시 멈춘다.
강의 원칙애니메이션은 먼저 보여주고, 설명은 나중에 짧게 얹는다. 카드의 문장을 읽기보다 “지금 무엇이 바뀌었는지”를 장면 중심으로 풀어준다.
라이브 시연필요하면 라이브 시연 창으로 git status, npm run build, .env.local, .gitignore를 바로 보여준다. 단, 실제 강의에서는 명령어를 오래 치기보다 결과를 읽어주는 데 집중한다.

1

표지 · 내 프로젝트가 인터넷의 서비스가 되는 순간

핵심 문장 “오늘은 기능을 더 만드는 시간이 아니라, 여러분 프로젝트를 ‘나만 보는 화면’에서 ‘누구나 들어올 수 있는 서비스’로 보내는 시간입니다.”
SAY

오늘 5강은 배포와 보안 그리고 데이터입니다. 이름만 들으면 각각 따로 배우는 것처럼 느껴질 수 있지만, 실제로는 하나의 공개 과정입니다. 내가 만든 프로젝트를 인터넷에 올리려면 먼저 버전을 기록해야 하고, 공개되면 안 되는 값은 코드 밖으로 빼야 하고, 공개된 뒤에는 누가 어떤 데이터를 볼 수 있는지까지 정해야 합니다.

그래서 오늘은 세 가지를 따로 암기하지 않습니다. “내 프로젝트가 세상 밖으로 나갈 때 무엇을 같이 챙겨야 하는가”라는 하나의 이야기로 보겠습니다.

DO
표지의 `LOCAL → GITHUB → SECURE → LIVE URL` 흐름을 왼쪽에서 오른쪽으로 천천히 짚는다. 오른쪽 실사 화면은 도구 설명용이 아니라 “내 프로젝트가 실제 서비스가 된다”는 증거 장면으로 사용한다.
ASK
“지금 여러분 프로젝트는 localhost에서만 열리나요, 아니면 친구가 URL로 들어올 수 있나요?” 한두 명에게 짧게 답변을 받아 분위기를 연다.
2

오늘의 지도

핵심 문장 “배포는 공개, 보안은 보호, 데이터는 기억입니다.”
SAY

오늘은 이 세 가지를 함께 봅니다. 배포는 내 프로젝트를 밖으로 공개하는 일입니다. 보안은 공개해도 되는 것과 숨겨야 하는 것을 구분하는 일입니다. 데이터는 새로고침해도 남는 정보와 그 접근 권한을 다루는 일입니다.

슬라이드가 길어질 수 있기 때문에, 중간에 길을 잃은 것 같으면 항상 이 세 단어로 돌아오면 됩니다. 지금 우리가 하고 있는 설명이 공개 쪽인지, 보호 쪽인지, 기억 쪽인지만 보면 흐름을 다시 잡을 수 있습니다.

DO
세 카드를 짚으면서 “오늘 이 세 가지를 따로 배우는 게 아니라 하나의 릴레이처럼 이어집니다”라고 연결한다.
3

내 컴퓨터와 공개 URL

핵심 문장 “같은 화면이라도, 어디에서 실행되느냐가 완전히 다릅니다.”
SAY

지금 왼쪽과 오른쪽 브라우저는 거의 같은 화면처럼 보입니다. 그런데 핵심 차이는 디자인이 아닙니다. 실행 위치입니다. 왼쪽은 내 컴퓨터 안에서만 켜진 화면이고, 오른쪽은 주소를 가진 누구나 들어올 수 있는 공개 URL입니다.

여기서 학생들이 자주 하는 오해가 있습니다. 배포를 하면 화면이 더 예뻐지거나 더 화려해지는 것처럼 느끼기도 하는데, 사실 배포는 디자인 작업이 아닙니다. 같은 프로젝트를 내 노트북 밖의 실행 환경으로 옮겨서, 내가 꺼도 계속 켜져 있게 만드는 작업입니다.

DO
`공개 URL 만들기`를 눌러 로컬 → 공개 상태 변화가 일어나는 장면을 먼저 보여준 뒤 설명한다. “접속자 1명 → 여러 사용자” 대비를 꼭 짚는다.
강조 문장
“배포는 브라우저를 바꾸는 일이 아니라, 프로젝트가 실행되는 장소를 바꾸는 일입니다.”
4

배포는 빌드해서 올리는 과정

핵심 문장 “코드는 원고이고, build는 그 원고를 읽을 수 있는 책으로 만드는 과정입니다.”
SAY

수강생이 가장 많이 헷갈리는 부분입니다. 배포는 파일 복사가 아닙니다. 코드 원고를 바로 서점에 올리는 게 아니라, 먼저 사람이 읽을 수 있는 책으로 제작해야 합니다. 그 제작 단계가 build입니다.

그래서 `npm run build`는 형식적인 확인 버튼이 아니라, “이 코드가 실제 공개 가능한 결과물로 만들어질 수 있는가”를 검증하는 과정입니다. 이 단계를 통과하지 못하면 공개는 시작조차 못 합니다.

DO
`다음 장면`으로 원고 작성 → 책 제작 → 서점 진열 → 독자 이용을 천천히 한 바퀴 보여준다. 두 번째 장면에서 `npm run build = 책 제작`이라고 분명히 말한다.
TIP
“배포가 안 돼요”라고 말하는 학생이 있으면 가장 먼저 “로컬에서 `npm run build`는 통과하나요?”부터 묻게 습관을 들인다.
5

로컬과 서버는 다른 환경

핵심 문장 “내 컴퓨터와 배포 서버는 같은 방이 아니라, 서로 다른 나라라고 생각하면 쉽습니다.”
SAY

“제 컴퓨터에서는 되는데 배포하면 안 돼요”라는 말이 나오는 이유가 여기 있습니다. 내 컴퓨터에는 이미 필요한 값이 들어 있고, 경로를 조금 틀려도 넘어가고, 개발 서버가 실수를 적당히 숨겨주기도 합니다. 반면 배포 서버는 매우 엄격합니다.

그래서 환경변수 누락, 파일명 대소문자 불일치, build에서만 드러나는 import 오류가 자주 터집니다. 오늘 5강에서 가장 실전적인 메시지 하나를 고르라면, 로컬과 서버는 다르다는 사실입니다.

DO
LOCAL / SERVER 두 칸을 짚은 뒤 아래 세 원인 카드를 하나씩 읽는다. 특히 `Button.jsx`와 `button.jsx` 대소문자 예시는 꼭 말로 설명한다.
복구 순서
1) 로컬 build 확인 2) 환경변수 설정 확인 3) 배포 로그 첫 빨간 줄 확인. 학생이 막힐 때 이 세 줄만 반복해도 된다.
6

Git 명령어와 GitHub 확인

핵심 문장 “git 명령어는 암기 과목이 아니라, 프로젝트 상태를 단계별로 바꾸는 조작입니다.”
SAY

학생들은 git을 어려운 문법처럼 느끼지만, 오늘은 기능만 이해하면 충분합니다. `git init`은 내 폴더를 Git 프로젝트로 시작하는 일이고, `remote add origin`은 GitHub와 연결하는 일입니다. 그 다음부터는 `status`로 상태를 보고, `add`로 기록할 파일을 고르고, `commit`으로 저장 지점을 만들고, `push`로 GitHub에 전송합니다.

중요한 점은 `commit`까지는 아직 내 컴퓨터 안의 기록이라는 것입니다. GitHub 페이지에서 실제로 보이는 것은 `push` 이후입니다. 이 차이를 이해하지 못하면 학생들이 “commit 했는데 왜 GitHub에 안 보여요?”라고 묻기 시작합니다.

DO
레일을 status → add → commit → push 순서로 눌러가며 가운데 터미널과 오른쪽 GitHub 확인 위치를 함께 읽는다. 꼭 “지금은 내 PC 안”, “이제 GitHub로 감”을 나눠 말한다.
라이브 시연 문장
“필요하면 지금 T를 눌러 실제로 `git status`를 보여드릴 수 있습니다. 하지만 중요한 건 명령어 철자보다, 지금 어떤 상태를 확인하는지입니다.”
7

프론트엔드는 모두에게 열려있다

핵심 문장 “브라우저에 내려간 순간, 그건 이미 사용자에게 공개된 것입니다.”
SAY

이제부터는 보안 구간입니다. 보안의 첫 질문은 어렵지 않습니다. “이건 어디에서 실행되지?” 브라우저에서 실행된다면, 사용자의 컴퓨터로 내려갔다는 뜻입니다. 그러면 사용자는 그 코드를 볼 수 있고, 저장할 수 있고, 요청도 확인할 수 있습니다.

반대로 서버는 내가 통제하는 공간입니다. 사용자는 결과만 받고, 내부 키나 중요한 로직은 서버 안에 남습니다. 그래서 API 키, 결제 키, 관리자 토큰처럼 진짜 비밀인 값은 절대 프론트에 두면 안 됩니다.

DO
`브라우저 공개 보기`와 `서버 보호 보기`를 번갈아 눌러가며 “여기는 보이는 공간, 여기는 통제되는 공간”이라고 단순하게 정리한다.
8

브라우저에서 확인하는 공개 요청

핵심 문장 “F12는 개발자만 보는 비밀 창이 아니라, 공개된 요청과 코드를 확인하는 창입니다.”
SAY

이 슬라이드는 학생들 반응이 가장 큰 장면입니다. 개발자도구는 특별한 권한이 있어야 열 수 있는 게 아닙니다. 공개된 웹사이트를 보는 사람이라면 누구나 F12를 눌러 Network와 Sources를 볼 수 있습니다.

그래서 프론트 코드에 진짜 비밀값을 넣으면 위험합니다. 요청 헤더에서 보일 수도 있고, 번들된 app.js 안에서 그대로 발견될 수도 있습니다. 한 번 보였으면 그냥 지우는 것으로 끝나지 않습니다. 이미 노출된 키는 폐기하고 다시 발급해야 합니다.

DO
`다음 확인`을 눌러 Request → Authorization → SOURCE LEAK 경고 순서로 진행한다. 경고가 뜨는 순간 잠깐 멈추고 “이게 오늘 보안 파트의 핵심 장면”이라고 말한다.
예상 질문
“그럼 Firebase 설정의 웹 키도 위험한가요?”라고 물으면, 식별용 공개값과 진짜 비밀키는 다르며 실제 접근은 인증·권한·Security Rules로 다시 막는다고 답한다.
9

비밀값과 배포 환경

핵심 문장 “비밀값은 코드에 넣는 것이 아니라, 실행 환경에 전달하는 것입니다.”
SAY

이 슬라이드는 5강의 핵심 개념 슬라이드입니다. `.env.local`에는 내 컴퓨터에서만 쓸 실제 값이 들어 있습니다. 그런데 그 파일이 GitHub에 올라가면 안 되기 때문에 `.gitignore`가 막아줍니다. 그리고 배포할 때는 같은 값을 Vercel이나 Firebase 설정 화면에 따로 넣습니다.

즉 비밀값은 코드와 함께 여행하지 않습니다. 코드 저장소는 공개 기록용, 환경변수는 실행 환경용입니다. 이 분리가 되어 있어야 배포도 안전하고 협업도 가능합니다.

DO
`다음 전달`을 눌러 KEY → STOP → LOCK 상태를 보여준다. local에서는 “여기엔 실제 값이 있음”, gitignore에서는 “저장소 기록 차단”, deploy에서는 “운영 환경에 안전하게 저장”이라고 단계별로 끊어서 설명한다.
강조 문장
“비밀값은 GitHub에 저장하는 것이 아니라, 실행 환경에 주입하는 것입니다.”
10

공개해도 되는 값 vs 절대 안 되는 값

핵심 문장 “주소는 공개 정보지만, 현관 비밀번호는 절대 비밀입니다.”
SAY

학생들이 가장 헷갈리는 부분은 “이것도 key고 저것도 key인데, 뭐가 공개고 뭐가 비밀이죠?”입니다. 그래서 집 비유가 좋습니다. 우리 집 주소는 알려줘도 됩니다. 그래야 택배도 오고 사람도 찾아옵니다. 하지만 현관 비밀번호는 절대 공개하면 안 됩니다.

웹에서도 마찬가지입니다. 공개 API 주소나 브라우저용 공개 설정값은 보이는 것이 문제되지 않을 수 있습니다. 반면 결제 비밀키, DB 접속 정보, 관리자 토큰은 노출 순간 바로 폐기 대상입니다.

DO
PUBLIC / SECRET 두 칸을 읽고, 마지막에 집 장면으로 한 번 더 비유를 묶는다. 학생들에게 “이 값이 브라우저에 보여도 괜찮은가?”만 기억하게 만든다.
11

인증과 인가는 다른 질문

핵심 문장 “인증은 누구인지, 인가는 무엇을 할 수 있는지입니다.”
SAY

로그인만 했다고 모든 데이터가 열리는 것은 아닙니다. 인증은 ‘너 누구야?’라는 질문이고, 인가는 ‘넌 여기서 무엇을 해도 되니?’라는 질문입니다. 둘은 같이 다뤄지지만 완전히 다른 검증입니다.

건물 비유로 보면 출입증을 보여주고 건물 안으로 들어오는 것이 인증이고, 그 다음 어느 층까지 갈 수 있는지가 인가입니다. 로그인 성공과 데이터 접근 허용은 별개라는 점을 꼭 분리해서 말해야 합니다.

DO
WHO / WHAT을 짚은 뒤 건물 장면의 층별 허용과 차단을 읽는다. 마지막에 “로그인했다고 3층 운영 데이터까지 열리면 안 되겠죠?”라고 묻는다.
12

데이터 접근 규칙

핵심 문장 “데이터베이스는 창고이고, Rules는 창고 문을 여는 기준입니다.”
SAY

이제 인증과 인가를 실제 데이터 접근과 연결합니다. 비회원은 공개 정보만, 회원은 자기 정보만, 관리자는 운영 정보까지 볼 수 있도록 나누는 것이 데이터 규칙입니다. 이 판단은 화면 버튼이 아니라 마지막엔 Rules에서 이뤄집니다.

특히 Firebase를 사용하는 학생은 “프론트에서 숨겼으니까 안전하겠지”라고 생각하기 쉽습니다. 그런데 진짜 차단은 Firestore Rules처럼 데이터 계층의 마지막 문에서 이뤄져야 합니다.

DO
비회원 → 회원 → 관리자를 차례로 눌러 허용/차단 결과가 바뀌는 것을 보여주고, 왼쪽 Rules 코드와 trace를 함께 읽는다.
ASK
“학생 A가 학생 B의 주문을 읽을 수 있어야 할까요?”라고 묻고, “아니오”라면 그 판단은 어디에서 막아야 하는지 되묻는다.
13

Vercel과 Firebase의 역할

핵심 문장 “Vercel은 웹 공개, Firebase는 로그인·데이터·저장입니다.”
SAY

학생들이 자주 묻습니다. “둘 중 하나만 써야 하나요?” 꼭 그렇진 않습니다. Vercel은 GitHub와 연결해서 웹 화면을 빠르게 공개하는 데 강하고, Firebase는 로그인, 데이터, 파일 저장처럼 앱 기능을 붙이는 데 강합니다.

그래서 실제 프로젝트에서는 둘을 함께 쓰는 조합이 꽤 자연스럽습니다. 화면은 Vercel에 공개하고, 인증과 데이터는 Firebase에 연결하는 방식입니다.

DO
`웹 배포`와 `앱 기능` 버튼을 번갈아 누르며 역할 차이를 먼저 설명하고, 마지막에 아래 `Vercel + Firebase` 문장으로 묶는다.
14

push 한 번이 자동 배포로

핵심 문장 “push는 끝이 아니라, 공개 파이프라인의 시작 신호입니다.”
SAY

이 슬라이드는 GitHub와 Vercel이 어떻게 이어지는지 보여주는 장면입니다. 학생들은 종종 push를 최종 완료라고 느끼지만, 실제로는 push가 시작 신호입니다. 기록된 변경이 GitHub에 도착하면, Vercel이 그것을 감지하고, build를 만들고, 검사를 통과하면 live URL을 바꿉니다.

그래서 배포는 한 번에 크게 올리기보다 자주, 작게 push하는 게 훨씬 안전합니다. 문제가 나면 어디서부터 틀어졌는지 추적하기 쉽기 때문입니다.

DO
`다음 단계`를 눌러 PUSH 패키지가 이동하는 걸 보여준다. Git push → Vercel 감지 → Build → Launch가 단계별로 실제 흐름처럼 보이게 읽어준다.
강조 문장
“push는 GitHub까지의 이동이고, 배포는 그 뒤에 일어나는 자동 파이프라인입니다.”
15

주소(도메인)와 HTTPS

핵심 문장 “처음엔 임시 간판, 나중엔 내 간판으로 바꾼다고 이해하면 쉽습니다.”
SAY

배포를 마치면 기본 주소가 먼저 생깁니다. 예를 들어 `my-project.vercel.app` 같은 주소입니다. 이건 임시 간판처럼 생각하면 됩니다. 그리고 원하면 나중에 내가 산 도메인을 연결해 `class.vibecoding.kr` 같은 내 브랜드 주소로 바꿀 수 있습니다.

학생들이 HTTPS 자물쇠를 별도 기술로 생각하기도 하는데, 배포 서비스가 인증서를 자동으로 처리해 주는 경우가 많기 때문에 기초반에서는 “안전하게 암호화된 연결이 기본으로 붙는다” 정도만 이해하면 충분합니다.

DO
무료 주소 카드 → 커스텀 도메인 카드 순서로 보여준다. DNS를 길게 설명하지 말고 “기본 주소로 먼저 공개하고, 원하면 내 주소로 바꾼다”로 마무리한다.
16

에러와 로그 읽는 법

핵심 문장 “배포 실패는 감정이 아니라 로그로 읽어야 합니다.”
SAY

배포가 실패하면 많은 학생이 막연히 겁부터 냅니다. 그런데 로그는 혼내는 문장이 아닙니다. 어디에서 막혔는지 알려주는 안내문입니다. 그래서 무조건 첫 빨간 줄부터 읽어야 합니다.

무엇을 하다가, 어떤 명령에서, 어떤 파일 경로에서, 어떤 에러가 났는지를 통째로 읽으면 됩니다. 학생이 AI에게 도움을 요청할 때도 빨간 줄만 따로 떼지 말고 상황과 명령어까지 함께 줘야 정확도가 높아집니다.

DO
build.log의 빨간 줄을 짚고, 오른쪽 1~5 순서를 읽는다. 특히 `componets/Button` 오타 부분은 눈으로 한 번 확실히 보여준다.
17

무료 한도와 책임

핵심 문장 “무료로 시작할 수는 있지만, 공개하는 순간 책임도 같이 시작됩니다.”
SAY

Vercel과 Firebase 모두 개인 프로젝트 수준에서는 무료로 시작하기 좋습니다. 하지만 무료가 무한이라는 뜻은 아닙니다. 사용자가 늘고, 읽기/쓰기와 저장량이 늘면 비용이 발생할 수 있습니다.

또 하나 더 중요한 것은 개인정보 책임입니다. 사용자 이름, 이메일, 주문 정보처럼 누군가의 정보가 들어오는 순간부터는 그냥 연습용 장난감이 아니라 관리 책임이 생깁니다. 그래서 최소한의 정보만 받고, 비밀번호는 직접 저장하지 않고, 백업 습관도 들여야 합니다.

DO
무료로 시작 / 비용 신호 / 개인정보 최소 / 백업 네 카드를 읽고, 수치보다 개념 위주로 마무리한다.
18

release와 공개 URL 점검

핵심 문장 “배포는 URL이 생기는 순간 끝나는 게 아니라, 공개 URL을 사용자처럼 다시 검증할 때 끝납니다.”
SAY

마지막 두 슬라이드는 하나의 연결 장면으로 보시면 됩니다. 먼저 release 슬라이드에서는 이번 공개의 기준 버전을 고르고, build를 만들고, 환경변수와 연결을 확인하고, live URL을 활성화합니다. 여기서 학생들이 이해해야 하는 것은 ‘아무 파일이나 공개되는 게 아니라, 검증한 기준 release 하나를 골라 공개한다’는 점입니다.

그리고 공개 URL이 살아났다고 해서 끝이 아닙니다. 다음 장면에서는 실제 사용자처럼 로그인, 저장, 모바일 화면, 권한까지 다시 확인합니다. 성공 배포는 초록 배지가 아니라, 실제 공개 URL에서 핵심 기능이 정상 동작하는 상태입니다.

DO
`시작`으로 release를 자동 진행하거나, `다음`으로 한 단계씩 설명한다. 마지막에 공개 URL이 활성화된 뒤에는 launch 체크 슬라이드로 넘기면서 “이제부터가 진짜 최종 확인입니다”라고 연결한다.
최종 마무리 문장
“오늘의 핵심은 이것입니다. Git으로 남기고, build로 검증하고, 비밀값은 숨기고, 공개 URL에서 다시 확인한다. 이 네 줄이 여러분 프로젝트를 서비스로 만듭니다.”
강의 후 실습 과제자신의 프로젝트에서 `git status`, `.gitignore`, `.env.local`, 공개 URL 체크리스트 중 최소 2개 이상을 실제로 적용해 보게 한다.
강사 리허설GitHub 로그인, Vercel/Firebase 계정, build 성공 예시, build 실패 예시, 환경변수 예시, 공개 URL 예시를 수업 전 확인한다.
공식자료 재확인GitHub Docs, Vercel deployment / environment variables / domains, Firebase Authentication / Firestore Security Rules 문서를 수업 직전에 다시 확인한다.
