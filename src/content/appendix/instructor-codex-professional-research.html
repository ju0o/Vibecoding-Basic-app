01 · COURSE BOUNDARY

Codex Professional의 차별점

Workflow 과정이 “왜 이런 구조가 필요한가”라면, Codex 과정은 그 구조를 Codex에서 실제로 구현하고 검증하는 과정입니다.

구분Workflow ArchitectCodex Professional수업에서 지켜야 할 선
목표AI 업무를 설계하는 원리와 판단 기준Codex 표면, 지침, 권한, 검증, 릴리즈를 실제 저장소에서 운영Codex 수업에서는 이론 복습을 10분 이하로 줄이고 바로 구현 장면으로 들어갑니다.
핵심 증거워크플로 도식, 권한표, 역할표실제 파일, 터미널 로그, diff, 브라우저 캡처, PR, Release 자산카드 설명만 있으면 전문과정처럼 보이지 않습니다. 반드시 실행 증거를 남깁니다.
실패 복구위험을 예측하고 승인 지점 설계경로 오류, sandbox 거부, stale instruction, MCP 인증, browser QA, release mismatch 복구실패 화면에서 끝내지 않고 복구 후 성공 증거까지 보여줍니다.
수강 가치도구가 바뀌어도 유지되는 설계 감각Codex로 실제 업무용 워크스페이스를 만들고 검증 루프를 운영하는 능력“Codex 기능 소개”가 아니라 “Codex 운영 능력”으로 포지셔닝합니다.
강사용 기준: Codex 과정의 모든 슬라이드는 질문 하나에 답해야 합니다. “이 기능을 켜면 무엇을 더 잘할 수 있고, 대신 어떤 책임과 검증이 추가되는가?”
02 · SURFACE MAP

표면 선택을 가르치는 첫 장면

수강생이 Codex를 “대화창”으로만 이해하지 않도록, 작업 표면을 실제 운영실처럼 나눠 보여줍니다.

App계획, 리뷰, 브라우저 QA, 장기 작업을 한 화면에서 운영하는 표면입니다.
CLI터미널 중심 저장소 작업, 명령 검증, 자동화 실험에 적합합니다.
IDE현재 편집 중인 파일, 선택 영역, diff 감각이 중요할 때 씁니다.
Browser로컬 화면을 클릭하고 스크린샷으로 UI 품질을 검증합니다.
Chrome로그인 세션, 확장, 실제 프로필이 필요한 웹 작업에 씁니다.
GitHubPR, review, checks, release 같은 저장소 협업 표면입니다.
오해 차단: “어느 도구가 제일 좋은가”가 아니라 “이번 작업의 증거가 어디에 남는가”로 선택합니다. 화면 품질은 Browser, 정책은 config와 rules, 협업 검증은 GitHub, 빠른 로컬 명령은 CLI가 더 적합할 수 있습니다.

공식자료를 공부하는 순서

아래 순서로 읽으면 Codex를 기능 목록이 아니라 운영 체계로 이해할 수 있습니다. 원문은 링크로 확인하고 강의에서는 쉬운 한국어로 재구성합니다.

1. Codex 개요와 표면

Codex가 코드 작성, 코드베이스 이해, 리뷰, 디버깅을 지원하는 개발 Agent라는 큰 역할을 먼저 잡습니다.
developers.openai.com/codex

2. Sandbox와 승인

기술적 작업 경계와 사람이 승인해야 하는 지점을 분리해 설명합니다. 최소 권한은 강의의 핵심 주제입니다.
developers.openai.com/codex/security

반복 업무는 Skill로 만들고, 팀이나 다른 프로젝트에 배포할 때 Plugin으로 묶는 경계를 학습합니다.

developers.openai.com/codex/plugins

5. MCP와 Browser

외부 도구·문서·앱 연결은 MCP, 실제 렌더링 검증은 Browser로 나눠 가르칩니다. 인증과 민감정보는 항상 함께 다룹니다.
developers.openai.com/codex/mcp

developers.openai.com/codex/subagents

Hook은 작업 루프 안의 정책 실행, Automation은 반복 작업 운영입니다. 둘 다 실패 비용과 중지 기준을 먼저 설계합니다.

developers.openai.com/codex/github-action

05 · SIX LESSONS

6회차별 전문 강의 설계

각 회차는 고유 장면, 정상 흐름, 실패 흐름, 복구 흐름, 강사용 심화 해설을 반드시 갖습니다.

01
FOUNDATION

App·CLI·IDE·Workspace·Sandbox

대표 장면: 하나의 요청이 App 계획, CLI 실행, IDE diff, Browser QA로 이동하는 command center. 승인 게이트가 켜지는 순간마다 멈춥니다.

실습: 작업 표면 선택표, 권한 범위, 검증 명령, 성공 캡처를 한 장의 작업 계약서로 작성합니다.

02
PROJECT CONTROL

AGENTS.md·config.toml·Rules·Git

대표 장면: 전역 지침, 루트 지침, 하위 폴더 지침이 instruction stack으로 쌓이고 config와 rules가 실행 게이트로 작동합니다.

실습: 내 프로젝트용 AGENTS.md, 금지 행동 2개, 검증 명령 2개, 첫 commit을 만듭니다.

03
REUSABLE WORK

Skills·Plugins

대표 장면: 반복 업무가 Trigger, SKILL.md, references, scripts, verification, plugin.json으로 압축되는 패키징 라인.

실습: 개인 반복 작업 하나를 Skill 후보로 만들고, 명시 호출과 암시 호출을 모두 테스트합니다.

04
CONNECTED WORK

MCP·Apps·Connectors·Browser

대표 장면: 공개 웹, 공식 API, 인증 Connector, MCP, Browser 중 어떤 경로를 타야 하는지 선택하는 권한망.

실습: 외부 연결 후보를 민감도, 읽기/쓰기, 승인, 대체 경로, 화면 증거 기준으로 평가합니다.

05
PARALLEL DELIVERY

Subagents·Worktrees·Review·QA

대표 장면: Main Lead가 요구사항을 고정하고 Research, Builder, Reviewer가 격리된 Worktree에서 작업 후 요약 증거만 합류합니다.

실습: 병렬 가능 작업과 불가능 작업을 나누고, 파일 소유권과 반환 형식을 작성합니다.

06
OPERATIONS

Hooks·Automations·GitHub Actions·Release

대표 장면: Hook gate, automation schedule, CI checks, PR review, tag, release artifact, checksum이 한 줄 파이프라인으로 켜집니다.

실습: 릴리즈 전 검증 명령 3개, 실패 중지 조건, version/tag/artifact 일치 체크리스트를 만듭니다.

06 · MOTION BRIEF

슬라이드와 애니메이션 고도화 기준

전문가 과정의 모션은 장식이 아니라 인과 관계를 보여주는 증거여야 합니다.

APPROVAL GATE

권한 요청은 멈춰야 한다

명령이 sandbox 밖으로 나가면 화면 전체를 어둡게 하고 명령 목적, 영향 범위, 되돌릴 방법 3개만 밝힙니다. 발표자가 승인 버튼을 눌러야 다음 단계로 갑니다.

INSTRUCTION STACK

지침은 위에서 아래로 쌓인다

Global, Project, Folder 지침 카드를 한 장씩 쌓고 마지막에 실제 작업 프롬프트가 얹힙니다. 가까운 폴더 지침이 마지막 판단에 영향을 주는 장면을 보여줍니다.

SKILL LOADING

필요할 때만 읽는다

처음에는 skill 이름과 설명만 보이고, 선택된 순간 SKILL.md, references, scripts가 단계적으로 열립니다. 이것이 progressive disclosure라는 점을 시각화합니다.

MCP PERMISSION NET

연결은 권한망이다

읽기 도구는 얇은 초록선, 쓰기 도구는 노란 승인선, 삭제성 행동은 빨간 차단선으로 표시합니다. 연결 성공보다 권한 범위가 먼저 보이게 합니다.

WORKTREE BOARD

병렬 작업은 격리되어야 한다

같은 파일을 두 agent가 잡으면 충돌 표시가 뜨고, 파일 소유권이 나뉘면 각 작업이 별도 트랙으로 움직입니다. 마지막 merge 전에는 review gate가 멈춥니다.

RELEASE PIPELINE

릴리즈는 증거 묶음이다

version, tag, build artifact, SHA-256, changelog가 맞을 때만 초록색으로 연결됩니다. 하나라도 틀리면 배포 자산 업로드 노드가 잠깁니다.

07 · SCRIPT TEMPLATE

강사용 대본을 얕게 만들지 않는 틀

각 슬라이드는 SAY, DO, ASK만 적는 것이 아니라 공식 근거, 실패 복구, 시간 조정까지 포함해야 합니다.

SAY / DO / ASK

수업 중 실제 멘트 구조

SAY

“지금 보는 화면은 Codex가 코드를 쓰는 장면이 아니라, 어디까지 자동으로 움직이고 어디서 사람이 승인해야 하는지 보여주는 장면입니다.”

DO

승인 게이트 앞에서 멈춘 뒤 명령, 영향 범위, 되돌릴 방법을 하나씩 하이라이트합니다.

ASK

“이 명령은 읽기 작업인가요, 쓰기 작업인가요? 실패하면 무엇을 확인해야 할까요?”

DEEP / RECOVER

전문 과정의 깊이를 만드는 부분

근거

공식 매뉴얼의 sandbox와 approval 개념을 쉬운 말로 연결합니다. “경계”와 “승인”은 다른 통제라는 점을 강조합니다.

복구

승인 실패, 경로 오류, 네트워크 차단, UI 캡처 실패가 나면 대체 캡처와 로그 예시로 같은 설명을 이어갑니다.

시간

시간이 부족하면 개념 설명을 줄이고 정상 흐름 1회, 실패 흐름 1회, 복구 흐름 1회만 남깁니다.

08 · FAILURE DRILLS

반드시 보여줄 실패 훈련

유료 전문과정은 성공 시연보다 실패 복구를 잘 보여줄 때 신뢰가 올라갑니다.

실패보여줄 화면강사용 설명복구 산출물
Workspace 오류현재 폴더와 Git root가 다른 터미널Codex가 틀린 게 아니라 공유 작업공간이 맞지 않는 상황입니다.올바른 cwd, repo root, 실행 명령 기록
Sandbox 거부권한 밖 파일 또는 네트워크 접근 요청막힌 것은 실패가 아니라 안전장치가 작동한 것입니다.명령 목적, 영향 범위, 승인 여부 표
AGENTS.md 과밀지침이 길어 핵심 규칙이 묻힌 파일지침은 많이 적는 것이 아니라 반복 기준만 남기는 것입니다.검증 명령, 금지 행동, 리뷰 기대치만 남긴 축약본
MCP 인증 누락서버는 연결됐지만 빈 결과 또는 권한 오류연결과 인증은 다릅니다. 데이터 접근에는 scope와 토큰이 필요합니다.권한 범위, 인증 상태, 대체 자료 경로
Browser QA 실패테스트 통과, 실제 화면 overflowDOM 존재와 사용자가 보는 화면은 다릅니다.스크린샷, viewport, 수정 diff
Release 불일치tag, package version, 파일명이 서로 다름릴리즈는 파일 업로드가 아니라 신뢰 가능한 증거 묶음입니다.version/tag/artifact/checksum 일치표
09 · PROFESSIONAL Q&A

강사가 준비해야 할 질문

질문에 답할 때는 기능명보다 판단 기준, 위험, 검증 증거를 먼저 말합니다.

Q1

Codex와 Claude Code 중 무엇을 먼저 배워야 하나요?

둘 다 “AI와 저장소에서 일하는 방식”을 다루지만, 이 과정에서는 Codex의 표면, sandbox, AGENTS.md, Browser QA, GitHub release 중심으로 갑니다. Workflow Architect를 먼저 들으면 설계 기준이 잡히고, 이후 도구 전문과정은 선택형으로 들으면 됩니다.

Q2

AGENTS.md와 Skill은 무엇이 다른가요?

AGENTS.md는 저장소에서 항상 적용되는 작업 계약이고, Skill은 특정 업무를 수행할 때 불러오는 재사용 절차입니다. 저장소 기본 규칙은 AGENTS.md, 반복 업무 방법론은 Skill로 분리합니다.

Q3

MCP를 많이 연결하면 더 좋은가요?

아닙니다. 연결이 늘수록 권한, 인증, 비용, 실패 표면도 늘어납니다. 필요한 데이터와 행동을 먼저 분류하고, 가장 좁은 연결부터 사용합니다.

Q4

Subagent는 언제 써야 하나요?

읽기 중심 조사, 테스트 로그 분석, 리뷰처럼 독립적이고 요약 가능한 작업에 좋습니다. 같은 파일을 동시에 고치는 작업은 충돌과 통합 비용이 커질 수 있습니다.

Q5

Hook과 GitHub Actions는 무엇이 다른가요?

Hook은 Codex 작업 루프 안에서 빠르게 정책을 실행하는 장치이고, GitHub Actions는 저장소 이벤트 기준의 독립 검증 파이프라인입니다. 둘은 보완 관계입니다.

Q6

자동화하면 사람이 볼 필요가 없나요?

자동화는 반복 실행을 맡길 뿐입니다. 실패 조건, 권한, 비용, 알림, 중지 기준을 사람이 설계해야 실제 운영이 가능합니다.
