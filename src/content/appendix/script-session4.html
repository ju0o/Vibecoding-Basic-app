Teacher Script · Session 04

4강 파일 구조 이해 : 강사 대본

4강의 목표는 폴더명을 기계적으로 암기시키는 것이 아닙니다. 브라우저에서 수정할 장면을 고르고, 관련 파일을 찾아 AI에게 수정 범위를 설명한 뒤 결과를 다중 검증하는 '아키텍트적 협업 흐름'을 체득시키는 시간입니다.

수업 목표화면 → 파일 탐색 → AI 설명 → 수정 제약 지시 → 교차 검증의 경로를 이해시킨다.
핵심 용어src, components, app, lib, node_modules, package.json, diff, 상대 경로, 대소문자
운영 원칙강의 및 인터랙티브 시연 25분, 수강생 프로젝트 직접 수정 및 실습 35분

1

표지 · 파일 구조는 프로젝트의 지도

핵심 문장 “오늘은 복잡한 코드를 읽는 날이 아니라, 원하는 코드가 들어있는 서랍장을 찾아가는 지도를 배우는 날입니다.”
SAY

여러분, 반갑습니다. 4강에 오신 것을 환영합니다. 지난 세션들에서는 AI와 함께 화면을 띄우고 데이터 흐름을 대략적으로 다루어 보았습니다. 그런데 문득 AI가 코드를 알아서 고쳐주기는 하지만, 내 컴퓨터의 어떤 폴더에 무슨 파일이 들어가 있고 무엇이 바뀌는지 도무지 알 길이 없어서 불안하셨던 적이 있으실 겁니다.

오늘은 코딩 공부를 하는 날이 아닙니다. 내가 고치고 싶은 화면의 버튼이나 텍스트가 어느 폴더에 들어 있는지 빠르게 찾고, AI가 엉뚱한 코드를 고쳐서 프로젝트를 망가뜨리지 않도록 통제하는 '지도 읽는 방법'을 배울 것입니다. 이 4강 지도를 터득하시면 AI와의 대화가 2배 더 선명해집니다.

DO
표지 하단의 "요청 → 파일 찾기 → 수정 → 브라우저 확인" 프로세스 아이콘을 마우스로 천천히 가리키며 동선을 강조해 줍니다.
2

왜 파일 구조가 다를까

핵심 문장 “파일 개수가 다른 것이 아니라, 만들려는 건물 규모가 다른 것입니다.”
SAY

AI로 바이브코딩을 하다 보면 학생마다 결과물이 다르게 나옵니다. 어떤 분은 index.html 하나만 생기고, 어떤 분은 index.html, style.css, script.js가 따로 생깁니다. 또 어떤 분은 src, components, app 같은 폴더가 생깁니다.

이때 “내 AI가 이상하게 만든 건가?”라고 생각하기 쉽지만, 대부분은 프로젝트의 규모와 기술 스택이 다르기 때문입니다. 원룸을 지을 때와 쇼핑몰을 지을 때 설계도가 다르듯이, 웹 프로젝트도 규모가 커질수록 폴더가 역할별로 나뉩니다.

이 장표에서는 건물 이미지를 미리 다 보여주지 않고, AI가 만들어줄 수 있는 결과 형태만 네 가지로 비교합니다. 건물 비유는 다음 장부터 하나씩 보여주면서 천천히 설명합니다.

DO
오른쪽의 네 결과 카드를 짧게 훑습니다. 여기서는 세부 폴더 설명을 오래 하지 말고, “다음 장부터 원룸, 주택, 아파트, 쇼핑몰 순서로 하나씩 보겠습니다”라고 연결합니다.
3

원룸 구조 · index.html 하나

핵심 문장 “HTML 하나로 나온 것은 틀린 것이 아니라 작은 원룸 구조입니다.”
SAY

원룸은 침대, 책상, 주방이 한 공간 안에 있습니다. 불편해 보일 수도 있지만, 혼자 살고 물건이 적다면 오히려 빠르고 간단합니다. index.html 하나 안에 HTML, CSS, JavaScript가 모두 들어간 구조도 마찬가지입니다.

작은 계산기, 간단한 자기소개 페이지, 임시 테스트 화면은 이 구조로 충분합니다. 학생이 index.html 하나만 받았다고 해서 실패한 것이 아닙니다. 다만 기능이 늘고 디자인이 복잡해지면 한 파일 안에서 모든 것을 찾기 어려워지기 때문에 다음 단계로 분리하는 것입니다.

ASK
“간단한 소개 페이지라면 파일 하나가 나쁜 구조일까요?”라고 묻고, 작은 규모에서는 오히려 간단한 구조가 장점이라고 정리합니다.
4

일반 주택 구조 · HTML/CSS/JS 분리

핵심 문장 “방을 나누면 어디를 고쳐야 하는지 찾기 쉬워집니다.”
SAY

일반 주택은 침실, 거실, 주방이 나뉩니다. 웹 프로젝트도 조금 커지면 index.html은 구조, style.css는 디자인, script.js는 기능으로 나뉩니다.

버튼 색을 바꾸고 싶으면 style.css, 클릭했을 때 동작을 바꾸고 싶으면 script.js를 찾으면 됩니다. 이 단계부터 학생은 “코드를 읽는다”보다 “역할을 보고 파일 후보를 좁힌다”는 감각을 가져야 합니다.

DO
파일 트리의 세 파일을 읽으며 “구조, 디자인, 기능”을 손으로 구분해 줍니다. 나중에 AI에게 요청할 때도 “디자인만 분리해줘”, “동작 코드는 script.js로 분리해줘”라고 말할 수 있음을 강조합니다.
5

아파트 구조 · src 중심 정리

핵심 문장 “기능이 많아지면 비슷한 역할끼리 모아두는 구역이 필요합니다.”
SAY

아파트는 세대, 주차장, 관리실, 엘리베이터가 구역별로 정리되어 있습니다. 프로젝트도 회원가입, 로그인, 게시판, 알림, 마이페이지가 생기면 파일이 수십 개로 늘어납니다. 그래서 src/ 안에 components/, pages/, hooks/, services/, utils/처럼 역할별 폴더가 생깁니다.

중요한 점은 이 이름들이 모든 프로젝트의 정답은 아니라는 것입니다. React, Vite, Next.js, AI IDE의 생성 방식에 따라 조금씩 다릅니다. 하지만 “비슷한 역할끼리 모은다”는 원리는 같습니다.

ASK
“버튼이 여러 페이지에서 반복되면 어디로 빼는 것이 좋을까요?”, “날짜 계산이나 API 호출은 화면 파일 안에 계속 두는 것이 좋을까요?”라고 물어 역할별 분리 감각을 확인합니다.
6

대형 쇼핑몰 구조 · app 라우팅

핵심 문장 “app 폴더는 쇼핑몰 안내도처럼 주소와 페이지를 연결합니다.”
SAY

대형 쇼핑몰은 층별 안내도와 동선이 없으면 사람이 길을 잃습니다. 서비스형 프로젝트도 마찬가지입니다. 로그인, 대시보드, 관리자, 결제, 데이터 페이지가 많아지면 주소와 화면을 체계적으로 연결해야 합니다.

Next.js App Router에서는 src/app/dashboard/page.tsx 같은 파일이 /dashboard 주소와 연결될 수 있습니다. 이 구조는 React 전체의 유일한 방식이 아니라, Next.js에서 자주 볼 수 있는 프레임워크 기반 구조라고 설명해야 정확합니다.

따라서 app/이 보인다면 “이 프로젝트는 주소별 페이지 구조를 프레임워크가 관리하는구나”라고 이해하면 됩니다.

DO
src/app/dashboard/page.tsx와 /dashboard를 연결해서 읽어 줍니다. “주소가 곧 폴더 구조와 연결될 수 있다”는 감각만 주고, 라우터 세부 문법은 깊게 들어가지 않습니다.
7

프로젝트 규모 키우기

핵심 문장 “작게 시작한 프로젝트도 AI에게 단계적으로 구조화해 달라고 요청하면 됩니다.”
SAY

만약 내 프로젝트가 index.html 하나로 나왔는데 점점 커지고 있다면, 한 번에 쇼핑몰 구조로 바꾸려고 하지 마세요. 오늘은 딱 한 가지 요청법만 기억하면 됩니다. “먼저 쉽게 설명해줘. 그 다음 필요한 파일만 최소 범위로 나눠줘.”

수강생 화면에는 이 쉬운 요청만 보여줍니다. 강사가 추가로 설명할 때는 이렇게 풀어 말하면 됩니다. 처음에는 HTML 안의 스타일과 스크립트를 분리하고, 반복 UI가 생기면 components로 빼고, 페이지가 늘어나면 app 또는 pages 구조를 고민합니다. API 키나 DB 주소가 생기면 .env.local, .env.example, .gitignore까지 정리합니다.

핵심은 규모가 커질 때마다 구조를 단계적으로 키우는 것입니다. 바이브코딩은 처음부터 완벽한 설계도를 외우는 것이 아니라, 지금 프로젝트의 규모에 맞게 AI에게 재정리시키는 능력입니다.

DO
화면의 세 단계 “먼저 설명 → 최소 정리 → 바뀐 파일 확인”을 읽습니다. 기술 폴더명 설명은 길게 하지 말고, 필요한 경우에만 말로 덧붙입니다.
8

프로젝트 전체 지도

핵심 문장 “프로젝트 폴더를 열면 숲을 먼저 보고 나무를 봅니다.”
SAY

이제 규모별 구조를 이해했으니 실제 프로젝트의 최상위 디렉토리를 봅니다. IDE(VS Code 등)에서 내 프로젝트를 처음 열었을 때 나오는 가장 바깥 폴더를 '루트(Root) 디렉토리'라고 합니다. 여기서 가장 중요한 점은 src, public, node_modules, package.json, README.md, .gitignore, .env 파일들이 모두 루트에서 같은 선상에 있다는 것입니다. public이나 node_modules가 src 안에 들어가는 구조로 설명하면 학생들이 나중에 파일을 완전히 잘못 찾게 됩니다.

실제 화면과 기능 코드는 주로 src 안에서 찾고, 이미지나 로고는 public 또는 프로젝트가 쓰는 asset 폴더에서 찾습니다. 실행 명령과 패키지는 package.json, 설치 결과는 node_modules, 비밀값은 .env.local, 공유용 환경변수 견본은 .env.example으로 구분합니다.

DO
탐색기 트리의 src, public, package.json 등을 차례로 클릭하여 우측 마인드맵 노드들이 반응하는 인터랙션을 차례대로 시연합니다.
9

VS Code 파일 탐색기

핵심 문장 “이번 시연의 목표는 폴더를 구경하는 것이 아니라, 화면과 공용 부품이 서로 다른 파일에 있다는 사실을 찾는 것입니다.”
SAY

슬라이드가 열려도 시연은 자동으로 시작하지 않습니다. 먼저 화면을 설명한 뒤 시연 시작 버튼을 누르겠습니다. 왼쪽은 파일 탐색기, 가운데는 선택한 파일의 코드, 오른쪽은 그 파일이 영향을 주는 브라우저 화면입니다.

첫 단계에서는 src/app을 선택합니다. app은 주소별 화면이 시작되는 구역입니다. 두 번째 단계에서는 page.tsx를 엽니다. 이 파일에는 해당 주소에서 보이는 제목, 설명, 배치가 들어갑니다. 세 번째 단계에서는 components/Button.tsx로 이동합니다. 같은 버튼을 여러 페이지에서 반복해서 쓸 때는 페이지마다 복사하지 않고 공용 부품으로 분리합니다.

따라서 “예약 화면의 제목을 바꿔줘”와 “서비스 전체의 공용 버튼을 바꿔줘”는 전혀 다른 파일을 찾아야 합니다. 이 차이를 구분하는 것이 이번 시연의 목적입니다.

DO
수강생이 세 영역을 먼저 확인한 뒤 시연 시작을 누릅니다. 커서가 움직일 때마다 잠시 멈추어 app → page.tsx → Button.tsx의 역할을 말합니다. 시연 중에는 실제 마우스를 움직여도 재생이 취소되거나 제어권을 빼앗기지 않습니다.
10

src 작업 영역

핵심 문장 “src 안에서는 파일명을 외우지 않고, 내가 바꾸려는 것이 화면·부품·처리·모양 중 무엇인지 먼저 판단합니다.”
SAY

src/는 우리가 실제 서비스를 만드는 작업 영역입니다. 이 안을 네 구역으로 나누면 파일을 찾기가 훨씬 쉬워집니다.

app 또는 pages는 주소별 화면을 조립합니다. 예약 주소의 제목과 배치를 바꾸고 싶다면 페이지 파일이 첫 후보입니다. components는 버튼, 카드, 모달처럼 반복되는 UI 부품입니다. 같은 모양이 여러 화면에서 보인다면 공용 컴포넌트를 의심합니다.

lib 또는 utils는 날짜 계산, 데이터 요청, 금액 계산처럼 화면 뒤에서 반복되는 처리를 둡니다. styles는 색상, 글꼴, 간격처럼 서비스의 시각 규칙을 관리합니다.

왼쪽의 네 항목을 하나씩 눌러보면 오른쪽에 대표 경로, 맡은 역할, AI에게 물어볼 문장이 함께 바뀝니다. 핵심은 정답 파일을 혼자 맞히는 것이 아니라, 후보 구역을 좁혀 AI에게 먼저 찾아달라고 요청하는 것입니다.

ASK
“예약 화면의 제목은 어디부터 찾을까요?”, “모든 화면에서 쓰는 버튼은 어디일까요?”, “날짜 계산 오류는 어느 구역일까요?”, “글꼴과 간격은 어디일까요?”를 차례로 묻고 네 버튼을 직접 선택합니다.
11

코드와 화면 연결 · 직접 수정 실습

핵심 문장 “수정은 코드에서 끝나지 않습니다. 파일을 찾고, 한 줄을 바꾸고, 브라우저에서 확인해야 끝납니다.”
SAY

이 시연도 자동으로 재생되지 않습니다. 시연 시작을 누르면 네 단계가 천천히 진행됩니다. 첫째, 화면의 큰 제목이 들어 있는 page.tsx를 선택합니다. 둘째, 코드 중 실제 제목 문구가 적힌 한 줄을 고릅니다. 셋째, 문구가 “집중할 수 있는 공간”에서 “오늘의 작업 공간”으로 바뀌는 동안 오른쪽 브라우저의 제목도 동시에 변합니다. 넷째, 마지막에는 브라우저 화면을 다시 가리키며 결과를 검증합니다.

여기서 중요한 것은 코드를 읽는 능력이 아닙니다. AI가 “page.tsx를 수정했습니다”라고 말했을 때, 그 파일과 화면이 실제로 연결되어 있는지 눈으로 확인하는 습관입니다.

시연이 끝난 뒤에는 아래의 문구 수정, 색상 변경, 간격 변경 버튼을 직접 눌러보겠습니다. 같은 화면이라도 문구는 페이지 파일, 버튼 모양은 컴포넌트나 스타일 파일, 간격은 스타일 규칙에서 바뀔 수 있다는 점을 비교합니다.

DO
시연 전 왼쪽 파일 트리·가운데 코드·오른쪽 브라우저를 짚습니다. 재생 후 각 단계에서 충분히 설명하고, 완료 뒤 수동 변경 버튼을 한 번씩 눌러 수정 위치와 결과를 연결합니다.
12

페이지 조립과 수정 영향

핵심 문장 “브라우저의 한 화면은 여러 파일이 조립된 결과이고, 어떤 파일을 바꾸느냐에 따라 영향 범위가 달라집니다.”
SAY

이 장표는 기존의 두 장면을 하나로 합친 장표입니다. 왼쪽에서는 화면이 어떻게 조립되는지 봅니다. page.tsx가 주소와 화면의 큰 배치를 만들고, components/Button.tsx 같은 공용 부품이 들어오고, globals.css 같은 스타일 규칙이 적용되고, 마지막으로 데이터가 채워져 실제 서비스 화면이 됩니다.

오른쪽에서는 같은 수정이라도 영향 범위가 달라지는 것을 비교합니다. app/reserve/page.tsx를 바꾸면 예약 페이지 중심으로 바뀌지만, components/Button.tsx를 바꾸면 그 버튼을 쓰는 여러 화면이 함께 바뀔 수 있습니다. styles/globals.css는 서비스 전체 인상에 영향을 줄 수 있습니다.

결론은 간단합니다. AI에게 바로 “고쳐줘”라고 말하기 전에, 먼저 “이 파일이 어디에서 쓰이는지, 바꾸면 어떤 화면에 영향이 있는지 설명해줘”라고 요청해야 합니다.

DO
왼쪽 조립 단계를 하나씩 누른 뒤, 오른쪽 영향 범위 3개 옵션을 차례로 선택합니다. “지금은 무엇이 추가되었나요?”, “지금은 몇 화면이 바뀌었나요?”라고 짧게 질문합니다.
13

AI 수정 내역 검토 · diff

핵심 문장 “AI가 수정을 다 했다고 할 때, 브라우저만 보지 말고 변경 코드 차이인 diff를 검토해야 합니다.”
SAY

AI와 일할 때 가장 중요한 것은 최종 검토입니다. AI가 소스코드를 수정한 내역을 이전 원본 코드와 비교해 보여주는 창을 diff라고 합니다.

여기서 우리는 네 가지만 봅니다. 첫째, 내가 수정해 달라고 요청한 파일만 바뀌었는가? 둘째, 버튼 색 하나 바꿨는데 변경 파일 개수가 비상식적으로 많지 않은가? 셋째, 기존에 멀쩡히 돌아가던 코드가 대거 빨간색(삭제) 처리되지는 않았는가? 넷째, package.json에 불필요한 패키지가 임의로 설치되지 않았는가?

AI가 쓸데없는 패키지를 깔아 두었다면 “새 패키지 설치 없이 기존 문법으로만 버튼을 바꿔줘”라고 명령해서 되돌려야 안전합니다.

DO
Button.tsx, globals.css, package.json 탭을 이동하며 빨간 줄(-)과 초록 줄(+)의 의미와 package.json에 패키지가 임의 추가된 예시를 짚어 설명합니다.
14

바이브코딩 수정 작업 순서

핵심 문장 “브라우저에서 출발하여 브라우저로 돌아옵니다.”
SAY

바이브코딩의 성공 법칙 5단계입니다. 화면을 보고 목표를 정하고, 문구로 검색해 파일을 찾고, AI에게 관계를 물어본 뒤 제약을 주고, 코드를 수정하고, 마지막에 모바일 모드와 다른 화면에 에러가 없는지 확인합니다. 이 루틴이 버그 없는 결과물을 만듭니다.

초보자가 자주 겪는 파일 구조 실수 3가지

핵심 문장 “상대 경로, 대소문자 매칭, 그리고 이미지 파일 경로만 조심해도 파일 구조 에러 대부분을 줄일 수 있습니다.”
SAY

실습에 들어가기 전에 자주 만나는 파일 구조 오류 세 가지를 정리하겠습니다. 첫째는 현재 파일을 기준으로 한 상대 경로의 층수를 잘못 세는 경우, 둘째는 파일명과 import 문장의 대소문자가 다른 경우, 셋째는 이미지 파일의 실제 위치와 브라우저에서 사용하는 주소가 다른 경우입니다.

윈도우에서는 대소문자를 대충 넘어가는 경우가 있지만 배포 서버는 대소문자를 엄격하게 구분할 수 있습니다. 이미지도 public에서 직접 주소로 부르는 방식과 src/assets에서 import하는 방식이 프로젝트마다 다를 수 있으니, 기존 방식을 AI에게 먼저 확인하게 하세요.

16

오늘의 파일 지도

핵심 문장 “파일 구조를 이해한다는 것은 수많은 이름을 외우는 일이 아니라, 수정의 네 단계를 반복할 수 있다는 뜻입니다.”
SAY

오늘 배운 내용을 네 단어로 정리하겠습니다. 첫째 FIND, 브라우저에서 바꾸고 싶은 장면을 정합니다. 둘째 TRACE, 페이지·공용 부품·스타일·처리 파일의 연결을 찾습니다. 셋째 CHANGE, AI에게 필요한 파일만 최소 범위로 수정하게 합니다. 넷째 VERIFY, 변경 파일 목록과 diff를 보고 브라우저에서 기능을 다시 확인합니다.

DO
네 카드를 왼쪽부터 차례로 가리키며 수강생과 함께 FIND → TRACE → CHANGE → VERIFY를 한 번 말합니다.

30분 실습

진행 문장 “지금부터 실습 시간입니다. 오늘 배운 흐름을 각자의 프로젝트에 적용해 보세요.”
SAY

지금부터 30분 동안 각자의 프로젝트를 이어서 작업하겠습니다. 오늘 배운 파일 찾기와 안전한 수정 흐름을 활용해 보세요. 막히면 AI에게 “관련 파일과 연결 관계부터 설명해줘”라고 먼저 요청하시면 됩니다. 시작하겠습니다.

DO
추가 과제나 성공 기준을 화면에서 길게 설명하지 않습니다. 30:00 타이머가 잘 보이는지 확인한 뒤 시작 버튼을 누르고 개별 코칭으로 전환합니다.

다음 강의 예고

연결 문장 “오늘은 프로젝트 안의 위치를 찾았고, 다음 시간에는 그 프로젝트를 인터넷에 공개하면서 지켜야 할 것을 배웁니다.”
SAY

다음 5강은 배포와 보안, 그리고 데이터입니다. 내 컴퓨터 안의 프로젝트가 공개 주소를 얻고, API 키와 비밀번호 같은 비밀값을 코드 밖으로 분리하며, 회원·게시글·주문 같은 정보가 데이터베이스에 어떻게 저장되는지 확인합니다.

DEPLOY, SECRET, DATA, CHECK 네 카드를 순서대로 가리킨 뒤 수업을 마칩니다.
시연 팁6번 슬라이드의 실시간 인라인 편집 기능을 수강생들에게 크게 환기시켜 "내가 코드를 치면 실시간 갱신되는 화면 동기화"를 반드시 직접 만져보게 유도합니다.

빌드 실패 개입실습 중 대소문자 미스매칭이나 경로 탐색 깨짐으로 빌드 크래시가 나면, 당황하지 말고 에러 로그를 복사해 AI에게 "대소문자 파일명 매칭 오류와 상대 경로 깊이를 전수 확인해서 경로 지시문을 교정해줘"라고 제약하도록 교정해 줍니다.
