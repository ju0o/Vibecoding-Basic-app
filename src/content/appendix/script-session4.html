1

표지 · 파일 구조는 프로젝트의 지도

핵심 문장 “오늘은 복잡한 코드를 읽는 날이 아니라, 원하는 코드가 들어있는 서랍장을 찾아가는 지도를 배우는 날입니다.”
SAY

여러분, 반갑습니다. 4강에 오신 것을 환영합니다. 지난 세션들에서는 AI와 함께 화면을 띄우고 데이터 흐름을 대략적으로 다루어 보았습니다. 그런데 문득 AI가 코드를 알아서 고쳐주기는 하지만, 내 컴퓨터의 어떤 폴더에 무슨 파일이 들어가 있고 무엇이 바뀌는지 도무지 알 길이 없어서 불안하셨던 적이 있으실 겁니다.

오늘은 코딩 공부를 하는 날이 아닙니다. 내가 고치고 싶은 화면의 버튼이나 텍스트가 어느 폴더에 들어 있는지 빠르게 찾고, AI가 엉뚱한 코드를 고쳐서 프로젝트를 망가뜨리지 않도록 통제하는 '지도 읽는 방법'을 배울 것입니다. 이 4강 지도를 터득하시면 AI와의 대화가 2배 더 선명해집니다.

DO
표지 하단의 "요청 → 파일 찾기 → 수정 → 브라우저 확인" 프로세스 아이콘을 마우스로 천천히 가리키며 동선을 강조해 줍니다.
2

프로젝트 전체 지도

핵심 문장 “프로젝트 폴더를 열면 숲을 먼저 보고 나무를 봅니다.”
SAY

IDE(VS Code 등)에서 내 프로젝트를 처음 열었을 때 나오는 최상위 디렉토리를 '루트(Root) 디렉토리'라고 합니다. 여기서 가장 중요한 점은 src, public, node_modules, package.json, README.md, .gitignore, .env 파일들이 모두 루트에서 같은 선상에 있다는 것입니다. public이나 node_modules가 src 안에 들어가는 구조로 설명하면 학생들이 나중에 파일을 완전히 잘못 찾게 됩니다.

실제 화면과 기능 코드는 주로 src 안에서 찾고, 이미지나 로고는 public 또는 프로젝트가 쓰는 asset 폴더에서 찾습니다. 실행 명령과 패키지는 package.json, 설치 결과는 node_modules, 비밀값은 .env.local, 공유용 환경변수 견본은 .env.example으로 구분합니다.

DO
탐색기 트리의 src, public, package.json 등을 차례로 클릭하여 우측 마인드맵 노드들이 반응하는 인터랙션을 차례대로 시연합니다.
3

대형 식당 주방 비유

핵심 문장 “프로젝트 파일 구조는 대형 음식점 주방이 요리하는 원리와 완벽히 똑같습니다.”
SAY

복잡하게 얽혀 있는 이 폴더 구조를 대형 식당 주방으로 비유해 보겠습니다.
가장 먼저, 외부에서 트럭으로 배달된 대용량 냉동 밀키트들이 잔뜩 쌓인 냉동창고가 있습니다. 이것이 node_modules/입니다. 요리사들은 여기서 재료를 꺼내 쓰기만 하지, 포장지를 뜯어 제조법을 바꾸지 않습니다.

그 옆에는 바로바로 접시에 담아 서빙할 수 있도록 미리 썰어둔 대파나 소스 그릇들이 놓인 조리 준비대가 있습니다. 이것이 components/입니다. 언제든 가져다 쓸 수 있는 공용 UI 조각입니다.

주방장 머리맡에 붙어 있는 특제 육수 계산법, 소스 배합 공식 수첩은 lib/ 또는 utils/입니다. 손님에게 이걸 서빙하지 않지만 요리를 완성하는 핵심 로직입니다.

마지막으로 손님이 주문한 요리를 취합해 주문 벨과 함께 올리는 메뉴 서빙대는 주소별 화면을 모아 보여주는 app/ (또는 pages/) 폴더입니다. 주방 비유를 머릿속에 담아두시면 앞으로 파일 찾기가 매우 직관적으로 변합니다.

DO
좌측 주방 구역(냉동창고, 조리대, 레시피북, 서빙대)을 하나씩 클릭하며 우측의 폴더 카드 매치 애니메이션과 하단의 네온 설명 팝업이 활성화되는 과정을 입체감 있게 보여줍니다.
4

VS Code 파일 탐색기

핵심 문장 “이번 시연의 목표는 폴더를 구경하는 것이 아니라, 화면과 공용 부품이 서로 다른 파일에 있다는 사실을 찾는 것입니다.”
SAY

슬라이드가 열려도 시연은 자동으로 시작하지 않습니다. 먼저 화면을 설명한 뒤 시연 시작 버튼을 누르겠습니다. 왼쪽은 파일 탐색기, 가운데는 선택한 파일의 코드, 오른쪽은 그 파일이 영향을 주는 브라우저 화면입니다.

첫 단계에서는 src/app을 선택합니다. app은 주소별 화면이 시작되는 구역입니다. 두 번째 단계에서는 page.tsx를 엽니다. 이 파일에는 해당 주소에서 보이는 제목, 설명, 배치가 들어갑니다. 세 번째 단계에서는 components/Button.tsx로 이동합니다. 같은 버튼을 여러 페이지에서 반복해서 쓸 때는 페이지마다 복사하지 않고 공용 부품으로 분리합니다.

따라서 “예약 화면의 제목을 바꿔줘”와 “서비스 전체의 공용 버튼을 바꿔줘”는 전혀 다른 파일을 찾아야 합니다. 이 차이를 구분하는 것이 이번 시연의 목적입니다.

DO
수강생이 세 영역을 먼저 확인한 뒤 시연 시작을 누릅니다. 커서가 움직일 때마다 잠시 멈추어 app → page.tsx → Button.tsx의 역할을 말합니다. 시연 중에는 실제 마우스를 움직여도 재생이 취소되거나 제어권을 빼앗기지 않습니다.
5

src 작업 영역

핵심 문장 “src 안에서는 파일명을 외우지 않고, 내가 바꾸려는 것이 화면·부품·처리·모양 중 무엇인지 먼저 판단합니다.”
SAY

src/는 우리가 실제 서비스를 만드는 작업 영역입니다. 이 안을 네 구역으로 나누면 파일을 찾기가 훨씬 쉬워집니다.

app 또는 pages는 주소별 화면을 조립합니다. 예약 주소의 제목과 배치를 바꾸고 싶다면 페이지 파일이 첫 후보입니다. components는 버튼, 카드, 모달처럼 반복되는 UI 부품입니다. 같은 모양이 여러 화면에서 보인다면 공용 컴포넌트를 의심합니다.

lib 또는 utils는 날짜 계산, 데이터 요청, 금액 계산처럼 화면 뒤에서 반복되는 처리를 둡니다. styles는 색상, 글꼴, 간격처럼 서비스의 시각 규칙을 관리합니다.

왼쪽의 네 항목을 하나씩 눌러보면 오른쪽에 대표 경로, 맡은 역할, AI에게 물어볼 문장이 함께 바뀝니다. 핵심은 정답 파일을 혼자 맞히는 것이 아니라, 후보 구역을 좁혀 AI에게 먼저 찾아달라고 요청하는 것입니다.

ASK
“예약 화면의 제목은 어디부터 찾을까요?”, “모든 화면에서 쓰는 버튼은 어디일까요?”, “날짜 계산 오류는 어느 구역일까요?”, “글꼴과 간격은 어디일까요?”를 차례로 묻고 네 버튼을 직접 선택합니다.
6

코드와 화면 연결 · 직접 수정 실습

핵심 문장 “수정은 코드에서 끝나지 않습니다. 파일을 찾고, 한 줄을 바꾸고, 브라우저에서 확인해야 끝납니다.”
SAY

이 시연도 자동으로 재생되지 않습니다. 시연 시작을 누르면 네 단계가 천천히 진행됩니다. 첫째, 화면의 큰 제목이 들어 있는 page.tsx를 선택합니다. 둘째, 코드 중 실제 제목 문구가 적힌 한 줄을 고릅니다. 셋째, 문구가 “집중할 수 있는 공간”에서 “오늘의 작업 공간”으로 바뀌는 동안 오른쪽 브라우저의 제목도 동시에 변합니다. 넷째, 마지막에는 브라우저 화면을 다시 가리키며 결과를 검증합니다.

여기서 중요한 것은 코드를 읽는 능력이 아닙니다. AI가 “page.tsx를 수정했습니다”라고 말했을 때, 그 파일과 화면이 실제로 연결되어 있는지 눈으로 확인하는 습관입니다.

시연이 끝난 뒤에는 아래의 문구 수정, 색상 변경, 간격 변경 버튼을 직접 눌러보겠습니다. 같은 화면이라도 문구는 페이지 파일, 버튼 모양은 컴포넌트나 스타일 파일, 간격은 스타일 규칙에서 바뀔 수 있다는 점을 비교합니다.

DO
시연 전 왼쪽 파일 트리·가운데 코드·오른쪽 브라우저를 짚습니다. 재생 후 각 단계에서 충분히 설명하고, 완료 뒤 수동 변경 버튼을 한 번씩 눌러 수정 위치와 결과를 연결합니다.
7

설정과 기록 파일

핵심 문장 “코드가 아닌 파일들은 프로젝트의 계약서와 창고 장부입니다.”
SAY

왼쪽에서 파일을 선택할 때마다 오른쪽의 문서 모양과 내용이 완전히 달라집니다. 이름만 바뀌는 장면이 아니라 각 파일이 실제로 어떤 정보를 담는지 비교하는 장면입니다.

package.json은 프로젝트 이름, 실행 명령, 필요한 패키지 목록을 담은 계획표입니다. package-lock.json은 팀원과 배포 서버가 같은 버전을 설치하도록 정확한 버전을 고정한 영수증입니다. 둘은 함께 관리하지만 lock 파일을 사람이 임의로 편집하지는 않습니다.

node_modules/는 npm install로 내려받은 패키지의 실제 파일이 모이는 큰 창고입니다. 용량이 크고 다시 설치할 수 있으므로 직접 수정하거나 공유하지 않습니다. README.md는 프로젝트 목적과 실행 방법을 사람이 읽을 수 있게 정리한 설명서입니다. .gitignore는 .env, .env.local, node_modules처럼 GitHub에 보내지 않을 항목을 정하는 출입 금지 목록입니다.

.env.local은 내 컴퓨터에서만 쓰는 실제 비밀값이고, .env.example은 팀원과 AI에게 “이런 이름의 값이 필요하다”만 알려주는 공유용 견본입니다. 이 둘을 구분하지 못하면 학생들이 실제 API 키를 자료나 GitHub에 올리는 사고가 날 수 있습니다.

ASK
“실행 명령은 어디에 있을까요?”, “설치된 실제 파일은 어디일까요?”, “비밀 환경변수가 GitHub에 올라가지 않도록 막는 파일은 무엇일까요?”를 묻고 해당 항목을 눌러 오른쪽 시각 자료가 바뀌는지 확인합니다.
8

페이지와 부품의 관계

핵심 문장 “브라우저의 한 화면은 한 파일이 아니라, 여러 역할의 파일이 차례로 조립된 결과입니다.”
SAY

첫 번째 버튼인 페이지 뼈대에서는 app/reserve/page.tsx가 주소와 화면의 큰 배치를 만듭니다. 아직 공용 버튼과 스타일, 데이터가 연결되지 않아 화면은 기본적인 뼈대처럼 보입니다.

두 번째 공용 버튼 부품을 누르면 components/Button.tsx가 페이지 안으로 들어옵니다. 이것이 import, 즉 다른 파일에서 만든 부품을 가져와 조립하는 개념입니다.

세 번째 스타일 규칙에서는 색상, 간격, 글꼴과 버튼 모양이 적용됩니다. 네 번째 데이터와 최종 화면에서는 예약 가능한 항목이 채워지며 사용자가 실제로 이용할 수 있는 화면이 됩니다.

따라서 화면이 이상할 때는 “페이지 파일 하나가 문제다”라고 단정하지 않습니다. 배치, 공용 부품, 스타일, 데이터 중 어느 층이 빠졌는지 먼저 구분해야 합니다.

DO

초보자가 자주 겪는 파일 구조 실수 3가지

핵심 문장 “상대 경로, 대소문자 매칭, 그리고 이미지 파일 경로만 조심하면 파일 구조 에러의 90%가 방지됩니다.”
