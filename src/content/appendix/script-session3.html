Teacher Script · Session 03 · Detailed Edition

개발 용어 이해

강사가 개념을 먼저 이해하고, 화면을 조작하며, 자신의 말투로 다시 연습할 수 있도록 구성한 12장 상세 대본입니다. 이론 30분과 실습 30분을 기준으로 합니다.

수업 목표용어를 암기시키는 것이 아니라 앱의 어느 부분을 뜻하는지 눈으로 구분하게 합니다.
설명 원칙장면을 먼저 보여주고, 수강생이 관찰한 내용을 말하게 한 뒤 마지막에 용어를 붙입니다.
강사의 역할정답을 많이 말하기보다 “지금 어디에서 무슨 일이 일어났는가”를 반복해서 질문합니다.
설명 범위코드 문법과 세부 기술은 다루지 않습니다. AI에게 작업 위치를 말할 수 있을 정도까지만 설명합니다.

FIVE SENTENCES TO REMEMBER

이 다섯 문장이 3강 전체의 뼈대입니다

  1. 프론트엔드사용자가 직접 보고 누르는 화면과 반응
  2. 백엔드화면 뒤에서 권한, 계산, 규칙을 처리하는 공간
  3. 데이터베이스회원, 상품, 주문 같은 기록을 구조적으로 보관하는 공간
  4. API서로 다른 화면과 서비스가 요청과 응답을 주고받는 약속
  5. 파일 구조이 모든 기능이 실제 프로젝트 안에서 자리 잡고 있는 주소
1

개발 용어는 서비스의 내부 지도

약 1분 30초
핵심 한 문장 개발 용어는 코드를 외우기 위한 단어가 아니라 AI에게 작업 위치를 알려주는 주소입니다.
강사가 먼저 이해할 것
비개발자가 프론트엔드, 백엔드, API 같은 말을 배우는 가장 현실적인 이유는 직접 코드를 작성하기 위해서가 아닙니다. AI가 만든 결과를 보고 “화면 문제인지, 처리 문제인지, 저장 문제인지” 구분하고 수정 위치를 말하기 위해서입니다.
상세 멘트

“오늘은 개발자가 되기 위한 용어 암기 시간이 아닙니다. 코드를 한 줄씩 배우는 시간도 아닙니다.”

“우리가 화면에서 버튼 하나를 누르면 화면이 요청을 보내고, 보이지 않는 곳에서 규칙을 처리하고, 필요한 기록을 저장한 뒤, 결과를 다시 화면으로 돌려주는 일이 이어집니다.”

“지금부터 흐름 재생을 눌러 보겠습니다. 화면, 처리, 저장, 응답이 어떤 순서로 이어지는지만 눈으로 따라와 주세요.”

“우리가 개발 용어를 알아야 하는 이유는 이 흐름 중 어느 위치를 AI에게 맡기고 확인해야 하는지 말하기 위해서입니다.”

화면 조작
먼저 아무 말 없이 흐름 재생을 한 번 보여 줍니다. 두 번째에는 화면 → 처리 → 저장 → 응답을 한 단계씩 직접 클릭합니다. 표지에서는 세부 정의를 설명하지 않고 순서만 인식시킵니다.
수강생에게 물어보기
“AI에게 사이트를 만들어 달라고 했는데 화면은 나왔지만 버튼이 안 눌렸던 경험이 있나요?” 손을 들거나 짧게 사례를 말하게 합니다. 정답을 평가하지 말고 “오늘 바로 그 차이를 구분해 보겠습니다”로 받습니다.
다음 장 연결
“먼저 앱을 건물 하나라고 생각해 보겠습니다. 빈 땅에서 실제 사용할 수 있는 건물이 되기까지 어떤 공정이 필요한지 보겠습니다.”
2

아이디어가 진짜 서비스가 되는 과정

약 4분
핵심 한 문장 화면이 만들어진 것은 외관이 완성된 것이고, 기능과 데이터가 연결되어야 실제로 사용할 수 있는 건물이 됩니다.
강사가 먼저 이해할 것
이 장은 3강 전체를 이해시키는 기준 장면입니다. 건축과 개발이 완전히 같은 것은 아니지만, “아이디어 → 기획 → 프로젝트 구조 → UI → 기능과 데이터 연결 → 테스트와 배포”의 단계 차이를 보여주는 데 적합합니다. 외관을 UI, 내부 설비를 백엔드·API·DB·상태 연결에 대응시키되 일대일 공식처럼 강요하지 않습니다.
단계별 상세 멘트

01 빈 땅: “처음에는 만들고 싶은 생각만 있습니다. 예약 사이트를 만들고 싶다, 포트폴리오를 만들고 싶다 같은 아이디어만 있고 아직 화면도 파일도 없습니다.”

02 설계도: “바로 코딩부터 시작하기 전에 누가 사용할지, 어떤 화면과 기능이 필요한지 정리합니다. 우리는 이 정리를 GPT나 Claude 같은 설계 AI에게 부탁할 수 있습니다.”

03 철골: “AI IDE가 프로젝트를 만들면 폴더와 파일, 페이지, 컴포넌트 같은 기본 구조가 생깁니다. 아직 예쁜 서비스는 아니지만 앞으로 모든 기능이 붙을 뼈대입니다.”

04 외관: “화면 색상, 메뉴, 카드, 버튼이 만들어집니다. 바이브코딩을 처음 하면 이 단계에서 가장 큰 만족을 느낍니다. 눈앞에 결과물이 보이기 때문입니다.”

05 내부 진입: “그런데 건물 안에 들어왔더니 조명도 없고, 수도도 없고, 방도 정리되지 않았다면 사용할 수 없습니다. 앱도 버튼은 있지만 로그인되지 않고, 주문은 되지만 저장되지 않고, 새로고침하면 내용이 사라질 수 있습니다.”

06 내부 공사: “이제 조명과 배관, 회의실과 업무공간을 실제로 완성합니다. 앱에서는 로그인 처리, 데이터베이스 저장, API 연결, 로딩과 성공 상태 같은 내부 기능을 연결하는 단계입니다.”

07 준공: “마지막으로 모든 동선이 정상인지 확인하고 실제 사용자가 접속할 수 있게 배포합니다. 화면만 있는 결과물이 아니라 실제로 운영 가능한 서비스가 됩니다.”

화면 조작
각 단계를 한 번씩 천천히 클릭합니다. 4번 외관에서 잠시 멈춰 “여기까지가 우리가 초반에 가장 쉽게 만드는 부분입니다”라고 말합니다. 5번 내부 진입에서 2초간 침묵한 뒤 부족한 점을 수강생이 먼저 찾게 합니다. 6번에서 가구와 설비가 채워지는 장면을 보여주고, 7번에서 전체 건물로 빠져나옵니다.
반드시 짚을 오해
“화면이 보인다 = 서비스가 완성됐다”는 뜻이 아닙니다. 반대로 “개발 용어를 모두 알아야 시작할 수 있다”는 뜻도 아닙니다. 만들면서 필요한 내부 공사의 이름을 하나씩 배우는 것이 이번 과정의 방식입니다.
예상 질문과 답변
Q. AI가 내부 기능도 전부 만들어 주지 않나요?
A. 만들 수 있습니다. 하지만 어떤 기능이 필요하고 어디까지 정상 작동해야 하는지 사람이 확인해야 합니다. AI가 공사를 해도 준공 검사는 사용자가 해야 합니다.

Q. 화면만 만든 뒤 나중에 기능을 붙여도 되나요?
A. 작은 프로젝트는 가능합니다. 다만 로그인, 결제, 데이터 저장이 핵심이라면 초기에 필요한 구조를 함께 설계하는 편이 수정 비용이 적습니다.
다음 장 연결
“그렇다면 건물 안의 외관, 관리실, 창고, 통로에 해당하는 개발 용어를 하나씩 위치에 붙여 보겠습니다.”
3

개발 용어 위치 지도

약 2분
핵심 한 문장 프론트는 보이는 곳, 백엔드는 처리하는 곳, DB는 저장하는 곳, API는 서로 연결하는 통로입니다.
상세 멘트

“이번에는 개발 용어를 식당 안에서 찾아보겠습니다. 이 네 단어를 오늘 완벽하게 정의할 필요는 없습니다. 우선 위치만 구분하겠습니다.”

“손님이 보고 주문하는 카운터는 프론트엔드입니다. 주문을 받아 규칙대로 음식을 만드는 주방은 백엔드입니다. 돈과 회원·주문 기록을 보관하는 금고와 기록실은 데이터베이스입니다. 외부 거래처에서 재료를 받아오는 납품 통로는 API에 가깝습니다.”

“중요한 것은 이 네 공간이 서로 떨어져 일하는 것이 아니라, 주문 하나를 완성하기 위해 함께 움직인다는 점입니다.”

화면 조작
주문 카운터 → 주방 → 금고·기록실 → 납품 통로 순서로 클릭합니다. 클릭할 때마다 “보임”, “처리”, “저장”, “외부 연결”이라는 한 단어를 반복합니다.
확인 질문
“회원 정보를 보관하는 곳과 로그인 가능 여부를 판단하는 곳은 같은 역할일까요?” 예상 답변은 “보관은 DB, 판단은 백엔드”입니다. 정확한 표현이 아니어도 위치를 구분하면 충분합니다.
다음 장 연결
“이제 가장 익숙한 공간부터 보겠습니다. 지금 여러분 눈앞에 보이는 화면, 프론트엔드입니다.”
4

프론트엔드: 사용자가 만나는 제품

약 2분 30초
핵심 한 문장 프론트엔드는 색과 글자뿐 아니라 사용자의 입력, 이동, 상태 변화를 화면으로 전달하는 영역입니다.
강사가 먼저 이해할 것
프론트엔드는 브라우저나 앱에서 사용자가 직접 보고 조작하는 전체 접점입니다. 화면 배치뿐 아니라 검색어 입력, 메뉴 이동, 장바구니 숫자 변화, 로그인 팝업, 완료 알림처럼 사용자의 행동에 반응하는 부분까지 포함합니다. 이번 장에서는 기술 이름보다 수강생이 평소 사용하는 쇼핑몰 화면에서 프론트엔드를 찾아내게 합니다.
상세 멘트

“이 화면은 우리가 평소 인터넷 쇼핑을 할 때 보는 아주 익숙한 사이트입니다. 상단에는 브랜드와 검색창이 있고, 아래에는 메뉴와 상품 정보가 있습니다.”

“검색 버튼을 누르는 것, 신상품 페이지로 이동하는 것, 상품을 찜하거나 장바구니에 담는 것, 로그인 팝업을 여는 것 모두 사용자가 화면에서 직접 확인하는 일입니다. 이 전체 영역을 프론트엔드라고 부릅니다.”

“중요한 점은 프론트엔드가 단순한 그림이 아니라는 것입니다. 사용자가 누르면 화면이 바뀌고, 숫자가 올라가고, 결과 안내가 나타나야 합니다.”

“AI에게도 ‘쇼핑몰을 예쁘게 해 주세요’라고 말하기보다 ‘상단 검색창을 크게 하고, 신상품 카드를 세 개 보여 주고, 담기 버튼을 누르면 장바구니 숫자와 완료 알림이 같이 바뀌게 해 주세요’라고 요청하면 훨씬 정확합니다.”

화면 조작
전체 메뉴 열기 → 신상품 이동 → 상품 찜 → 장바구니 담기 → 로그인 팝업 순서로 천천히 조작합니다. 클릭할 때 나타나는 반투명 설명창에서 내비게이션, 콘텐츠, 행동과 피드백, 화면 상태, 오버레이의 역할을 한 문장씩 읽습니다. 완료 알림과 설명창은 서로 다른 위치에 나타납니다.
예상 질문과 답변
Q. 디자인과 프론트엔드는 같은가요?
A. 디자인은 어떻게 보여야 하는지를 설계하고, 프론트엔드는 그 디자인이 실제로 움직이고 입력을 받도록 구현하는 영역까지 포함합니다.

Q. 버튼을 눌러 주문이 저장되는 것도 프론트엔드인가요?
A. 버튼과 로딩 화면은 프론트엔드지만, 주문을 검사하고 저장하는 처리는 백엔드와 DB까지 연결됩니다.
다음 장 연결
“같은 프론트엔드 화면이라도 보기 좋은 것과 사용하기 좋은 것은 다를 수 있습니다. UI와 UX의 차이를 보겠습니다.”
5

UI와 UX: 보이는 것과 사용되는 방식

약 2분
핵심 한 문장 UI는 사용자가 보는 조작 요소이고, UX는 그 요소를 사용해 목표까지 도달하는 전체 경험입니다.
강사가 먼저 이해할 것
UI는 버튼, 입력창, 색, 글자, 배치처럼 화면에 존재하는 인터페이스입니다. UX는 사용자가 주문을 완료하거나 정보를 찾는 과정에서 느끼는 이해도, 편리함, 신뢰, 속도까지 포함합니다. 예쁜 UI가 반드시 좋은 UX를 보장하지 않습니다.
상세 멘트

“두 화면 모두 결제를 할 수 있지만 사용자가 겪는 과정은 다릅니다.”

“UI는 버튼 이름, 색, 크기, 배치처럼 눈에 보이는 조작 요소입니다. 화면 A는 확인과 다음이라는 모호한 버튼이 여러 개 있고 정보 우선순위가 약합니다.”

“UX는 현재 위치를 아는가, 다음 행동을 예측할 수 있는가, 최종 결과를 확신할 수 있는가의 문제입니다. 화면 A는 배송비가 늦게 나타나고 진행 단계를 알기 어려워 여러 번 탐색하게 합니다.”

“화면 B는 3단계 중 마지막이라는 위치, 최종 금액, 결제 후 결과를 한 화면에서 알려 줍니다. 그래서 덜 찾고, 덜 고민하고, 실수할 가능성이 낮습니다.”

수강생 관찰 포인트
두 화면의 커서 이동 거리, 클릭 횟수, 현재 단계 표시, 최종 금액이 보이는 시점, 버튼 문구를 비교하게 합니다. “어느 쪽이 예쁜가”보다 “어느 쪽에서 실수할 가능성이 낮은가”를 질문합니다.
AI 요청 예시
나쁜 요청: “결제 화면을 더 예쁘게 해 줘.”

화면 애니메이션: 변화를 이해시키는 움직임

약 2분
핵심 한 문장 좋은 애니메이션은 원인, 변화, 결과를 연결해 사용자가 다음 상황을 이해하게 합니다.
강사가 먼저 이해할 것
애니메이션은 단순 장식과 기능적 움직임으로 나눠 생각할 수 있습니다. 수업에서는 메뉴가 들어오는 방향, 로딩 자리 표시, 상품이 장바구니로 이동하는 흐름, 완료 메시지가 나타나는 장면처럼 사용자의 이해를 돕는 기능적 애니메이션에 집중합니다. 움직임은 짧고 목적이 분명해야 하며, 끝난 뒤 화면의 최종 상태가 명확해야 합니다.
상세 멘트

“메뉴 전환은 새 영역이 어디에서 나타났는지 알려 줍니다. 로딩 전환은 화면이 멈춘 것이 아니라 내용을 준비하고 있음을 보여 줍니다.”

“장바구니 이동은 선택한 상품과 바뀐 숫자를 연결하고, 완료 전환은 작업이 끝났다는 확신을 줍니다.”

“탭 전환은 같은 화면 안에서 현재 위치가 어디로 바뀌었는지 보여 줍니다. 입력 검증은 문제가 생긴 칸과 고쳐야 할 방법을 같은 위치에서 알려 줍니다.”

“AI에게는 ‘화려한 애니메이션’보다 원인, 움직이는 대상, 시간, 마지막 상태를 말해야 합니다.”

화면 조작
메뉴 → 로딩 → 장바구니 → 완료 → 탭 → 입력 검증의 여섯 예시를 하나씩 누릅니다. 각 장면은 첫 번째에는 말없이, 두 번째에는 “어디서 시작했는가, 무엇이 변했는가, 어떤 결과가 남았는가”를 설명합니다.
다음 장 연결
“그런데 화면에 ‘처리 중’이라고 표시되는 동안 실제 뒤에서는 무엇이 일어날까요? 이제 백엔드로 들어가 보겠습니다.”

백엔드: 버튼 뒤에서 규칙을 처리하는 공간

약 2분 30초
핵심 한 문장 백엔드는 사용자의 요청을 받아 권한과 규칙을 확인하고 필요한 작업을 순서대로 처리합니다.
강사가 먼저 이해할 것
백엔드는 서버에서 실행되는 처리 로직을 뜻합니다. 사용자의 요청을 받고, 로그인 권한과 입력값을 확인하고, 재고 계산이나 결제 요청을 수행하고, DB에 저장한 뒤 결과를 반환합니다. 서버는 백엔드 코드가 실행되는 컴퓨터 또는 환경이라고 설명하면 충분합니다.
상세 멘트

“사용자는 브라우저에서 주문 버튼 하나만 누릅니다. 하지만 버튼 뒤에서는 여러 검사가 순서대로 일어납니다.”

“먼저 프론트엔드가 어떤 상품을 몇 개 주문하는지 데이터를 포장합니다. 백엔드는 이 사용자가 로그인했는지, 주문 권한이 있는지, 재고가 남았는지 확인합니다.”

“그다음 결제 서비스에 승인을 요청하고, 성공하면 주문 기록을 저장합니다. 마지막으로 주문 번호와 성공 결과를 다시 브라우저에 보내 화면을 바꿉니다.”

“따라서 주문 버튼의 모양을 바꾸는 일과 주문 처리 규칙을 바꾸는 일은 서로 다른 작업입니다.”

화면 조작
주문하기를 눌러 요청 접수까지만 진행합니다. 이후 다음 처리 보기를 한 번씩 눌러 권한 → 재고 → 결제 → 저장 → 응답 → 완료를 진행합니다. 각 단계에서 멈춰 “지금 어떤 판단이 끝났습니까?”를 질문합니다. 자동 재생은 사용하지 않습니다.
예상 질문과 답변
Q. 백엔드는 화면이 없나요?
A. 일반 사용자가 보는 화면은 없을 수 있지만, 관리자 화면이나 로그처럼 운영자가 확인하는 화면은 있을 수 있습니다. 핵심은 화면보다 처리 역할입니다.

Q. 프론트엔드만으로 사이트를 만들 수 있나요?
A. 소개 페이지처럼 저장과 로그인이 필요 없는 사이트는 가능합니다. 회원, 주문, 결제처럼 규칙과 기록이 필요하면 백엔드가 필요합니다.
다음 장 연결
“백엔드가 주문을 처리한 뒤 그 결과를 어디엔가 남겨야 다음에도 조회할 수 있습니다. 그 기록 보관소가 데이터베이스입니다.”

데이터베이스: 필요한 기록을 나눠 보관하는 곳

약 2분 30초
핵심 한 문장 데이터베이스는 회원, 게시글, 상품, 주문 기록을 알맞은 보관함에 넣고 필요할 때 다시 찾는 공간입니다.
강사가 먼저 이해할 것
데이터베이스는 새로고침하거나 다음 날 다시 접속해도 남아야 하는 기록을 보관합니다. 실제 내부에는 표, 행, 열 같은 구조가 있지만 이번 수업에서는 회원정보 창고, 게시글 창고, 상품 창고, 주문내역 창고라는 네 공간으로만 설명합니다. 저장은 새 기록을 넣는 일, 조회는 기존 기록을 찾는 일, 수정은 재고 수량처럼 이미 있는 기록을 바꾸는 일입니다.
상세 멘트

“회원가입을 누르면 새 사람의 이름과 이메일이 회원정보 창고로 들어갑니다. 아직 없던 기록을 새로 넣는 것이므로 저장입니다.”

“로그인은 새 회원을 만드는 일이 아닙니다. 회원정보 창고에서 입력한 이메일과 같은 기록을 찾아 비교하는 일입니다. 이것을 조회라고 생각하면 됩니다.”

“게시글 작성은 제목과 내용, 작성자를 게시글 창고에 넣습니다. 다음에 다시 접속해도 글이 보여야 하므로 화면이 잠깐 기억하는 것만으로는 부족합니다.”

“상품 주문은 두 창고가 함께 움직입니다. 먼저 상품 창고에서 재고 12개를 11개로 바꾸고, 주문내역 창고에는 누가 어떤 상품을 샀는지 새 기록을 남깁니다.”

“AI에게 문제가 생겼다고 말할 때도 ‘주문이 이상해요’보다 ‘결제 후 상품 재고는 줄었지만 주문내역이 저장되지 않습니다’라고 말하면 확인할 위치가 분명해집니다.”

화면 조작
왼쪽 실제 브라우저에서 회원가입 → 로그인 → 게시글 작성 → 상품 주문 화면을 바꿉니다. 입력 폼과 버튼의 차이를 먼저 보여 준 뒤 오른쪽 기록 봉투와 반응하는 보관함을 짚습니다. 상품 주문에서는 상품 창고 재고 12 → 11과 주문내역 창고 저장이 함께 일어나는 것을 확인합니다.
예상 질문과 답변
Q. 엑셀과 데이터베이스는 같은가요?
A. 표 형태라는 점은 비슷하지만 데이터베이스는 여러 사용자의 대량 요청, 관계, 권한, 검색과 수정을 안정적으로 처리하도록 설계된 시스템입니다.

Q. 새로고침하면 사라지는 값도 DB 문제인가요?
A. 반드시 그렇지는 않습니다. 화면 상태에만 보관하고 DB에 저장하지 않았을 수도 있고, 저장은 됐지만 다시 불러오지 못했을 수도 있습니다.
다음 장 연결
“이제 내 서비스가 날씨, 결제, AI 같은 외부 서비스와 대화하려면 어떤 통로가 필요한지 보겠습니다.”

API: 요청과 응답을 주고받는 약속

약 2분 30초
핵심 한 문장 API는 다른 기능이나 서비스에 정해진 주소와 형식으로 요청하고 결과를 돌려받는 약속입니다.
강사가 먼저 이해할 것
API는 서로 다른 프로그램이 정해진 방법으로 부탁하고 답을 받는 연결 창구입니다. 내부적으로는 주소, 요청 방식, 인증, 데이터 형식 같은 규칙이 있지만 3강에서는 이 용어를 먼저 외우게 하지 않습니다. “내 서비스가 부탁한다 → API가 전달한다 → 외부 서비스가 답한다 → 내 화면이 답을 보여 준다”는 네 단계만 명확히 남깁니다.
상세 멘트

“왼쪽은 우리가 만든 여행 준비 서비스이고 오른쪽은 날씨 정보를 가진 외부 서비스입니다. 우리 앱이 세상의 모든 날씨를 직접 측정할 수는 없습니다.”

“그래서 사용자가 서울 날씨 불러오기를 누르면 우리 서비스가 ‘서울의 현재 날씨를 알려 주세요’라고 부탁합니다. 가운데 API 창구는 이 부탁을 외부 서비스가 이해하는 방식으로 전달합니다.”

“외부 날씨 서비스는 서울은 24도이고 맑다는 답을 보냅니다. API가 그 답을 다시 가져오면 왼쪽의 빈 날씨 카드가 24도와 맑음으로 바뀝니다.”

“API는 다른 회사의 기능을 내 화면 안으로 순간 이동시키는 마법이 아닙니다. 정해진 약속에 맞춰 질문을 전달하고 답을 받아 내 화면에 표시하는 통로입니다.”

“연결 끊기를 눌러 보겠습니다. 화면은 그대로 있지만 외부 서비스와 이어지는 통로가 끊어졌기 때문에 답을 받지 못합니다. 이때 사용자는 실패 안내와 다시 시도할 방법을 봐야 합니다.”

화면 조작
서울 날씨 불러오기를 눌러 요청 봉투가 아래로 이동하고 응답 봉투가 돌아오는 장면을 설명합니다. 다음에는 연결 끊기를 누른 뒤 다시 요청해 실패 상태를 보여 줍니다. 코드는 보여주지 않고 왼쪽 화면, 가운데 창구, 오른쪽 제공처를 손으로 짚습니다.
예상 질문과 답변
Q. API를 쓰면 다른 회사의 기능을 가져올 수 있나요?
A. 해당 서비스가 API를 제공하고 사용 권한을 허용한다면 가능합니다. 결제, 지도, 번역, AI 기능이 대표적입니다.

Q. API 키는 왜 숨겨야 하나요?
A. 서비스 사용 권한과 비용이 연결된 비밀 열쇠이기 때문입니다. 프론트 화면에 그대로 넣으면 다른 사람이 복사할 수 있습니다.
다음 장 연결
“지금까지 화면과 내부 흐름을 봤습니다. 이제 하나의 화면도 어떤 역할의 요소들로 나뉘는지 찾아보고, AI에게 수정 범위를 정확하게 말하는 연습을 하겠습니다.”

화면 구성 요소: 수정할 곳을 정확히 가리키기

약 3분
핵심 한 문장 하나의 사이트 화면도 상단 메뉴, 검색, 콘텐츠 카드, 행동 버튼, 결과 안내처럼 서로 다른 역할의 영역으로 나뉩니다.
상단 메뉴서비스 이름과 주요 이동 경로를 보여 주는 공통 영역
검색사용자가 원하는 정보나 상품을 찾도록 입력을 받는 영역
콘텐츠 카드상품, 글, 사람처럼 반복되는 정보를 같은 형식으로 보여 주는 영역
행동과 피드백버튼을 누르게 하고 처리 중·성공·실패 결과를 알려 주는 영역
강사가 먼저 이해할 것

이 장표에서는 특정 기술 이름이나 코드 구조를 가르치지 않습니다. 수강생이 화면을 한 덩어리로 보지 않고 역할별 구역으로 나누어 관찰하게 만드는 것이 목표입니다.

이 구분이 중요한 이유는 AI에게 “사이트를 예쁘게 바꿔 줘”라고 말하는 대신 “상단 메뉴의 로그인 버튼을 더 잘 보이게 하고, 상품 카드 아래에 장바구니 버튼을 추가해 줘”처럼 수정 범위를 말할 수 있기 때문입니다.

실제 개발에서는 각 영역이 여러 파일로 나뉘거나 하나의 파일에 함께 있을 수 있습니다. 오늘은 파일 이름을 맞히는 시간이 아니라 화면에서 수정 대상을 정확히 찾는 연습입니다.

상세 멘트

“이 화면을 그냥 쇼핑몰이라고 한 덩어리로 보지 말고, 사용자의 눈이 이동하는 순서대로 나눠 보겠습니다.”

“가장 위의 상단 메뉴는 서비스 이름과 카테고리, 로그인, 장바구니처럼 어디로 이동할지 알려 줍니다. 이 부분이 없다면 사용자는 지금 어느 서비스에 있고 다음에 어디로 가야 하는지 헤매게 됩니다.”

“검색 영역은 사용자가 원하는 것을 직접 입력하는 곳입니다. 상품 카드는 사진, 이름, 가격처럼 같은 형식의 정보를 반복해서 보여 줍니다. 카드가 반복되면 사용자는 매번 새로 읽는 법을 배우지 않아도 됩니다.”

“주문하기나 장바구니 담기 같은 버튼은 사용자의 행동을 시작합니다. 버튼을 누른 뒤에는 로딩, 완료 알림, 오류 안내처럼 결과를 알려 주는 피드백 영역이 필요합니다. 버튼만 있고 반응이 없다면 사용자는 눌렸는지조차 알 수 없습니다.”

화면 조작과 질문 순서
1. 상단 메뉴를 클릭하고 “이 영역이 사라지면 사용자가 무엇을 잃을까요?”라고 묻습니다.
2. 검색을 클릭하고 “사용자의 입력을 받는 곳은 어디인가요?”라고 묻습니다.
3. 상품 카드를 클릭하고 사진·상품명·가격이 반복되는 규칙을 짚습니다.
