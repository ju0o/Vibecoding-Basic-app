## 한 줄 정의

Generative AI(생성 AI)는 주어진 조건에 맞춰 **새로운 텍스트·이미지·오디오 등 샘플을 만들어 내는** AI 접근입니다. “분류만 하는 모델”과 대비해 이해하면 쉽습니다.

## 왜 등장했는가

많은 초기 성공 사례는 입력에 라벨을 붙이는 **판별·분류**에 있었습니다. 하지만 초안 작성, 이미지 생성, 코드 제안처럼 **없던 출력을 만들어야** 하는 요구가 커졌습니다. 생성 모델은 데이터 분포를 학습해 새로운 샘플을 뽑는 쪽으로 발전했습니다. (interpretation / educational_example)

## 이전 기술의 한계

딥러닝 분류기는 “이 사진은 고양이인가?”에는 강할 수 있어도, “고양이 설명 문단을 새로 써라”에는 구조가 맞지 않을 수 있습니다. 규칙 템플릿 생성은 반복 문구에는 쓰이지만 다양성과 유연성이 떨어집니다.

## 무엇을 해결했는가

생성 AI는 **조건부 생성**(프롬프트·스케치·부분 입력 → 완성본 후보)을 가능하게 합니다. 한계: 그럴듯하지만 틀린 내용(환각), 저작권·안전·편향 이슈, 평가가 분류보다 어렵다는 점. 모든 생성 AI가 LLM은 아닙니다(이미지·음성 전용 모델 등).

## 실제 사례

- 텍스트 초안·요약·번역 보조 (educational_example)
- 이미지 생성·편집 보조 (educational_example)
- 코드 제안 (도구마다 다름 · 반드시 검토)

심화: 토큰·컨텍스트 기초는 Textbook `tokenization-and-context` · KB `tokenization-context`.

## 대표 기업

생성 모델을 연구·서비스하는 조직이 많습니다. 이 챕터는 특정 제품을 추천·순위로 제시하지 않습니다. 기능·요금·지역 정책은 공식 문서의 **확인일** 기준으로 따로 확인하세요.

## 대표 서비스

대화형 생성, 이미지 생성, 코드 어시스턴트 등이 대표 유형입니다. 학습 포인트는 브랜드 암기가 아니라 **입력 조건 → 생성 → 사람 검증** 루프입니다.

## 실제 프로젝트에서는 어떻게 사용하는가

바이브코딩에서 생성 AI는 “완성 코드 자동 배포기”가 아니라 **초안 엔진**에 가깝습니다. 좋은 패턴: 작은 단위로 생성 → 테스트 → 수정 요청. 나쁜 패턴: 한 번에 전체 시스템을 생성하고 검증 생략. 생성 결과를 사실·법률·보안 판단의 최종 근거로 쓰지 마세요.

## 인터랙티브 다이어그램

Roadmap에서 Deep Learning → Generative AI → LLM 흐름을 확인하고, LLM이 생성 AI의 한 갈래임을 Passport로 복습합니다.

## 실습

1. “이 이메일이 스팸인가?”(분류)와 “사과하는 이메일 초안을 써 줘”(생성)를 비교합니다.
2. 각 과제에서 모델이 내야 할 출력 형태를 적어 봅니다.
3. 생성 결과를 바로 보내지 않고 사람이 고칠 체크리스트 3개를 만듭니다.

## 퀴즈

Generative AI와 LLM의 포함 관계, “생성=진실” 오해를 점검합니다.
