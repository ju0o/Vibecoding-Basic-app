## 한 줄 정의

CI/CD는 **지속적 통합(Continuous Integration)과 지속적 배포/전달(Continuous Delivery)**로, 코드 변경을 자동으로 빌드·테스트·배포하는 파이프라인입니다. GitHub Actions는 이를 ==빌드·테스트·배포 파이프라인을 자동화하는 CI/CD 플랫폼==으로 정의합니다.

핵심은 **자동화**입니다. 사람이 매번 손으로 "테스트 돌리고, 빌드하고, 배포하고"를 반복하면 실수가 나고 느립니다. CI/CD는 이 과정을 커밋 하나로 자동 실행되게 엮습니다 — 앞 강의들에서 배운 PR(협업), `npm run verify`(스크립트), 배포 플랫폼이 하나의 자동 흐름으로 연결되는 지점입니다. 흩어져 배운 조각들이 여기서 하나의 파이프라인으로 합쳐집니다.

> [!KEY]
> CI/CD의 뼈대는 하나의 흐름입니다 — ==이벤트(커밋·PR)가 워크플로를 트리거하고, 워크플로가 잡을 실행하며, 잡이 스텝(테스트·빌드·배포)을 순서대로 수행==합니다. 각 이름(워크플로·이벤트·잡·스텝)은 이 흐름의 한 층위일 뿐이므로, 흐름을 잡으면 용어는 저절로 자리를 찾습니다.

![CI/CD 흐름: 이벤트→워크플로→잡(검증·배포)→스텝, 검증 통과 시에만 배포](/lesson-diagrams/ci-cd-pipeline-basics/ci-cd-flow.svg)

## 왜 존재하는가

빌드·테스트·배포를 사람이 손으로 하면 세 가지 문제가 생깁니다.

첫째, **실수와 누락.** "배포 전에 테스트를 돌려야 한다"를 사람이 매번 기억하면, 급하거나 피곤할 때 건너뜁니다. 그렇게 검증 없이 나간 코드가 사용자 앞에서 터집니다. 자동화는 "언제나 테스트를 먼저"를 규칙으로 강제해, 사람의 그날 컨디션과 무관하게 같은 검증을 보장합니다.

둘째, **느림과 반복.** 매 배포마다 여러 명령을 순서대로 실행하는 것은 지루하고 시간이 듭니다. 그 시간에 실수가 끼어들 여지도 커지고, 반복 작업은 집중력을 갉아먹습니다. 파이프라인은 이 반복을 기계에 맡겨, 사람은 코드에만 집중하게 합니다.

셋째, **일관성 없음.** 사람마다 다른 환경·순서로 배포하면 "내 컴퓨터에서는 됐는데"가 반복됩니다. 누구는 테스트를 돌리고 누구는 건너뛰고, 누구는 옛 의존성으로 빌드하면 결과가 제각각입니다. CI/CD는 정해진 러너(서버)에서 언제나 같은 절차로 실행해, 배포를 재현 가능하게 만듭니다.

## 작동 원리

### 여섯 구성 요소

GitHub Actions를 예로 들면, CI/CD 파이프라인은 여섯 개념으로 구성됩니다:

| 요소 | 정의(공식) | 역할 |
|---|---|---|
| 워크플로 | "a configurable automated process that will run one or more jobs" | 자동화의 최상위 단위 |
| 이벤트 | "a specific activity in a repository that triggers a workflow run" | 워크플로를 촉발 |
| 잡 | "a set of steps ... executed on the same runner" | 스텝의 묶음 |
| 스텝 | "either a shell script ... or an action" | 개별 작업 |
| 액션 | "a pre-defined, reusable set of jobs or code" | 재사용 작업 |
| 러너 | "a server that runs your workflows" | 실제 실행 서버 |

### 흐름: 커밋에서 배포까지

이 요소들이 하나의 흐름을 만듭니다:

```
[커밋/PR = 이벤트]
   │  트리거
   ▼
[워크플로 실행]
   ├─ 잡: 검증
   │   ├─ 스텝: npm ci        (의존성 설치)
   │   ├─ 스텝: npm run verify (린트·타입·테스트)
   │   └─ 스텝: npm run build  (빌드)
   └─ 잡: 배포 (검증 통과 시에만)
       └─ 스텝: 배포 플랫폼으로 전송
```

==앞 단계가 실패하면 뒤 단계는 실행되지 않습니다==. 검증 잡이 실패하면 배포 잡은 돌지 않으므로, 깨진 코드가 배포되는 일이 구조적으로 막힙니다.

### CI와 CD의 구분

- **CI(지속적 통합)**: 변경을 자주 통합하며 자동으로 빌드·테스트하는 것. "이 변경이 기존 코드를 깨뜨리지 않는가"를 매번 확인합니다.
- **CD(지속적 배포/전달)**: 검증을 통과한 변경을 자동으로 배포 가능 상태로 만들거나 실제 배포하는 것.

CI가 "안전한가"를 묻고, CD가 "그럼 내보내자"를 실행합니다. GitHub Actions는 둘 다의 플랫폼입니다. 둘을 나눠 이해하면 도입 순서도 정해집니다 — 먼저 CI(자동 검증)로 안전망을 깔고, 그 검증이 믿을 만해지면 CD(자동 배포)를 얹습니다. 검증 없는 자동 배포는 "깨진 코드를 더 빨리 내보내는" 역효과를 낳기 때문입니다.

### 러너 — 일관된 실행 환경

파이프라인이 도는 곳은 내 컴퓨터가 아니라 러너(정해진 서버)입니다. 이것이 중요한 이유는 "내 컴퓨터에서만 되는" 문제를 없애기 때문입니다. 내 컴퓨터에는 우연히 설치된 도구나 설정이 있을 수 있지만, 러너는 매번 깨끗한 정해진 환경에서 시작합니다. 그래서 파이프라인이 통과했다는 것은 "특정 누군가의 컴퓨터가 아니라 표준 환경에서 검증됐다"는 뜻이 되어, 재현성과 신뢰가 생깁니다.

> [!EXAMPLE]
> 이 사이트를 CI/CD로 자동화한다면 이렇게 됩니다 — main에 커밋을 push(이벤트)하면 워크플로가 트리거되고, 검증 잡이 `npm run verify`(린트·타입·테스트·빌드)를 스텝으로 실행합니다. 통과하면 배포 잡이 Firebase로 배포하고, 실패하면 거기서 멈춰 배포되지 않습니다. 지금은 사람이 손으로 하는 이 과정(verify → deploy)이, 파이프라인에서는 커밋 하나로 자동 실행됩니다.

## 스펙과 세부

### 구성 요소의 위계

| 층위 | 담는 것 |
|---|---|
| 워크플로 | 여러 잡 |
| 잡 | 여러 스텝(같은 러너에서) |
| 스텝 | 셸 스크립트 또는 액션 하나 |

### 흔한 파이프라인 구성

| 단계 | 스텝 예시 |
|---|---|
| 준비 | 체크아웃, Node 설치(액션 재사용) |
| 검증(CI) | `npm ci` → `npm run verify` |
| 빌드 | `npm run build` |
| 배포(CD) | 배포 플랫폼으로 전송(검증 통과 시) |

### 게이트 원칙

| 원칙 | 의미 |
|---|---|
| 검증 먼저 | 배포 잡은 검증 잡 통과에만 실행 |
| 실패 시 중단 | 앞 스텝 실패 시 뒤는 미실행 |
| secret 보호 | 로그에 토큰·키 노출 금지 |

### 상황별 빠른 참조

| 하고 싶은 것 | 처방 |
|---|---|
| PR마다 자동 테스트 | PR 이벤트에 검증 잡 |
| 검증 없는 배포 막기 | 배포 잡을 검증 잡에 의존시킴 |
| 반복 작업 재사용 | 액션으로 추출 |
| 실패 지점 빨리 찾기 | 의미 단위로 스텝 분리 |
| 커밋 시 자동 배포 | push 이벤트 → 검증 → 배포 |

## 원문으로 읽기

> "GitHub Actions is a continuous integration and continuous delivery (CI/CD) platform that allows you to automate your build, test, and deployment pipeline."
>
> — GitHub Actions는 빌드·테스트·배포 파이프라인을 자동화할 수 있게 해주는 CI/CD(지속적 통합·지속적 전달) 플랫폼이다.
> [Understanding GitHub Actions](https://docs.github.com/en/actions/about-github-actions/understanding-github-actions)

"automate your build, test, and deployment pipeline" — CI/CD의 목적이 이 세 단어(build, test, deployment)에 담겨 있습니다. 이 셋은 앞 강의들의 주제(빌드/런타임, 검증, 배포 플랫폼)와 정확히 겹칩니다. CI/CD는 새로운 것을 만드는 게 아니라, 이미 배운 단계들을 ==자동으로 이어 붙이는== 것입니다.

> "A workflow is a configurable automated process that will run one or more jobs."
>
> — 워크플로는 하나 이상의 잡을 실행하는, 설정 가능한 자동화된 프로세스다.
> [Understanding GitHub Actions](https://docs.github.com/en/actions/about-github-actions/understanding-github-actions)

워크플로가 자동화의 최상위 단위입니다. "configurable"(설정 가능)이라는 점이 중요합니다 — 무엇을 언제 어떻게 실행할지 파일(YAML)로 명시하므로, 파이프라인 자체가 코드로 관리되고 리뷰됩니다. 배포 절차가 사람의 머릿속이 아니라 저장소에 기록되는 것입니다.

> "An event is a specific activity in a repository that triggers a workflow run."
>
> — 이벤트는 워크플로 실행을 촉발하는, 저장소 내의 특정 활동이다.
> [Understanding GitHub Actions](https://docs.github.com/en/actions/about-github-actions/understanding-github-actions)

이벤트가 자동화의 방아쇠입니다. 커밋 push, PR 생성 같은 ==저장소의 활동이 워크플로를 자동으로 시작==시킵니다. 앞 강의(PR 흐름)에서 배운 PR이 여기서 이벤트가 되어, "PR을 열면 자동으로 테스트가 돈다"는 협업과 자동화의 결합이 이뤄집니다.

> "A job is a set of steps in a workflow that is executed on the same runner."
>
> — 잡은 워크플로 안에서 같은 러너에서 실행되는 스텝의 묶음이다.
> [Understanding GitHub Actions](https://docs.github.com/en/actions/about-github-actions/understanding-github-actions)

잡이 스텝을 묶는 단위이고 "같은 러너"에서 실행된다는 점이 핵심입니다. 그래서 잡을 나누면(검증 잡, 배포 잡) 서로 다른 조건·의존을 걸 수 있습니다 — "배포 잡은 검증 잡이 성공해야만"처럼요. 이 잡 단위의 의존이 "검증 없는 배포 금지"를 구조로 만듭니다.

> "A runner is a server that runs your workflows when they're triggered."
>
> — 러너는 워크플로가 트리거될 때 그것을 실행하는 서버다.
> [Understanding GitHub Actions](https://docs.github.com/en/actions/about-github-actions/understanding-github-actions)

러너가 파이프라인이 실제로 도는 곳입니다. 내 컴퓨터가 아니라 정해진 서버에서 언제나 같은 환경으로 실행되므로, "내 컴퓨터에서만 되는" 문제가 사라집니다. ==일관된 실행 환경==이 CI/CD가 재현성을 보장하는 이유입니다.

## 실전에서

### AI가 만든 워크플로 검토하기

AI에게 "CI 설정해줘"라고 하면 워크플로 YAML을 만듭니다. 그때 그 파이프라인이 무엇을 검증하는지를 사람이 봐야 합니다 — ==테스트·타입 검사·빌드가 포함됐는가, 배포 잡이 검증 통과에만 실행되는가==. "동작하는 자동화"와 "안전한 게이트"는 다르므로, 각 잡·스텝의 목적과 순서를 확인하는 것이 검토의 핵심입니다. 특히 배포 잡이 검증 잡에 제대로 의존하는지를 봐야 합니다.

### secret을 파이프라인에 노출하지 않기

CI/CD는 배포를 위해 토큰·키 같은 secret을 다룹니다. 앞 강의(환경변수·로그)의 원칙이 그대로 적용됩니다 — secret은 워크플로 로그에 출력하지 말고, 플랫폼의 secret 저장소를 통해 주입해야 합니다. AI가 만든 워크플로가 secret을 평문으로 echo하거나 로그에 남기지 않는지 확인하세요.

### 검증을 배포의 전제로 묶기

파이프라인의 가장 큰 이득은 "검증 없이는 배포 불가"를 구조로 만드는 것입니다. 배포 잡을 검증 잡에 의존시키면, 테스트가 실패한 코드는 배포 단계에 도달조차 못 합니다. npm-scripts 강의의 pre/post 규칙과 같은 정신 — ==사람의 규율이 아니라 구조가 순서를 지키게== 하는 것입니다. 이 프로젝트가 지금 `npm run verify`를 손으로 돌린 뒤 배포하는 것도 같은 원칙의 수동 버전이며, CI/CD는 그 "손으로"를 "자동으로"로 바꿉니다.

> [!TIP]
> CI/CD를 처음 도입할 때는 ==CD(자동 배포)보다 CI(자동 검증)를 먼저== 갖추세요. "커밋마다 테스트가 자동으로 돈다"만 있어도 대부분의 회귀 버그를 조기에 잡습니다. 자동 배포는 검증이 충분히 신뢰될 때 더하는 것이 안전합니다 — 믿을 수 없는 검증 위에 자동 배포를 얹으면, 깨진 코드를 빠르게 배포하는 기계가 될 뿐입니다. 자동화의 속도는 그 안의 검증이 옳을 때만 이득이 됩니다.

## 한계와 트레이드오프

**파이프라인은 검증만큼만 안전합니다.** "테스트가 통과하면 배포"는 그 테스트가 실제 문제를 잡을 때만 유효합니다. 테스트가 빈약하면 파이프라인은 "빈약한 검증을 빠르게 통과시켜 깨진 코드를 자동 배포"하는 도구가 됩니다. 자동화의 가치는 그 안에 담긴 검증의 질에 달려 있습니다.

**자동화에도 유지 비용이 있습니다.** 워크플로 자체가 코드이므로, 의존성·플랫폼 변화에 따라 깨지고 손봐야 합니다. 작은 프로젝트에서는 수동 배포(`npm run verify && deploy`)가 더 단순할 수 있습니다 — 이 사이트도 현재는 사람이 verify 후 배포하는 방식입니다. 자동화는 반복 빈도가 그 구축·유지 비용을 넘어설 때 이득입니다.

**이 강의는 CI/CD의 개념입니다.** 구체적인 YAML 문법, 매트릭스 빌드, 캐싱, 환경별 배포, 승인 게이트 같은 세부는 여기서 다루지 않았습니다. 하지만 "이벤트 → 워크플로 → 잡 → 스텝"과 "검증 먼저, 배포 나중"이라는 뼈대를 잡으면, 어떤 CI/CD 도구(GitHub Actions, GitLab CI 등)를 만나도 그 구성을 같은 틀로 읽을 수 있습니다. 도구마다 문법과 이름은 조금씩 다르지만, "무언가가 트리거되어 정해진 단계를 순서대로 실행한다"는 골격은 공통이기 때문입니다.

> [!WARNING]
> 파이프라인이 초록불(통과)이니 안전하다는 과신은 위험합니다. 초록불은 "정의된 검사를 통과했다"일 뿐, "모든 문제가 없다"가 아닙니다. 검사에 없는 종류의 버그(성능 저하, 특정 상황의 오류)는 초록불 뒤에 숨어 배포됩니다. 파이프라인은 안전의 바닥을 높이는 도구이지, 사람의 판단을 없애는 도구가 아닙니다. 자동 검증이 잡아주는 것과, 사람이 눈으로 확인해야 하는 것을 구분하는 안목이 여전히 필요합니다.

### 설명 연습: 파이프라인을 자동 체크리스트로 말하기

CI/CD를 설명할 때는 "자동으로 배포한다"보다 "커밋 이후 사람이 반복하던 체크리스트를 서버가 같은 순서로 실행한다"고 말하면 정확합니다. 이벤트가 workflow를 깨우고, job이 실행 환경을 잡고, step이 명령을 수행하며, runner가 그 명령을 실제로 돌립니다. 이 구조를 알면 실패 메시지를 볼 때도 어느 층에서 멈췄는지 구분할 수 있습니다.

또한 파이프라인은 신뢰를 만드는 장치이지 신뢰 그 자체가 아닙니다. 무엇을 검사할지 YAML에 적지 않았다면 초록불은 그 부분을 보증하지 않습니다. 그래서 좋은 팀은 lint, typecheck, test, build처럼 빠른 검사를 기본으로 두고, 배포 전 필요한 secret, 권한, 대상 환경을 따로 확인합니다. AI가 만든 코드도 PR에 올라온 순간 같은 파이프라인을 지나야 합니다. 자동화는 사람을 빼는 장치가 아니라 매번 같은 기준으로 사람의 판단을 보조하는 장치입니다.
