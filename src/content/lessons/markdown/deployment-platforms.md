## 한 줄 정의

배포 플랫폼은 **빌드된 앱을 사용자에게 서빙하는 실행 환경**입니다. 앞 강의(빌드 타임과 런타임)의 세 단계 중 ==실행(run) 단계를 실제로 담당하는 인프라==가 바로 이것입니다. 개발자가 빌드한 산출물을 받아 전 세계 사용자에게 빠르고 안전하게 전달하는 일을, 플랫폼이 대신 운영합니다.

대표적으로 Firebase Hosting은 ==웹 앱을 위한 빠르고 안전한 호스팅==을 제공하며 파일을 CDN 엣지에 캐시해 서빙하고, Vercel은 배포를 "프로젝트 빌드 성공의 결과물"로 정의하며 배포마다 고유 URL을 만듭니다. 이 사이트도 Firebase Hosting으로 배포됩니다.

> [!KEY]
> 배포 플랫폼을 고를 때 가장 먼저 물어야 할 것은 **정적 모델인가, 서버 모델인가**입니다. 정적 호스팅은 빌드된 파일을 CDN으로 그대로 서빙하고, 서버·함수 모델은 요청마다 코드를 실행합니다. ==정적 모델에는 런타임 서버가 없으므로==, 서버에서 돌아야 할 코드(요청 시 DB 조회 등)를 정적 호스팅에 올리면 동작하지 않습니다.

![배포 플랫폼: 정적 CDN 호스팅과 서버·함수 모델, 배포마다 고유 URL](/lesson-diagrams/deployment-platforms/deployment-models.svg)

## 왜 존재하는가

빌드한 산출물이 있어도, 그것을 사용자에게 전달하는 일은 별개의 큰 문제입니다.

첫째, **전 세계에 빠르게.** 서버가 한국에 하나만 있으면 지구 반대편 사용자는 느립니다. 데이터가 물리적으로 먼 거리를 오가야 하기 때문입니다. 배포 플랫폼은 CDN(Content Delivery Network)으로 파일을 전 세계 엣지에 복제해, 사용자와 가까운 곳에서 서빙합니다 — 거리가 곧 속도이기 때문입니다.

둘째, **안전하게.** HTTPS(암호화 전송)를 직접 설정하려면 인증서 발급·갱신 같은 번거로운 작업이 필요합니다. 인증서는 만료되면 사이트가 "안전하지 않음" 경고를 띄우므로 갱신을 놓치면 큰일입니다. 좋은 플랫폼은 발급도 갱신도 자동으로 해줘, 개발자가 보안 인프라를 직접 다루지 않아도 되게 합니다.

셋째, **되돌릴 수 있게.** 배포한 것이 문제를 일으키면 빠르게 이전 상태로 돌아가야 합니다. 사용자가 깨진 사이트를 보는 시간은 짧을수록 좋습니다. 배포마다 고유하게 기록되면, 새로 빌드할 필요 없이 과거의 검증된 배포로 되돌리는 롤백이 간단해집니다.

## 작동 원리

### 정적 모델 — CDN 호스팅

Firebase Hosting이 대표하는 정적 모델은 단순하고 강력합니다. 빌드된 파일(HTML/CSS/JS)을 업로드하면, ==각 파일이 전 세계 CDN 엣지의 SSD에 캐시==되어 gzip/Brotli로 압축 전송됩니다. 요청이 오면 서버가 코드를 실행하는 게 아니라, 이미 만들어진 파일을 가까운 엣지에서 그대로 내보냅니다.

```
빌드 산출물 (HTML/JS)
   │  업로드
   ▼
[CDN 엣지: 서울·도쿄·런던·뉴욕 …]  ← 파일이 전 세계에 복제
   │  요청 시
   ▼
사용자에게 가장 가까운 엣지에서 즉시 서빙 (HTTPS)
```

이 사이트가 정확히 이 방식입니다 — Next.js를 `output: export`로 정적 빌드해 Firebase Hosting에 올리면, 전 세계 어디서든 빠르게 열립니다. 서버를 한 대도 직접 운영하지 않으면서, 수십 개의 강의 페이지가 각국 사용자에게 즉시 서빙되는 것은 이 CDN 정적 모델 덕분입니다.

### 서버·함수 모델 — 요청마다 실행

반대편에는 요청마다 코드를 실행하는 모델이 있습니다. 사용자가 요청할 때 서버(또는 서버리스 함수)가 코드를 돌려 응답을 만듭니다. 매 요청 시 DB를 조회하거나, 사용자마다 다른 페이지를 생성하는 등 ==런타임 로직이 필요할 때== 이 모델을 씁니다. Vercel은 정적 파일과 서버 함수를 함께 배포할 수 있어 두 모델을 섞습니다.

### 배포마다 고유 URL

Vercel의 핵심 성질 하나는 ==각 배포가 고유 URL을 가진다==는 것입니다. 이 덕분에 배포를 서로 비교하고, 미리보기(Preview)에서 검증한 뒤 운영(Production)으로 승격하며, 문제가 생기면 이전 배포로 되돌릴 수 있습니다. Vercel은 Local·Preview·Production 세 환경을 두어, 운영에 영향 없이 안전하게 검증하는 흐름을 만듭니다.

이 설계의 우아함은 배포를 "덮어쓰기"가 아니라 "쌓기"로 다룬다는 데 있습니다. 파일을 덮어쓰면 이전 상태가 사라지지만, 각 배포가 고유 URL로 보존되면 과거의 모든 배포가 그대로 남아 언제든 되돌아갈 지점이 됩니다. 앞서 Git 강의에서 배운 "커밋마다 이력이 쌓여 되돌릴 수 있다"는 원리가, 배포 계층에서 다시 나타나는 셈입니다.

### Git 연동 자동 배포

많은 플랫폼이 Git 저장소와 연결되어, 커밋이나 PR마다 배포를 자동으로 트리거합니다. feature 브랜치를 push하면 그 브랜치의 Preview 배포가 자동 생성되고, main에 병합되면 Production 배포가 일어납니다. 이것이 다음 강의(CI/CD)의 토대입니다 — "커밋하면 배포된다"는 자동화가 여기서 시작됩니다. 개발자는 코드를 push하는 익숙한 동작만으로 배포까지 이르게 됩니다.

> [!EXAMPLE]
> 팀원이 새 기능 브랜치를 push하면 Vercel이 자동으로 Preview 배포를 만들고 고유 URL을 줍니다. 팀은 그 URL로 실제 동작을 확인하고(운영 사이트는 그대로), 문제없으면 Production으로 승격합니다. 만약 승격 후 버그가 발견되면, 이전 배포의 URL로 즉시 롤백합니다 — 배포마다 고유 URL이 있기에 "되돌릴 지점"이 항상 존재하는 것입니다.

## 스펙과 세부

### 두 배포 모델 비교

| 구분 | 정적 호스팅 (Firebase) | 서버·함수 모델 |
|---|---|---|
| 서빙 방식 | 빌드된 파일을 CDN으로 그대로 | 요청마다 코드 실행 |
| 런타임 서버 | 없음 | 있음(서버/함수) |
| 적합한 것 | 정적 사이트, SPA, 문서 | 동적 API, 사용자별 페이지 |
| 속도 | 매우 빠름(엣지 캐시) | 실행 시간만큼 지연 |
| 이 사이트 | ✓ (Firebase) | — |

### Firebase Hosting의 기본 제공

| 기능 | 설명 |
|---|---|
| CDN 엣지 캐시 | 전 세계 SSD에 파일 캐시, gzip/Brotli 압축 |
| zero-config SSL | 설정 없이 HTTPS 기본 적용 |
| 빠른 롤백 | 이전 릴리스로 되돌리기 |

### Vercel의 환경 구분

| 환경 | 용도 |
|---|---|
| Local | 로컬에서 개발·테스트 |
| Preview | 운영 영향 없이 QA·협업 |
| Production | 사용자 대상 실제 사이트 |

### 상황별 빠른 참조

| 상황 | 처방 |
|---|---|
| 정적 사이트를 빠르게 서빙 | Firebase Hosting(CDN·SSL 기본) |
| 요청마다 다른 응답 필요 | 서버·함수 모델 |
| 배포 전 안전하게 확인 | Preview 환경에서 검증 후 승격 |
| 배포 후 문제 발생 | 이전 배포로 롤백 |
| HTTPS 설정이 번거로움 | zero-config SSL 플랫폼 선택 |

## 원문으로 읽기

> "Firebase Hosting provides fast and secure hosting for your web app."
>
> — Firebase Hosting은 웹 앱을 위한 빠르고 안전한 호스팅을 제공한다.
> [Firebase Hosting](https://firebase.google.com/docs/hosting)

"fast and secure"라는 두 단어가 배포 플랫폼의 핵심 가치를 압축합니다. 개발자가 직접 서버를 세우고 CDN을 구성하고 인증서를 관리하는 대신, 플랫폼이 "빠름"(CDN)과 "안전함"(SSL)을 기본으로 제공합니다. 이것이 배포를 인프라 작업에서 "파일 올리기"로 단순화하는 이유입니다.

> "Each file that you upload is cached on SSDs at CDN edges around the world and served as gzip or Brotli."
>
> — 업로드한 각 파일은 전 세계 CDN 엣지의 SSD에 캐시되어 gzip 또는 Brotli로 압축 전송된다.
> [Firebase Hosting](https://firebase.google.com/docs/hosting)

정적 호스팅이 왜 빠른지가 이 문장에 다 있습니다 — "CDN edges around the world"(전 세계 엣지)와 "gzip or Brotli"(압축). 파일이 사용자 가까이 복제되어 있고, 작게 압축되어 전송되므로, 지구 어디서든 빠릅니다. 서버가 매번 계산하지 않고 이미 만든 파일을 내보내기에 가능한 속도입니다.

> "Zero-configuration SSL is built into Firebase Hosting, so content is always delivered securely."
>
> — Zero-configuration SSL이 Firebase Hosting에 내장되어 있어, 콘텐츠가 항상 안전하게 전달된다.
> [Firebase Hosting](https://firebase.google.com/docs/hosting)

"zero-configuration"이 핵심입니다. HTTPS는 원래 인증서 발급·설치·갱신이라는 작업을 요구하지만, 플랫폼이 이를 자동화해 ==개발자가 아무것도 설정하지 않아도 HTTPS가 켜집니다==. 보안이 선택이 아니라 기본값이 되는 것 — 이것이 "안전함을 기본 제공"의 실제 모습입니다.

관련 원문(링크): [Deploying to Vercel](https://vercel.com/docs/deployments)

배포가 "빌드 성공의 결과물"이라는 정의가 앞 강의(빌드/런타임)와 이 강의를 잇습니다. 빌드가 실패하면 배포도 없습니다 — 즉 배포 플랫폼은 빌드 단계를 통과한 산출물만 실행 단계로 넘깁니다. 이 순서가 "깨진 코드가 사용자에게 가지 않게" 막는 첫 관문이며, 빌드와 배포를 분리해 둔 덕분에 얻는 안전장치입니다.

관련 원문(링크): [Deploying to Vercel](https://vercel.com/docs/deployments)

"a unique URL"이 미리보기·롤백·비교를 모두 가능하게 하는 열쇠입니다. 각 배포가 사라지지 않고 고유 주소로 남으므로, 새 배포를 안전하게 시험하고 문제가 생기면 옛 배포로 돌아갈 수 있습니다. ==배포를 "덮어쓰기"가 아니라 "쌓기"로 다루는== 이 설계가 안전한 배포의 토대입니다.

## 실전에서

### 플랫폼 모델을 먼저 확인하기

AI에게 "이거 배포해줘"라고 하면, 그 플랫폼이 정적 모델인지 서버 모델인지에 따라 되는 것과 안 되는 것이 갈립니다. 이 사이트처럼 Firebase 정적 호스팅이면 ==런타임 서버 코드가 동작하지 않으므로==, AI가 "요청 시 DB를 조회하는 API"를 넣은 코드를 정적 배포하면 실패합니다. "이 플랫폼은 무엇을 실행할 수 있는가"를 알아야 AI의 배포 구성을 검증할 수 있습니다. 이 확인 없이 AI 결과를 그대로 배포하면 "로컬에서는 됐는데 배포하면 안 되는" 전형적 상황에 빠집니다.

### Preview로 검증한 뒤 승격

운영 사이트에 바로 배포하는 것은 사용자를 대상으로 실험하는 것과 같습니다. Preview 환경이 있는 플랫폼이라면, 새 변경을 Preview 고유 URL에서 먼저 확인하고 문제없을 때만 Production으로 승격하세요. ==운영에 영향 없이 검증하는 안전지대==가 Preview입니다.

### 롤백 계획을 미리 세우기

배포 전에 "문제가 생기면 어떻게 되돌리나"를 알아두어야 합니다. 배포마다 고유 URL·기록이 남는 플랫폼에서는 이전 배포로 되돌리기가 간단하지만, 그 방법을 급할 때 처음 찾으면 늦습니다. 평소에 롤백 절차를 확인해두는 것이 장애 대응의 기본입니다. 롤백은 "빠르게 정상으로 돌아가기"이고, 원인 분석은 그다음입니다 — 불이 났을 때 먼저 끄고 원인은 나중에 조사하는 것과 같습니다. 이 순서를 알아두면 장애 상황에서 당황하지 않습니다.

> [!TIP]
> 새 프로젝트의 배포 플랫폼을 고를 때 =="이 앱은 정적으로 충분한가, 서버 로직이 필요한가"==를 먼저 답하세요. 블로그·문서·랜딩 페이지·이 사이트 같은 학습 아카이브는 정적으로 충분해 CDN 호스팅이 빠르고 저렴합니다. 반면 사용자별 대시보드나 실시간 API는 서버·함수 모델이 필요합니다. 요구가 모델을 정하지, 그 반대가 아닙니다 — "멋져 보여서" 서버 모델을 고르면 불필요한 복잡성과 비용만 얻습니다.

## 한계와 트레이드오프

**정적의 빠름은 동적의 유연함과 맞바꿉니다.** CDN 정적 호스팅은 압도적으로 빠르지만, "요청마다 달라지는 응답"은 만들 수 없습니다. 사용자별 페이지, 실시간 데이터, 서버 측 인증 같은 것이 필요하면 서버·함수 모델로 가야 합니다. 많은 사이트가 정적 부분은 CDN으로, 동적 부분만 함수로 처리하는 하이브리드를 씁니다.

**플랫폼 편의는 종속을 부릅니다.** 배포 플랫폼이 제공하는 편의(자동 SSL, 미리보기, 롤백)에 깊이 기대면, 다른 플랫폼으로 옮기기 어려워집니다(vendor lock-in). 대부분의 경우 편의가 이기지만, 핵심 로직은 특정 플랫폼에 종속되지 않는 표준(HTTP, 컨테이너 등) 위에 두는 것이 이전 가능성을 지킵니다.

**이 강의는 배포의 시작입니다.** 커스텀 도메인 연결, 서버리스 함수의 콜드 스타트, 엣지 함수, 캐시 무효화 전략 같은 세부는 여기서 다루지 않았습니다. 하지만 "정적이냐 서버냐", "CDN이 왜 빠른가", "배포마다 고유 URL"이라는 뼈대를 잡으면, 그 위의 구체 기능들도 "어느 모델의 어떤 보완인가"로 읽힙니다. 예컨대 엣지 함수는 "정적 CDN의 빠름에 약간의 동적 로직을 더하는" 절충이고, 캐시 무효화는 "CDN 캐시가 옛 파일을 붙잡는 문제의 해결책"입니다 — 뼈대를 알면 이런 기능들의 존재 이유가 저절로 설명됩니다.

> [!WARNING]
> 정적 호스팅에 secret(API 키 등)을 넣은 코드를 배포하면 그 secret이 전 세계에 공개됩니다 — 정적 파일은 CDN으로 모두에게 그대로 전송되기 때문입니다. 앞 강의(환경변수)에서 다룬 "클라이언트에 노출되는 값에는 secret을 담지 않는다"가 정적 배포에서 특히 중요합니다. 이 사이트가 비밀번호 원문이 아니라 해시만 담는 이유이기도 합니다 — 해시는 노출돼도 원문을 역산하기 어렵기 때문에 정적 파일에 담아도 안전한 값입니다.

### 설명 연습: 플랫폼을 서버가 아니라 운영 경계로 보기

배포 플랫폼을 설명할 때는 "파일을 올리는 곳"보다 "빌드, URL, 환경, 캐시, 롤백의 경계를 관리하는 곳"이라고 말하는 편이 좋습니다. Preview URL은 변경을 검토하는 공간이고, Production URL은 실제 사용자가 보는 공간입니다. 이 둘을 구분하면 PR마다 미리 확인하고, 문제가 생기면 이전 배포로 되돌리는 운영 흐름이 이해됩니다.

정적 사이트에서는 특히 무엇이 빌드 산출물에 들어가는지 설명해야 합니다. HTML, CSS, JavaScript는 CDN으로 복제되어 사용자에게 전달됩니다. 따라서 브라우저로 내려가면 안 되는 secret은 플랫폼 환경변수에 있어도 클라이언트 번들로 섞이는 순간 공개 정보가 됩니다. 플랫폼은 배포를 쉽게 해 주지만, 무엇이 공개되고 무엇이 서버에만 남아야 하는지 판단하는 책임은 여전히 개발자에게 있습니다.
