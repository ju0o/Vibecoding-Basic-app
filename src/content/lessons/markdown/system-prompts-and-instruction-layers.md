## 오늘 배울 것

오늘은 시스템 프롬프트와 지침 계층을 배웁니다. 시스템 프롬프트는 AI가 어떤 행동을 해야 하는지 알려주는 상위 지시이고, 지침 계층은 시스템 지시, 메시지, 도구 정의, 예시가 함께 컨텍스트를 이루는 구조입니다.

핵심은 지시를 많이 쓰는 법이 아닙니다. AI가 헷갈리지 않도록 행동 기준을 분명히 하고, 겹치거나 깨지기 쉬운 지시를 줄이는 법을 배웁니다.

## 한 줄 정의

시스템 프롬프트는 모델에게 원하는 행동을 분명히 제시하는 지시입니다.

지침 계층은 시스템 프롬프트, 사용자 메시지, 도구 설명, 예시처럼 모델이 추론할 때 함께 받는 여러 지시 재료가 한 컨텍스트 안에 놓이는 구조입니다.

## 쉬운 비유

식당 주방을 생각해봅시다. 주방에는 기본 위생 규칙, 오늘의 주문서, 조리 도구 사용법, 대표 레시피가 함께 있습니다. 요리사는 이 자료들을 보고 지금 어떤 요리를 어떻게 만들지 판단합니다.

시스템 프롬프트는 주방의 기본 운영 규칙에 가깝습니다. 사용자 메시지는 오늘 들어온 주문이고, 도구 설명은 어떤 조리 도구를 언제 써야 하는지 알려주는 안내입니다. 다만 AI는 사람처럼 상식으로 빈칸을 안정적으로 메우지 않으므로, 지시가 모호하거나 서로 겹치면 결과가 흔들릴 수 있습니다.

## 왜 생겼는가

Context Engineering은 Prompt Engineering의 확장으로 설명됩니다. 단일 지시문만 잘 쓰는 것으로는 장기 실행 에이전트가 안정적으로 일하기 어렵습니다. 에이전트는 여러 턴 동안 시스템 지시, 메시지, 도구 결과, 외부 데이터를 누적합니다.

그래서 시스템 프롬프트도 전체 컨텍스트의 일부로 다뤄야 합니다. 시스템 지시 하나만 고치면 끝나는 것이 아니라, 도구 정의와 예시, 대화 이력이 함께 어떤 행동 기준을 만드는지 봐야 합니다.

## 어떤 문제를 해결하는가

첫 번째 문제는 모호한 지시입니다. KB는 시스템 프롬프트가 원하는 행동을 분명히 제시해야 한다고 설명합니다. “잘 처리해줘” 같은 일반론은 모델이 어떤 기준으로 행동해야 하는지 알려주지 못합니다.

두 번째 문제는 깨지기 쉬운 조건문 목록입니다. KB는 brittle한 조건문 목록을 피해야 한다고 설명합니다. 예외를 끝없이 나열하면 지시가 길어지고, 중요한 행동 기준이 흐려질 수 있습니다.

## 핵심 개념

첫째, 시스템 프롬프트는 행동 기준을 세우는 지시입니다. 모델이 어떤 방식으로 답해야 하는지, 어떤 제약을 따라야 하는지 분명히 제시해야 합니다.

둘째, 시스템 프롬프트도 컨텍스트를 소비합니다. 컨텍스트 창에는 시스템 프롬프트, 메시지, 도구 결과, 문서, 도구 정의가 함께 들어갑니다. 지시가 길어질수록 다른 정보가 들어갈 공간도 줄어듭니다.

셋째, 도구 정의는 지침 계층의 일부입니다. KB는 도구 정의를 에이전트와 정보·행동 공간 사이의 계약으로 설명합니다. 도구 설명이 겹치거나 모호하면 모델이 어떤 도구를 써야 할지 헷갈립니다.

넷째, 예시는 대표 행동 패턴을 보여주는 재료입니다. KB는 많은 예외를 나열하기보다 대표적인 행동 패턴을 보여주는 방식으로 예시를 선별해야 한다고 설명합니다.

다섯째, 좋은 지침은 작고 신호가 높아야 합니다. Anthropic은 좋은 컨텍스트가 가능한 한 작고 신호가 높아야 한다고 설명합니다. 지침 계층도 같은 원칙을 따릅니다.

여섯째, 긴 세션에서는 지침과 상태를 구분해야 합니다. 변하지 않는 행동 기준은 시스템 지시로 두고, 현재 목표나 실패한 테스트 같은 변화하는 정보는 상태 산출물로 관리합니다. 이렇게 나누면 지시가 계속 길어지는 문제를 줄일 수 있습니다.

## 실제 예시

AI에게 코드 리뷰를 맡긴다고 해봅시다. 나쁜 지시는 “코드를 잘 봐줘”처럼 기준이 없습니다. 다른 나쁜 지시는 수십 개 예외 조건을 길게 늘어놓아 핵심 우선순위를 흐리게 만듭니다.

더 나은 방식은 행동 기준을 작게 정리하는 것입니다. “버그, 보안 위험, 테스트 누락을 우선 보고한다. 스타일 취향은 낮은 우선순위로 둔다. 수정 제안은 근거와 함께 쓴다.”처럼 AI가 실제로 판단할 기준을 줍니다.

도구가 포함된 작업이라면 도구 설명도 함께 정리합니다. 예를 들어 파일 읽기 도구와 명령 실행 도구가 있다면, 각각 언제 써야 하는지와 어떤 결과를 기대하는지 분리해 설명해야 합니다. 도구 설명이 겹치면 모델이 행동 공간을 헷갈릴 수 있습니다.

긴 에이전트 작업에서는 이전 도구 결과도 지침처럼 작용할 수 있습니다. 실패한 명령 결과가 남아 있으면 다음 판단에 영향을 줍니다. 그래서 지침 계층을 볼 때는 처음의 시스템 프롬프트뿐 아니라 대화 이력과 도구 결과까지 함께 봐야 합니다.

결국 좋은 지침은 길이가 아니라 신호의 선명함으로 판단해야 합니다. 이 기준이 핵심입니다.

## 코드 예시

아래 코드는 지침을 작은 묶음으로 나누어 관리하는 예시입니다.

```ts
type InstructionLayer = {
  system: string
  task: string
  toolRule: string
  examplePattern: string
}

const reviewGuide: InstructionLayer = {
  system: "버그와 위험을 먼저 찾습니다",
  task: "로그인 코드 변경을 검토합니다",
  toolRule: "파일 읽기 도구는 관련 파일에만 사용합니다",
  examplePattern: "문제, 근거, 영향 순서로 설명합니다",
}

console.log(`${reviewGuide.system} / ${reviewGuide.task}`)
```

## AI 시대에서의 의미

바이브코딩에서 시스템 프롬프트는 AI의 성격을 꾸미는 문장이 아닙니다. 반복 작업에서 AI가 어떤 기준으로 판단하고 어떤 행동을 피해야 하는지 알려주는 운영 규칙입니다.

도구를 쓰는 에이전트에서는 지침 계층이 더 중요합니다. 도구 설명, 사용자 요청, 이전 결과가 모두 컨텍스트에 들어가기 때문에, 시스템 지시는 작고 명확해야 하며 도구 설명과 충돌하지 않아야 합니다.

## 자주 헷갈리는 것

시스템 프롬프트가 길수록 좋은 것은 아닙니다. 컨텍스트는 유한하고, 토큰이 늘수록 중요한 내용이 흐려질 수 있습니다.

예외를 많이 쓰면 안전해 보이지만 항상 그렇지는 않습니다. KB는 많은 예외를 나열하기보다 대표 행동 패턴을 보여주는 예시를 선별하라고 설명합니다.

도구 설명은 단순 문서가 아닙니다. 모델이 어떤 도구를 언제 써야 하는지 판단하는 계약이므로, 지침 계층의 중요한 부분입니다.

## 실무에서 쓰는 방식

실무에서는 시스템 지시를 역할, 제약, 우선순위, 출력 기준으로 작게 나눕니다. 그리고 도구 설명이 이 기준과 겹치거나 충돌하지 않는지 점검합니다.

긴 작업에서는 지침을 계속 덧붙이지 않고 상태 산출물로 분리합니다. 작업 로그는 요약하고, 현재 목표와 다음 행동만 남겨 컨텍스트 신호를 유지합니다.

예시도 같은 방식으로 관리합니다. 모든 예외를 적기보다 대표 행동 패턴을 보여주는 예시를 고릅니다. 모델이 따라야 할 기준이 예시에서 드러나면, 짧은 지침으로도 반복 작업의 품질을 더 안정적으로 만들 수 있습니다.

## 공부 체크리스트

- 시스템 프롬프트를 모델의 행동 기준 지시라고 설명할 수 있다.
- 시스템 지시, 메시지, 도구 정의, 예시가 모두 컨텍스트에 들어간다는 점을 말할 수 있다.
- brittle한 조건문 목록과 모호한 일반론이 왜 위험한지 설명할 수 있다.
- 도구 정의가 지침 계층의 일부인 이유를 예로 들 수 있다.
