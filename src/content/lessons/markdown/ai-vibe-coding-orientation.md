## 한 줄 정의

AI 바이브코딩은 사람이 만들고 싶은 제품 행동, 검증 기준, 학습 목표를 붙잡고 AI와 빠르게 초안 작성, 실행 확인, 수정, 설명을 반복하는 개발 방식입니다. Collins는 vibe coding을 자연어를 컴퓨터 코드로 바꾸는 방식으로 설명하지만, 이 강의에서 더 중요한 부분은 "자연어로 시킨다"가 아니라 "결과를 사람이 검토 가능한 단위로 되돌려 받는다"입니다. Karpathy가 2025년에 널리 알린 표현은 개발자가 코드의 존재를 잊을 만큼 AI에게 흐름을 맡기는 감각을 강조했지만, 교육용 바이브코딩은 그 감각을 그대로 따라 하는 방식이 아닙니다.

입문자에게 이 개념은 두 층으로 나뉩니다. 첫째, AI는 문법과 boilerplate를 빠르게 제안해 학습의 마찰을 줄입니다. 둘째, 사람은 목표를 명확히 쓰고, 맥락을 제공하고, 실행 결과와 출처를 확인하고, 나중에 다른 사람에게 설명할 수 있을 만큼 구조를 이해해야 합니다. ==바이브코딩의 핵심은 코드를 안 보는 것이 아니라, 코드를 더 빨리 만들고 더 엄격하게 검증하는 리듬==입니다.

이 강의는 사이트 전체의 출발점입니다. HTML, CSS, JavaScript, TypeScript, React, Next.js, Git, API, DB, 배포, 보안, AI 시스템 설계까지 이어지는 긴 커리큘럼을 "AI에게 맡길 목록"으로 보지 않고, AI와 협업할 때 사람이 판단해야 할 층으로 읽는 법을 잡습니다.

## 왜 존재하는가

개발 학습은 오래전부터 두 가지 장벽을 가졌습니다. 하나는 도구 장벽입니다. 초보자는 화면 하나를 만들려고 해도 editor, terminal, browser, local server, Git, package manager, framework 문서를 동시에 만납니다. 다른 하나는 판단 장벽입니다. 코드가 돌아가는 것처럼 보여도 왜 돌아가는지, 어떤 edge case에서 깨지는지, 어떤 변경이 위험한지 설명하기 어렵습니다. AI 코딩 도구는 첫 장벽을 크게 낮춥니다. 빈 파일 앞에서 멈추는 시간을 줄이고, 에러 메시지를 해석하고, 반복적인 구조를 빠르게 제안합니다.

하지만 두 번째 장벽은 자동으로 사라지지 않습니다. AI가 코드를 만들어도 사용자는 "이 기능이 요구사항을 만족하는가", "보안적으로 위험한가", "내 프로젝트 구조와 맞는가", "출처가 있는 주장인가", "테스트로 확인했는가"를 판단해야 합니다. 그래서 바이브코딩이라는 말이 유행할수록 교육 사이트는 더 깊은 검증 루틴을 가르쳐야 합니다. 빠르게 만들 수 있다는 사실이 곧 안전하게 만들 수 있다는 뜻은 아니기 때문입니다.

이 개념이 생긴 배경에는 자연어 인터페이스의 변화도 있습니다. 예전에는 사람이 API 문서와 예제를 찾아 코드를 직접 조립했습니다. 이제는 사람이 "어떤 행동을 원하는지"와 "무엇을 근거로 검증할지"를 자연어로 표현하면 AI가 초안을 만듭니다. 이 변화는 개발자의 역할을 없애지 않습니다. 오히려 요구사항을 제품 행동으로 번역하고, 결과를 작은 단위로 쪼개 검토하는 능력을 더 중요하게 만듭니다.

> [!KEY]
> 입문 단계에서 바이브코딩을 잘못 배우면 "AI가 해주니까 됐다"로 끝납니다. 제대로 배우면 "AI가 만든 것을 실행, 출처, 코드 구조, 설명 가능성으로 확인한다"는 습관이 먼저 생깁니다.

## 작동 원리

### 1. 목표를 화면 행동으로 바꾼다

AI에게 "멋진 학습 사이트를 만들어줘"라고 말하면 모델은 많은 빈칸을 추측해야 합니다. 반대로 "홈 화면에서 사용자가 다음 강의를 찾고, 현재 진행률을 보고, 모바일에서도 목차를 접을 수 있게 해줘"라고 말하면 결과를 판단할 기준이 생깁니다. 제품 행동은 사용자가 관찰할 수 있는 결과입니다. 버튼이 보이는가, 링크가 이동하는가, 오류 메시지가 이해되는가, 저장된 진행률이 새로고침 후 유지되는가 같은 식으로 검증할 수 있습니다.

목표를 행동으로 바꾸는 일은 코딩 전 단계에서만 끝나지 않습니다. AI가 첫 코드를 만든 뒤에도 "이 구현은 어떤 사용자 행동을 만족하는가"를 다시 묻습니다. 만족하지 않는다면 프롬프트가 부족했는지, 맥락이 잘못됐는지, 코드가 틀렸는지 나눠야 합니다. ==좋은 요청은 AI에게 일을 맡기는 문장이면서 동시에 나중에 결과를 검사할 체크포인트==입니다.

### 2. 맥락을 좁고 정확하게 제공한다

AI는 현재 대화와 주어진 파일, 도구 결과 안에서 판단합니다. 그래서 프로젝트의 기술 스택, 현재 파일 구조, 이미 존재하는 컴포넌트, 금지된 변경, 완료 기준을 주는 것이 중요합니다. "Next.js, TypeScript, Tailwind 기반이고 콘텐츠는 `src/content`에 있다"는 말은 단순한 배경 설명이 아닙니다. AI가 새 구조를 마음대로 만들지 않고 기존 구조에 맞추게 하는 제약입니다.

맥락은 많이 넣는 것보다 정확히 넣는 편이 낫습니다. 불필요한 로그, 오래된 계획, 이미 폐기된 지침이 들어가면 AI는 그것까지 판단 재료로 삼을 수 있습니다. 따라서 바이브코딩의 맥락 제공은 "많이 알려주기"가 아니라 "현재 작업에 필요한 근거를 선별하기"입니다. 이 습관은 나중에 Context Engineering을 배울 때 그대로 이어집니다.

### 3. 초안은 빠르게 받고 검증은 느리게 한다

AI가 빠르게 코드를 제안하면 사람은 그 속도에 끌려 바로 다음 기능으로 넘어가고 싶어집니다. 하지만 학습용 바이브코딩에서는 초안 작성과 검증 속도를 분리해야 합니다. 초안은 빠르게 받아도 됩니다. 대신 검증은 실행, 화면 확인, 타입 검사, 테스트, 코드 리뷰, 출처 대조를 차례대로 봅니다. 빠른 생성은 품질 보증을 대신하지 않습니다.

이때 검증은 "마음에 드는가"가 아닙니다. 예를 들어 강의 페이지를 만들었다면 이전/다음 이동이 맞는지, 사이드바 목차가 현재 섹션을 가리키는지, 검색 결과가 누락되지 않는지, 모바일에서 텍스트가 잘리지 않는지 확인합니다. 코드도 같은 방식입니다. 타입이 맞는지, 상태가 어디에 저장되는지, 클라이언트 컴포넌트와 서버 컴포넌트 경계가 적절한지 봅니다.

### 4. 대화는 기록으로 남아야 한다

바이브코딩은 대화형이지만, 좋은 대화는 프로젝트 기록으로 남습니다. 결정한 요구사항, 바꾼 파일, 테스트 결과, 남은 위험, 다음 작업을 기록하면 다음 세션이나 다른 사람이 이어받을 수 있습니다. 기록이 없으면 AI와의 대화는 그 순간의 감각으로 흩어지고, 왜 특정 구조가 만들어졌는지 추적하기 어려워집니다.

이 프로젝트가 `ai-ops/STATE.md`, `MASTER_PROGRESS.md`, release note, QA report를 쓰는 이유도 여기에 있습니다. 사람과 AI가 번갈아 일하더라도 현재 상태를 파일로 남겨야 흐름이 끊기지 않습니다. 기록은 관료적 절차가 아니라 긴 작업의 기억 장치입니다.

### 5. 설명 가능성이 학습 완료 기준이다

초보자가 AI로 코드를 만들었다고 해서 개념을 배운 것은 아닙니다. 배웠다는 말은 다른 사람에게 "왜 이 파일이 필요하고, 이 코드는 어떤 데이터를 받고, 이 오류는 어디서 생기며, 다음에 무엇을 확인해야 하는지" 설명할 수 있다는 뜻입니다. 그래서 이 사이트의 강의는 단순 실습보다 개념의 배경, 문제, 원리, 예시, AI 시대의 의미를 길게 다룹니다.

설명 가능성은 검증의 한 형태입니다. 코드를 실행했는데도 설명하지 못한다면 아직 AI가 만든 결과를 소유하지 못한 상태입니다. 반대로 설명할 수 있으면 다음 기능을 만들 때 더 좋은 요청을 쓸 수 있고, AI가 틀렸을 때 더 빨리 알아차릴 수 있습니다.

```ts
type VibeCodingTurn = {
  goal: string
  context: string[]
  constraints: string[]
  verification: string[]
  explanationTarget: string
}

const turn: VibeCodingTurn = {
  goal: "강의 상세 페이지에 현재 섹션 목차를 표시한다",
  context: ["Next.js App Router", "Markdown 기반 lesson content", "모바일 사이드바 존재"],
  constraints: ["콘텐츠 문장은 수정하지 않기", "기존 디자인 토큰 사용"],
  verification: ["npm run verify", "모바일 폭에서 목차가 접히는지 확인"],
  explanationTarget: "목차가 markdown heading에서 어떻게 만들어지는지 설명할 수 있다",
}
```

이 작은 타입은 바이브코딩 요청의 뼈대를 보여줍니다. 목표, 맥락, 제약, 검증, 설명 목표가 함께 있어야 AI의 초안이 학습으로 이어집니다.

## 스펙과 세부

### 용어의 강한 의미와 교육용 의미를 구분한다

Karpathy의 표현은 바이브코딩의 강한 버전을 보여줍니다. AI가 코드를 생성하고 사용자는 자연어로 흐름을 이어가며, 때로는 코드 자체를 거의 보지 않는 감각입니다. 그러나 교육용 사이트에서 이 의미를 그대로 받아들이면 위험합니다. 초보자는 아직 코드의 위험 신호를 읽는 눈이 충분하지 않기 때문입니다. 따라서 이 사이트의 "AI 바이브코딩"은 자연어 중심 협업을 받아들이되, human review와 검증 루틴을 핵심 규칙으로 둡니다.

### 자연어는 요구사항 형식이지 품질 보증이 아니다

자연어로 개발을 지시할 수 있다는 사실은 강력합니다. 하지만 자연어는 모호할 수 있고, 모델은 빈칸을 그럴듯하게 채울 수 있습니다. "로그인"이라는 단어 하나 안에도 이메일 형식 검사, 비밀번호 정책, 세션 유지, 실패 메시지, 접근성, rate limit, 보안 헤더 같은 선택지가 숨어 있습니다. 좋은 바이브코딩은 이 선택지를 숨기지 않고 하나씩 드러냅니다.

### 출처와 테스트는 서로 다른 검증이다

출처 검증은 "이 설명이 공식 문서나 승인 KB와 맞는가"를 확인합니다. 테스트 검증은 "이 코드가 지금 환경에서 실제로 동작하는가"를 확인합니다. 둘 중 하나만으로 충분하지 않습니다. 공식 문서와 맞는 코드를 잘못 연결할 수도 있고, 지금 돌아가는 코드가 장기적으로 위험한 패턴일 수도 있습니다. 그래서 학습 사이트는 인용과 실행 확인을 모두 다룹니다.

### AI 결과는 작은 변경 단위로 받아야 한다

초보자는 큰 요청을 한 번에 던지고 완성된 앱을 기대하기 쉽습니다. 하지만 변경 단위가 커질수록 검토 범위도 커지고 실패 원인도 흐려집니다. "홈 전체를 다시 디자인"보다 "진행률 카드의 텍스트 대비를 개선"이 안전합니다. 큰 목표는 작은 작업으로 나누고, 각 작업마다 결과를 확인해야 합니다.

### 기록 파일은 협업의 일부다

AI와 일할 때 기록은 선택이 아닙니다. 작업이 길어질수록 어떤 KB가 승인됐는지, 어떤 강의가 통합됐는지, 어떤 QA가 남았는지 파일로 추적해야 합니다. 이 프로젝트의 운영 문서들은 그 역할을 맡습니다. 사용자 입장에서는 조금 무겁게 보일 수 있지만, 실제로는 "어디까지 했는지 다시 설명하는 비용"을 줄여 줍니다.

AI 도구를 믿을지 말지는 한 번 정해지는 태도가 아닙니다. 작업 종류, 위험도, 테스트 가능성, 출처 품질, 사용자의 이해 수준에 따라 계속 바뀝니다. 간단한 CSS 여백 수정과 인증 로직 수정은 같은 정도로 맡길 수 없습니다. 이 동적인 신뢰 조절이 바이브코딩을 실무 기술로 만드는 핵심입니다.

## 실전에서

### 패턴 1: 요청은 작업 계약으로 쓴다

실전 요청은 "만들어줘"가 아니라 작은 계약이어야 합니다. 계약에는 목표, 현재 맥락, 변경 금지 영역, 완료 기준, 검증 명령이 들어갑니다. 예를 들어 "검색 기능 개선"보다 "강의 제목과 glossary term을 대상으로 검색하고, 결과가 없을 때 empty state를 보여주며, `npm run verify`가 통과해야 한다"가 낫습니다. 이 요청은 AI가 무엇을 바꿀 수 있고, 사용자가 무엇으로 완료를 판단할지 알려줍니다.

### 패턴 2: 코드 리뷰 질문을 미리 준비한다

AI가 코드를 만든 뒤에는 "왜 이 컴포넌트를 client component로 만들었는가", "상태는 어디에 저장되는가", "에러 상태는 어떻게 보이는가", "모바일에서 레이아웃이 깨지지 않는가", "기존 콘텐츠를 바꾸지 않았는가"를 묻습니다. 질문이 없으면 검토는 감상으로 흐릅니다. 질문이 있으면 검토는 재현 가능한 절차가 됩니다.

### 패턴 3: 실패를 다음 맥락으로 되돌린다

오류가 나면 AI에게 "안 돼"라고 말하지 않습니다. 실행한 명령, 오류 메시지, 기대한 결과, 실제 결과, 바꾼 파일을 함께 줍니다. 예를 들어 `npm run verify`에서 TypeScript 오류가 났다면 오류 줄과 타입 이름을 그대로 제공해야 합니다. 실패 정보를 다음 맥락으로 되돌리는 순간, 바이브코딩은 단순 채팅이 아니라 반복 개선 루프가 됩니다.

> [!TIP]
> 좋은 바이브코딩 세션의 끝에는 항상 기록이 남습니다. 바꾼 파일, 확인한 명령, 남은 위험, 다음 작업을 한 문단으로 남기면 다음 작업의 품질이 올라갑니다.

## 한계와 트레이드오프

바이브코딩의 가장 큰 장점은 속도입니다. 초보자는 첫 화면을 빠르게 보고, 에러 설명을 즉시 받고, 낯선 API 사용 예시를 얻을 수 있습니다. 그러나 같은 속도가 위험이 되기도 합니다. 빠르게 나온 코드는 빠르게 틀릴 수 있고, 겉으로 돌아가는 화면이 내부 구조의 안전함을 보장하지 않습니다. 특히 인증, 결제, 개인정보, 권한, 보안 헤더, 데이터 삭제처럼 위험도가 높은 영역에서는 더 작은 단위의 검토와 공식 문서 대조가 필요합니다.

또 다른 한계는 이해의 착시입니다. AI가 친절하게 설명하면 사용자는 자신이 이해했다고 느낄 수 있습니다. 하지만 실제 이해는 설명을 다시 구성하고, 코드를 조금 바꿔 보고, 실패했을 때 원인을 좁히는 과정에서 생깁니다. 그래서 이 사이트는 실습 앱을 무작정 만들기보다 읽기, 원문 인용, 코드 예시, 실무 패턴, 한계 설명을 길게 제공합니다.

바이브코딩은 프롬프트 엔지니어링과도 다릅니다. 프롬프트 엔지니어링은 좋은 지시문을 쓰는 기술에 가깝고, 바이브코딩은 그 지시문을 실제 개발 루프 안에서 실행하고 검증하는 방식입니다. 나중에 배우는 Context Engineering, Tool Calling, RAG, MCP, Agent Loop는 이 루프를 시스템 수준으로 확장합니다. 즉 이 강의는 AI 개발의 끝이 아니라 시작점입니다.
