## 한 줄 정의

AI 시스템 설계는 프롬프트 한 번에 의존하던 작업을 컨텍스트, 도구, 루프, 검증 기준이 결합된 실행 구조로 바꾸는 일입니다.

일회성 프롬프트의 한계를 이해하고, 컨텍스트·도구·루프·검증을 갖춘 AI 시스템 설계로 확장합니다. 이 강의의 핵심 질문은 “AI에게 무엇을 말할 것인가”에서 멈추지 않습니다. ==일회성 요청을 반복 가능한 실행 구조로 바꾸는 설계 전환==을 기준으로, 모델이 판단하는 재료와 시스템이 책임지는 실행 경계를 함께 봅니다.

초보자는 이 주제를 새 용어로만 받아들이기 쉽습니다. 하지만 실제로는 이미 매일 겪는 문제와 연결됩니다. AI가 엉뚱한 파일을 읽거나, 오래된 로그를 근거로 판단하거나, 도구를 호출해야 할 때 그냥 설명문만 쓰는 일이 모두 같은 뿌리를 가집니다.

이 강의는 요약이 아니라 구조를 익히는 글입니다. 마지막까지 읽고 나면 프롬프트에서 시스템으로을 “정의”가 아니라 “어떤 문제가 생겨서, 어떤 부품이 어떻게 맞물리고, 어디에서 실패하는지”로 설명할 수 있어야 합니다.

## 왜 존재하는가

좋은 문장 하나로 AI 결과를 통제하려는 방식은 작업이 길어질수록 흔들립니다. 파일을 읽고, 도구를 호출하고, 결과를 반영하고, 실패를 다시 고쳐야 하는 순간부터 필요한 것은 더 멋진 지시문이 아니라 회복 가능한 작업 구조입니다.

초기의 AI 사용은 대개 한 번의 요청과 한 번의 답변으로 설명됐습니다. 그러나 바이브코딩의 실제 작업은 그보다 길고 구체적입니다. 요구사항을 정리하고, 파일을 읽고, 도구를 실행하고, 실패를 관찰하고, 다시 고치는 과정이 이어집니다. 이때 단순한 프롬프트 작성법만으로는 작업 상태를 안정적으로 유지하기 어렵습니다.

프롬프트에서 시스템으로은 바로 그 지점에서 등장합니다. 한 문장을 더 잘 쓰는 문제가 아니라, 모델에게 들어가는 정보와 모델 밖에서 실행되는 행동을 어떤 구조로 나눌지의 문제입니다. 이 구조가 없으면 결과가 우연히 좋아도 재현하기 어렵고, 실패했을 때 어디를 고쳐야 하는지 알기 어렵습니다.

중요한 변화는 “AI가 알아서 하게 한다”가 아닙니다. 오히려 반대입니다. AI가 잘 판단하도록 필요한 재료를 선별하고, 실행 권한을 제한하고, 결과를 검증할 수 있게 만드는 쪽으로 설계가 이동합니다. ==좋은 AI 시스템은 자유도가 큰 시스템이 아니라 책임 경계가 선명한 시스템==입니다.

### 1. 요청을 목표와 제약으로 분리한다

## 스펙과 세부

### 입력과 출력의 경계

프롬프트에서 시스템으로에서 가장 먼저 확인할 세부는 입력과 출력입니다. 입력은 사용자 요청만 뜻하지 않습니다. 시스템 지시, 도구 정의, 외부 문서, 검색 결과, 이전 메시지, 실행 로그가 모두 판단 재료가 될 수 있습니다. 출력도 최종 답변만이 아닙니다. 도구 호출, 상태 기록, 검증 보고, 사용자 확인 요청처럼 다음 단계를 움직이는 중간 산출물이 포함됩니다.

이 경계를 문서화하지 않으면 AI의 행동이 “그럴듯한 답변” 중심으로 흐릅니다. 반대로 입력과 출력이 정해져 있으면 각 단계의 실패 원인을 추적할 수 있습니다. 예를 들어 검색 결과가 부족한지, 도구 스키마가 모호한지, 루프 종료 조건이 약한지 분리해서 볼 수 있습니다.

### 버전과 출처

이 강의는 2026-07-05에 확인한 승인 KB와 Quote Bank만 근거로 합니다. 새 사실을 추가하지 않고, 공식 문서와 공식 블로그의 짧은 원문 구절을 사용합니다. ==인용은 설명의 장식이 아니라 사실 경계==입니다. 원문을 벗어난 주장은 강의에 넣지 않는 것이 원칙입니다.

### 실패를 추적하는 단위

실무에서 중요한 세부는 실패를 어디까지 쪼갤 수 있는가입니다. 프롬프트에서 시스템으로을 제대로 설계하면 실패가 “AI가 이상했다”로 끝나지 않습니다. 입력이 부족했는지, 도구 설명이 겹쳤는지, 검색 chunk가 문맥을 잃었는지, 루프가 너무 길었는지 같은 단위로 나뉩니다.

### 코드와 문서의 연결

문서화된 원칙은 코드와 연결되어야 합니다. 강의 본문에서 설명한 구조가 타입, 설정 객체, 검증 함수, 라우팅 규칙 같은 형태로 내려오면 팀이 같은 기준으로 작업할 수 있습니다. 이 연결이 없으면 지식은 읽기 자료로만 남고, 실제 제품의 행동을 바꾸지 못합니다.

## 실전에서

### 패턴 1: 작업 시작 전에 목표, 제약, 완료 조건을 분리합니다.

이 패턴은 프롬프트에서 시스템으로을 실제 작업 흐름으로 옮기는 방법입니다. 중요한 점은 AI에게 결과만 요구하지 않고, 입력과 경계와 확인 기준을 함께 제공한다는 것입니다. 그렇게 해야 모델이 불확실한 부분을 임의로 채우지 않고, 시스템이 허용한 정보와 도구 안에서 판단하게 됩니다.

### 실행 가능한 TypeScript 예시

아래 코드는 프롬프트에서 시스템으로의 핵심 구조를 작은 TypeScript 값으로 표현한 예시입니다. 외부 라이브러리 없이 실행할 수 있고, 타입이 어떤 책임을 분리하는지 보는 데 목적이 있습니다.

```ts
type AiSystemPacket = {
  goal: string
  constraints: string[]
  context: Array<{ claim: string; source: string }>
  allowedTools: string[]
  doneWhen: string
}

const packet: AiSystemPacket = {
  goal: "검색 결과가 없을 때 안내 UI를 개선합니다",
  constraints: ["기존 디자인 토큰 유지", "모바일 줄바꿈 확인"],
  context: [{ claim: "검색은 강의 제목과 요약을 대상으로 한다", source: "src/content" }],
  allowedTools: ["read_file", "run_tests"],
  doneWhen: "빈 결과 상태가 렌더되고 테스트가 통과한다",
}

console.log(packet.doneWhen)
```

코드에서 중요한 것은 변수 이름이 아니라 책임 분리입니다. 목표, 제약, 증거, 도구, 완료 조건을 한 문자열에 섞지 않으면 사람이 읽어도 검토가 쉬워지고, AI에게 전달할 때도 필요한 부분만 선별하기 쉬워집니다.

## 한계와 트레이드오프

### 오해 1: 프롬프트만 고치면 시스템이 된다는 오해

이 오해는 일회성 요청을 반복 가능한 실행 구조로 바꾸는 설계 전환를 하나의 기능 이름으로만 외울 때 자주 생깁니다. 실제로는 입력, 실행, 관찰, 검증이 연결된 구조이므로 한 부분만 강화해도 전체 품질이 자동으로 좋아지지는 않습니다. 교정 방법은 간단합니다. 먼저 어떤 책임이 모델에게 있고 어떤 책임이 애플리케이션, host, workflow, 또는 사람에게 있는지 나누어 봅니다.

또 하나의 교정 기준은 실패했을 때 되돌아갈 위치입니다. 실패 원인이 입력 부족인지, 도구 정의 문제인지, 검색 품질 문제인지, 루프 제한 문제인지 구분할 수 없다면 설계가 아직 충분히 분해되지 않은 것입니다.

### 오해 3: 최종 답변만 보고 성공을 판단하는 오해

이 오해는 일회성 요청을 반복 가능한 실행 구조로 바꾸는 설계 전환를 하나의 기능 이름으로만 외울 때 자주 생깁니다. 실제로는 입력, 실행, 관찰, 검증이 연결된 구조이므로 한 부분만 강화해도 전체 품질이 자동으로 좋아지지는 않습니다. 교정 방법은 간단합니다. 먼저 어떤 책임이 모델에게 있고 어떤 책임이 애플리케이션, host, workflow, 또는 사람에게 있는지 나누어 봅니다.

또 하나의 한계는 비용과 속도입니다. 더 많은 단계, 더 명확한 게이트, 더 엄격한 출처 관리는 작업을 느리게 만들 수 있습니다. 하지만 복잡한 작업에서는 이 느림이 낭비가 아니라 재작업을 줄이는 장치가 됩니다. 반대로 간단한 질문에는 단일 LLM 호출과 짧은 컨텍스트가 더 적합할 수 있습니다.

따라서 판단 기준은 “가장 복잡한 구조를 쓰자”가 아닙니다. 현재 작업이 실패했을 때 복구 비용이 큰가, 외부 시스템에 실제 영향을 주는가, 장기 상태가 필요한가, 출처가 중요한가를 보고 구조의 무게를 정해야 합니다.
