## 한 줄 정의

빌드 타임(build time)과 런타임(runtime)은 코드가 **"만들어지는 때"와 "실행되는 때"**를 가르는 구분입니다. Twelve-Factor App은 코드가 사용자에게 도달하기까지를 세 단계로 나눕니다 — build(빌드), release(릴리스), run(실행). ==빌드 단계는 코드 저장소를 실행 가능한 번들로 변환==하고, 릴리스는 그 빌드에 설정을 결합하며, 실행(런타임) 단계는 실행 환경에서 앱을 구동합니다.

이 구분이 중요한 이유는 실무의 흔한 질문에 답하기 때문입니다 — "빌드는 됐는데 왜 안 돌지?", "환경변수를 바꿨는데 왜 반영이 안 되지?" 이 질문들은 모두 "지금 어느 단계의 문제인가"를 가려야 풀립니다.

> [!KEY]
> Twelve-Factor의 핵심 원칙은 세 단계를 **엄격히 분리**하는 것입니다. 그 결과 하나의 강한 규칙이 나옵니다 — ==실행 중에는 코드를 바꿀 수 없다==. 런타임의 변경은 빌드 단계로 되돌아갈 방법이 없기 때문입니다. 그래서 코드를 고치려면 "실행 중인 서버를 손보는" 것이 아니라 "빌드부터 다시" 시작해야 합니다.

![빌드→릴리스→실행 3단계: 한 방향 흐름, 빌드 타임 값과 런타임 값의 구분](/lesson-diagrams/build-and-runtime/build-release-run.svg)

## 왜 존재하는가

코드가 사용자에게 닿기까지를 뭉뚱그려 "배포"라고 부르면 세 가지가 헷갈립니다.

첫째, **언제 무엇이 확정되는가.** 어떤 값은 빌드할 때 번들에 박혀 굳고, 어떤 값은 실행할 때마다 새로 읽힙니다. 이 둘을 구분하지 못하면 "환경변수를 바꿨는데 왜 그대로지?" 같은 혼란에 빠집니다.

둘째, **오류가 어디서 났는가.** 빌드 오류(타입 에러, 번들 실패)와 런타임 오류(실행 중 예외)는 원인도 해결법도 완전히 다릅니다. 빌드 오류는 코드를 고쳐야 하고, 런타임 오류는 환경·설정·외부 연결을 봐야 합니다. "배포가 안 돼요"를 이 두 구간으로 나누는 것이 문제 해결의 첫걸음이며, 이 구분 없이는 엉뚱한 곳을 계속 파게 됩니다.

셋째, **같은 코드를 여러 곳에서 돌리기.** 개발·스테이징·운영이 같은 코드로 돌아야 하는데, 환경마다 설정(DB 주소, API 키)은 다릅니다. 빌드를 한 번만 하고 설정만 갈아 끼우면, "코드 하나, 배포 여럿"이 깔끔하게 성립합니다. 만약 환경마다 따로 빌드하면, "개발에서는 됐는데 운영 빌드는 다르게 나왔다" 같은 미묘한 차이가 끼어들 여지가 생깁니다 — 하나의 빌드를 재사용하는 것이 그 불확실성을 없앱니다.

## 작동 원리

### 세 단계

Twelve-Factor가 나눈 세 단계는 각각 하는 일이 명확합니다:

```
[소스 코드]
   │  build  — 코드를 실행 가능한 번들로 변환 (컴파일·번들링)
   ▼
[빌드 산출물]
   │  release — 빌드 + 그 배포의 설정(환경변수)을 결합
   ▼
[릴리스]
   │  run    — 실행 환경에서 앱 프로세스를 구동 (= 런타임)
   ▼
[동작하는 앱]
```

핵심은 **방향이 한쪽**이라는 것입니다 — 소스에서 빌드로, 빌드에서 릴리스로, 릴리스에서 실행으로. 반대 방향은 없습니다. 그래서 실행 중(런타임)에 무언가를 고쳐도 그것이 빌드로 거슬러 올라가지 못합니다.

### 빌드 타임 값 vs 런타임 값

가장 실무적으로 중요한 구분입니다. 어떤 값은 ==빌드 시점에 번들 안에 박혀== 고정되고(정적), 어떤 값은 ==실행 시점에 환경에서 읽혀==(동적) 매번 달라질 수 있습니다.

| 종류 | 확정 시점 | 바꾸려면 |
|---|---|---|
| 빌드 타임 값 | 빌드할 때 번들에 박힘 | 재빌드 필요 |
| 런타임 값 | 실행할 때 환경에서 읽음 | 재시작으로 반영 |

이 사이트가 산 예시입니다 — 비밀번호 해시(`NEXT_PUBLIC_SITE_PASSWORD_HASH`)는 빌드 타임에 번들에 박힙니다. 그래서 비밀번호를 바꾸면 `.env.local`만 고쳐서는 안 되고, 반드시 다시 빌드하고 재배포해야 반영됩니다.

> [!EXAMPLE]
> 환경변수를 바꿨는데 사이트에 그대로라는 상황의 90%가 이 구분의 혼동입니다. 그 변수가 빌드 타임에 박히는 종류(Next.js의 `NEXT_PUBLIC_` 접두사 등)라면, 실행 중인 서버를 아무리 재시작해도 소용없습니다 — 이미 옛 값이 번들에 굳어 있기 때문입니다. 답은 "재빌드"이고, 이 사이트도 비밀번호 변경 시 재빌드·재배포를 명시합니다.

### 릴리스 = 빌드 + 설정

빌드와 실행 사이에 릴리스가 있는 이유가 여기 있습니다. 같은 빌드 산출물이라도 개발 설정을 결합하면 개발 릴리스, 운영 설정을 결합하면 운영 릴리스가 됩니다. ==빌드는 한 번, 릴리스는 환경마다==. 이것이 앞 강의(환경변수)의 "설정을 코드에서 분리"가 배포 구조에서 실현되는 지점입니다 — 설정은 코드(빌드)가 아니라 릴리스에서 주입됩니다.

릴리스를 별도 단계로 두는 또 다른 이득은 **롤백**입니다. 각 릴리스가 "이 빌드 + 이 설정"으로 고유하게 기록되면, 문제가 생겼을 때 이전 릴리스로 되돌리는 것이 간단해집니다 — 새로 빌드할 필요 없이 과거의 검증된 릴리스를 다시 실행하면 됩니다. 세 단계를 분리한 덕분에 "안전하게 되돌릴 수 있는 지점"이 생기는 것입니다.

### 이 사이트의 배포가 밟는 세 단계

추상적으로 들리는 이 구분이, 이 사이트의 배포에서 그대로 일어납니다. `npm run build`가 **빌드**(React/Next.js 코드를 정적 HTML·JS 번들로 변환)이고, 그 번들에 `.env.local`의 설정이 결합되는 것이 **릴리스**이며, Firebase 호스팅이 그 결과를 서빙하는 것이 **실행**입니다. 비밀번호를 바꾸면 왜 재빌드가 필요한지가 여기서 설명됩니다 — 해시가 빌드 단계에서 번들에 박히므로, 실행 단계(호스팅)만 다시 해서는 옛 해시가 그대로이기 때문입니다.

| 증상 | 구간 | 흔한 원인 |
|---|---|---|
| 타입 에러·번들 실패로 빌드 중단 | 빌드 타임 | 코드 오류, 의존성 문제 |
| 빌드는 성공했는데 실행 중 크래시 | 런타임 | 환경변수 누락, 외부 연결 실패 |

| 재시작하니 값이 바뀜 | 런타임 값 | 정상(동적 값) |

### 빌드 1회, 실행 N회

| 원칙 | 의미 |
|---|---|
| 빌드는 한 번 | 하나의 산출물을 만들어 재사용 |
| 릴리스는 환경마다 | 같은 빌드 + 다른 설정 |
| 실행은 여러 번 | 같은 릴리스를 여러 프로세스로 |

### 상황별 빠른 참조

| 상황 | 처방 |
|---|---|
| 환경변수 바꿨는데 반영 안 됨 | 빌드 타임 값이면 재빌드·재배포 |
| "배포 실패" 원인 모름 | 빌드 로그 / 런타임 로그로 구간 분리 |
| 환경마다 다른 값 필요 | 빌드 1회 + 릴리스에서 설정 주입 |
| 실행 중 코드 고치고 싶음 | 불가 — 빌드부터 다시 |
| 정적 사이트 값 변경 | 재빌드 (빌드 시점 고정) |

## 원문으로 읽기

> "The build stage is a transform which converts a code repo into an executable bundle known as a build."
>
> — 빌드 단계는 코드 저장소를 빌드라 불리는 실행 가능한 번들로 변환하는 과정이다.
> [Twelve-Factor App: Build, release, run](https://12factor.net/build-release-run)

"a transform"(변환)이라는 단어가 빌드의 본질입니다. 빌드는 코드를 "실행"하는 게 아니라 "변환"합니다 — 소스를 실행 가능한 형태(번들)로 바꾸는 것입니다. TypeScript를 JavaScript로 컴파일하고, 여러 파일을 하나로 묶고, 최적화하는 이 모든 과정이 "변환"이며, 그 결과물이 실행의 재료가 됩니다.

> "The run stage (also known as \"
>
> — 실행 단계(런타임이라고도 함)는 앱의 프로세스들을 구동해 실행 환경에서 앱을 돌린다.
> [Twelve-Factor App: Build, release, run](https://12factor.net/build-release-run)

런타임의 정의가 "runs the app in the execution environment"입니다. 빌드가 "재료를 만드는 때"라면 런타임은 "그 재료로 실제 요리를 하는 때"입니다. 사용자가 만나는 것은 언제나 런타임의 앱이며, 빌드는 그 뒤에 숨은 준비 과정입니다. 그래서 사용자 눈에 보이는 문제라도 그 원인은 훨씬 앞선 빌드 시점에 이미 심어졌을 수 있습니다.

> "The twelve-factor app uses strict separation between the build, release, and run stages."
>
> — twelve-factor 앱은 빌드, 릴리스, 실행 단계를 엄격히 분리해 사용한다.
> [Twelve-Factor App: Build, release, run](https://12factor.net/build-release-run)

"strict separation"(엄격한 분리)이 이 전체 원칙의 핵심입니다. 세 단계가 섞이면 — 예컨대 실행 중에 빌드를 다시 하거나 런타임에 코드를 고치면 — 재현성이 무너집니다. 분리를 지켜야 "이 릴리스는 정확히 이 빌드 + 이 설정"이라는 추적 가능성이 생깁니다.

관련 원문(링크): [Twelve-Factor App: Build, release, run](https://12factor.net/build-release-run)

"impossible ... no way to propagate back" — 이 강한 표현이 실무 규율을 정합니다. 운영 서버에 직접 접속해 파일을 고치는 것은, 설령 당장 동작해도 다음 배포에서 사라지는 임시 변경입니다. ==모든 변경은 빌드부터==라는 원칙이, 코드와 실제 배포가 항상 일치하도록 지켜줍니다.

## 실전에서

### "배포 실패"를 두 구간으로 나누기

AI에게 "배포가 안 돼요"를 도와달라고 하면, 가장 먼저 할 일은 그것이 빌드 실패인지 런타임 실패인지 가리는 것입니다. 빌드 로그에서 멈췄다면 타입·번들·의존성 문제이고, 빌드는 통과했는데 실행 중 죽었다면 환경변수 누락·외부 연결 실패 같은 런타임 문제입니다. ==두 구간은 원인도 해결도 다르므로==, 로그를 먼저 나눠 보는 것이 추측을 줄입니다.

### 환경변수 미반영의 진짜 원인

"환경변수를 바꿨는데 그대로예요"라는 신고를 받으면, 그 변수가 빌드 타임 값인지 런타임 값인지를 물어야 합니다. 빌드 타임 값이면 재시작이 아니라 재빌드가 답입니다. AI가 이 구분 없이 "서버를 재시작해 보세요"라고만 하면 문제가 안 풀립니다 — "이 값이 언제 확정되는가"가 정확한 처방을 가릅니다.

### 운영 서버를 직접 고치지 않기

급할 때 운영 서버에 접속해 파일을 직접 고치고 싶은 유혹이 있습니다. 하지만 그 변경은 빌드로 전파되지 않아, 다음 배포에서 사라지고 코드와 실제 배포가 어긋납니다. 올바른 길은 코드를 고쳐 커밋하고, 빌드·릴리스·실행의 정상 흐름을 다시 태우는 것입니다. 이 규율이 지켜지면 "저장소의 코드 = 실제로 돌아가는 것"이라는 등식이 유지되어, 나중에 "왜 이렇게 동작하지?"를 코드에서 답할 수 있습니다. 등식이 깨지면 코드를 아무리 읽어도 실제 동작을 설명할 수 없는 유령 상태가 됩니다.

### AI에게 빌드 단계를 맡길 때

AI가 배포 스크립트나 CI 설정을 만들 때, "빌드 → 릴리스 → 실행"의 어느 단계를 다루는지 의식하고 검토해야 합니다. 예컨대 AI가 secret을 빌드 단계에서 번들에 넣는 코드를 만들면, 그 secret이 빌드 산출물에 박혀 배포됩니다 — 앞 강의(환경변수)의 "빌드 타임에 노출되는 값" 경고와 직결됩니다. 어느 단계에서 무엇이 주입되는지를 아는 것이, AI가 만든 배포 구성의 안전성을 판단하는 기준입니다.

> [!TIP]
> 새 값을 다룰 때 ==이 값이 빌드 타임에 박히나, 런타임에 읽히나==를 먼저 정하세요. 빌드 타임 값은 "코드처럼" 다뤄 재빌드가 필요하고, 런타임 값은 "설정처럼" 다뤄 재시작으로 바뀝니다. Next.js의 `NEXT_PUBLIC_` 접두사처럼 "언제 확정되는가"를 이름이 알려주는 규칙을 익혀두면 혼동이 줄어듭니다. 이름 규칙이 없는 값이라면, 그 값을 쓰는 코드가 빌드 시점에 실행되는지 요청 시점에 실행되는지를 따라가 보면 답이 나옵니다.

## 한계와 트레이드오프

**빌드 1회 원칙은 재현성과 속도를 맞바꿉니다.** 같은 빌드를 재사용하면 재현성이 좋지만, 환경마다 조금씩 다른 최적화가 필요할 때는 제약이 됩니다. 대부분의 경우 재현성이 이기지만, "빌드 타임에 환경별 값을 넣어야만 하는" 상황(정적 사이트의 공개 설정 등)에서는 환경마다 빌드하는 절충을 씁니다 — 이 사이트도 비밀번호 해시가 빌드 타임 값이라 그 예외에 속합니다.

**단계 분리는 규율을 요구합니다.** "실행 중 직접 수정 금지" 같은 원칙은 도구가 강제하지 않으면 급할 때 깨집니다. 배포 자동화(CI/CD)와 불변 인프라가 이 규율을 구조적으로 지켜주지만, 그런 장치가 없으면 결국 사람의 절제에 달립니다. "이번 한 번만 서버에서 직접 고치자"가 반복되면, 어느새 저장소의 코드와 실제 배포가 다른 두 세계가 되어 아무도 진실을 모르는 상태가 됩니다.

**이 강의는 배포의 개념 지도입니다.** 실제 빌드 도구(webpack, Vite, Next.js 빌드)의 세부, 컨테이너·서버리스 같은 실행 환경의 종류, CI/CD 파이프라인의 구성은 여기서 다루지 않았습니다. 하지만 "빌드 → 릴리스 → 실행"이라는 뼈대를 잡으면, 그 위의 구체 도구들도 "이건 어느 단계의 일인가"로 자리를 잡아 읽힙니다. 새로운 배포 도구를 만나도 "이 도구는 빌드를 하나, 릴리스를 하나, 실행을 하나, 아니면 여러 단계를 묶나"를 물으면 그 도구의 역할이 금세 잡힙니다 — 뼈대가 있으면 세부는 그 위에 얹힙니다.

> [!WARNING]
> 로컬에서는 되는데 배포하면 안 되는 문제의 상당수가 빌드/런타임 환경 차이입니다. 로컬 개발 서버는 런타임에 파일을 다시 읽지만(hot reload), 배포된 정적 빌드는 빌드 시점에 모든 것이 굳습니다. 로컬에서 동작한다고 배포도 동작한다는 보장은 없으며, 배포 환경에서 실제로 빌드·실행해 확인하는 것이 유일하게 확실한 검증입니다.

### 설명 연습: 언제 굳고 언제 바뀌는지 묻기

빌드와 런타임을 설명할 때 가장 좋은 질문은 "이 값은 언제 결정되는가"입니다. 소스 코드는 build에서 실행 가능한 산출물로 굳고, release에서는 환경 설정과 결합되며, run에서는 실제 요청을 받습니다. 이 구분이 없으면 환경변수를 고쳤는데 왜 화면이 그대로인지, 코드를 바꿨는데 왜 재배포가 필요한지, 정적 페이지가 왜 사용자의 요청마다 새로 계산되지 않는지 설명하기 어렵습니다.

초보자에게는 배포 오류를 이 세 단계로 분류하게 해 보세요. 빌드에서 실패하면 의존성, 타입, 파일 경로, 정적 생성 문제가 의심됩니다. 릴리스에서 실패하면 환경변수나 secret 주입이 문제일 수 있습니다. 런타임에서 실패하면 실제 요청, 권한, 외부 API, 데이터 상태를 봐야 합니다. 같은 "안 된다"도 어느 단계에서 멈췄는지에 따라 읽어야 할 로그와 수정 위치가 달라집니다.
