## 한 줄 정의

관계형 데이터베이스에서 데이터는 **테이블**에 저장됩니다 — PostgreSQL 문서의 표현으로 ==종이 위의 표와 매우 비슷한, 행과 열로 이루어진 구조==입니다. 열(column)은 "어떤 종류의 데이터"인지를 데이터 타입으로 정하고, 행(row)은 실제 데이터 한 건씩을 담습니다.

**인덱스(index)**는 그 테이블에서 특정 행을 빠르게 찾기 위한 보조 구조입니다. 책 뒤의 색인이 "이 단어가 몇 페이지에 있는지"를 미리 정리해 두듯, 인덱스는 "이 값을 가진 행이 어디 있는지"를 미리 정리해 전수 탐색을 피하게 합니다.

> [!KEY]
> 이 강의를 관통하는 트레이드오프는 하나입니다 — **인덱스는 조회를 빠르게 하지만 공짜가 아닙니다.** 인덱스는 테이블과 항상 동기화되어야 해서, 데이터를 바꿀 때마다(INSERT/UPDATE/DELETE) 인덱스도 갱신됩니다. "읽기 이득 vs 쓰기 비용"의 저울질이 인덱스 설계의 전부입니다.

## 왜 존재하는가

데이터를 그냥 파일에 쌓아두지 않고 테이블·타입·인덱스로 구조화하는 데는 세 가지 이유가 있습니다.

첫째, **모양의 약속.** 테이블의 열과 타입은 "이 데이터는 이런 형태여야 한다"를 강제합니다. 나이 열이 정수 타입이면 "스물다섯"이라는 문자열은 애초에 들어갈 수 없습니다 — 잘못된 데이터의 저장을 입구에서 막아, 나중에 데이터를 쓰는 모든 코드가 그 약속을 신뢰할 수 있게 합니다.

둘째, **빠른 조회.** 인덱스가 없으면 "id가 42인 행"을 찾기 위해 테이블 전체를 행 단위로 훑어야 합니다. 행이 백만 개인데 찾는 건 하나라면, 이 전수 스캔은 명백히 낭비입니다. 인덱스는 이 낭비를 없앱니다.

셋째, **의미와 계산.** 데이터 타입은 값의 범위를 제한할 뿐 아니라, 그 데이터에 의미를 부여해 계산에 쓸 수 있게 합니다. 날짜 타입이면 "어제 이후"를 계산할 수 있고, 숫자 타입이면 합계를 낼 수 있습니다. 반대로 모든 것을 문자열로 저장하면, 저장은 되지만 그 위에서 정렬·집계·비교가 모두 어긋납니다 — 데이터의 "형태"를 잃으면 그 데이터로 할 수 있는 일도 함께 잃습니다.

## 작동 원리

### 테이블 = 행 × 열

테이블의 구조는 단순합니다 — 열의 수와 순서는 고정이고 각 열은 이름을 가지며, 행의 수는 저장된 데이터 양에 따라 변합니다. 열은 "구조"(고정)이고 행은 "내용"(가변)입니다.

```
users 테이블
┌──────┬─────────────┬─────┐
│ id   │ email       │ age │   ← 열(구조·타입 고정)
├──────┼─────────────┼─────┤
│ 1    │ a@x.com     │ 25  │   ← 행(내용·가변)
│ 2    │ b@x.com     │ 31  │
└──────┴─────────────┴─────┘
```

### 데이터 타입의 두 역할

데이터 타입은 두 가지를 동시에 합니다: 값의 범위를 **제한**하고, 데이터에 **의미를 부여**합니다. `age`가 정수 타입이면 문자열이 못 들어오고(제한), 동시에 "이 값으로 평균을 낼 수 있다"는 의미가 생깁니다(의미 부여). 그래서 "모든 걸 문자열로 저장"하는 것은 편해 보이지만, 제한과 계산 능력을 모두 포기하는 선택입니다.

### 인덱스 = 색인 = 트리 탐색

인덱스가 있으면 데이터베이스는 전체 테이블을 훑는 대신 탐색 트리를 몇 단계만 내려가 목표 행을 찾습니다. 백만 행이라도 트리의 깊이는 얕아서, 몇 번의 비교만으로 도달합니다. 인덱스의 이득은 조회에만 그치지 않습니다 — 검색 조건이 있는 UPDATE·DELETE, 그리고 여러 테이블을 잇는 조인(join)까지 가속합니다.

> [!EXAMPLE]
> `SELECT * FROM users WHERE email = 'b@x.com'`을 실행한다고 합시다. email에 인덱스가 없으면 백만 행을 처음부터 하나씩 비교합니다. email에 인덱스가 있으면, 정렬된 색인에서 'b@x.com'을 곧장 찾아 해당 행 위치로 점프합니다 — 도서관에서 책을 서가마다 뒤지는 것과 청구기호로 바로 가는 것의 차이입니다.

## 스펙과 세부

### 테이블 설계 체크리스트

| 항목 | 원칙 |
|---|---|
| 열 이름 | 명확하고 일관되게 (id, email, created_at) |
| 데이터 타입 | 값의 범위·계산 용도에 맞게 (정수/문자열/날짜/불리언) |
| 고정 vs 가변 | 열=구조(고정), 행=내용(가변) |

### 인덱스 판단 기준

| 상황 | 인덱스 |
|---|---|
| 자주 WHERE 조건에 쓰는 열 | 만들 가치 높음 |
| 조인 조건에 쓰는 열 | 만들 가치 높음 |
| 거의 조회에 안 쓰는 열 | 만들지 말 것(쓰기 비용만) |
| 쓰기가 매우 잦은 테이블 | 신중히 — 갱신 오버헤드 큼 |
| 이미 만들었지만 안 쓰이는 인덱스 | 제거 권장 |

### 인덱스의 비용 구조

인덱스가 하나 생기면, 그 테이블에 대한 모든 쓰기 작업이 "테이블 갱신 + 인덱스 갱신"으로 늘어납니다. 인덱스가 다섯 개면 한 번의 INSERT가 테이블 1 + 인덱스 5 = 여섯 곳을 갱신합니다. ==인덱스는 읽기에서 벌고 쓰기에서 냅니다==. 그래서 "읽기가 잦은 열"에만 만드는 것이 원칙입니다.

### 왜 조회가 빨라지는가 — 정렬의 힘

인덱스가 빠른 근본 이유는 **정렬**에 있습니다. 정렬되지 않은 백만 개의 이메일에서 하나를 찾으려면 평균 오십만 번을 비교해야 하지만, 정렬되어 있으면 가운데를 짚어 위/아래를 반씩 좁혀가는 방식으로 스무 번 안에 도달합니다. 인덱스는 특정 열의 값을 이렇게 정렬·구조화해 둔 별도의 자료구조이고, 그래서 "정렬 기준이 된 열"로 조회할 때만 이득을 줍니다. 인덱스를 만들지 않은 열로 조회하면 여전히 전수 스캔입니다 — 인덱스는 "어떤 열로 찾을 것인가"를 미리 정해 두는 결정이기도 합니다.

### 조인과 인덱스

여러 테이블을 잇는 조인(join)은 실무 쿼리의 큰 부분입니다. `users`와 `orders`를 `user_id`로 이을 때, 그 연결 열에 인덱스가 없으면 한쪽 테이블의 각 행마다 다른 테이블 전체를 훑는 최악의 조합이 벌어집니다. 조인 조건에 쓰는 열은 인덱스의 가장 확실한 후보입니다 — 공식 문서도 인덱스가 조인 검색을 "significantly speed up"(상당히 가속)한다고 명시합니다.

### 상황별 빠른 참조

| 하고 싶은 것 | 처방 |
|---|---|
| 잘못된 값 저장을 막고 싶다 | 열에 적절한 데이터 타입 지정 |
| 특정 열 조회가 느리다 | 그 열에 인덱스 생성 |
| 조인이 느리다 | 조인 조건 열에 인덱스 |
| 쓰기가 느려졌다 | 불필요한 인덱스 제거 검토 |
| 인덱스가 실제로 쓰이는지 모르겠다 | 사용 통계 확인 후 미사용분 제거 |

## 원문으로 읽기

> "A table in a relational database is much like a table on paper: It consists of rows and columns. [...]"
>
> — 관계형 데이터베이스의 테이블은 종이 위의 표와 매우 비슷하다: 행과 열로 이루어진다.
> [PostgreSQL Table Basics](https://www.postgresql.org/docs/current/ddl-basics.html)

가장 기본적인 정의가 가장 강력한 은유입니다. "종이 위의 표"라는 익숙한 그림이 관계형 DB의 출발점입니다 — 엑셀 시트를 떠올리면 됩니다. 열은 항목, 행은 기록. 이 단순한 모델이 수십 년간 데이터 저장의 표준이 된 이유는, 사람이 직관적으로 이해하면서도 기계가 엄밀히 다룰 수 있기 때문입니다.

> "The data type constrains the set of possible values that can be assigned to a column and assigns semantics to the data [...]"
>
> — 데이터 타입은 열에 할당될 수 있는 가능한 값의 집합을 제한하고, 열에 저장된 데이터에 의미를 부여해 계산에 쓸 수 있게 한다.
> [PostgreSQL Table Basics](https://www.postgresql.org/docs/current/ddl-basics.html)

"constrains ... and assigns semantics" — 데이터 타입의 두 역할이 한 문장에 정확히 담겨 있습니다. 제한(constrain)만 하는 게 아니라 의미(semantics)를 부여합니다. 이것이 "모두 문자열로 저장"이 나쁜 이유입니다 — 문자열은 제한도 약하고, "1 + 1"을 계산하지 못하고 "11"로 이어붙일 뿐입니다.

> "After an index is created, the system has to keep it synchronized with the table. This adds overhead to data manipulation operations. [...]"
>
> — 인덱스가 생성된 후, 시스템은 그것을 테이블과 동기화된 상태로 유지해야 한다. 이는 데이터 조작 연산에 오버헤드를 더한다.
> [PostgreSQL Indexes Introduction](https://www.postgresql.org/docs/current/indexes-intro.html)

이 문장이 이 강의의 핵심 경고입니다. 인덱스는 "keep it synchronized"의 대가를 요구합니다. 조회를 빠르게 하려고 만든 인덱스가, 데이터를 바꿀 때마다 함께 갱신되어 쓰기를 느리게 합니다. 공식 문서가 직접 "adds overhead"라고 못 박는 이유입니다.

관련 원문(링크): [PostgreSQL Indexes Introduction](https://www.postgresql.org/docs/current/indexes-intro.html)

인덱스의 이득이 조회(SELECT)에만 그치지 않는다는 점을 문서가 명시합니다. 조건이 붙은 UPDATE·DELETE도 "먼저 대상 행을 찾는" 단계가 있으므로 인덱스의 덕을 보고, 조인은 특히 크게 가속됩니다. 인덱스를 "조회용"으로만 생각하면 이 넓은 이득을 놓칩니다.

관련 원문(링크): [PostgreSQL Indexes Introduction](https://www.postgresql.org/docs/current/indexes-intro.html)

"should be removed" — 공식 문서가 제거를 권고합니다. 안 쓰는 인덱스는 조회 이득은 0인데 쓰기 비용은 그대로이므로, 순손실입니다. 인덱스를 만드는 것만큼이나 ==안 쓰는 인덱스를 찾아 지우는 것==도 성능 관리의 일부입니다.

## 실전에서

### AI의 "인덱스 추가하세요"를 검증하기

AI에게 "이 조회가 느린데 고쳐줘"라고 하면 십중팔구 "인덱스를 추가하세요"라고 답합니다. 맞는 경우가 많지만, AI는 보통 인덱스의 유지 비용을 함께 말하지 않습니다. 그 테이블이 쓰기가 잦다면 인덱스 추가가 조회는 빠르게 하되 쓰기 전체를 느리게 만들 수 있습니다. ==AI의 인덱스 제안은 "읽기 이득 > 쓰기 비용"인지를 사람이 저울질==해야 완성됩니다.

### 스키마의 타입을 코드의 타입과 맞추기

DB 열의 데이터 타입은 런타임 값의 제약이고, TypeScript 타입은 코드의 제약입니다. 이 둘이 어긋나면(DB는 정수인데 코드는 문자열로 다룸) 버그의 온상이 됩니다. 스키마 설계를 AI에 맡기더라도, "이 열의 타입이 코드에서 쓰는 타입과 일치하는가"는 확인해야 할 지점입니다. 예를 들어 DB의 `created_at`이 날짜 타입인데 코드가 문자열로 받아 정렬하면, "2026-1-9"가 "2026-12-1"보다 뒤로 가는 문자열 정렬의 함정에 빠집니다 — 타입을 맞춰야 "날짜로서" 올바르게 비교됩니다.

### 느린 쿼리를 먼저 측정하기

인덱스는 추측이 아니라 측정에서 출발해야 합니다. "느릴 것 같은" 곳이 아니라 "실제로 느린" 쿼리를 먼저 찾고, 그 쿼리가 어떤 열로 조회·조인하는지를 본 뒤 그 열에 인덱스를 답니다. 대부분의 DB는 쿼리의 실행 계획(전수 스캔인지 인덱스 탐색인지)을 보여주는 도구를 제공하므로, 인덱스 추가 전후로 계획이 실제로 바뀌었는지 확인할 수 있습니다. ==측정 없는 인덱스는 대부분 비용만 남깁니다==.

### 안 쓰는 인덱스 감사

인덱스는 만들 때만 신경 쓰고 잊기 쉽습니다. 하지만 요구사항이 바뀌면 한때 유용했던 인덱스가 이제 아무 쿼리에도 안 쓰일 수 있습니다. 주기적으로 "실제로 쓰이는 인덱스"를 확인해 미사용분을 제거하는 것이, 쓰기 성능을 조용히 회복하는 방법입니다.

> [!TIP]
> 인덱스를 추가하기 전에 물어보세요 — ==이 열로 조회·조인하는 쿼리가 실제로 자주 실행되는가==? "언젠가 필요할 것 같아서" 만드는 인덱스는 대부분 쓰기 비용만 남기는 미사용 인덱스가 됩니다. 인덱스는 실측된 느린 쿼리에 대한 처방이지, 예방접종이 아닙니다.

## 한계와 트레이드오프

**인덱스는 만능이 아닙니다.** 결과가 테이블의 대부분을 차지하는 조회(예: 전체의 80%를 반환)라면, 인덱스로 하나씩 찾는 것보다 전체를 훑는 게 빠를 수 있습니다. 인덱스가 이득인 것은 "많은 행 중 적은 행"을 찾을 때입니다 — 찾는 비율이 클수록 이득은 줄어듭니다.

**타입 제한은 유연성과 맞바꿉니다.** 엄격한 타입은 잘못된 데이터를 막지만, 요구사항이 바뀌어 "때로는 문자열, 때로는 숫자"가 필요해지면 스키마 변경이라는 비용이 듭니다. 그래서 타입 설계는 "지금의 정확성"과 "미래의 변경 가능성" 사이의 판단입니다.

**이 강의는 관계형 DB의 입구입니다.** 정규화(중복 제거), 트랜잭션(여러 변경의 원자적 처리), 복합 인덱스(여러 열을 묶은 인덱스), 쿼리 실행 계획 같은 주제는 여기서 다루지 않았습니다. 하지만 테이블·타입·인덱스의 트레이드오프를 이해하면, 그다음 주제들도 같은 "이득과 비용의 저울질"로 읽을 수 있습니다. 예컨대 정규화는 "중복 제거의 이득 vs 조인 증가의 비용"이고, 트랜잭션은 "일관성의 이득 vs 동시성 저하의 비용"입니다 — 데이터베이스 설계의 거의 모든 결정이 이 저울질의 변주입니다.

> [!WARNING]
> 성능을 위한답시고 모든 열에 인덱스를 거는 것은 흔한 실수입니다. 인덱스 10개짜리 테이블은 한 번의 INSERT가 열한 곳을 갱신해, 쓰기가 잦은 서비스에서는 오히려 전체가 느려집니다. 인덱스는 조회에 실제로 쓰이는 열에만 — 나머지는 순수한 비용입니다.

### 설명 연습: 테이블과 인덱스를 제품 질문으로 번역하기

테이블을 설명할 때는 "행과 열"만 말하지 말고 제품 질문으로 바꿔 보세요. 사용자를 저장하는가, 주문을 저장하는가, 학습 진행률을 저장하는가에 따라 row 하나가 의미하는 사건이 달라집니다. column은 그 사건을 설명하는 속성이고, data type은 그 속성이 어떤 값이어야 하는지 제한합니다. 이 관점이면 DB 설계가 추상적인 표 만들기가 아니라 제품 세계를 정확히 자르는 일이라는 점이 보입니다.

인덱스도 "빠르게 찾게 해 주는 구조"에서 한 걸음 더 나아가야 합니다. 어떤 화면이 자주 목록을 조회하는지, 어떤 조건으로 검색하는지, 쓰기와 읽기 중 무엇이 더 많은지 묻습니다. 인덱스는 읽기 속도를 얻는 대신 쓰기 비용과 저장 비용을 냅니다. 그래서 좋은 설명은 언제 인덱스를 만들지뿐 아니라 언제 만들지 말아야 하는지도 함께 말합니다.
