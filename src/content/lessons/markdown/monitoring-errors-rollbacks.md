## 한 줄 정의

배포는 끝이 아니라 시작입니다. **모니터링**은 배포된 앱이 잘 돌아가는지 지켜보는 것, **오류 추적**은 문제를 감지·기록하는 것, **롤백**은 문제 시 이전 상태로 되돌리는 것입니다. Vercel은 롤백을 ==이전 프로덕션 배포로 빠르게 되돌리는 방법==으로 정의하며, 이는 "깨진 변경·버그 같은 운영 사고에서 신속 복구"에 쓰입니다.

관찰의 토대는 앞 강의(백엔드 로그)에서 배운 로그입니다 — ==집계되고 시간순으로 정렬된 이벤트의 스트림==. 이 로그로 이상을 감지하고, 문제가 있으면 롤백으로 복구합니다. CI/CD가 "배포까지"를 자동화했다면, 이 강의는 "배포 이후"를 다룹니다. 배포 버튼을 누르는 순간이 일의 끝처럼 느껴지지만, 실제로는 사용자와 만나는 첫 순간일 뿐입니다.

> [!KEY]
> 사고 대응의 순서에는 원칙이 있습니다 — ==원인 분석보다 복구가 먼저==입니다. 사용자가 깨진 화면을 보는 시간을 줄이는 것이 최우선이므로, 문제가 감지되면 즉시 롤백해 정상화하고, 원인은 되돌린 뒤 로그로 분석합니다. 불이 나면 먼저 끄고 원인은 나중에 조사하는 것과 같습니다.

![배포 후 운영 사이클: 관찰(로그)→감지→롤백(복구)→분석](/lesson-diagrams/monitoring-errors-rollbacks/incident-response-cycle.svg)

## 왜 존재하는가

CI/CD로 배포를 자동화하고 테스트를 통과했어도, 배포 후에 안심할 수 없는 이유가 세 가지 있습니다.

첫째, **테스트가 모든 것을 잡지 못합니다.** 테스트는 "예상한 상황"을 검증하지만, 운영에서는 예상 못 한 조합(실제 데이터, 실제 부하, 특정 사용자 흐름)이 문제를 일으킵니다. 테스트에서 상상하지 못한 입력이 실제 사용자에게서 나오는 것입니다. 그래서 배포 후 실제 환경을 지켜보는 관찰이 필요합니다 — 테스트는 배포의 문턱을 지키고, 모니터링은 배포 이후를 지킵니다.

둘째, **문제는 조용히 옵니다.** 앱이 완전히 죽으면 금방 알지만, "가끔 느리다", "일부 요청만 실패한다" 같은 문제는 로그·지표 없이는 보이지 않습니다. 이런 부분적 장애는 사용자 신고가 들어올 때쯤이면 이미 오래 지속된 경우가 많습니다. 모니터링이 이 조용한 이상을 사용자가 알아채기 전에 드러냅니다.

셋째, **되돌릴 수 있어야 합니다.** 문제를 감지해도 되돌릴 방법이 없으면, 급하게 새 코드를 짜서 다시 배포하는 위험한 상황에 빠집니다 — 급히 짠 코드는 또 다른 버그를 부르기 쉽습니다. 롤백은 "검증된 과거로 즉시 돌아가는" 안전한 복구 경로입니다. 새것을 만드는 것보다 검증된 옛것으로 돌아가는 것이 사고 상황에서 훨씬 안전합니다.

## 작동 원리

### 모니터링 — 무엇을 지켜보나

모니터링의 근거 데이터는 로그입니다. 앞 강의에서 배운 대로 로그는 시간순 이벤트 스트림이고, 여기서 이상 신호를 읽습니다. 좋은 로그가 남아 있어야 좋은 모니터링이 가능하다는 점에서, 앞 강의(관찰 가능성)와 이 강의는 하나로 이어집니다:

| 신호 | 의미 |
|---|---|
| 429 급증 | 남용·재시도 폭주·한도 과빡빡 |
| 5xx 급증 | 서버 오류·장애 |
| 응답 지연 증가 | 성능 저하·과부하 |
| 특정 엔드포인트 오류 집중 | 그 기능의 버그 |

핵심은 ==평소를 알아야 이상이 보인다==는 것입니다. 응답 시간이 평소 300ms에서 3초로 늘었다는 것은, 평소의 300ms를 기록해 두었기에 "이상"으로 보입니다. 그래서 모니터링은 사고가 난 뒤가 아니라 평온할 때부터 시작해야 합니다 — 정상 상태의 기준선(baseline)이 있어야 그로부터의 이탈을 감지할 수 있기 때문입니다. 오류만 기록하면 "무엇이 잘못됐나"는 알아도 "평소와 얼마나 다른가"는 알 수 없습니다.

### 롤백 — 즉시 이전으로

문제가 감지되면 롤백합니다. Vercel의 Instant Rollback은 ==새로 빌드하지 않고 도메인을 이전 배포로 다시 가리켜== 즉시 복구합니다 — 문서의 표현으로 "The rollback happens instantaneously"(즉각적으로 일어난다). 앞 강의(배포 플랫폼)에서 배운 "배포마다 고유 URL·기록이 남는다"는 성질이 바로 이 롤백을 가능하게 합니다. 되돌아갈 지점이 보존되어 있기 때문입니다.

```
[새 배포에서 문제 감지]
   │  즉시 롤백
   ▼
[도메인을 이전(검증된) 배포로 재지정]  ← 재빌드 없음, 즉시
   │
   ▼
[사용자는 정상 상태 복구] → 그 다음 원인 분석
```

### 롤백 후의 상태

롤백에는 알아야 할 성질이 있습니다. Vercel은 ==롤백 후 프로덕션 도메인 자동 할당을 끕니다==("turns off auto-assignment of production domains"). 즉 롤백 상태에서는 새 push가 자동으로 나가지 않아, 애써 되돌린 상태가 다음 커밋에 덮이지 않습니다. 정상 배포로 돌아가려면 명시적으로 다시 승격해야 합니다 — 이는 "실수로 문제 코드를 다시 배포"하는 것을 막는 안전장치입니다. 롤백은 "잠깐 멈춤"이 아니라 "명시적으로 풀 때까지 유지되는 안전 상태"인 셈입니다.

> [!EXAMPLE]
> 새 기능을 배포했는데 결제 페이지에서 5xx가 급증하기 시작합니다. 올바른 대응은 이렇습니다 — ① 로그에서 5xx 급증을 확인(모니터링), ② 즉시 이전 배포로 롤백해 결제를 정상화(복구 우선), ③ 그다음 문제 배포의 로그를 요청 ID로 추적해 원인 분석. 만약 ②를 건너뛰고 ③부터 하면, 원인을 찾는 동안 사용자는 계속 결제에 실패합니다. 복구가 먼저인 이유입니다.

## 스펙과 세부

### 사고 대응 순서

| 단계 | 행동 |
|---|---|
| 1. 감지 | 로그·지표에서 이상 신호 확인 |
| 2. 복구 | 즉시 롤백으로 정상화 |
| 3. 분석 | 되돌린 뒤 로그로 원인 추적 |
| 4. 재발 방지 | 원인 수정 + 검증 보강 후 재배포 |

### 롤백이 되돌리는 것과 아닌 것

| 되돌림 | 안 되돌림 |
|---|---|
| 코드(이전 배포) | DB의 데이터 변경 |
| 도메인 연결 | 외부 API에 이미 보낸 요청 |
| 배포 설정 | 이미 발송된 이메일·결제 |

Vercel도 롤백 시 "external APIs, databases"의 변화에 주의를 줍니다 — ==롤백은 코드를 되돌릴 뿐 외부 상태는 되돌리지 않습니다==.

### 상황별 빠른 참조

| 상황 | 처방 |
|---|---|
| 배포 후 5xx·429 급증 | 로그 확인 → 즉시 롤백 |
| "가끔 느리다" 신고 | 응답 지연 지표 모니터링 |
| 롤백했는데 또 문제 배포됨 | 자동 배포 중단 확인, 명시적 승격만 |
| 롤백 후 데이터가 이상 | 외부 상태(DB)는 별도 복구 |
| 배포 전 준비 | 롤백 절차·모니터링 지표 미리 확인 |

## 원문으로 읽기

> "Vercel provides Instant Rollback as a way to quickly revert to a previous production deployment."
>
> — Vercel은 이전 프로덕션 배포로 빠르게 되돌리는 방법으로 Instant Rollback을 제공한다.
> [Performing an Instant Rollback](https://vercel.com/docs/instant-rollback)

"quickly revert to a previous production deployment" — 롤백의 정의가 "빠르게"와 "이전 배포로"에 있습니다. 새 코드를 짜는 게 아니라 이미 있던 검증된 배포로 돌아가는 것이므로, 복구가 빠르고 안전합니다. 앞 강의의 "배포마다 고유 URL"이 이 "이전 배포"를 보존해 두었기에 가능한 일입니다.

> "This can be useful in situations that require a swift recovery from production incidents, like breaking changes or bugs."
>
> — 이는 깨진 변경이나 버그 같은 운영 사고에서 신속한 복구가 필요한 상황에 유용하다.
> [Performing an Instant Rollback](https://vercel.com/docs/instant-rollback)

"swift recovery from production incidents"가 롤백의 목적을 정확히 말합니다. 운영 사고(incident)의 핵심은 시간입니다 — 문제가 지속되는 매 순간 사용자가 피해를 봅니다. 그래서 "신속한 복구"가 "완벽한 해결"보다 먼저이고, 롤백이 그 신속함을 제공합니다.

> "The rollback happens instantaneously."
>
> — 롤백은 즉각적으로 일어난다.
> [Performing an Instant Rollback](https://vercel.com/docs/instant-rollback)

"instantaneously" — 왜 즉각적일까요? 새로 빌드하지 않고 이미 만들어진 이전 배포로 도메인만 다시 가리키기 때문입니다. 빌드에 몇 분이 걸린다면 그 시간 동안 사고가 지속되지만, 롤백은 도메인 재지정만으로 끝나므로 즉시입니다. 앞 강의(빌드/런타임)의 "빌드는 한 번, 실행은 여러 번"이 여기서 빛을 발합니다 — 과거 빌드가 남아 있어 재빌드가 필요 없습니다. 만약 롤백할 때마다 재빌드해야 한다면, 그 몇 분이 사고 지속 시간이 되어 복구가 늦어졌을 것입니다.

> "After a rollback, Vercel turns off auto-assignment of production domains."
>
> — 롤백 후, Vercel은 프로덕션 도메인의 자동 할당을 끈다.
> [Performing an Instant Rollback](https://vercel.com/docs/instant-rollback)

이 문장이 롤백의 숨은 안전장치입니다. 롤백했는데 자동 배포가 그대로 켜져 있으면, 다음 커밋(문제를 아직 못 고친)이 자동으로 나가 애써 되돌린 상태를 덮어씁니다. 자동 할당을 꺼둠으로써, ==사람이 "이제 괜찮다"고 명시적으로 승격할 때까지 되돌린 상태를 지킵니다==.

> "Logs are the stream of aggregated, time-ordered events collected from the output streams of all running processes and backing services."
>
> — 로그는 실행 중인 모든 프로세스와 백킹 서비스의 출력에서 수집된, 집계되고 시간순으로 정렬된 이벤트의 스트림이다.
> [Twelve-Factor App: Logs](https://12factor.net/logs)

모니터링의 근거가 왜 로그인지가 이 정의에 있습니다. "time-ordered events"(시간순 이벤트)가 있어야 "언제부터 5xx가 늘었는가", "이 오류가 어느 배포 이후인가"를 재구성할 수 있습니다. 로그 없는 모니터링은 눈을 감고 이상을 감지하려는 것과 같습니다.

## 실전에서

### AI 배포 후 관찰까지 챙기기

AI에게 "배포해줘"라고 하면 배포까지는 잘하지만, "배포 후 무엇을 지켜보고 문제 시 어떻게 되돌리나"는 명시하지 않으면 빠집니다. 테스트가 통과했다고 운영에서 문제가 없는 것은 아니므로, ==AI 결과를 배포할 때 "모니터링 지표와 롤백 절차"까지 사람이 챙겨야== 합니다. 배포는 코드를 내보내는 것이고, 운영은 그 코드가 실제로 잘 도는지 계속 지켜보는 것입니다. AI가 자동화하기 어려운 것이 바로 이 "지켜보고 판단하는" 부분이며, 그래서 운영은 여전히 사람의 몫이 큽니다. "무엇이 정상이고 무엇이 이상인가"의 판단에는 그 서비스에 대한 맥락과 경험이 필요하기 때문입니다.

### 복구와 분석을 분리하기

사고가 나면 원인을 알고 싶은 충동이 큽니다. 하지만 원인을 파는 동안 사용자는 계속 피해를 봅니다. 훈련된 대응은 먼저 롤백(복구)하고 그다음 로그를 분석(원인)하는 것입니다. 롤백으로 시간을 벌어 놓고, 안정된 상태에서 문제 배포의 로그를 요청 ID로 차분히 추적하는 것이 정석입니다. 급한 불을 끄지 않은 채 원인부터 찾으면, 분석하는 내내 피해가 쌓입니다.

### 롤백의 한계를 기억하기

롤백은 코드를 되돌리지만 외부 상태는 되돌리지 않습니다. 문제 배포가 DB에 잘못된 데이터를 썼거나, 외부 결제 API에 요청을 보냈다면, 코드를 되돌려도 그 부작용은 남습니다. ==롤백 후에는 "코드는 정상화됐지만 데이터·외부 상태는 괜찮은가"를 별도로 점검==해야 합니다. 롤백은 복구의 시작이지 끝이 아닙니다. 특히 결제·이메일 발송처럼 되돌릴 수 없는 부작용을 일으키는 기능은, 배포 전부터 "잘못 실행되면 어떻게 수습하나"를 설계에 넣어두는 것이 안전합니다.

> [!TIP]
> 배포하기 전에 ==두 가지를 미리 준비==하세요 — ① 무엇을 보고 "문제"라고 판단할지(모니터링 지표: 5xx율, 응답시간 등), ② 문제 시 어떻게 되돌릴지(롤백 절차). 이 둘을 사고가 난 뒤 처음 찾으면 이미 늦습니다. 소방 훈련을 불이 난 뒤에 하지 않듯, 대응 계획은 평온할 때 세워두는 것입니다. 롤백 절차를 한 번이라도 미리 연습해 보면, 실제 사고에서 손이 떨리지 않습니다.

## 한계와 트레이드오프

**모니터링은 무엇을 볼지 정한 만큼만 봅니다.** 지켜보기로 한 지표(5xx, 응답시간)는 감지하지만, 정의하지 않은 종류의 문제는 놓칩니다. "무엇이 잘못될 수 있는가"를 미리 상상해 지표를 정해야 하며, 사고를 겪을 때마다 "이건 왜 못 봤나"를 물어 관찰 범위를 넓혀갑니다. 완벽한 모니터링은 없고, 계속 배우는 모니터링만 있습니다 — 겪은 사고 하나하나가 다음 사고를 감지할 지표를 하나씩 늘려줍니다.

**롤백은 만능이 아닙니다.** 코드를 되돌리는 것은 즉시지만, 외부 상태(DB 마이그레이션, 발송된 메일)는 되돌릴 수 없습니다. 특히 데이터 구조를 바꾸는 배포는 롤백이 어렵거나 불가능할 수 있어, 그런 변경은 앞뒤 호환을 유지하며 단계적으로 하는 별도 전략이 필요합니다. 되돌리기 어려운 변경일수록 배포 전 검증을 더 신중히 하고, 작게 나눠 점진적으로 내보내는 것이 안전합니다. "롤백하면 되지"라는 안심이 위험한 경우가 있습니다.

**이 강의는 운영의 입구입니다.** 지표(metric)·추적(trace)·알림(alert)·온콜(on-call)·사후분석(postmortem) 같은 본격 운영 체계는 여기서 다루지 않았습니다. 하지만 "관찰 → 감지 → 복구(롤백) → 분석"이라는 사고 대응의 뼈대를 잡으면, 그 위의 도구·프로세스도 "이 네 단계의 어디를 돕는가"로 읽힙니다. 예컨대 알림은 "감지를 사람에게 빠르게 전달하는" 보완이고, 사후분석은 "분석을 조직의 학습으로 남기는" 보완입니다 — 뼈대를 알면 각 도구의 자리가 저절로 잡힙니다.

> [!WARNING]
> 테스트가 통과했으니 배포 후엔 신경 안 써도 된다는 생각이 가장 위험합니다. 테스트는 배포 전 검증이고, 운영은 배포 후 현실입니다. 둘은 다른 세계이며, 실제 사용자·데이터·부하는 테스트가 재현하지 못한 문제를 드러냅니다. 배포 버튼을 누른 순간이 안심의 끝이 아니라 관찰의 시작입니다.
