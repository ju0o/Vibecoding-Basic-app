# AI와 만드는 방식은 해마다 어떻게 바뀌었을까?

## Student Question

> 몇 년 전의 코드 자동완성과 지금의 AI Agent는 무엇이 다를까? Chat, IDE Agent, Multi-Agent가 차례로 나오면서 사람은 덜 확인해도 되는 걸까?

학생은 D1–D7에서 LLM의 출력 원리, Prompt·Context·Workflow, Agent 역할 분담, 외부 도구 연결, Orchestration, AI 코딩 도구, 배포·인프라를 각각 배웠다. 그러나 이 개념을 연도 순으로만 나열하면 “새 도구가 옛 도구를 완전히 대체했다”거나 “최근 도구일수록 자동으로 더 안전하다”는 오해가 생기기 쉽다.

이 노드는 모든 AI 사건을 담은 완전한 역사 수업이 아니다. 공식 발표로 확인할 수 있는 몇 개의 이정표를 사용해 **사람이 AI에 맡기는 작업 단위가 `다음 코드 제안 → 대화형 문제 해결 → 저장소 단위 작업 → 여러 Agent 감독`으로 커졌고, 그에 따라 Context·권한·검증·운영 책임도 커졌음**을 읽는 수업이다.

## Why Now

D7에서 학생은 앱을 공개하려면 코드 생성뿐 아니라 실행 환경, 데이터 권한, Preview, 복구까지 설계해야 한다는 것을 배웠다. 이제 과정 전체를 돌아보며 다음을 구분해야 한다.

- 어떤 변화가 공식 발표 날짜로 확인되는 사실인가?
- 어떤 “시대 구분”이 학습을 위한 해석인가?
- 자동완성·Chat·Agent·Multi-Agent는 무엇을 입력받고 무엇을 바꾸는가?
- 위임 범위가 커질수록 사람은 어떤 증거를 더 봐야 하는가?
- 새 도구가 등장한 뒤에도 이전 방식이 계속 쓰이는 이유는 무엇인가?

연표를 읽는 목적은 연도를 많이 외우는 것이 아니다. **새 도구를 만났을 때 이름과 출시 연도만 보지 않고, 작업 단위·Context·행동 권한·검증 증거·사람 승인 지점을 판별하는 것**이 목표다.

## Outcomes와 완료 증거

| 수준 | 학생이 할 수 있는 일 | 관찰 가능한 완료 증거 |
|---|---|---|
| Observed | 2021·2022·2023·2025·2026의 선택된 공식 이정표에서 AI에 위임된 작업 단위가 달라지는 모습을 관찰한다. | 각 연도 카드에 입력, AI 행동, 출력, 사람 확인을 서로 다른 색이나 기호로 표시한다. |
| Assisted | 안내표를 사용해 공식 사실과 교육용 시대 구분을 나누고 Autocomplete·Chat·Agent·Multi-Agent의 경계를 비교한다. | 각 카드에 출처·확인일·fact/interpretation 태그와 권한·검증 수준이 기록되어 있다. |
| Independent | 새로운 도구 설명 하나를 보고 어느 작업 표면에 가까운지 판단하고, 필요한 Context·권한·검증을 도움 없이 설계한다. | 분류 근거, 반례, 최소 증거, 사람 승인 지점이 포함된 “새 도구 배치 카드”가 남아 있다. |
| Explainable | 최신 도구가 이전 도구를 모두 대체하지 않으며 위임 범위 확대가 사람 책임의 소멸을 뜻하지 않는 이유를 설명한다. | 60초 teach-back 또는 6문장 설명에 연표 이정표, 공존, 위임 단위, 검증 강도, 출처 한계, 자신의 다음 행동이 모두 들어 있다. |

### 한 줄 완료 조건

학생이 자료를 보지 않고 선택된 연표를 **연도 → 작업 표면 → 위임 단위 → 권한 → 완료 증거**로 다시 그린 뒤, 처음 보는 AI 개발 도구를 어느 칸에 둘지와 사람이 확인할 항목을 자기 말로 설명하면 이 노드의 학습 Outcome을 충족한다.

## 개념 지도

```text
전통적 IDE 보조
  └─ 현재 코드 주변의 completion·parameter info·quick info
       ↓ 2021 공식 이정표
AI Autocomplete / Pair Programming
  └─ 코드 Context를 바탕으로 줄·함수 제안
       ↓ 2022–2023 공식 이정표
Conversational / Chat Coding
  └─ 자연어 질문·후속 질문·설명·디버깅
       ↓ 2025 공식 이정표
Coding Agent
  └─ 저장소 조사·계획·파일 변경·명령·테스트·PR 제안
       ↓ 2026 공식 이정표
Multi-Agent Supervision
  └─ 여러 작업을 병렬 위임·전환·검토·조정

위임 단위가 커짐
  → 필요한 Context·권한 경계·실패 복구·검증 증거도 커짐
```

이 흐름은 “이전 시대가 끝나고 다음 시대만 남았다”는 교체표가 아니다. 2026년에도 completion, inline suggestion, Chat, 단일 Agent, 여러 Agent가 과업에 따라 함께 쓰인다. 연도는 선택된 공개 이정표의 위치이고, “시대”는 그 변화의 의미를 이해하기 위한 교육용 분류다.

| 연도 | 공식 출처로 확인하는 이정표 | 위임 단위의 변화 | 사람이 확인할 증거 |
|---:|---|---|---|

| 2026 | OpenAI가 여러 Agent 작업을 병렬로 관리하는 Codex app을 발표했다. | 단일 작업 위임에서 여러 장기 작업의 감독·전환·조정으로 넓어진다. | 작업별 범위·상태·격리·handoff·review·최종 사람 승인 |

## Bridges

### Previous Why

D7에서 학생은 로컬 성공을 실제 사용자 환경으로 옮기며 배포와 운영의 책임을 분해했다. D8은 그 지점에서 뒤를 돌아보고, **자동완성부터 배포 가능한 작업 위임까지 무엇이 커졌고 어떤 검증 습관이 계속 남았는지** 하나의 시간축으로 연결한다.

### Next Why

이 노드는 8개 샘플 도메인의 마지막이다. 다음 질문은 새 용어가 아니라 학생 자신의 능력으로 돌아간다.

> 이제 나는 작은 문제를 발견하고, AI와 함께 만들고, 도구와 권한을 통제하고, 결과를 검증하고, 배포 구조를 설명하는 과정을 혼자 다시 할 수 있을까?

다음 단계는 Website 페이지를 먼저 만드는 것이 아니라, D1–D8에서 남긴 완료 증거를 모아 **작은 프로젝트의 문제 정의 → 제작 → 검증 → 공개 전 판정**을 재현하는 Outcome 회고다. 부족한 단계가 보이면 해당 노드의 Practice로 돌아간다.

## 3-step Practice

준비물: 아래 이정표 카드, 빈 연표, 색 펜 또는 메모 앱. 실제 AI 도구·Git·외부 계정은 사용하지 않는다.

카드 다섯 장:

```text
A. 코드 Context에서 줄·함수를 제안하는 AI pair programmer
B. 후속 질문이 가능한 대화형 research preview
C. IDE 안에서 코딩 질문·설명·디버깅을 하는 Chat
D. 저장소를 조사하고 변경·테스트·PR을 제안하는 coding agent
E. 여러 Agent 작업을 병렬로 감독하는 작업 공간
```

### Step 1. 연도와 위임 단위를 함께 관찰한다

- **Start:** 2021, 2022, 2023, 2025, 2026이 적힌 빈 연표와 카드 A–E를 받는다.
- **Action:** 카드를 연도에 배치하고 각 카드에 `입력/AI 행동/출력/사람 확인`을 한 줄씩 쓴다. 공식 발표로 확인되는 문장에는 `FACT`, “Autocomplete era”처럼 교육을 위한 구분에는 `INTERPRETATION` 태그를 붙인다.
- **Expected:** 학생은 연도와 제품명뿐 아니라 작업 위임 단위와 완료 증거의 변화를 표시한다. FACT와 교육용 시대 구분을 섞지 않는다.
- **Fail:** 2021 이전에는 코드 completion이 없었다고 쓰거나, 2025 이후에는 Chat·Autocomplete가 사라졌다고 쓴다.
- **Recover:** `공식 발표가 처음 존재를 증명하는가, 선택한 공개 이정표를 증명하는가?`, `새 표면이 추가됐는가, 옛 표면을 삭제했는가?`에 답한 뒤 문장을 고친다.
- **Evidence:** 완성 연표, 다섯 카드의 네 항목, FACT/INTERPRETATION 태그, 수정 전 오해와 교정 문장을 남긴다.

### Step 2. 잘못된 “최신=자동 완료” 연표를 고친다

- **Start:** 다음 설명을 읽는다: `2021 자동완성은 코드 한 줄을 만들었다. 2022 Chat은 대화로 모든 문제를 해결했다. 2025 Agent가 나온 뒤 사람의 테스트와 리뷰는 필요 없어졌다. 2026 Multi-Agent는 여러 Agent가 서로 검토하므로 운영 승인도 자동이다.`
- **Action:** 공식 사실, 근거 없는 과장, 교육용 해석을 구분한다. 각 연도에서 사람이 확인해야 할 증거를 하나 이상 추가하고, 2025·2026 문장을 안전한 표현으로 다시 쓴다.
- **Expected:** “위임 범위가 커졌다”와 “정확성·책임이 자동 이전됐다”를 구분한다. Agent 결과에도 diff·test·review가 필요하고, 여러 Agent의 상호 검토가 최종 사람 책임을 없애지 않는다고 교정한다.
- **Fail:** 최신 제품의 공식 소개 문장을 성능·안전·완전 자율성의 보장으로 확대하거나, 모든 변화가 한 해에 동시에 일어났다고 단정한다.
- **Recover:** 각 주장 옆에 `누가/언제/무엇을 발표했는가?`, `이 문장이 말하지 않는 것은 무엇인가?`, `실패하면 무엇으로 발견하는가?`를 답한다. 근거가 없으면 삭제하거나 `교육용 해석`으로 낮춘다.
- **Evidence:** 주장 분류표, 과장 표시, 안전하게 고친 문장, 연도별 사람 검증 증거, 삭제한 주장과 이유를 남긴다.

### Step 3. 처음 보는 도구를 연표에 배치하고 검증 계획을 혼자 만든다

- **Start:** 가상의 2027 도구 설명을 받는다: `Nova는 요구사항을 받아 세 Agent가 UI·API·테스트를 병렬 작성하고 결과를 하나의 변경 묶음으로 제출한다.` 실제 제품 사실이 아니라 분류 실습용 시나리오다.
- **Action:** Nova를 기존 표면 중 어디에 가까운지 판단한다. 필요한 Context, 역할별 쓰기 범위, handoff, 충돌 검사, 테스트, 최종 승인 지점을 설계한다. 첫 실행에서 UI Agent와 API Agent가 같은 타입 파일을 다르게 수정했다는 실패를 주입하고, 중단→충돌 기록→책임자 결정→제한된 재실행→통합 재검사의 복구 흐름을 작성한다.
- **Expected:** 학생은 “2027이므로 더 좋다”가 아니라 병렬 역할·권한·증거를 기준으로 Multi-Agent 표면에 배치한다. 최종 변경 묶음의 diff·test·review를 사람이 확인하도록 한다.
- **Fail:** 제품 설명을 사실 검증 없이 실제 연표에 넣거나, Agent가 서로 검토한다는 이유로 역할 충돌과 사람 승인을 생략한다.
- **Recover:** `공식 사실인가 가상 시나리오인가?`, `각 Agent가 바꿀 수 있는 파일은?`, `같은 파일 충돌의 소유자는?`, `어떤 증거 없이는 완료할 수 없는가?`에 답해 카드를 다시 쓴다.
- **Evidence:** 새 도구 배치 카드, 분류 근거 3개, FACT/SIMULATION 표시, 권한·handoff 표, 실패·복구 기록, 최종 승인 체크리스트를 남긴다.

## Quiz와 teach-back

### Q1. 이 노드의 연표를 읽는 가장 적절한 방법은?

A. 각 해의 가장 유명한 제품 이름만 외운다.  
B. 새 표면이 등장할 때 위임 단위·Context·권한·검증 증거가 어떻게 달라졌는지 비교한다.  
C. 최신 도구가 이전 도구를 모두 없앴다고 가정한다.  
D. 공식 발표 문장을 모든 성능과 안전성의 보장으로 해석한다.

**정답: B**

- A가 아닌 이유: 이름과 연도만으로 도구가 무엇을 읽고 바꾸며 어떻게 검증되는지 판단할 수 없다.
- B인 이유: 작업 단위와 책임의 변화를 보면 처음 보는 도구에도 같은 판단 기준을 적용할 수 있다.
- C가 아닌 이유: completion·Chat·Agent 표면은 2026년에도 과업에 따라 공존한다.
- D가 아닌 이유: 공식 발표는 정해진 기능과 시점의 근거이지 모든 조건에서의 품질·안전 보장이 아니다.

### Q2. 2025 coding agent 이정표가 보여 주는 변화와 사람의 행동을 가장 정확하게 묶은 것은?

A. 저장소 단위 작업이 가능해졌으므로 diff와 test는 필요 없어졌다.  
B. 파일 변경·명령·테스트·PR 제안까지 위임 범위가 넓어졌으므로 계획·로그·diff·review 확인이 더 중요해졌다.  
C. Chat은 즉시 사라지고 모든 코딩이 cloud agent로만 바뀌었다.  
D. 발표 연도만 알면 어떤 저장소 권한을 줘도 안전하다.

**정답: B**

- A가 아닌 이유: 위임 범위 확대는 오류와 범위 초과 가능성도 넓히므로 검증을 제거할 근거가 아니다.
- B인 이유: Agent가 더 많은 행동을 수행할수록 실제 행동 기록과 결과 증거를 함께 확인해야 한다.
- C가 아닌 이유: 새 표면의 추가는 기존 표면의 소멸을 뜻하지 않는다.
- D가 아닌 이유: 권한은 과업·환경·데이터 위험에 맞춰 별도로 제한해야 한다.

### Q3. “2026년에는 여러 Agent가 서로 검토하므로 사람 승인이 필요 없다”는 주장에 대한 가장 좋은 교정은?

A. 최신 연도이므로 맞는 말이다.  
B. Agent 수가 많으면 항상 오류가 줄어드니 승인만 자동화하면 된다.  
C. 여러 Agent는 병렬화와 역할 분담을 돕지만 같은 오해·범위 충돌·잘못된 handoff가 생길 수 있어 작업별 증거와 최종 사람 판정이 필요하다.  
D. Multi-Agent를 전혀 사용하지 않는 것만이 유일한 해결책이다.

**정답: C**

- A가 아닌 이유: 연도는 책임 이전이나 안전성을 증명하지 않는다.
- B가 아닌 이유: Agent 수 자체는 독립성·검토 품질·권한 통제를 보장하지 않는다.
- C인 이유: 분업의 이점과 새로운 실패 지점을 함께 보고 검증·승인 경계를 유지한다.
- D가 아닌 이유: 위험을 통제할 수 있다면 Multi-Agent는 분리 가능한 작업에 유용할 수 있으며 무조건 금지할 이유는 없다.

### Teach-back

다음 질문에 자료를 보지 않고 60초 안에 답한다.

> “2021의 AI 코드 제안, 2022–2023의 대화형 코딩, 2025의 coding agent, 2026의 multi-agent 감독은 무엇이 달라졌는가? 새 도구가 나올수록 사람은 무엇을 더 확인해야 하는가?”

통과 기준:

- 선택된 공식 이정표를 연도와 함께 세 개 이상 말한다.
- Autocomplete·Chat·Agent·Multi-Agent의 위임 단위를 구분한다.
- 새 표면이 이전 표면을 완전히 대체하지 않고 공존함을 말한다.
- 위임 범위가 커질수록 Context·권한·실패 복구·증거 요구가 커짐을 설명한다.
- 공식 사실과 교육용 시대 구분의 차이를 말한다.
- 자신이 다음 AI 도구를 볼 때 확인할 행동을 두 가지 이상 제안한다.
