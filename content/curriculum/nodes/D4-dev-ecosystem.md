# AI는 어떻게 바깥 도구와 연결될까?

## Student Question

> AI가 일정, 파일, 데이터베이스 같은 바깥 정보를 읽거나 행동하려면 무엇을 연결해야 할까? API, SDK, Tool·Function Call, MCP는 각각 어디에서 어떤 일을 할까?

학생은 앞 노드에서 Agent가 목표를 받아 작업하고, Planner·SubAgent·Reviewer가 역할과 전달물을 나눌 수 있음을 배웠다. 그러나 역할을 정했다고 해서 AI가 자동으로 일정표를 읽거나 파일을 저장할 수 있는 것은 아니다. 외부 시스템과 연결하려면 **사용 가능한 기능을 설명하고, 호출을 구조화하고, 실제 실행 주체와 권한을 정하며, 결과를 다시 모델에 전달하는 경로**가 필요하다.

이 노드는 네 용어를 경쟁 제품처럼 비교하지 않는다. 한 번의 도구 사용 흐름 안에서 **API는 시스템이 제공하는 접점, SDK는 그 접점을 코드에서 쓰기 쉽게 돕는 개발 도구 모음, Tool·Function Call은 모델이 필요한 기능과 인자를 구조화해 요청하는 방식, MCP는 도구와 컨텍스트를 클라이언트와 서버 사이에 노출하는 표준 연결 규약**으로 구분한다.

## Why Now

D3에서 학생은 “누가 계획하고, 누가 실행하고, 누가 검토할까?”를 역할 지도로 만들었다. 이제 실행 역할이 실제 바깥 시스템을 사용하려면 “무엇을 호출하고, 누가 실행하며, 어디에서 멈춰야 할까?”를 설계해야 한다. 이 경계를 모르면 다음과 같은 실패가 생긴다.

- 모델이 함수 이름과 인자를 만들었다는 사실을 실제 실행 완료로 착각한다.
- API, SDK, MCP를 모두 같은 종류의 도구나 서로를 대체하는 제품으로 이해한다.
- 읽기와 쓰기 권한을 구분하지 않고 일정 생성·메일 전송·파일 삭제를 자동 실행한다.
- 잘못된 인자나 실패 응답을 확인하지 않고 성공한 것처럼 사용자에게 답한다.
- 연결 방식부터 고른 뒤, 정작 학생이 해결하려는 행동과 필요한 데이터는 놓친다.

이 노드의 목표는 특정 서비스의 설정법을 외우는 것이 아니다. **작은 사용 사례 하나를 API → SDK(선택) → Tool·Function Call → MCP(선택) 층으로 나누고, 호출 제안·실행·결과·사람 승인 경계를 도움 없이 설명하는 것**이 목표다.

## Outcomes와 완료 증거

| 수준 | 학생이 할 수 있는 일 | 관찰 가능한 완료 증거 |
|---|---|---|
| Observed | 사용자 요청이 구조화된 도구 호출과 외부 시스템 응답을 거쳐 최종 답으로 돌아오는 사례를 관찰한다. | 예시 흐름에서 모델의 호출 제안, 애플리케이션의 실행, API 응답, 모델의 최종 답을 서로 다른 색이나 기호로 표시한다. |
| Assisted | 안내 카드를 사용해 API·SDK·Tool/Function Call·MCP의 역할과 필수·선택 관계를 구분한다. | 네 개념 카드에 역할·입력·출력·실행 주체를 쓰고, SDK와 MCP가 없는 직접 연결 경로도 함께 그린다. |
| Independent | 새로운 외부 기능 하나에 대해 도구 계약, 권한, 정상·실패·복구 경로를 도움 없이 설계한다. | 도구 이름·설명·입력 스키마, 연결 선택 근거, 실행 전 검증, 실패 처리, 쓰기 전 사람 승인 지점이 한 장의 기록에 남아 있다. |
| Explainable | MCP가 API를 대체하지 않고 Tool Calling이 곧 실행 완료가 아닌 이유를 설명한다. | 60초 teach-back 또는 6문장 설명에 네 개념의 차이, 실제 실행 주체, 결과 반환, 권한 확인이 모두 들어 있다. |

### 한 줄 완료 조건

학생이 자료를 보지 않고 새로운 사용 사례 하나를 **사용자 요청 → 도구 정의 → 구조화된 호출 제안 → 애플리케이션 검증·승인 → SDK 또는 직접 API 실행 → 결과 반환 → 최종 응답** 흐름으로 그린 뒤, MCP를 사용할 때와 사용하지 않을 때의 차이를 자기 말로 설명하면 이 노드의 학습 Outcome을 충족한다.

## 개념 지도

```text
사용자의 목표
  ↓ 사용할 수 있는 기능을 설명
Tool: AI 애플리케이션이 사용할 수 있도록 이름·설명·입력 조건으로 정의한 기능
  ↓ 모델이 필요하다고 판단하면
Tool·Function Call: 모델이 도구 이름과 인자를 구조화해 반환하는 호출 제안
  ↓ 검증·권한·사용자 승인
Host / 애플리케이션: 호출을 받을지 판단하고 실제 코드를 실행하는 주체
  ↓ 선택적 개발 편의 계층
SDK: 특정 API나 플랫폼을 코드에서 사용하기 쉽게 감싼 라이브러리·도구 모음
  ↓ 시스템 접점 호출
API: 프로그램이 다른 시스템의 데이터나 기능을 요청·응답으로 사용하는 접점
  ↓
외부 시스템 결과
  ↓ 애플리케이션이 tool result로 반환
모델의 최종 응답
```

MCP를 사용하면 위 흐름에서 도구와 리소스를 제공하는 쪽과 AI 애플리케이션을 연결하는 방식이 표준화된다.

```text
AI Host
  ↕ 권한·승인·전체 사용자 경험 조정
MCP Client
  ↕ 프로토콜 메시지
MCP Server
  ├─ Tool: 호출 가능한 행동 노출
  └─ Resource: 필요한 컨텍스트 데이터 노출
        ↓ 내부 구현은 필요에 따라
      SDK 또는 직접 API 호출
```

MCP를 쓰지 않아도 애플리케이션이 함수를 직접 등록하고 API를 호출할 수 있다. SDK 없이 HTTP 요청을 직접 작성할 수도 있다. 따라서 이 지도는 모든 층을 반드시 써야 한다는 조립 순서가 아니라, **각 층이 어떤 문제를 줄이는지 판단하기 위한 입문용 모델**이다.

### 다섯 개념을 구분하는 질문

|---|---|---|
| API | “외부 시스템이 어떤 데이터나 행동의 접점을 제공하는가?” | API를 AI 전용 기술이나 단순 URL 하나로만 생각하기 |
| SDK | “개발자가 그 접점을 더 편리하게 사용하도록 어떤 코드와 도구를 제공하는가?” | SDK가 별도 서버이거나 API 자체를 대체한다고 생각하기 |
| Tool | “모델에게 어떤 기능을 언제 어떤 입력으로 사용할 수 있다고 설명하는가?” | 설명과 입력 계약 없이 함수 이름만 주면 충분하다고 생각하기 |

| 완료 증거 | 요청, 응답, 변경 전후 상태 중 무엇을 남겨야 하는가? |

## Bridges

### Previous Why

D3에서 Planner·SubAgent·Reviewer의 책임과 전달물을 분리했다. 그러나 실행 역할이 외부 정보나 행동을 필요로 할 때는 역할 카드만으로 부족하다. 이번 노드는 D3의 `Input Context`, `Action`, `Output`, `Stop / Escalate`, `Forbidden`을 **도구 입력 스키마, 실제 실행, 결과 반환, 권한·승인 경계**로 구체화한다.

### Next Why

도구 연결을 설계하고 나면 다음 질문이 생긴다.

> 같은 도구라도 어떤 모델이 언제 호출하게 할까? 호출 결과가 정확하고 안전한지는 어떤 테스트와 평가로 증명할까?

이 질문은 Orchestration·Model Routing·Evaluation·Harness로 이어진다. 도구를 연결했다는 사실만으로 올바른 선택, 낮은 비용, 안전한 실행, 좋은 최종 답이 보장되지는 않는다.

## 3-step Practice

준비물: 종이 또는 메모 앱, 아래 공통 시나리오와 카드. 실제 캘린더 계정·API 키·MCP 서버는 연결하지 않으며 모든 외부 응답은 제공된 모의 데이터로 처리한다.

공통 시나리오: 사용자가 AI 일정 도우미에게 `내일 오후에 비어 있는 30분을 찾아 줘.`라고 요청한다.

제공된 모의 데이터:

```json
{
  "date": "2026-07-17",
  "busy": [
    { "start": "13:00", "end": "14:00" },
    { "start": "15:30", "end": "16:00" }
  ],
  "working_hours": { "start": "13:00", "end": "17:00" }
}
```

### Step 1. 호출 제안과 실제 실행의 경계를 관찰한다

- **Start:** `get_schedule` 도구 카드와 다음 모델 출력을 읽는다: `{"name":"get_schedule","arguments":{"date":"2026-07-17"}}`.
- **Action:** 전체 흐름을 `사용자`, `모델`, `애플리케이션`, `외부 API`, `모델`, `사용자` 여섯 칸으로 나눈다. 각 칸에 요청, 구조화된 호출, 실행, 모의 API 응답, 최종 설명을 배치하고 실제 네트워크 실행 주체에 별표를 한다.
- **Expected:** 모델 출력은 호출 **제안**이며, 애플리케이션이 입력과 권한을 확인한 뒤 API를 실행하고 결과를 모델에 돌려줘야 최종 답이 만들어짐을 구분한다.
- **Fail:** 구조화된 호출이 나온 칸에 `일정 조회 완료`라고 표시하거나, API 응답 없이 모델이 빈 시간을 확정한다.
- **Recover:** `누가 함수 이름을 골랐는가?`, `누가 외부 시스템에 요청했는가?`, `어떤 실제 결과를 모델이 다시 받았는가?` 세 질문에 답하고 화살표를 다시 놓는다.
- **Evidence:** 실행 주체가 표시된 6칸 흐름도, 호출 제안과 실행 결과의 차이 한 문장, 모의 데이터에서 찾은 빈 30분 한 구간을 남긴다.

### Step 2. 네 연결 층을 사용해 읽기 도구 계약을 만든다

- **Start:** 다음 카드를 준비한다: `API`, `SDK(선택)`, `Tool/Function Call`, `MCP(선택)`, `Host 승인`, `결과 반환`.
- **Action:** `get_schedule`의 목적, 입력 `date`, 출력 `busy`와 `working_hours`, 읽기 전용 권한, 오류 형식을 적는다. 먼저 `애플리케이션 → 직접 API` 경로를 그리고, SDK를 쓸 때 바뀌는 코드 계층을 표시한다. 이어 여러 AI 클라이언트에 같은 일정 조회 기능을 제공한다는 조건을 추가하고 `MCP Client → MCP Server Tool → SDK/API` 경로를 그린다.
- **Expected:** API는 외부 접점으로 남고, SDK는 선택적 호출 도우미이며, Tool Calling은 모델의 구조화된 요청이고, MCP는 도구 노출·연결 경로임이 한 지도에서 구분된다.
- **Fail:** SDK·API·MCP를 모두 외부 서버 세 개로 그리거나, MCP가 있으면 API와 실행 코드가 사라진다고 표시한다.
- **Recover:** 각 카드에 `접점`, `개발 도우미`, `호출 제안`, `표준 연결` 중 하나만 붙인 뒤, `실제 일정 데이터는 최종적으로 어디에서 오는가?`를 따라 화살표를 다시 그린다.
- **Evidence:** 도구 계약 1개, 직접 연결 지도 1개, MCP 연결 지도 1개, MCP를 선택할 조건과 선택하지 않을 조건을 각각 한 문장으로 남긴다.

### Step 3. 쓰기 실패를 주입하고 승인·복구 흐름을 혼자 설계한다

- **Start:** 사용자가 `그 시간에 팀 회의를 잡아 줘.`라고 후속 요청했다고 가정한다. 모델이 `create_event` 호출을 제안했지만 입력에는 참석자와 시간대가 없고, 사용자는 최종 제목과 시간을 아직 확인하지 않았다.
- **Action:** `필수 입력 검증 → 누락 정보 질문 → 변경 미리보기 → 사람 확인 → 모의 API 실행 → 응답 검증 → 최종 보고` 순서를 스스로 설계한다. 사용자가 확인을 거절하는 경로, API가 오류를 반환하는 경로, 성공 시 생성된 event id를 확인하는 경로도 추가한다.
- **Expected:** 누락된 입력이나 승인 없음 상태에서는 실행하지 않는다. 승인 뒤에도 모의 API 응답을 확인해야만 완료를 보고하며, 거절·오류는 생성되지 않음으로 끝난다.
- **Fail:** 모델의 자신 있는 문장을 승인으로 간주하거나, 오류 응답 뒤에도 회의가 만들어졌다고 답하거나, 실패할 때 무조건 같은 쓰기 요청을 반복한다.
- **Recover:** `실행 전 무엇이 확정돼야 하는가?`, `어떤 행동이 외부 상태를 바꾸는가?`, `성공을 증명하는 응답 필드는 무엇인가?`, `재시도가 중복 생성을 만들 수 있는가?`에 답해 중단 조건과 증거를 다시 쓴다.
- **Evidence:** 정상·거절·오류의 세 갈래 흐름도, 입력 스키마, 승인 문구, 모의 API 성공/실패 응답, 실제 외부 변경을 하지 않았다는 표시를 남긴다.

## Quiz와 teach-back

### Q1. 모델이 다음 출력을 만들었다: `{"name":"create_event","arguments":{"time":"15:00"}}`. 가장 정확한 설명은?

A. 캘린더 일정 생성이 이미 완료됐다.  
B. 모델이 구조화된 도구 호출을 제안했으며, 애플리케이션이 검증·승인 후 실제 함수를 실행해야 한다.  
C. MCP 서버가 없어도 모델이 캘린더 데이터베이스를 직접 수정했다.  
D. JSON 형식이므로 입력 누락이나 권한 문제는 자동으로 해결됐다.

**정답: B**

- A가 아닌 이유: 구조화된 호출과 외부 시스템의 실행 결과는 서로 다른 단계다.
- B인 이유: 모델은 도구와 인자를 선택할 수 있지만 client tool의 실제 실행과 결과 반환은 애플리케이션 책임이다.
- C가 아닌 이유: MCP 사용 여부와 무관하게 외부 변경에는 허가된 실행 코드와 시스템 접점이 필요하다.
- D가 아닌 이유: 구조가 맞아도 필수 입력, 값의 의미, 권한, 사용자 승인은 별도로 검증해야 한다.

### Q2. API와 SDK의 관계를 가장 정확하게 설명한 것은?

A. SDK는 언제나 네트워크 서버이고 API는 SDK 안의 문서 파일이다.  
B. API는 프로그램이 기능이나 데이터에 접근하는 접점이고, SDK는 그 API나 플랫폼을 코드에서 사용하기 쉽게 돕는 선택적 개발 도구 모음이다.  
C. SDK를 사용하면 인증·오류·권한 검토가 필요 없다.  
D. AI가 Tool Calling을 사용하면 API와 SDK는 모두 필요 없는 개념이 된다.

**정답: B**

- A가 아닌 이유: SDK는 보통 개발에 사용하는 라이브러리·도구·문서 묶음이며 별도 서버와 같은 뜻이 아니다.
- B인 이유: 접점과 그 접점을 사용하는 개발 편의 계층의 역할을 구분한다.
- C가 아닌 이유: SDK가 호출 코드를 도울 수는 있어도 인증, 권한, 입력 검증, 오류 처리를 자동으로 면제하지 않는다.
- D가 아닌 이유: Tool Calling은 호출 선택을 구조화하는 층이며 실제 외부 기능의 접점과 실행 코드는 여전히 필요하다.

### Q3. MCP가 필요한 이유와 경계를 가장 정확하게 설명한 것은?

A. 모든 AI 도구 연결은 반드시 MCP를 사용해야만 작동한다.  
B. MCP는 모델 자체이며 API 응답을 대신 생성한다.  
C. MCP는 서버의 도구·리소스를 클라이언트에 공통 방식으로 노출하는 연결 규약이며, 내부에서 SDK나 API를 사용할 수 있다.  
D. MCP를 연결하면 Host의 권한 관리와 사용자 승인은 필요 없어도 된다.

**정답: C**

- A가 아닌 이유: 애플리케이션은 MCP 없이도 함수를 직접 등록하고 API를 호출할 수 있다.
- B가 아닌 이유: MCP는 모델이 아니라 AI 애플리케이션과 외부 시스템 사이의 프로토콜이다.
- C인 이유: MCP의 표준 연결 역할과 실제 외부 시스템 구현 계층을 함께 구분한다.
- D가 아닌 이유: Host는 권한과 사용자 승인 같은 안전 경계를 계속 조정해야 한다.

### Teach-back

다음 상황을 보지 않고 60초 안에 설명한다.

> “AI에게 ‘내일 일정을 확인하고 회의를 잡아 줘’라고 요청했다. API, SDK, Tool·Function Call, MCP는 각각 어디에 놓일 수 있으며, 누가 실제로 조회·생성을 실행하고 언제 사람에게 확인해야 하는가?”

통과 기준:

- API·SDK·Tool/Function Call·MCP의 역할을 서로 다르게 설명한다.
- 모델의 구조화된 호출과 애플리케이션의 실제 실행을 구분한다.
- SDK와 MCP가 각각 선택적일 수 있음을 말한다.
- 조회와 일정 생성의 권한 위험이 다름을 설명한다.
- 입력 검증, 사람 승인, 실행 결과 확인 중 최소 두 가지를 완료 증거와 연결한다.
