# 어떤 AI 코딩 도구를 어떻게 골라야 할까?

## Student Question

> Cursor, Claude Code, Codex, Windsurf처럼 이름이 다른 AI 코딩 도구가 많은데 무엇을 골라야 할까? 도구를 열고 “고쳐 줘”라고 말한 뒤, 어디까지 맡기고 무엇을 내가 확인해야 할까?

학생은 AI와 함께 작은 작업을 나누고, Agent·Tool·Workflow·Harness의 역할을 배웠다. 그러나 실제 프로젝트 앞에서는 도구 이름과 기능 목록부터 비교하다가 시작하지 못하거나, 반대로 첫 추천만 믿고 파일 변경·명령 실행·완료 판정까지 모두 맡기기 쉽다.

이 노드는 네 제품의 순위를 정하는 수업이 아니다. 학생이 **현재 도구에서 관찰할 수 있는 작업 표면, 읽을 Context, 허용할 행동, 변경 미리보기, 실행 증거**를 확인하고, 자신의 과업에 맞는 도구 하나를 선택해 작은 수정을 끝까지 검증하는 방법을 익히는 수업이다.

## Why Now

D5에서 학생은 반복 업무를 단계·상태·검증·복구가 있는 Workflow로 설계했다. 이제 그 흐름을 실제 코드와 파일이 있는 작업 공간에서 실행하려면 다음 질문에 답해야 한다.

- 프로젝트 폴더와 파일은 어디에서 보고 선택할까?
- AI가 읽은 Context와 바꾸려는 파일을 어떻게 확인할까?
- 파일 쓰기나 명령 실행 전에 무엇을 미리 봐야 할까?
- 결과가 그럴듯한 설명이 아니라 실제 변경·실행 증거를 남겼는지 어떻게 확인할까?
- 도구가 없거나 기능 이름이 달라졌을 때도 같은 판단법을 재사용할 수 있을까?

이 노드의 목표는 네 도구의 최신 기능표를 외우는 것이 아니다. **작업 요구를 정의하고, 도구의 현재 동작을 직접 관찰하고, 최소 권한으로 작은 변경을 실행한 뒤 diff·실행 결과·복구 기록으로 완료를 증명하는 것**이 목표다.

## Outcomes와 완료 증거

| 수준 | 학생이 할 수 있는 일 | 관찰 가능한 완료 증거 |
|---|---|---|
| Observed | 같은 작은 수정 과제가 AI 코딩 도구 안에서 `Context 확인 → 계획 → 변경 제안 → 실행 → 검증`으로 진행되는 사례를 관찰한다. | 예시 기록에서 사람의 요청, AI의 제안, 파일 변경, 명령 실행, 검증 결과를 서로 다른 기호로 표시한다. |
| Assisted | 안내표를 사용해 Cursor·Claude Code·Codex·Windsurf 중 현재 접근 가능한 도구의 작업 표면과 권한 경계를 확인한다. | 도구별 관찰 날짜, 작업 표면, Context 선택 방식, 쓰기·명령 승인 방식, 변경 확인 위치를 근거와 함께 기록한다. |
| Independent | 새로운 작은 수정 과제에 도구 하나를 선택하고 최소 Context·허용 행동·완료 기준을 정해 도움 없이 실행하고 복구한다. | 선택 근거, 작업 요청, 변경 전후 diff, 실행 또는 검사 결과, 실패 시 복구 기록이 한 작업 로그에 남아 있다. |
| Explainable | “가장 좋은 도구”가 과업과 환경에 따라 달라지는 이유와 AI의 완료 보고만으로 작업을 끝내면 안 되는 이유를 설명한다. | 60초 teach-back 또는 6문장 설명에 선택 기준, 권한 경계, Context, 검증 증거, 사람 책임이 모두 들어 있다. |

### 한 줄 완료 조건

학생이 자료를 보지 않고 작은 프로젝트 수정 하나를 **과업 정의 → 도구 관찰·선택 → 최소 Context 지정 → 계획 확인 → 제한된 변경 → diff 확인 → 실행 검증 → 완료 또는 복구** 흐름으로 수행하고, 선택 이유와 사람이 확인한 증거를 설명하면 이 노드의 학습 Outcome을 충족한다.

## 개념 지도

```text
학생의 과업과 완료 기준
  ↓ 어디에서 작업할지 선택
작업 표면: 편집기 안, 터미널 안, 또는 둘을 연결한 인터페이스
  ↓ 필요한 범위만 제공
Context: 프로젝트 구조·대상 파일·요구사항·현재 오류·금지 범위
  ↓ 행동 전에 확인
Plan / Preview: 읽을 파일, 바꿀 파일, 실행할 명령, 예상 결과
  ↓ 허용된 범위에서 실행
AI 코딩 도구: Cursor / Claude Code / Codex / Windsurf 중 현재 사용 가능한 하나
  ↓ 실제 결과를 사람이 확인
Evidence: diff·파일 내용·명령 출력·테스트 또는 수동 확인
  ↓
완료 / 수정 요청 / 되돌림 / 중단
```

이 지도는 제품별 화면이나 기능 이름을 고정하는 설명이 아니다. 같은 제품도 버전·운영체제·설정·계정·실행 표면에 따라 보이는 기능과 승인 방식이 달라질 수 있다. 따라서 학생은 도구 이름만 보고 능력이나 안전성을 추정하지 않고, **현재 환경에서 직접 확인한 행동과 증거**로 선택한다.

### 도구 이름보다 먼저 묻는 여섯 질문

| 질문 | 학생이 확인할 내용 | 피해야 할 오해 |
|---|---|---|
| 작업 표면 | 편집기, 터미널, 브라우저 중 어디에서 파일과 결과를 볼 수 있는가? | 편집기형 또는 터미널형이라는 이름만으로 실제 기능을 단정하기 |
| Context | 어떤 폴더·파일·오류 메시지를 읽게 할 것인가? | 프로젝트 전체를 주면 항상 더 정확하다고 생각하기 |
| 계획 | 어떤 파일을 왜 바꾸고 어떤 명령을 실행하려는가? | 계획 문장이 자연스러우면 실행도 성공했다고 생각하기 |
| 권한 | 읽기, 파일 쓰기, 명령 실행, 네트워크, 외부 전송 중 무엇을 허용할 것인가? | 로컬 도구이므로 모든 행동이 자동으로 안전하다고 생각하기 |
| 변경 확인 | 적용 전 미리보기 또는 적용 후 diff를 어디에서 확인할 것인가? | AI가 “수정했습니다”라고 말하면 파일도 올바르게 바뀌었다고 생각하기 |
| 완료 증거 | 어떤 실행 결과나 수동 확인이 완료를 증명하는가? | 오류 없이 대화가 끝난 것을 프로젝트 성공으로 생각하기 |

### Cursor·Claude Code·Codex·Windsurf 관찰 카드

네 이름 각각에 대해 **현재 직접 확인한 항목만** 채운다. 기능을 사용할 수 없거나 확인하지 못했으면 `미확인`이라고 쓴다.

| 카드 | 기록할 내용 |
|---|---|
| 관찰 정보 | 도구 이름, 관찰 날짜, 운영체제, 실행한 화면 또는 명령 |
| 작업 표면 | 파일 트리·편집기·터미널·대화가 어디에 보이는가? |
| Context 확인 | 선택되거나 읽힌 파일 범위를 어디에서 확인했는가? |
| 변경 제안 | 계획, patch, diff, 미리보기 중 무엇을 볼 수 있었는가? |
| 행동 승인 | 파일 쓰기·명령 실행 전에 어떤 확인 또는 제한을 둘 수 있었는가? |
| 검증 | 변경 뒤 파일 내용·명령 출력·테스트 결과를 어디에서 확인했는가? |
| 제한·미확인 | 아직 확인하지 못한 기능, 계정·설정·환경 제약은 무엇인가? |
| 과업 적합성 | 이번 과업에 선택 또는 제외한 이유는 무엇인가? |

### 과업에 맞는 도구 선택표

| 과업 조건 | 우선 확인할 능력 | 선택 근거로 부족한 것 |
|---|---|---|
| 처음 보는 프로젝트 구조를 이해해야 한다. | 폴더 범위 지정, 파일 역할 설명, 읽은 Context 확인 | “프로젝트를 잘 이해한다”는 홍보 문장 |
| 한두 파일의 문구나 코드를 안전하게 바꾼다. | 대상 파일 제한, 변경 미리보기 또는 diff, 되돌림 경로 | 자동 수정 횟수나 화려한 화면 |
| 명령을 실행해 오류를 재현해야 한다. | 작업 폴더 확인, 실행 명령 표시, 출력 보존, 중단 가능성 | AI의 성공 요약만 있는 대화 |
| 여러 단계를 반복 실행한다. | 계획·단계 상태·승인 지점·실패 복귀 기록 | 한 번의 데모 성공 |
| 외부 쓰기·전송·배포 위험이 있다. | 최소 권한, 명시적 사람 승인, 실행 전 미리보기 | 도구가 유명하거나 최신이라는 이유 |

## Bridges

### Previous Why

D5에서 Scheduler·Workflow·Orchestration·Memory·Harness를 사용해 시작, 단계, 상태, 검증, 복구를 설계했다. 이번 노드는 그 추상 흐름을 실제 프로젝트 작업 공간에 옮겨 **어떤 파일을 읽고, 어떤 변경과 명령을 허용하며, 무엇을 완료 증거로 남길지** 직접 결정하게 한다.

### Next Why

도구 하나로 작은 변경을 완료하고 나면 다음 질문이 생긴다.

> 한 번 성공한 수정이 다른 입력과 실패 사례에서도 정확하고 안전하다는 것을 어떻게 증명할까?

이 질문은 Evaluation·Safety·Reliability로 이어진다. 도구 선택과 실행 로그가 있어도 대표 사례·경계 사례·실패 사례에 대한 평가 기준이 없다면 “이번에 됐다”와 “반복해서 믿을 수 있다”를 구분할 수 없다.

## 3-step Practice

준비물: Cursor·Claude Code·Codex·Windsurf 중 현재 접근 가능한 도구 하나. 도구가 없으면 아래 모의 작업 기록을 사용한다. 실습용 프로젝트 **복사본**, 메모 앱, diff를 볼 수 있는 편집기 또는 파일 비교 화면을 준비한다. Git, 배포, 외부 전송은 사용하지 않는다.

공통 시나리오: 작은 인사말 프로젝트에서 `src/message.txt`의 `안녕하세요`를 `반갑습니다`로 바꾸고, `checks.txt`에 적힌 세 조건을 확인한다.

```text
sample-greeting/
├─ README.md          # 실습 범위와 실행 방법
├─ src/
│  └─ message.txt     # 수정 허용 파일
└─ checks.txt         # "반갑습니다 포함 / 기존 줄바꿈 유지 / 다른 파일 변경 없음"
```

허용 범위: 프로젝트 읽기, `src/message.txt` 한 파일 수정, 로컬 확인 명령 1회. 금지 범위: 다른 파일 수정, 패키지 설치, 네트워크, Git, 배포, 외부 전송.

도구를 사용할 수 없을 때의 모의 기록:

```text
USER: src/message.txt의 인사말만 바꾸고 checks.txt 기준으로 확인해 줘.
AI PLAN: README.md, src/message.txt, checks.txt를 읽고 src/message.txt만 수정한 뒤 확인 명령을 실행한다.
PROPOSED CHANGE: - 안녕하세요 / + 반갑습니다
COMMAND: Select-String -Path src/message.txt -Pattern '반갑습니다'
RESULT: src/message.txt:1:반갑습니다
CHANGED FILES: src/message.txt
```

### Step 1. 도구의 말과 실제 행동을 구분해 관찰한다

- **Start:** 선택한 도구에서 실습용 프로젝트 복사본을 열거나 모의 기록을 읽는다. 아직 쓰기나 명령 실행은 허용하지 않는다.
- **Action:** `README.md`, `src/message.txt`, `checks.txt`만 읽고 계획을 먼저 보여 달라고 요청한다. 응답에서 읽을 파일, 바꿀 파일, 실행할 명령, 예상 결과를 표시하고 허용·금지 범위와 대조한다.
- **Expected:** 계획에는 대상 파일 하나와 검사 기준 세 개가 보이며, 패키지 설치·네트워크·Git·배포가 포함되지 않는다. 계획과 실제 실행이 다른 단계임을 구분한다.
- **Fail:** 도구가 프로젝트 전체 수정, 설치, 네트워크 접근을 제안하거나 무엇을 읽을지 밝히지 않는다.
- **Recover:** 실행을 중단하고 `읽기는 세 파일, 쓰기는 src/message.txt만, 명령은 로컬 확인 1회만 허용`이라고 범위를 다시 제시한 뒤 새 계획을 받는다.
- **Evidence:** 도구 이름·관찰 날짜·환경, 원래 계획, 위험 또는 범위 초과 표시, 수정된 계획, 아직 파일이 바뀌지 않았다는 확인을 남긴다.

### Step 2. 한 파일 변경을 승인하고 diff와 결과를 확인한다

- **Start:** Step 1의 계획이 허용 범위와 일치하는지 확인한다.
- **Action:** `src/message.txt` 한 파일의 변경만 승인한다. 적용 전 미리보기가 있으면 먼저 보고, 없으면 적용 직후 파일 내용과 diff를 확인한다. 이어 `checks.txt`에 적힌 조건을 확인하는 로컬 명령 또는 수동 검사를 한 번 수행한다.
- **Expected:** diff에는 `안녕하세요 → 반갑습니다` 한 변경만 있고, 기존 줄바꿈이 유지되며, 다른 파일은 바뀌지 않는다. 명령 출력 또는 수동 확인표가 세 조건을 증명한다.
- **Fail:** 다른 파일도 바뀌거나, diff를 찾을 수 없거나, 도구가 변경했다고 말했지만 실제 파일은 그대로다.
- **Recover:** 추가 행동을 멈춘다. 실습용 복사본의 원본과 현재 파일을 비교해 범위 밖 변경을 목록으로 만들고, 원본 복사본에서 `src/message.txt`만 다시 수정한다. 검사 세 개를 처음부터 다시 수행한다.
- **Evidence:** 변경 전후 내용, diff 또는 파일 비교 결과, 검사 출력, 변경 파일 목록을 남긴다.

### Step 3. 새 과업에 도구를 선택하고 실패에서 혼자 복구한다

- **Start:** 새 과업을 받는다: `README.md의 실행 안내에서 틀린 파일명 message.md를 message.txt로 고쳐라. 다른 문장은 바꾸지 마라.` 두 도구를 실제로 실행할 필요는 없지만, 접근 가능한 도구와 다른 후보 하나의 관찰 카드를 비교한다.
- **Action:** 작업 표면, Context 확인, 변경 확인, 명령·쓰기 승인, 검증 증거를 기준으로 도구 하나를 선택한다. 대상 파일·금지 범위·완료 기준을 포함한 요청을 작성하고 변경한다. 첫 시도에서 AI가 README 전체 문체도 고쳤다고 가정해 범위 초과를 발견하고, 추가 실행을 중단한 뒤 원본 복사본과 비교해 해당 한 줄만 다시 수정한다.
- **Expected:** 선택 근거가 제품 순위가 아니라 이번 한 파일 수정과 확인 방식에 연결된다. 범위 초과가 기록되고, 최종 diff에는 파일명 한 곳만 바뀌며, 사람이 완료를 판정한다.
- **Fail:** “유명해서”, “AI가 가장 강하다고 해서”만으로 선택하거나, 범위 초과를 발견하고도 결과가 더 좋아 보인다는 이유로 그대로 완료 처리한다.
- **Recover:** `이번 과업에서 반드시 볼 증거는 무엇인가?`, `어떤 행동은 허용되지 않았는가?`, `마지막으로 확인된 원본은 무엇인가?`, `최종 diff는 몇 줄이어야 하는가?`에 답해 선택과 복구 경로를 다시 쓴다.
- **Evidence:** 두 관찰 카드의 비교, 선택 이유 3개, 실제 작업 요청, 실패 기록, 복구 전후 diff, 최종 확인표, 선택하지 않은 도구도 다른 과업에서는 적합할 수 있다는 한 문장을 남긴다.

## Quiz와 teach-back

### Q1. Cursor·Claude Code·Codex·Windsurf 중 하나를 고르는 가장 좋은 첫 기준은?

A. 온라인에서 가장 많이 언급되는 도구인지 확인한다.  
B. 제품 이름만 보고 편집기형·터미널형 기능을 단정한다.  
C. 내 과업에 필요한 Context 확인, 변경 미리보기, 권한, 검증 증거를 현재 환경에서 관찰한다.  
D. 가장 많은 파일을 한 번에 바꿀 수 있는 도구를 고른다.

**정답: C**

- A가 아닌 이유: 인기나 언급량은 내 과업의 권한·검증·환경 적합성을 증명하지 않는다.
- B가 아닌 이유: 제품의 화면과 기능은 버전·설정·실행 표면에 따라 달라질 수 있으므로 직접 확인해야 한다.
- C인 이유: 과업 요구와 현재 관찰 가능한 행동을 연결하면 선택 근거와 한계를 함께 남길 수 있다.
- D가 아닌 이유: 변경 범위가 넓다는 사실은 정확성이나 안전성의 증거가 아니며 작은 과업에는 오히려 위험을 키울 수 있다.

### Q2. AI 코딩 도구가 “수정을 완료했습니다”라고 답했다. 가장 적절한 다음 행동은?

A. 자연스러운 완료 문장이므로 작업을 끝낸다.  
B. 대상 파일의 diff와 변경 파일 목록을 확인하고, 완료 기준에 맞는 검사나 실행 결과를 직접 본다.  
C. 같은 요청을 다른 도구에도 보내 답변 길이를 비교한다.  
D. 검증 전에 바로 Git·배포·외부 전송으로 이어 간다.

**정답: B**

- A가 아닌 이유: 대화의 완료 보고는 실제 파일 상태와 실행 성공을 자동으로 증명하지 않는다.
- B인 이유: diff는 무엇이 바뀌었는지, 검사 결과는 요구한 행동이 작동하는지 보여 주는 서로 다른 증거다.
- C가 아닌 이유: 답변 길이는 변경 정확성이나 완료 기준 충족 여부를 판정하지 못한다.
- D가 아닌 이유: 외부 상태를 바꾸기 전에 로컬 변경과 검증 증거를 확인하고 별도 승인을 받아야 한다.

### Q3. 한 파일만 바꾸라고 했는데 도구가 세 파일을 수정했다. 가장 복구 가능한 행동은?

A. 결과가 좋아 보이면 범위 초과를 무시한다.  
B. 도구가 알아서 했으므로 세 파일 모두 필요한 변경이라고 가정한다.  
C. 추가 행동을 멈추고 변경 파일과 diff를 기록한 뒤, 확인된 원본 복사본에서 허용된 한 파일만 다시 수정하고 전체 기준을 재검사한다.  
D. 변경 기록을 지우고 같은 요청을 제한 없이 반복한다.

**정답: C**

- A가 아닌 이유: 결과 취향과 허용 범위는 다른 기준이며, 승인되지 않은 변경은 완료로 볼 수 없다.
- B가 아닌 이유: AI의 행동은 사람의 권한 결정과 범위 검토를 대신하지 않는다.
- C인 이유: 범위 초과를 증거로 남기고 신뢰할 수 있는 원본에서 필요한 변경만 재수행하면 복구 과정과 최종 상태를 설명할 수 있다.
- D가 아닌 이유: 실패 기록과 종료 조건이 없으면 같은 범위 초과가 반복되고 원인을 확인할 수 없다.

### Teach-back

다음 상황을 보지 않고 60초 안에 설명한다.

> “작은 프로젝트 수정을 위해 Cursor, Claude Code, Codex, Windsurf 중 하나를 고른다면 무엇을 직접 확인할 것인가? 도구가 파일을 바꾸고 완료했다고 말한 뒤에는 어떤 증거를 보고, 범위 밖 변경이 생기면 어떻게 복구할 것인가?”

통과 기준:

- 제품 인기 대신 과업·환경·권한·검증에 연결된 선택 기준을 세 가지 이상 말한다.
- Context와 변경 허용 범위를 구분해 설명한다.
- 계획·호출·완료 보고와 실제 파일 변경·명령 결과가 같은 것이 아님을 말한다.
- diff와 실행 또는 수동 검사 증거를 모두 제안한다.
- 범위 밖 변경에서 중단→기록→원본 확인→제한된 재수정→전체 재검사의 복구 경로를 설명한다.
