# AI에게 여러 역할을 맡기면 무엇이 달라질까?

## Student Question

> 하나의 AI에게 계획·작성·검토를 모두 맡기는 것과 Planner, SubAgent, Reviewer로 역할을 나누는 것은 무엇이 다를까? 여러 Agent가 일하면 결과가 언제 더 좋아지고, 어디에서 사람이 확인해야 할까?

학생은 앞 노드에서 작은 작업을 Prompt, Context, Workflow로 나누고 단계별 결과를 확인했다. 그러나 작업이 커지면 한 대화 안에 조사·작성·검토 조건이 뒤섞이고, 잘못된 판단이 다음 단계로 그대로 전달되기 쉽다. 반대로 역할을 많이 만들기만 하면 같은 일을 중복하거나 서로 다른 기준으로 결과를 내어 오히려 확인할 것이 늘어난다.

이 노드는 Agent 관련 용어를 외우는 수업이 아니다. 학생이 **하나의 목표를 계획·실행·검토 역할로 분리하고, 각 역할의 입력·출력·완료 기준·중단 조건을 연결한 뒤, 최종 판단의 책임을 사람에게 남기는 방법**을 익히는 수업이다.

## Why Now

앞 노드의 3단계 Workflow는 작업 순서를 보이게 만들었다. 이제 여러 파일이나 서로 다른 전문 판단이 필요한 작업에서는 “다음 단계를 무엇이 수행하고, 그 결과를 누가 어떤 기준으로 확인할까?”라는 질문이 생긴다. 이 구분이 없으면 다음과 같은 실패가 발생한다.

- Planner가 만든 계획을 확인하지 않은 채 잘못된 범위로 실행을 시작한다.
- 두 SubAgent가 같은 일을 중복하거나 서로 충돌하는 결과를 만든다.
- Reviewer가 요구사항이 아니라 자신의 취향으로 결과를 평가한다.
- 검토 실패 뒤 어느 단계로 돌아갈지 몰라 전체 작업을 처음부터 반복한다.
- AI가 낸 최종 답을 사람의 승인 없이 곧바로 쓰기·전송·게시 같은 행동으로 이어 간다.

이 노드의 목표는 Agent 수를 늘리는 것이 아니다. **분업이 필요한 작업과 단일 Agent로 충분한 작업을 구분하고, 분업할 때도 증거와 승인 지점이 남는 복구 가능한 흐름을 설계하는 것**이 목표다.

## Outcomes와 완료 증거

| 수준 | 학생이 할 수 있는 일 | 관찰 가능한 완료 증거 |
|---|---|---|
| Observed | 같은 과제를 단일 Agent 방식과 역할 분담 방식으로 비교하고 차이를 관찰한다. | 두 흐름에서 작업 단계, 중간 산출물, 확인 지점, 중복 위험의 차이를 각각 한 가지 이상 표시한다. |
| Assisted | 안내 틀을 사용해 Planner·SubAgent·Reviewer의 책임과 전달물을 나눈다. | 역할별 입력·행동·출력·완료 기준·금지 행동이 채워진 역할 카드와 전달 표가 남아 있다. |
| Independent | 새로운 다단계 과제에 단일 Agent 또는 Multi-Agent 방식을 선택하고 정상·실패·복구 경로를 혼자 설계한다. | 선택 근거, 역할 지도, 실행 순서, Reviewer 판정, 실패 시 복귀 지점, 사람 승인 지점이 한 장의 실행 기록에 남아 있다. |
| Explainable | 왜 역할을 많이 만드는 것이 항상 좋은 것은 아니며 Reviewer가 최종 책임자를 대신하지 않는지 설명한다. | 60초 teach-back 또는 6문장 설명에 분업 기준, 전달물, 검토 기준, 복구, 사람 책임이 모두 들어 있다. |

### 한 줄 완료 조건

학생이 자료를 보지 않고 새로운 작업 하나에 대해 **단일 Agent와 Multi-Agent 중 하나를 선택하고, Planner → SubAgent → Reviewer → 사람 승인 흐름의 역할·전달물·실패 복구를 설계한 뒤 선택 이유를 설명**하면 이 노드의 학습 Outcome을 충족한다.

## 개념 지도

```text
사람이 정한 목표·제약·완료 조건
  ↓
Agent: 목표를 받아 상태를 확인하며 한 단계 이상의 작업을 수행하는 실행 주체
  ↓ 작업이 작고 결합도가 높으면
단일 Agent: 계획·실행·자체 점검을 하나의 흐름에서 수행
  ↓ 독립적인 하위 작업과 별도 검토가 필요하면
Planner: 작업을 나누고 순서·의존성·완료 기준을 정함
  ↓ 작업 패킷 전달
SubAgent: 한정된 하위 작업을 수행하고 결과·증거·위험을 반환
  ↓ 결과 취합
Reviewer: 원래 요구사항과 기준에 맞는지 독립적으로 판정
  ↓ PASS / REVISE / STOP
사람 승인: 실제 사용·쓰기·전송·게시 등 다음 행동을 결정
```

이 지도는 역할 분담을 이해하기 위한 **교육용 작업 모델**이다. 제품이나 프레임워크마다 Agent, SubAgent, Multi-Agent, Planner, Reviewer의 이름과 구현 방식은 다를 수 있다. 역할을 별도 모델이나 별도 프로세스로 실행해야만 한다는 뜻도 아니다. 중요한 것은 이름보다 책임 경계, 전달물, 판정 기준, 복구 경로가 보이는가이다.

### 다섯 개념을 구분하는 질문

| 개념 | 이 노드에서 묻는 질문 | 피해야 할 오해 |
|---|---|---|
| Agent | “목표를 받아 어떤 상태를 확인하고 어떤 행동을 이어서 수행하는가?” | 한 번 답하는 모든 AI를 무조건 자율 Agent라고 부르기 |
| SubAgent | “전체 목표 중 어떤 한정된 하위 작업을 맡고 무엇을 돌려주는가?” | 작은 Agent이므로 책임과 Context도 대충 줘도 된다고 생각하기 |
| Multi-Agent | “여러 역할 사이의 분업이 실제로 독립적이며 전달 규칙이 있는가?” | Agent 수가 많을수록 품질이 자동으로 좋아진다고 생각하기 |
| Planner | “무엇을 어떤 순서로 나누고, 각 단계의 완료를 무엇으로 판단하는가?” | 계획을 만들면 계획 자체가 정답이라고 생각하기 |
| Reviewer | “어떤 요구사항과 증거로 PASS·REVISE·STOP을 판정하는가?” | 결과를 대신 작성하거나 최종 책임까지 가져가는 역할로 생각하기 |

### 역할 카드와 작업 패킷

| 항목 | 학생이 적을 내용 |
|---|---|
| Goal | 전체 작업이 끝났을 때 무엇이 달라져야 하는가? |
| Role | 이 역할이 맡는 한 가지 핵심 책임은 무엇인가? |
| Input Context | 판단에 꼭 필요한 요구사항·자료·이전 단계 결과는 무엇인가? |
| Action | 허용된 범위에서 무엇을 하는가? |
| Output | 다음 역할에 어떤 형식의 산출물과 증거를 넘기는가? |
| Done | 무엇을 확인하면 이 역할의 작업이 끝나는가? |
| Stop / Escalate | 정보 부족·충돌·위험이 있을 때 어디에서 멈추고 누구에게 알리는가? |
| Forbidden | 쓰기·전송·게시처럼 이 역할이 해서는 안 되는 행동은 무엇인가? |

### 단일 Agent와 Multi-Agent 선택 기준

| 상황 | 먼저 고려할 방식 | 이유 |
|---|---|---|
| 단계가 짧고 같은 Context를 계속 사용한다. | 단일 Agent | 전달 비용과 역할 간 정보 손실을 줄일 수 있다. |
| 하위 작업이 서로 독립적이고 결과 형식이 명확하다. | Multi-Agent 후보 | 역할별 산출물을 따로 만들고 비교하기 쉽다. |
| 작성자와 다른 관점의 검토가 중요하다. | 실행 역할 + Reviewer | 같은 기준으로 작성과 판정을 분리해 확인 흔적을 남길 수 있다. |
| 요구사항이 아직 모호하거나 역할끼리 강하게 의존한다. | 사람 확인 후 단일 흐름 | 먼저 범위와 기준을 정하지 않으면 분업이 혼선을 키울 수 있다. |

## Bridges

### Previous Why

앞 노드에서 Prompt는 목표와 조건을, Context는 판단 자료를, Workflow는 단계와 확인 순서를 분명하게 만들었다. 이제 작업 단계가 많아지면 **각 단계의 주인과 전달물을 분명히 하고, 작성과 검토를 구분하는 방법**이 필요하다. D2에서 만든 단계별 완료 기준이 이번 노드에서는 Planner의 작업 분해와 Reviewer의 판정 기준으로 이어진다.

### Next Why

역할과 복구 경로를 설계해 보니 다음 질문이 생긴다.

> 여러 Agent가 사용할 도구에는 어떤 권한을 주어야 하며, 작업마다 속도·비용·품질이 다른 모델을 어떻게 선택하고 결과가 안전한지 어떻게 증명할까?

이 질문은 도구 권한, Orchestration, Model Routing, Evaluation과 Harness로 이어진다. 역할 분담만으로 정확성·안전성·비용 효율이 자동 보장되지는 않으므로 다음 노드들에서 별도의 선택 기준과 평가 증거가 필요하다.

## 3-step Practice

준비물: 메모 앱 또는 종이, 아래 공통 과제와 요구사항 카드. AI 채팅 도구는 선택 사항이며, 실제 파일 쓰기·전송·게시 기능은 사용하지 않는다.

공통 과제: 코딩 동아리 체험 행사 페이지의 **콘텐츠 초안과 게시 전 검토 보고서**를 준비한다.

확인된 요구사항:

- 대상은 코딩을 처음 접하는 중학생이다.
- 페이지에는 행사 소개, 일시·장소·준비물, 신청 행동이 있어야 한다.
- 일시는 `8월 10일 오후 2시`, 장소는 `배움실`, 준비물은 `개인 노트북`이다.
- 확인되지 않은 비용·혜택·연락처는 만들지 않는다.
- 이번 실습의 최종 산출물은 초안과 검토 보고서이며, 실제 게시는 사람이 별도로 승인한다.

### Step 1. 단일 Agent 흐름에서 역할이 섞이는 지점을 찾는다

- **Start:** `행사 페이지 콘텐츠를 계획하고 작성하고 검토해 줘.`라는 단일 요청과 공통 요구사항을 읽는다.
- **Action:** 예상 작업을 `계획`, `정보 정리`, `초안 작성`, `검토`, `승인`으로 나누고, 하나의 Agent가 전부 수행할 때 중간에 확인하기 어려운 지점과 같은 판단을 스스로 검토하게 되는 지점을 표시한다.
- **Expected:** 단일 Agent 방식도 실행 가능하지만 계획·작성·판정이 한 결과에 섞이면 누락의 발생 단계와 검토 근거를 추적하기 어렵다는 점을 발견한다.
- **Fail:** “Agent가 알아서 한다”라고만 적고 중간 산출물이나 확인 기준을 찾지 못한다.
- **Recover:** 각 단계 뒤에 `다음 단계가 시작되기 전에 사람이 볼 수 있는 것은 무엇인가?`를 묻고 산출물 하나씩을 적는다.
- **Evidence:** 5단계 흐름, 단계별 산출물, 역할 충돌 위험 2개, 단일 Agent로 유지할 때 필요한 확인 지점 1개를 남긴다.

### Step 2. Planner·SubAgent·Reviewer 작업 패킷을 만든다

- **Start:** 역할 카드 네 장을 만들고 `Planner`, `정보 정리 SubAgent`, `초안 작성 SubAgent`, `Reviewer`라고 적는다.
- **Action:** Planner는 요구사항을 하위 작업과 완료 기준으로 나눈다. 정보 정리 SubAgent는 확인된 사실과 금지된 추측을 표로 만든다. 초안 작성 SubAgent는 그 표와 형식 조건만 받아 콘텐츠 초안을 만든다. Reviewer는 원래 요구사항과 두 결과를 대조해 `PASS`, `REVISE`, `STOP` 중 하나로 판정한다. 각 카드에 Input Context, Output, Done, Stop, Forbidden을 채운다.
- **Expected:** 각 역할이 같은 전체 요청을 반복하지 않고, 앞 역할의 명시적 산출물을 다음 역할이 입력으로 사용하며, Reviewer의 판정 근거가 원래 요구사항에 연결된다.
- **Fail:** 두 SubAgent가 모두 전체 초안을 작성하거나 Reviewer가 요구사항에 없는 문체 취향으로 내용을 다시 쓴다.
- **Recover:** 각 역할의 핵심 책임을 동사 하나로 줄이고(`분해한다`, `정리한다`, `작성한다`, `판정한다`), 겹치는 행동을 삭제한 뒤 Output→Input 연결을 다시 그린다.
- **Evidence:** 역할 카드 4장, 작업 패킷 3개, Output→Input 전달선, Reviewer 판정표, 사람 승인 지점을 남긴다.

### Step 3. 실패를 주입하고 복구 가능한 흐름을 혼자 완성한다

- **Start:** 정보 정리 SubAgent 결과에 확인되지 않은 문장 `참가비는 무료다.`가 들어갔다고 가정한다.
- **Action:** 이 결과가 초안으로 전달되고 Reviewer가 발견하는 과정을 표시한다. Reviewer는 근거가 없음을 이유로 `REVISE`를 판정하고, 전체를 다시 시작하지 않고 정보 정리 단계로 돌려보낸다. 수정된 사실 표를 받은 초안 작성 역할은 영향받은 문장만 고치며, Reviewer는 요구사항 전체를 다시 점검한다. 마지막에는 사람이 게시 여부를 판단한다.
- **Expected:** 실패 지점, 판정 근거, 복귀 대상, 재사용 가능한 산출물, 재검토 범위가 보이고 확인되지 않은 정보가 최종 초안에서 제거된다.
- **Fail:** Reviewer가 직접 내용을 조용히 고치거나, 오류 하나 때문에 모든 역할을 처음부터 다시 실행하거나, 검토 없이 게시 완료로 표시한다.
- **Recover:** `누가 잘못된 정보를 만들었나?`, `마지막으로 통과한 산출물은 무엇인가?`, `무엇만 다시 실행하면 되는가?`, `누가 최종 행동을 승인하는가?` 네 질문에 답해 복귀 화살표를 다시 그린다.
- **Evidence:** 정상 경로와 실패 경로가 있는 흐름도, `REVISE` 사유, 수정 전후 사실 표, 재검토 결과, 사람 승인 전 `게시하지 않음` 표시를 남긴다.

## Quiz와 teach-back

### Q1. Multi-Agent 방식을 선택할 이유로 가장 적절한 것은?

A. Agent가 많아 보이면 더 전문적인 결과가 나올 것 같기 때문이다.  
B. 서로 독립적인 하위 작업이 있고 각 결과의 입력·출력·완료 기준을 분명히 나눌 수 있기 때문이다.  
C. 요구사항이 모호하므로 여러 Agent가 각자 추측하게 하기 위해서다.  
D. 사람이 최종 결과를 확인하지 않아도 되게 하기 위해서다.

**정답: B**

- A가 아닌 이유: 역할 수 자체는 품질 근거가 아니며 전달 비용과 충돌을 늘릴 수 있다.
- B인 이유: 독립적인 작업과 명시적인 전달 계약이 있을 때 분업의 이점을 관찰하고 검토할 수 있다.
- C가 아닌 이유: 모호한 요구사항을 여러 역할에 복제하면 서로 다른 추측과 재작업이 늘어날 수 있다.
- D가 아닌 이유: Multi-Agent는 사람의 책임과 승인 필요성을 없애지 않는다.

### Q2. Reviewer의 행동으로 가장 적절한 것은?

A. 원래 요구사항과 증거를 대조해 PASS·REVISE·STOP 중 하나를 사유와 함께 판정한다.  
B. 작성 결과가 마음에 들지 않으면 자신의 취향으로 전부 다시 쓴다.  
C. 작성 Agent가 자신 있게 답했으면 근거 없이 PASS한다.  
D. 게시 권한까지 넘겨받아 검토 직후 자동으로 외부에 공개한다.

**정답: A**

- A인 이유: Reviewer는 미리 정한 기준과 관찰 가능한 증거에 따라 판정하고 다음 경로를 분명히 한다.
- B가 아닌 이유: 조용히 다시 쓰면 작성과 검토의 책임 경계와 실패 원인이 사라진다.
- C가 아닌 이유: 표현의 확신은 요구사항 충족이나 사실 정확성의 증거가 아니다.
- D가 아닌 이유: 검토 판정과 외부 게시 승인은 다른 권한이며 이번 흐름의 최종 승인은 사람에게 있다.

### Q3. 정보 정리 SubAgent가 확인되지 않은 정보를 넣었고 Reviewer가 발견했다. 가장 복구 가능한 행동은?

A. 모든 결과를 버리고 처음부터 같은 방식으로 다시 실행한다.  
B. Reviewer가 오류를 숨긴 채 최종 문장만 고친다.  
C. Reviewer가 근거와 실패 지점을 기록해 REVISE하고, 마지막으로 통과한 산출물은 유지한 채 정보 정리 단계부터 영향받은 결과를 다시 검토한다.  
D. 여러 Agent가 만들었으므로 누구도 책임질 필요 없이 그대로 사용한다.

**정답: C**

- A가 아닌 이유: 통과한 산출물까지 버리면 재작업이 커지고 같은 실패 원인이 남는다.
- B가 아닌 이유: 실패 기록과 역할 경계가 사라져 같은 오류를 예방하거나 설명할 수 없다.
- C인 이유: 실패한 단계와 영향 범위를 기준으로 되돌아가고 수정 뒤 연결된 결과를 다시 확인한다.
- D가 아닌 이유: 분업은 책임을 없애는 방식이 아니라 책임과 전달을 더 분명하게 만드는 방식이어야 한다.

### Teach-back

다음 상황을 보지 않고 60초 안에 설명한다.

> “작은 AI 작업에서 언제 단일 Agent를 유지하고 언제 Planner·SubAgent·Reviewer로 나눌 수 있는가? 역할을 나눴다면 실패를 어떻게 발견하고 복구하며, 마지막에 사람은 무엇을 결정해야 하는가?”

통과 기준:

- 단일 Agent와 Multi-Agent를 선택하는 기준을 각각 하나 이상 말한다.
- Planner·SubAgent·Reviewer의 책임을 서로 다르게 설명한다.
- 역할 사이에 전달할 산출물 또는 증거를 하나 이상 예로 든다.
- Reviewer의 `REVISE` 판정 뒤 실패한 단계로 돌아가는 복구 경로를 설명한다.
- 실제 쓰기·전송·게시 같은 최종 행동은 사람이 승인해야 한다고 말한다.
