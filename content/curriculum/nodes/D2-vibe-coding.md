# AI와 어떻게 함께 만들까?

## Student Question

> AI에게 “앱을 만들어 줘”라고 했는데 왜 내가 원한 결과와 다를까? Prompt, Context, Workflow를 어떻게 사용해야 AI와 함께 작업을 끝까지 진행할 수 있을까?

학생은 AI에게 요청을 보내고 결과를 받아 본 경험이 있다. 하지만 첫 결과가 마음에 들지 않으면 같은 요청을 반복하거나, 목표·자료·제약을 한 메시지에 뒤섞어 보내기 쉽다. 이 노드는 “좋은 문장 한 번”을 찾는 요령이 아니라 **목표를 Prompt로 분명히 하고, 작업에 필요한 Context를 제공하며, 확인 가능한 Workflow로 나누어 협업하는 방법**을 익히게 한다.

## Why Now

앞 노드에서 학생은 LLM이 현재 입력과 제공된 컨텍스트를 바탕으로 출력을 생성하며, 자연스러운 답이 곧 정확한 답은 아니라는 점을 배웠다. 이제 그 한계를 실제 협업 방식으로 바꿀 차례다. Prompt·Context·Workflow를 구분할 수 있어야 다음과 같은 실패를 줄일 수 있다.

- 원하는 결과와 성공 기준을 말하지 않아 AI가 작업 범위를 추측한다.
- 필요한 파일이나 사용자 정보를 주지 않고 “알아서 고쳐 줘”라고 요청한다.
- 조사·작성·검토를 한 번에 맡긴 뒤 어느 단계에서 잘못됐는지 찾지 못한다.

이 노드의 목표는 완벽한 프롬프트 공식을 암기하는 것이 아니다. **작은 작업을 목표·컨텍스트·단계·확인 기준으로 구조화하고, 결과를 검토해 다음 요청으로 개선하는 것**이 목표다.

## Outcomes와 완료 증거

| 수준 | 학생이 할 수 있는 일 | 관찰 가능한 완료 증거 |
|---|---|---|
| Observed | 같은 과제를 모호한 요청과 구조화된 요청으로 실행했을 때 결과가 어떻게 달라지는지 관찰한다. | 두 요청과 두 결과에서 달라진 점을 목표·형식·근거 중 두 항목으로 표시한다. |
| Assisted | 안내 틀을 사용해 Prompt와 Context를 구분하고 3단계 Workflow를 만든다. | 목표·대상·제약·완료 기준이 있는 Prompt, 필요한 Context 목록, 단계별 산출물 표가 남아 있다. |
| Independent | 새로운 작은 제작 과제를 도움 없이 구조화해 AI와 한 단계씩 실행하고 결과를 확인한다. | 각 단계의 요청·산출물·확인 결과와 최소 한 번의 수정 요청이 작업 기록에 남아 있다. |
| Explainable | 왜 더 긴 요청이 아니라 더 관련 있는 Context와 확인 가능한 Workflow가 필요한지 설명한다. | 60초 teach-back 또는 5문장 설명에 세 개념의 역할, 실패 지점, 확인 행동이 모두 들어 있다. |

### 한 줄 완료 조건

학생이 자료를 보지 않고 작은 작업 하나를 **Prompt → Context → 3단계 Workflow → 단계별 확인 → 수정 요청**으로 실행한 뒤, 각 요소가 왜 필요했는지 자기 말로 설명하면 이 노드의 학습 Outcome을 충족한다.

## 개념 지도

```text
만들고 싶은 변화
  ↓ 요청을 명확히 표현하기
Prompt: AI에게 목표·대상·제약·원하는 결과·완료 기준을 전달하는 요청
  ↓ 작업에 필요한 근거와 현재 상태 붙이기
Context: 작업 판단에 필요한 파일·데이터·예시·대화·환경 정보
  ↓ 큰 작업을 확인 가능한 순서로 나누기
Workflow: 시작부터 완료까지 이어지는 단계·산출물·검토·복구의 흐름
  ↓ 각 단계 결과 확인하기
피드백: 기준과 실제 결과의 차이를 다음 요청에 반영
  ↓
검토 가능한 결과
```

이 지도는 입문용 협업 모델이다. 특정 도구나 하나의 프롬프트 형식을 정답으로 가정하지 않는다. 작업의 위험도와 복잡도에 따라 단계 수, 사람이 확인할 지점, 제공할 Context의 범위는 달라질 수 있다.

### 세 개념을 구분하는 질문

| 개념 | 이 노드에서 묻는 질문 | 피해야 할 오해 |
|---|---|---|
| Prompt | “AI에게 지금 무엇을, 어떤 조건으로 해 달라고 요청하는가?” | 길게 쓰기만 하면 좋은 요청이라고 생각하기 |
| Context | “이 작업을 판단하려면 어떤 자료와 현재 상태가 필요한가?” | 관련 없는 파일까지 많이 주면 항상 좋아진다고 생각하기 |
| Workflow | “어떤 순서로 만들고, 어디서 확인하고, 실패하면 어떻게 돌아갈까?” | 여러 할 일을 한 메시지에 나열하면 워크플로가 된다고 생각하기 |

### 최소 협업 카드

| 카드 | 학생이 적을 내용 |
|---|---|
| 목표 | 결과를 통해 무엇이 달라져야 하는가? |
| 대상 | 누가 이 결과를 사용하는가? |
| Context | AI가 반드시 봐야 할 자료와 현재 상태는 무엇인가? |
| 제약 | 바꾸면 안 되는 것, 시간·형식·범위 제한은 무엇인가? |
| 단계 | 조사·초안·검토처럼 어떤 순서로 진행할까? |
| 완료 기준 | 무엇을 보면 이 단계가 끝났다고 판단할 수 있는가? |

## Bridges

### Previous Why

앞 노드에서 LLM은 입력과 컨텍스트를 처리해 다음 출력을 만들지만, 요청 밖의 사실과 의도를 자동으로 모두 알지는 못한다는 점을 배웠다. 그래서 이제 **모델이 추측해야 하는 빈칸을 줄이고 결과를 확인할 수 있도록 작업을 설계하는 방법**이 필요하다.

### Next Why

Prompt·Context·Workflow로 작은 작업을 나누어 보니 다음 질문이 생긴다.

> 여러 파일을 읽거나 외부 도구를 사용해야 하는 반복 작업은 어디까지 AI에게 맡기고, 어디에서 사람이 승인해야 할까?

이 질문은 Agent·도구·권한 경계와 더 큰 Workflow 설계로 이어진다. 이후에는 작업 특성에 맞는 모델 선택과 결과 평가 기준도 연결한다.

## 3-step Practice

준비물: AI 채팅 도구(없으면 아래 예시 결과 사용), 메모 앱, 가상의 동아리 행사 안내문 요구사항.

공통 과제: 중학생 코딩 동아리의 체험 행사 안내문을 작성한다. 확인된 정보는 `대상: 코딩 초보 중학생`, `일시: 8월 10일 오후 2시`, `장소: 배움실`, `준비물: 개인 노트북`, `신청 마감: 8월 7일`이다.

### Step 1. 모호한 요청의 빈칸을 찾는다

- **Start:** 새 대화에서 `코딩 행사 안내문을 멋지게 써 줘.`라고 요청한다.
- **Action:** 결과를 읽고 AI가 추측한 항목과 빠진 항목을 표시한다. `대상`, `일시`, `장소`, `준비물`, `신청 마감`, `문체`, `길이`를 확인표로 사용한다.
- **Expected:** 요청에 없던 정보는 누락되거나 추측될 수 있고, “멋지게”만으로는 원하는 결과를 판정하기 어렵다는 점을 발견한다.
- **Fail:** 결과가 자연스러워 보여 빠진 정보나 추측을 찾지 못한다.
- **Recover:** 결과의 각 문장 옆에 “이 정보는 요청에 있었나?”를 적고 공통 과제의 확인된 정보와 한 줄씩 대조한다.
- **Evidence:** 추측 또는 누락 2개, 판단하기 어려운 표현 1개, 다음 요청에서 추가할 조건 2개를 기록한다.

### Step 2. Prompt와 Context를 분리해 요청을 개선한다

- **Start:** 최소 협업 카드에서 `목표·대상·Context·제약·완료 기준` 다섯 칸을 복사한다.
- **Action:** 목표는 `체험 행사 신청을 돕는 안내문 작성`, 대상은 `코딩 초보 중학생`, Context는 공통 과제의 확인된 다섯 정보로 채운다. 제약은 `친근한 한국어, 180자 안팎, 확인되지 않은 정보 추가 금지`, 완료 기준은 `필수 정보 5개와 신청 행동 포함`으로 정해 AI에게 다시 요청한다.
- **Expected:** 새 결과에 필수 정보가 포함되고, 첫 결과보다 검토 기준이 분명해진다.
- **Fail:** 조건을 모두 넣었지만 정보가 빠지거나 확인되지 않은 내용이 추가된다.
- **Recover:** 빠진 항목을 이름으로 지적하고 `아래 Context 밖의 사실은 추가하지 말고, 누락된 항목을 보완해 다시 작성해 줘.`라고 수정 요청한다.
- **Evidence:** 개선 Prompt, 사용한 Context 목록, 첫 결과와 달라진 점 3개, 완료 기준 체크 결과를 남긴다.

### Step 3. 3단계 Workflow로 혼자 완성한다

- **Start:** 새 과제 `행사 안내문과 게시 전 점검표 만들기`를 `① 요구사항 표 ② 안내문 초안 ③ 기준 검토와 수정`으로 나눈다.
- **Action:** 한 번에 최종본을 요구하지 않고 각 단계를 차례로 실행한다. 매 단계에서 산출물을 확인한 뒤 다음 단계로 진행하며, 마지막에는 필수 정보·추측 금지·문체·길이를 점검하고 필요한 수정 요청을 한 번 보낸다.
- **Expected:** 요구사항 표, 안내문, 점검 결과가 서로 연결되고 어느 단계에서 누락이 생겼는지 추적할 수 있다.
- **Fail:** 세 단계를 한 메시지에 맡긴 뒤 중간 결과를 확인하지 않거나, 잘못된 정보가 최종본까지 이어진다.
- **Recover:** 마지막으로 확인된 단계로 돌아가 잘못된 항목 하나만 수정한다. 수정 후 남은 단계의 산출물도 같은 기준으로 다시 점검한다.
- **Evidence:** 단계별 Prompt 3개, 단계별 산출물 3개, 체크 결과, 실패 또는 수정 기록 1개, 최종 안내문을 남긴다.

## Quiz와 teach-back

### Q1. Context를 가장 정확하게 사용한 요청은?

A. `알아서 최고의 안내문을 써 줘.`  
B. 행사와 관계없는 지난 회의록 20개를 모두 첨부한다.  
C. 확인된 행사 정보와 대상 독자, 현재 초안을 제공하고 빠진 필수 정보를 점검해 달라고 한다.  
D. 같은 요청을 설명 없이 세 번 반복한다.

**정답: C**

- A가 아닌 이유: 목표의 세부 조건과 판단에 필요한 자료가 없어 AI가 빈칸을 추측해야 한다.
- B가 아닌 이유: Context는 양이 아니라 현재 작업과의 관련성이 중요하며, 불필요한 자료는 판단을 흐릴 수 있다.
- C인 이유: 작업에 필요한 사실, 대상, 현재 상태와 점검 행동이 함께 제시되어 있다.
- D가 아닌 이유: 필요한 정보나 기준을 추가하지 않은 반복은 실패 원인을 해결하지 못한다.

### Q2. 다음 중 Workflow라고 보기 가장 어려운 것은?

A. 요구사항 정리 → 초안 작성 → 기준 검토 → 수정  
B. 입력 확인 → 처리 → 결과 검토 → 실패 시 이전 단계로 복구  
C. 조사와 작성과 검토를 전부 잘해 달라고 한 번 요청한 뒤 최종 결과만 받기  
D. 단계마다 산출물과 통과 기준을 정하고 다음 단계 진행 여부를 판단하기

**정답: C**

- A가 아닌 이유: 순서와 서로 다른 단계가 분명한 기본 Workflow다.
- B가 아닌 이유: 정상 흐름뿐 아니라 검토와 복구가 포함된 Workflow다.
- C인 이유: 할 일은 여러 개지만 중간 산출물, 확인 지점, 실패 복구가 구분되지 않는다.
- D가 아닌 이유: 각 단계의 완료 증거와 진행 판단이 연결되어 있다.

### Q3. 구조화된 Prompt를 사용했는데도 결과에 잘못된 날짜가 들어갔다. 가장 적절한 다음 행동은?

A. 문장이 자연스러우므로 그대로 게시한다.  
B. 확인된 원본 Context와 결과를 대조하고, 잘못된 날짜를 지적해 수정한 뒤 다시 점검한다.  
C. 아무 설명 없이 `다시`라고 요청한다.  
D. 더 긴 Prompt를 새로 쓰되 확인된 날짜는 제공하지 않는다.

**정답: B**

- A가 아닌 이유: 자연스러움은 사실의 정확성을 보장하지 않는다.
- B인 이유: 근거와 결과의 차이를 확인하고 구체적인 피드백을 다음 요청에 반영한다.
- C가 아닌 이유: 실패 위치와 수정 기준을 전달하지 않아 같은 문제가 반복될 수 있다.
- D가 아닌 이유: 길이보다 관련 있는 Context와 명확한 수정 기준이 필요하다.

### Teach-back

다음 상황을 보지 않고 60초 안에 설명한다.

> “AI에게 작은 제품 작업을 맡길 때 Prompt, Context, Workflow는 각각 어떤 역할을 하며, 첫 결과가 기준을 충족하지 못하면 무엇을 해야 하는가?”

통과 기준:

- Prompt·Context·Workflow를 서로 다른 역할로 설명한다.
- 작은 작업을 최소 세 단계로 나눈 예를 든다.
- 단계별로 확인할 산출물 또는 완료 기준을 하나 이상 말한다.
- 잘못된 결과를 근거와 대조하고 구체적으로 수정 요청하는 행동을 제안한다.
