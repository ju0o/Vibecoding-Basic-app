# AI Engineering Atlas V2 — 8개 도메인 커리큘럼 개요

## 문서 목적

이 문서는 학생이 AI 제품을 **혼자 질문하고, 만들고, 검증하고, 운영할 수 있게 되는 과정**을 8개 학습 도메인으로 정리한 상위 개요다. 각 도메인은 지식 목록이 아니라 학생이 실제로 해결하려는 질문에서 시작하며, 3개 차시로 이어지는 샘플 학습 흐름을 제안한다.

> **운영 경계:** 아래 차시는 후보 아크다. 개별 차시 제작이나 Track D 시작을 승인하지 않는다. 실제 제작 전에는 Education PM 절차에 따라 학생의 Top 질문을 확인하고, 후보 A/B/C를 제시한 뒤 운영자의 `PICK`을 받아야 한다.

## 전체 학습 흐름

```text
문제 발견 → 소프트웨어 구조 이해 → AI와 협업 → 모델 선택
→ 지식 연결 → 에이전트 자동화 → 품질 검증 → 출시와 운영
```

모든 도메인은 `Experience → Question → Theory → Practice → Experiment → Reflection → Outcome → Next` 흐름을 따른다. 샘플 아크의 세 번째 차시에서는 학생이 도움 없이 결과를 만들고 선택 이유를 설명하는 것을 목표로 한다.

## Domain 1. 문제 발견과 AI 제품 사고

### 목적

막연한 아이디어를 사용자의 실제 문제, 관찰 가능한 변화, 검증 가능한 성공 기준으로 바꾼다. 학생은 “AI를 어디에 넣을까?”보다 “누구의 어떤 어려움을 왜 지금 해결해야 할까?”를 먼저 묻는다.

### 대상 학습자 질문

- 내가 만들고 싶은 것은 기능인가, 해결해야 할 문제인가?
- 이 문제를 겪는 사람과 문제를 확인할 증거는 무엇인가?
- AI가 필요한 경우와 일반 소프트웨어가 더 나은 경우를 어떻게 구분할까?

### 샘플 3차시 아크

| 차시 | 학생 중심 질문과 경험 | 실습 및 완료 증거 |
|---|---|---|
| 1. 불편을 문제로 바꾸기 | 일상에서 반복되는 불편을 관찰하고 사용자·상황·장애물로 분해한다. | 실제 사례 3개를 수집하고 하나를 명확한 문제 문장으로 작성한다. |
| 2. 해결 가설 세우기 | 문제 원인과 원하는 변화를 연결하고 AI 사용 여부를 비교한다. | AI 방식과 비-AI 방식의 장단점을 비교한 해결 가설을 만든다. |
| 3. 성공을 측정 가능하게 만들기 | “좋아졌다”를 행동과 결과로 관찰하는 법을 익힌다. | 대상 사용자, 핵심 행동, 성공 지표가 포함된 한 페이지 제품 브리프를 혼자 완성하고 선택 이유를 설명한다. |

## Domain 2. 웹·소프트웨어 구조와 데이터 흐름

### 목적

화면, 프런트엔드, 백엔드, API, 데이터베이스가 어떻게 연결되는지 눈에 보이는 흐름으로 이해한다. 학생은 오류가 났을 때 무작정 다시 요청하지 않고 문제가 발생한 층을 좁힐 수 있다.

### 대상 학습자 질문

- 버튼을 누른 뒤 화면 뒤에서는 어떤 일이 일어날까?
- 프런트엔드, 백엔드, API, 데이터베이스는 각각 무엇을 맡을까?
- 오류가 화면·요청·서버·데이터 중 어디에서 생겼는지 어떻게 찾을까?

### 샘플 3차시 아크

| 차시 | 학생 중심 질문과 경험 | 실습 및 완료 증거 |
|---|---|---|
| 1. 화면에서 데이터까지 따라가기 | 로그인이나 할 일 추가 동작을 화면부터 저장까지 추적한다. | 사용자 행동을 요청·처리·응답·표시 단계로 그린 데이터 흐름도를 만든다. |
| 2. CRUD와 API로 연결하기 | 제품 행동이 생성·조회·수정·삭제 요청으로 바뀌는 과정을 익힌다. | 간단한 기능에 필요한 엔드포인트, 입력, 응답, 상태 코드를 정의한다. |
| 3. 층별로 오류 찾기 | 고장 난 샘플의 증상을 보고 원인 후보를 한 층씩 제거한다. | 재현 절차와 증거를 남기고 오류 층을 판별한 뒤 수정 요청서를 혼자 작성한다. |

## Domain 3. 프롬프트·컨텍스트 기반 AI 협업

### 목적

AI에게 막연히 “만들어 줘”라고 말하는 수준을 넘어 목표, 제약, 맥락, 완료 조건을 전달하고 결과를 반복 개선하는 협업 능력을 기른다.

### 대상 학습자 질문

- 같은 AI인데 왜 요청 방식에 따라 결과가 크게 달라질까?
- 프롬프트와 컨텍스트는 무엇이 다르며 무엇을 얼마나 제공해야 할까?
- AI 결과를 그대로 믿지 않고 다음 요청으로 개선하려면 무엇을 확인해야 할까?

### 샘플 3차시 아크

| 차시 | 학생 중심 질문과 경험 | 실습 및 완료 증거 |
|---|---|---|
| 1. 모호한 요청을 실행 가능한 작업으로 바꾸기 | 나쁜 요청과 좋은 요청의 결과 차이를 직접 비교한다. | 목표·대상·제약·완료 조건을 갖춘 작업 요청으로 다시 쓴다. |
| 2. 필요한 컨텍스트만 연결하기 | 관련 파일과 불필요한 파일을 구분하고 정보 누락의 영향을 실험한다. | 파일 역할 지도와 함께 최소 충분 컨텍스트 묶음을 구성한다. |
| 3. 생성–검토–수정 루프 운영하기 | 첫 결과의 결함을 근거로 후속 요청을 설계한다. | 결과 검토표, 수정 요청, 개선된 산출물을 남기고 왜 좋아졌는지 설명한다. |

## Domain 4. 모델 이해와 라우팅

### 목적

모델을 순위표로 외우지 않고 과업의 난도, 지연 시간, 비용, 위험에 맞춰 선택한다. 모델 라우팅은 하나의 공식 표준이 아니라 상황에 따른 **교육용 상대 분류와 의사결정 방법**으로 다룬다.

### 대상 학습자 질문

- 모든 작업에 가장 강한 모델을 쓰면 왜 안 될까?
- 빠른 모델, 저비용 모델, 고성능 모델 중 무엇을 언제 선택할까?
- 한 작업을 여러 모델이나 단계로 나누면 품질과 비용이 어떻게 달라질까?

### 샘플 3차시 아크

| 차시 | 학생 중심 질문과 경험 | 실습 및 완료 증거 |
|---|---|---|
| 1. 과업과 모델 특성 맞추기 | 분류, 요약, 코딩, 복합 추론 과업의 요구 차이를 비교한다. | 과업별 품질·속도·비용·위험 우선순위표를 작성한다. |
| 2. 단일 모델 선택 실험 | 같은 과업을 서로 다른 모델 등급에 맡기고 결과를 비교한다. | 교육용 상대 비용 지수와 평가 기준으로 선택 근거를 기록한다. |
| 3. 간단한 라우팅 설계 | 저위험 작업과 고위험 작업을 분기하고 실패 시 상향하는 흐름을 만든다. | 라우팅 규칙, 예외, 폴백, 중단 조건을 포함한 의사결정도를 혼자 완성한다. |

## Domain 5. 데이터·지식·RAG

### 목적

모델이 모르는 최신 정보나 조직 고유 정보를 외부 지식에서 찾아 근거와 함께 사용하도록 설계한다. 학생은 “자료를 많이 넣기”보다 필요한 근거를 잘 찾고 출처 범위를 지키는 데 집중한다.

### 대상 학습자 질문

- 모델의 기본 지식과 내가 제공한 자료는 어떻게 다르게 작동할까?
- 검색 결과가 있는데도 답이 틀리는 이유는 무엇일까?
- 어떤 답에 출처가 필요하며, 근거 부족을 어떻게 표시해야 할까?

### 샘플 3차시 아크

| 차시 | 학생 중심 질문과 경험 | 실습 및 완료 증거 |
|---|---|---|
| 1. 답변에 필요한 근거 찾기 | 근거 없는 답과 자료 기반 답을 비교하고 주장 단위를 구분한다. | 질문별 필수 근거와 허용 출처를 정의한 근거 지도를 만든다. |
| 2. 검색 가능한 지식으로 준비하기 | 긴 문서를 작은 의미 단위로 나누고 검색어에 따른 결과 차이를 실험한다. | 샘플 문서를 분할하고 질문–검색 결과 적합성을 평가한다. |
| 3. 근거 기반 답변 흐름 설계 | 검색, 선택, 답변, 출처 표시, 근거 부족 처리를 연결한다. | 출처가 있는 답변과 “근거 부족” 응답을 모두 통과하는 미니 RAG 흐름을 설명한다. |

## Domain 6. 도구 사용·에이전트·워크플로 자동화

### 목적

한 번의 답변을 넘어 AI가 도구를 사용하고 여러 단계를 수행하게 만든다. 학생은 자율성을 높이기 전에 작업 경계, 상태, 승인 지점, 실패 복구를 설계한다.

### 대상 학습자 질문

- 챗봇과 에이전트는 무엇이 다를까?
- AI에게 어떤 도구와 권한을 주어야 하며 어디서 멈추게 해야 할까?
- 여러 단계 중 하나가 실패했을 때 처음부터 다시 하지 않으려면 어떻게 설계할까?

### 샘플 3차시 아크

| 차시 | 학생 중심 질문과 경험 | 실습 및 완료 증거 |
|---|---|---|
| 1. 반복 작업을 단계로 분해하기 | 사람이 하던 반복 업무를 입력·판단·행동·출력으로 나눈다. | 자동화할 단계와 사람이 유지할 단계를 표시한 워크플로 지도를 만든다. |
| 2. 도구와 권한 경계 정하기 | 읽기, 쓰기, 전송 같은 도구 행동의 위험 차이를 체험한다. | 도구별 허용 범위, 확인 필요 행동, 금지 행동을 정의한다. |
| 3. 복구 가능한 에이전트 만들기 | 실패, 재시도, 중단, 사람 승인 상태가 있는 시나리오를 실행한다. | 정상 경로와 실패 경로를 모두 통과하고 실행 기록으로 완료를 증명한다. |

## Domain 7. 평가·안전·신뢰성

### 목적

“그럴듯해 보인다”를 품질 판단 기준으로 사용하지 않는다. 학생은 대표 사례, 실패 사례, 안전 기준을 포함한 평가를 만들고 변경 전후의 품질을 증거로 비교한다.

### 대상 학습자 질문

- AI 결과가 좋은지 무엇으로 판단할까?
- 정답이 하나가 아닌 결과도 일관되게 평가할 수 있을까?
- 환각, 편향, 개인정보 노출, 위험한 행동을 어떻게 발견하고 줄일까?

### 샘플 3차시 아크

| 차시 | 학생 중심 질문과 경험 | 실습 및 완료 증거 |
|---|---|---|
| 1. 좋은 결과를 기준으로 바꾸기 | 취향과 요구사항을 분리하고 관찰 가능한 평가 항목을 만든다. | 정확성·완전성·근거·형식 기준이 있는 루브릭을 작성한다. |
| 2. 실패를 먼저 시험하기 | 정상 사례뿐 아니라 모호함, 악의적 입력, 근거 부족 사례를 실행한다. | 대표·경계·실패 사례가 포함된 최소 평가 세트를 만든다. |
| 3. 변경 전후를 증명하기 | 프롬프트나 모델 변경이 실제 개선인지 회귀인지 비교한다. | 평가 결과, 실패 원인, 완화책, 남은 위험을 기록하고 출시 가능 여부를 설명한다. |

---

## Domain 8. 출시·관찰·지속 개선

### 목적

로컬에서 한 번 성공한 데모를 실제 사용자가 반복해서 쓸 수 있는 제품으로 발전시킨다. 학생은 배포 자체보다 사용 흐름, 비용, 로그, 피드백, 장애 대응을 포함한 운영 가능한 상태를 완성으로 본다.

### 대상 학습자 질문

- 내 컴퓨터에서 되는 것과 사용자가 쓸 수 있는 것은 무엇이 다를까?
- 출시 후 품질, 비용, 속도, 실패를 어떻게 관찰할까?
- 사용자 피드백을 다음 개선 우선순위로 어떻게 바꿀까?

### 샘플 3차시 아크

| 차시 | 학생 중심 질문과 경험 | 실습 및 완료 증거 |
|---|---|---|
| 1. 출시 가능한 완료 조건 정하기 | 데모와 제품의 차이를 사용자 여정과 실패 복구 관점에서 확인한다. | 핵심 경로, 접근성, 오류 안내, 개인정보, 비용을 포함한 출시 체크리스트를 만든다. |
| 2. 보이는 운영 만들기 | 요청 수, 지연, 비용, 오류, 사용자 성공 신호를 연결한다. | 최소 관찰 지표와 경고 기준이 있는 운영 대시보드를 설계한다. |
| 3. 작은 제품을 끝까지 운영하기 | 실제 사용 시나리오를 실행하고 피드백을 우선순위로 전환한다. | 실행 증거, 평가 결과, 남은 위험, 다음 개선 한 가지가 포함된 최종 운영 기록을 발표한다. |

|---|---|
| 문제와 성공 기준을 정의한다. | 이 제품은 화면부터 데이터까지 어떻게 작동해야 할까? |
| 소프트웨어의 층과 데이터 흐름을 설명한다. | AI에게 이 구조와 작업을 어떻게 정확히 전달할까? |
| 목표·제약·컨텍스트가 있는 요청을 만든다. | 이 작업에는 어떤 모델이 가장 적합할까? |
| 과업에 맞는 모델과 라우팅을 선택한다. | 모델에 없는 신뢰할 수 있는 지식을 어떻게 연결할까? |
| 외부 근거를 검색하고 출처와 함께 답한다. | 이 능력을 여러 단계와 도구 행동으로 어떻게 확장할까? |
| 경계와 복구가 있는 에이전트 흐름을 만든다. | 이 흐름이 정말 정확하고 안전한지 어떻게 증명할까? |
| 평가와 안전 기준으로 품질을 증명한다. | 실제 사용자 환경에서 어떻게 관찰하고 계속 개선할까? |

## V2 과정 완료의 공통 증거

학생은 최종적으로 다음을 혼자 수행하고 설명할 수 있어야 한다.

1. 실제 사용자 문제와 측정 가능한 성공 기준을 정의한다.
2. 제품의 화면·서버·데이터·AI 흐름을 설계하고 고장 지점을 좁힌다.
3. 적절한 컨텍스트, 모델, 지식, 도구를 선택해 작동하는 워크플로를 만든다.
4. 대표 사례와 실패 사례로 품질·안전·비용을 평가한다.
5. 제품을 출시 가능한 상태로 점검하고 운영 증거를 바탕으로 다음 개선을 결정한다.

각 도메인의 실제 노드가 승인되면 Observed → Assisted → Independent → Explainable 증거, 실행 가능한 Practice, 오답 이유가 있는 Checkpoint, 이전 Why와 다음 Why를 별도 노드 명세에서 구체화한다.
