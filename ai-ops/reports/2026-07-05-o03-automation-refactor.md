## 13. Batch 2부터의 운영 방식
```
운영자: STATE.md 열기 → NEXT의 프롬프트를 지정 세션에 붙여넣기 → Executor 보고의 "다음 →"을 따라 반복
       → NEXT에 "운영자:" 항목이 뜨면 승인/반려 → 끝
Fable(me): "run" 요청 시 승인 검토·기획·감사·DASHBOARD
```

## 14. 가장 빠른 완성 전략
1. **KB 물결(wave) 방식**: 강의보다 KB를 한 물결 앞서 생산 — 검증 세션이 놀지 않게 (지금: 2차 KB 3건 needed 등록 권장 — skills, orchestration, harness)
2. 배치 크기 상향: KB 5→7, 강의 4→5 (Loop 관리 가능 범위)
3. 배치 파이프라이닝: 배치 N 검증 중 배치 N+1 수집 (세션 2개로 충분)
4. M10 완성(15강) → M08(선행 모듈) → M02·M03(입문 트랙) 순 — CURRICULUM-MAP 그대로
5. Fable QA 승인은 보고서 검토로 신속 처리 (KB당 ~수 분), 전수 재검증은 O-02 표본으로

## 18~19. 운영자의 할 일 / 안 할 일
- **할 일**: ① NEXT가 시키는 붙여넣기 ② "운영자:" 게이트에서 승인/반려 ③ 원할 때 스팟체크 ④ Fable에게 "run"(하루 1~2회)
- **안 할 일**: 다음 단계 계산, Executor 선택, 프롬프트 작성·수정, {값} 채우기, Loop 판단, 병렬 판단, MASTER_PROGRESS/DASHBOARD 편집, Release 판단, 커밋 확인, 산출물 경로 추적

## 20. 최종 결론

**"상태는 STATE.md가 들고, 규칙은 상태 기계가 들고, 실행은 파라미터 없는 RUN 프롬프트가 들고, 사람은 게이트 2개(배포·에스컬레이션)만 든다."**

품질 게이트(Score 80+, Fable 승인, 세션 분리, verify, 판정·수정 분리)는 단 하나도 제거하지 않았다 — 게이트 사이의 이동만 자동화했다. Batch 1에서 사람 행동의 약 90%가 규칙 기반이었고 전부 문서로 이관 가능했다. 남은 기계적 행동은 "붙여넣기" 하나이며, 이것이 Level 6(CLI 자동 실행)의 유일한 대상이다. 운영이 2~3배치 안정되면 Level 6 설계를 제안하겠다.
