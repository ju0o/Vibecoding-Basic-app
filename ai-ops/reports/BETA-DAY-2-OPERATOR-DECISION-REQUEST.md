# Beta Day 2 운영자 결정 요청서

## 목적과 현재 판단

이 문서는 [Gate 진입 준비 종합 분석](./BETA-DAY-2-GATE-READINESS-ANALYSIS.md)에서 확인된 운영자 결정 5건을 한 번에 승인할 수 있도록 정리한 요청서다.

- 현재 Gate: `TRACK_D_REVIEW_OR_IMPLEMENTATION_SCOPE`
- 현재 준비도: **C등급 / 조건부 미준비**
- 현재 결정 상태: **HUMAN_APPROVAL_REQUIRED**
- 이번 문서의 범위: 보고서 작성만 수행. 소스 코드, Lesson, Practice, P0 콘텐츠는 수정하지 않는다.

### 빠른 결정 요약

| 번호 | 결정 항목 | 추천 | Gate에 미치는 핵심 영향 |
|---:|---|---|---|
| 1 | 상태 사전 canonical 권위 | C | 문서 상태값 동기화의 출발점 확정 |
| 2 | ID 표준화 적용 범위 | A | 공식 ID와 파일명 별칭을 분리하고 downstream 대조 가능 |
| 3 | 원본 수정 범위 | C | Gate 진입에 필요한 최소 변경만 승인 |
| 4 | Track D 재개 여부 | A | Track D는 유지하되 조건 충족 전까지 일시 정지 |
| 5 | Branch 정리 | A | 보고서만 별도 커밋하고 혼합 변경은 보류 |

아래 추천은 확정 사실이 아니라 검토 가능한 제안이다. 운영자는 각 항목의 `A/B/C`와 필요한 조건을 결정해 주면 된다.

## 1. 상태 사전 canonical 권위

### 문제

`DESIGN.md`, `CONCEPTS.md`, `INTERFACE_SPEC.md`가 상태를 각자의 관점에서 정의하거나 표시하고 있어, 같은 상태의 의미·표시·완료 판정을 어느 문서가 최종 결정하는지 확정되지 않았다. PM Docs 개선안은 `TEAM_GLOSSARY.md`의 Status Dictionary를 canonical 후보로 제시했지만, 운영자 승인과 적용은 아직 끝나지 않았다.

### 옵션

| 옵션 | 장점 | 단점 |
|---|---|---|
| **A. `DESIGN.md`를 SSOT** | 화면 표시·접근성 규칙과 가깝다. | UI 표현 문서가 공통 의미와 완료 판정까지 소유하게 되어 역할이 섞인다. |
| **B. `CONCEPTS.md`를 SSOT** | 학습적 의미와 연결하기 쉽다. | 실제 화면 계약·상태값·검증 증거의 기준으로 쓰기 어렵다. |
| **C. 별도 상태 사전 파일 생성** | 정의, 화면 표시, 교육적 해석, 실제 인덱스를 분리할 수 있다. | 새 문서의 owner·경로·변경 절차를 추가로 정해야 한다. |

### 추천

**C 추천.** 공통 정의는 별도 상태 사전에 두고, `DESIGN.md`는 표시·접근성, `CONCEPTS.md`는 교육적 해석, `INTERFACE_SPEC.md`는 화면 계약을 소유하도록 분리한다. 기존 제안의 `TEAM_GLOSSARY.md` canonical안과 새 파일안 중 실제 경로는 이 결정에 포함해 확정해야 한다.

### 영향과 Gate 연계

이 결정은 세 PM 문서, Interface 상태 계약, `master-toc.md`의 실제 상태값, 학생 완료 표시의 동기화 순서를 결정한다. 결정 전에는 상태 용어를 일괄 수정하거나 Gate-ready로 재판정할 수 없다. 결정 후에는 상태 정의 1곳, 참조 링크, 상태 검색·anchor 검증, 독립 리뷰가 필요하다.

### 결정 요청

`1번: A / B / C 중 ___`를 선택하고, C인 경우 상태 사전의 파일 경로와 owner를 지정해 달라.

## 2. ID 표준화 적용 범위

### 문제

공식 ID는 [Master TOC](../master-toc.md)의 기준을 따라야 하지만 파일 순번과 다르다. 예를 들어 `05-terminal-commands.md → A05`, `06-errors-to-ai.md → A06`, `07-web-how-pages-appear.md → B01`이다. A01–A06 파일에는 `node_id`가 없고, 기존 요청·보고서에는 파일 05–09를 B05–B09로 부르는 혼용이 남아 있다.

### 옵션

| 옵션 | 장점 | 단점 |
|---|---|---|
| **A. frontmatter에 `node_id` 추가, 파일명 유지** | 기존 링크·경로를 보존하면서 공식 ID를 기계적으로 대조할 수 있다. | 기존 파일·문서·Practice·route의 참조를 후속 점검해야 한다. |
| **B. 파일명 변경** | 파일명만 봐도 공식 ID를 알 수 있다. | 링크·경로·학생 표시·검토 보고서가 연쇄적으로 깨질 위험이 크다. |
| **C. 매핑표만 유지** | 원본 변경이 없고 즉시 적용 부담이 작다. | 새 문서가 파일을 읽을 때마다 같은 혼동이 재발하며 자동 대조가 어렵다. |

### 추천

**A 추천.** 파일명은 유지하고 A01–A06부터 공식 `node_id`를 추가한다. 공식 ID는 `master-toc.md`만 기준으로 삼고, 파일 번호는 필요한 경우에만 “파일 05 = A05”처럼 설명용 별칭으로 표시한다.

### 영향과 Gate 연계

Lesson의 frontmatter·Next, Practice 연결, route, Quiz/Outcome, PM Docs 예시가 모두 영향을 받는다. ID 적용만으로 품질 Gate를 통과하는 것은 아니며, 적용 후 전체 downstream 대조와 재검토가 완료되어야 Gate의 검토 범위를 확정할 수 있다.

### 결정 요청

`2번: A / B / C 중 ___`를 선택하고, 학생 화면에도 공식 ID를 표시할지와 파일 번호 별칭 허용 범위를 함께 정해 달라.

## 3. 원본 수정 범위

### 문제

검토·개선안 보고서는 누적되었지만 PM Docs 4종은 제안만 있고 원본 반영 후 재검토가 없다. Practice도 B07/B08은 개선안만 적용 전이며, B05/B06/B09와 공식 Lesson 범위의 후속 검토가 남아 있다. 모든 개선안을 한 번에 반영하면 현재 Gate의 문서·콘텐츠·P0 경계가 넓어진다.

### 옵션

| 옵션 | 장점 | 단점 |
|---|---|---|
| **A. HIGH 우선순위만 반영** | 상태 사전·핵심 PM Docs부터 빠르게 정리할 수 있다. | ID 정합성과 Practice 실행 증거 등 Gate 차단 요소가 남을 수 있다. |
| **B. 모든 개선안 반영** | 누적된 지적사항을 한 번에 처리한다. | 범위·검증량·P0 오염 위험이 가장 크고, 무엇이 Gate 필수인지 흐려진다. |
| **C. Gate 진입 필수 항목만 반영** | 현재 Gate의 목적과 변경 허용 범위를 가장 잘 통제한다. | 선택하지 않은 개선안은 별도 backlog로 남고, 후속 우선순위 관리가 필요하다. |

### 추천

**C 추천.** 최소 승인 범위는 (1) 선택된 상태 사전과 PM Docs/Interface의 권위 관계 동기화, (2) 공식 ID·metadata·downstream 연결 대조, (3) B07/B08 실행형 Practice 개선과 독립 검증이다. B05/B06/B09, 공식 Lesson 범위, B08 Sample Project 확장은 별도 범위로 명시하고 자동 포함하지 않는다. 소스 코드와 P0 콘텐츠는 이 요청서의 범위에 포함하지 않는다.

### 영향과 Gate 연계

선택 범위가 다음 작업의 파일 allowlist, 검증 명령, 독립 리뷰 범위를 결정한다. 원본 반영 후 링크·상태·ID·학생 can-do·a11y·static export 경계를 다시 확인해야 하며, 그 전에는 “개선 완료” 또는 품질 완료로 표시할 수 없다.

### 결정 요청

`3번: A / B / C 중 ___`를 선택하고, C인 경우 Gate 필수 목록에서 제외하거나 추가할 항목을 적어 달라.

## 4. Track D 재개 여부

### 문제

현재 준비도는 C등급/조건부 미준비다. `master-toc.md`와 인수인계 문서는 Track D를 `paused`로 유지하며, D01 시작을 운영자의 `CONTINUE_TRACK_D` 또는 잔여 사항 수락 이후로 제한한다. 따라서 현재 분석만으로 Track D를 재개하거나 V2 후보를 활성화할 수 없다.

### 옵션

| 옵션 | 장점 | 단점 |
|---|---|---|
| **A. Track D 유지 + 조건 충족 후 진행** | 기존 학습 경로와 투자 방향을 보존하면서 품질 조건을 지킬 수 있다. | 조건 충족 전에는 D01을 시작할 수 없어 즉시 진도는 나가지 않는다. |
| **B. Track D 일시 중단 + 다른 우선 작업** | 현재 차단 요소를 정리하는 데 집중할 수 있다. | Track D 재개 시점과 우선순위를 다시 조정해야 한다. |
| **C. Track D 포기** | 운영 리소스를 다른 방향에 완전히 집중할 수 있다. | 기존 Track 방향과 후속 연결을 폐기하는 결정이며 영향이 가장 크다. |

### 추천

**A 추천.** Track D 자체는 유지하되, 운영 상태는 당분간 `paused`로 둔다. 1–3번 결정 기록, 승인 범위 적용, ID/downstream 재검토, Practice/Lesson 잔여 범위 수락, 독립 리뷰가 끝난 뒤에만 `CONTINUE_TRACK_D`를 사용한다.

### 영향과 Gate 연계

이 결정은 D01 시작, Track D 상태 신호, V2 후보 노출, 후속 작업자의 우선순위를 통제한다. A를 선택해도 현재 Gate가 자동 통과되는 것은 아니며, 조건을 충족한 뒤 별도 Gate 판정을 받아야 한다.

### 결정 요청

`4번: A / B / C 중 ___`를 선택해 달라. A라면 재개 조건을 위 조건 그대로 수락할지, 추가 조건이 있는지 적어 달라.

## 5. Branch 정리

### 문제

읽기 시점의 실제 branch는 `feat/community-goose-01`이지만 `STATE.md`의 Branch/HEAD 기록은 `master`다. 작업 트리에는 소스·콘텐츠·설정·보고서가 섞인 변경이 있으며, 작업 시작 시점 `git status` 기준으로 수정 117개, 미추적 52개, staged 추가 1개가 확인됐다. 변경 소유권과 기준점을 먼저 정하지 않으면 보고서 커밋에 unrelated 또는 P0 변경이 섞일 수 있다.

### 옵션

| 옵션 | 장점 | 단점 |
|---|---|---|
| **A. 보고서만 커밋** | 이번 결정 요청의 범위를 가장 작게 유지하고 소스/P0 오염을 피할 수 있다. | 기존 dirty 변경과 branch/STATE 불일치는 별도 정리해야 한다. |
| **B. 전체 커밋** | 현재 작업물을 하나의 기준점으로 고정할 수 있다. | 소유자가 불명확한 소스·P0·설정 변경까지 함께 확정될 위험이 크다. |
| **C. 새 branch 생성** | 이후 작업을 별도 흐름으로 분리할 수 있다. | 현재 dirty tree의 분류·소유권·커밋 문제를 해결하지 않으며, 잘못된 변경도 새 branch에 따라간다. |

### 추천

**A 추천.** 운영자가 소유권을 확인한 보고서의 정확한 경로만 별도 커밋하고, 기존 소스·P0·untracked 변경은 커밋·삭제·정리하지 않는다. branch/STATE 기준점과 나머지 변경 소유권은 별도 inventory로 확정한 뒤 후속 작업을 시작한다.

### 영향과 Gate 연계

Branch 기준점과 dirty tree 소유권이 확정되어야 이후 Gate 결과가 어떤 작업물에 적용되는지 재현할 수 있다. B를 선택하면 커밋 전 전체 diff와 P0/보호 경로 검토가 필수이고, C를 선택해도 새 branch의 기준 commit과 잔여 dirty 목록을 기록해야 한다. 이번 문서 작성에서는 어떠한 커밋도 수행하지 않았다.

### 결정 요청

`5번: A / B / C 중 ___`를 선택하고, 커밋 대상 보고서 경로 또는 새 branch 이름을 지정해 달라.
