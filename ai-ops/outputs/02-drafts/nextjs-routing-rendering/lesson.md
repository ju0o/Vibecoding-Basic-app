## 한 줄 정의

Next.js의 라우팅·렌더링 모델은 **파일 시스템으로 URL 구조를 정의**하고(App Router), **서버 컴포넌트를 기본값**으로 서버와 클라이언트에 렌더링을 나누어 배치하는 구조입니다.

React가 "화면을 어떻게 조립하는가"를 답한다면, Next.js는 두 가지 질문을 더 답합니다 — 그 컴포넌트가 **어떤 URL에서**(라우팅), 그리고 **어느 환경에서**(서버/클라이언트 렌더링) 실행되는가. 이 강의는 두 축을 각각 파고든 뒤, ==파일의 위치와 파일 안의 지시어가 곧 아키텍처 결정==이라는 App Router의 사고방식으로 통합합니다. 기준 버전은 Next.js 16(문서 v16.2.10, 2026-06 갱신)입니다.

> [!KEY]
> 지금 읽고 있는 이 사이트가 곧 실습 예제입니다 — `app/lessons/[slug]/page.tsx` 파일 하나가 51개 강의 페이지 전부를 만들고, 페이지는 서버 컴포넌트로 렌더링됩니다. 이 강의를 읽고 나면 이 사이트의 폴더 구조를 열어 직접 확인할 수 있습니다.

## 왜 존재하는가

React만으로 여러 페이지의 앱을 만들면 두 가지 문제를 스스로 해결해야 합니다.

첫째, **라우팅이 없습니다.** React는 화면 조립 라이브러리이지 URL 관리자가 아닙니다. "어떤 주소에 어떤 컴포넌트를 보여줄까"를 별도 라이브러리와 설정 파일로 직접 연결해야 했고, 프로젝트마다 그 방식이 달랐습니다. Next.js는 이 설정을 **관례로 대체**했습니다 — 폴더가 URL 경로가 되고, `page` 파일이 그 경로의 화면이 됩니다. 설정 파일을 읽지 않아도 폴더 구조가 곧 사이트 지도입니다.

둘째, **모든 것이 클라이언트에서 실행됩니다.** 순수 React 앱은 빈 HTML에 JavaScript를 내려보내 브라우저에서 화면을 조립합니다. 그 결과 첫 화면이 늦고, 데이터를 가져오는 코드와 API 키까지 브라우저에 노출될 위험이 생깁니다. Next.js의 답이 서버 컴포넌트 기본값입니다 — 공식 문서 표현으로, 기본 상태의 레이아웃과 페이지는 서버에서 데이터를 가져와 UI를 렌더링하고, 결과를 캐시하고, 클라이언트로 스트리밍할 수 있습니다. 브라우저로 보내는 JavaScript 양을 줄이는 것이 문서가 명시하는 서버 컴포넌트의 사용 이유 중 하나입니다.

## 작동 원리

### 라우팅: 폴더 = URL 세그먼트

`app` 디렉터리 아래의 폴더 하나가 URL 세그먼트 하나에 대응합니다. `app/lessons/page.tsx`는 `/lessons`가 되고, 폴더를 중첩하면 경로도 중첩됩니다. 여기에 두 가지 특수 관례가 얹힙니다.

**layout** — 여러 페이지가 공유하는 UI입니다. 핵심 성질은 내비게이션 시의 동작에 있습니다: 페이지를 오가도 레이아웃은 상태를 유지하고, 상호작용을 유지하며, 다시 렌더링되지 않습니다. 이 사이트의 헤더·검색창이 페이지를 옮겨도 초기화되지 않는 이유입니다. 루트 레이아웃은 필수이며 `html`·`body` 태그를 포함해야 합니다.

**동적 세그먼트** — 폴더명을 대괄호로 감싸면(`[slug]`) 하나의 파일이 데이터 기반으로 여러 페이지를 만듭니다. `params`로 현재 값을 받아(Next.js 16 기준 Promise라 `await` 필요) 해당 데이터를 렌더링합니다.

### 렌더링: 두 환경, 하나의 트리

App Router의 렌더링은 "서버 아니면 클라이언트"의 양자택일이 아니라 **한 트리 안에서의 분업**입니다.

1. **서버에서**: 서버 컴포넌트들이 렌더링되어 **RSC Payload**라는 형식이 됩니다 — 공식 정의로는 "렌더링된 React 서버 컴포넌트 트리의 압축된 이진 표현". 여기에 클라이언트 컴포넌트가 렌더링될 자리 표시와 그 JS 파일 참조, 서버에서 클라이언트로 전달되는 props가 담깁니다.
2. **클라이언트 첫 로드에서**: HTML이 먼저 도착해 즉시 (아직 상호작용 없는) 화면을 보여주고, RSC Payload로 서버/클라이언트 트리를 맞춘 뒤, JavaScript가 **하이드레이션**을 수행합니다 — 정적 HTML에 이벤트 핸들러를 붙여 상호작용을 살리는 React의 절차입니다.
3. **이후 내비게이션에서**: RSC Payload가 미리 가져와져(prefetch) 즉시 전환되고, 클라이언트 컴포넌트는 서버 HTML 없이 클라이언트에서 렌더링됩니다.

### 경계 선언: "use client"

파일 상단의 `"use client"` 지시어가 서버 모듈 그래프와 클라이언트 모듈 그래프의 **경계**를 선언합니다. 중요한 것은 전파 규칙입니다: ==경계 파일이 import하는 모든 것과 직접 렌더링하는 컴포넌트가 전부 클라이언트 번들에 포함됩니다==. 그래서 모든 파일에 지시어를 붙일 필요가 없는 동시에, 경계를 너무 높은 곳(레이아웃 전체 등)에 그으면 트리 전체가 클라이언트로 끌려갑니다.

단, children으로 **전달되는** 서버 컴포넌트는 예외입니다 — import가 아니라 렌더링된 결과로 전달되므로 서버에 남습니다. 이것이 "클라이언트 모달 안에 서버 렌더링된 장바구니" 같은 인터리빙 패턴의 원리입니다.

> [!EXAMPLE]
> 이 사이트의 실제 분업: 강의 본문(마크다운 렌더링)은 서버 컴포넌트가 처리해 HTML로 도착하고, 진행률 완료 버튼·검색창·비밀번호 게이트만 `"use client"` 파일입니다. 51강의 본문 텍스트는 클라이언트 번들에 JS로 실려 오지 않습니다.

## 스펙과 세부

### 정적 vs 동적 렌더링의 분기점

같은 서버 컴포넌트라도 **언제** 렌더링되는지가 갈립니다 — 빌드 시(정적) 또는 요청 시(동적). 분기는 코드가 요청 정보를 필요로 하는가로 결정됩니다. 공식 문서의 예: `searchParams`를 사용하면 그 페이지는 동적 렌더링으로 전환됩니다 — 검색 파라미터를 읽으려면 실제 들어온 요청이 필요하기 때문입니다. 요청과 무관한 페이지는 빌드 시 HTML로 미리 만들어둘 수 있고, 이 사이트가 바로 그 경우입니다(51강 전부 빌드 시 생성 — `output: "export"` 정적 내보내기).

### 파일 관례 요약

| 파일/폴더 | 역할 |
|---|---|
| `app/경로/page.tsx` | 그 URL의 화면 — "A page is UI that is rendered on a specific route" |
| `app/경로/layout.tsx` | 하위 페이지들의 공유 UI (중첩 가능, 내비게이션 시 유지) |
| `app/[param]/` | 동적 세그먼트 — 데이터 개수만큼 페이지 생성 |
| `"use client"` (파일 첫 줄) | 이 파일부터 클라이언트 모듈 그래프 시작 |

### 환경 오염 방지 장치

서버 전용 코드가 클라이언트로 새는 것을 막는 규칙이 스펙에 내장되어 있습니다. 환경변수는 `NEXT_PUBLIC_` 접두사가 붙은 것만 클라이언트 번들에 포함되고, 나머지는 빈 문자열로 대체됩니다 — API 키가 든 모듈을 실수로 클라이언트에서 import해도 키 자체는 새지 않습니다. 더 강한 장치로 `server-only` 패키지를 import해 두면 클라이언트에서의 import가 **빌드 오류**가 됩니다. props로 서버→클라이언트에 데이터를 넘길 때는 직렬화 가능해야 한다는 제약도 있습니다.

### 페이지 간 이동: Link

내비게이션에는 HTML `<a>`를 확장한 `<Link>` 컴포넌트를 씁니다 — 프리페칭과 클라이언트 사이드 내비게이션이 얹혀, 레이아웃 유지 규칙과 결합해 페이지 전환이 전체 새로고침 없이 이루어집니다.

### 컨텍스트의 제약

React context는 서버 컴포넌트에서 지원되지 않습니다. 전역 테마 같은 컨텍스트가 필요하면 children을 받는 클라이언트 컴포넌트 provider를 만들어 서버 레이아웃에서 감싸는 패턴을 씁니다 — 이때 provider를 가능한 트리 깊은 곳에 두어야 정적 최적화가 살아납니다.

## 원문으로 읽기

> "Next.js uses file-system based routing, meaning you can use folders and files to define routes."
>
> — Next.js는 파일 시스템 기반 라우팅을 사용한다. 즉 폴더와 파일로 라우트를 정의할 수 있다.
> [Layouts and Pages — Next.js Docs](https://nextjs.org/docs/app/getting-started/layouts-and-pages)

문서의 첫 문장이 라우팅 모델 전부의 요약입니다. "설정할 수 있다"가 아니라 "폴더와 파일로 정의한다" — 라우팅이 코드가 아닌 구조의 문제가 되면서, 프로젝트 폴더를 여는 것만으로 사이트 지도를 읽을 수 있게 됩니다.

> "A layout is UI that is shared between multiple pages. On navigation, layouts preserve state, remain interactive, and do not rerender."
>
> — 레이아웃은 여러 페이지가 공유하는 UI다. 내비게이션 시 레이아웃은 상태를 보존하고, 상호작용을 유지하며, 다시 렌더링되지 않는다.
> [Layouts and Pages — Next.js Docs](https://nextjs.org/docs/app/getting-started/layouts-and-pages)

두 번째 문장의 세 동사(보존·유지·재렌더링 안 함)가 레이아웃의 존재 이유입니다. 페이지마다 헤더를 다시 그리는 낭비를 없애는 동시에, 입력 중이던 검색어 같은 상태가 페이지 이동에도 살아남는 사용자 경험을 관례 하나로 제공합니다.

> "By default, layouts and pages are Server Components, which lets you fetch data and render parts of your UI on the server, optionally cache the result, and stream it to the client."
>
> — 기본적으로 레이아웃과 페이지는 서버 컴포넌트이며, 덕분에 서버에서 데이터를 가져와 UI 일부를 렌더링하고, 선택적으로 결과를 캐시하고, 클라이언트로 스트리밍할 수 있다.
> [Server and Client Components — Next.js Docs](https://nextjs.org/docs/app/getting-started/server-and-client-components)

"By default"가 이 문장의 무게중심입니다 — 서버 렌더링이 옵션이 아니라 기본값이라는 뜻이고, 개발자가 명시적으로 선언해야 하는 쪽은 클라이언트입니다. 프레임워크의 기본값 설계는 곧 권장 아키텍처의 표명입니다: 가능한 한 서버에 두고, 필요한 만큼만 클라이언트로.

> "Hydration is React's process for attaching event handlers to the DOM, to make the static HTML interactive."
>
> — 하이드레이션은 정적 HTML을 상호작용 가능하게 만들기 위해 DOM에 이벤트 핸들러를 붙이는 React의 절차다.
> [Server and Client Components — Next.js Docs](https://nextjs.org/docs/app/getting-started/server-and-client-components)

"서버에서 렌더링했다면서 왜 JS가 또 필요하지?"라는 흔한 의문의 공식 답입니다. HTML은 화면을 보여주지만 클릭에 반응하지 못합니다 — 하이드레이션이 그 정적 화면에 생명(핸들러)을 불어넣는 두 번째 단계이며, 첫 화면이 빠르되 상호작용은 약간 늦게 도착하는 SSR 특유의 체감이 여기서 나옵니다.

## 실전에서

### AI에게 Next.js 작업을 시킬 때의 검토 축

AI가 만든 Next.js 코드에서 가장 자주 깨지는 것이 바로 이 강의의 두 축입니다. 검토 질문을 두 개로 고정하세요: **"이 파일의 위치가 의도한 URL인가?"**(라우팅), **"이 파일의 환경이 이 코드와 맞는가?"**(렌더링). 구체적 위반 신호:

- 서버 컴포넌트에 `useState`/`onClick` — 즉시 오류. 상호작용 조각만 분리해 `"use client"`를 붙이도록 요청
- `"use client"` 파일이 무거운 트리를 통째로 import — 번들 비대. 경계를 잎(leaf) 쪽으로 내리도록 요청
- API 키가 든 모듈을 클라이언트 파일에서 import — `server-only` 패키지로 빌드 차단을 걸어두면 AI의 실수가 자동으로 잡힘

### 경계를 좁게 긋는 연습

문서의 권장 패턴 그대로: 레이아웃은 서버에 두고, 그 안의 검색바만 클라이언트로. 이 사이트의 `SiteHeader`(서버) 안 검색창(클라이언트) 구조가 실물 예시입니다. "일단 전부 use client"는 동작하지만, 서버 컴포넌트 기본값이 주는 이점(번들 축소, 비밀 보호, 서버 데이터 접근)을 전부 반납하는 선택입니다.

> [!TIP]
> 어떤 컴포넌트를 클라이언트로 만들지 고민될 때 문서의 기준을 그대로 쓰세요 — 상태·이벤트 핸들러·생명주기 로직·브라우저 API·커스텀 훅이 필요하면 클라이언트, 데이터 페칭·비밀 사용·번들 축소가 목적이면 서버입니다.

### 정적 내보내기라는 선택지

서버 없이 배포하고 싶다면 `output: "export"`로 전 페이지를 빌드 시 HTML로 만들 수 있습니다 — 이 사이트가 Firebase 정적 호스팅에 올라가는 방식입니다. 대가는 요청 시 기능(동적 렌더링, 서버 미들웨어)의 포기이며, 이 사이트의 비밀번호 게이트가 서버 미들웨어 대신 클라이언트 컴포넌트인 이유가 정확히 이 트레이드오프입니다.

## 한계와 트레이드오프

**관례는 배우기 전엔 마법처럼 보입니다.** 파일 이름(page, layout)과 폴더 규칙([slug])을 모르면 "코드 어디에도 라우트 설정이 없는데 왜 동작하지?"가 됩니다. 설정의 명시성을 관례의 간결함과 맞바꾼 것 — 팀에 새 사람이 오면 관례부터 공유해야 합니다.

**서버/클라이언트 분리는 인지 비용을 요구합니다.** 한 트리 안에 두 실행 환경이 섞이므로, "이 코드는 지금 어디서 도는가"를 항상 의식해야 합니다. context 미지원, props 직렬화 제약, 환경변수 접두사 규칙이 전부 이 분리에서 파생된 규칙들입니다.

**하이드레이션은 공짜가 아닙니다.** 서버가 HTML을 미리 만들어도, 상호작용을 위해 클라이언트 컴포넌트의 JS는 결국 내려받아 실행됩니다. 서버 컴포넌트의 이점은 "JS 제로"가 아니라 "필요한 부분만 JS" — 그래서 경계를 좁게 긋는 습관이 성능과 직결됩니다.

**프레임워크 종속은 실재하는 비용입니다.** 파일 관례, RSC Payload, 캐싱 동작은 Next.js의 결정이며 React 표준이 아닙니다. 개념(서버 렌더링, 하이드레이션)은 이식되지만 관례는 프레임워크를 바꾸면 다시 배워야 합니다 — 이 강의가 관례보다 원리 설명에 무게를 둔 이유입니다.

> [!WARNING]
> "use client"를 파일 맨 위가 아닌 곳에 두거나, 서버 컴포넌트를 클라이언트 파일에서 직접 import하면(children 전달이 아니라) 의도치 않게 서버 코드가 클라이언트 그래프로 편입됩니다. 경계 선언은 항상 파일 첫 줄, 서버 조각의 전달은 항상 props/children으로.
