## 오늘 배울 것

프롬프트 한 번으로 AI에게 일을 시키는 방식이 왜 한계에 부딪히는지 배웁니다.

그리고 그 한계를 넘기 위해 등장한 AI 시스템 설계의 구성요소 지도를 그립니다. 이 지도는 이번 모듈 전체의 안내판이 됩니다.

## 한 줄 정의

AI 시스템 설계는 일회성 프롬프트 대신, AI가 안정적으로 일하도록 컨텍스트(재료), 도구 연결, 재사용 절차, 검증 장치를 갖춘 구조를 만드는 일입니다.

## 쉬운 비유

지나가는 사람에게 "저기 가서 커피 좀 사다 주세요"라고 부탁하는 것과, 새 직원을 온보딩하는 것의 차이를 생각해봅시다.

부탁 한마디는 그때그때 결과가 다릅니다. 어떤 날은 원하는 커피가 오고, 어떤 날은 엉뚱한 것이 옵니다. 반면 온보딩은 업무 문서, 사용할 도구, 일하는 절차, 보고 규칙까지 갖춰줍니다. 그러면 누가 그 자리에 와도 일정한 품질이 나옵니다.

다만 다른 점이 있습니다. 사람은 한 번 배우면 기억하지만, AI는 대화가 끝나면 기억이 사라집니다. 그래서 사람보다 AI에게 "매번 다시 주어지는 시스템"이 훨씬 더 중요합니다.

## 왜 생겼는가

초기의 AI 활용은 질문 한 번, 답변 한 번이었습니다. 이때는 프롬프트 문장을 잘 다듬는 것(Prompt Engineering)으로 충분했습니다.

그런데 AI가 파일을 읽고, 명령을 실행하고, 결과를 확인하며 여러 단계를 스스로 진행하는 에이전트로 발전했습니다. Anthropic은 에이전트를 "루프 안에서 자율적으로 도구를 사용하는 LLM"이라고 정의합니다. 여기서 LLM은 대형 언어 모델로, ChatGPT나 Claude 같은 AI 서비스의 기반 기술입니다. 단계가 반복될수록 대화에 쌓이는 정보가 늘어나는데, 연구에 따르면 컨텍스트가 길어질수록 모델이 그 안의 정보를 정확히 기억해내는 능력은 오히려 떨어집니다(context rot). 문장 하나를 잘 쓰는 기술만으로는 이 상황을 관리할 수 없게 된 것입니다.

## 어떤 문제를 해결하는가

- 같은 요청인데 매번 결과가 달라지는 비일관성을 줄입니다.
- 매번 처음부터 배경을 다시 설명하는 비용을 없앱니다.
- 그럴듯하지만 틀린 결과가 그대로 통과되는 것을 검증 단계로 막습니다.
- 외부 도구를 쓸 때마다 연결 방법을 새로 만드는 중복을 없앱니다.

## 핵심 개념

시스템의 구성요소는 다섯 가지로 나눌 수 있습니다. 각각이 이번 모듈의 강의 하나씩과 이어집니다.

첫째, 재료(컨텍스트)입니다. 시스템 프롬프트, 도구, 예시, 대화 이력처럼 AI가 판단에 쓰는 모든 정보입니다. 이 재료를 설계하는 일이 Context Engineering입니다.

둘째, 도구 연결입니다. AI가 파일, 데이터베이스, 외부 서비스와 대화하려면 연결 방법이 필요합니다. MCP는 이 연결을 표준화한 오픈소스 규약으로, 공식 문서는 "AI 애플리케이션의 USB-C 포트"라고 비유합니다.

셋째, 재사용 절차(Skill)입니다. 같은 지시나 체크리스트를 반복해서 붙여넣게 될 때, 그 절차를 파일로 저장해 재사용하는 방식입니다.

넷째, 작업 흐름입니다. 진행 경로를 미리 코드로 정해두면 Workflow, AI가 경로와 도구 사용을 스스로 결정하면 Agent라고 구분합니다.

다섯째, 검증입니다. 성과를 측정하고 반복 개선하는 장치가 없으면 시스템은 그럴듯한 결과를 대량 생산하는 기계가 됩니다.

## 실제 예시

"강의 검색 기능 만들어줘"라는 한 줄 요청을 생각해봅시다. AI는 데이터가 어디 있는지, 화면 어디에 붙는지, 무엇이 완성인지 전부 추측해야 합니다.

시스템 관점으로 바꾸면 이렇게 됩니다. 검색 대상 데이터 파일과 디자인 규칙을 함께 주고(재료), 프로젝트 파일을 직접 읽게 하고(도구), "UI 변경 후 모바일 화면을 확인한다"는 저장된 절차를 따르게 하고(절차), 마지막에 테스트 명령을 실행해 통과 여부를 확인합니다(검증). 같은 요청이라도 추측이 사라지고 결과가 안정됩니다.

## 코드 예시

한 줄 프롬프트와 구조화된 작업 명세의 차이를 타입으로 표현해봤습니다.

```ts
// 이전: 모든 것을 AI의 추측에 맡기는 요청
const request = "강의 검색 기능 만들어줘"

// 이후: 시스템의 부품이 되는 작업 명세
type TaskSpec = {
  readonly goal: string          // 무엇을 만들 것인가
  readonly materials: string[]   // 참고할 파일과 규칙 (재료)
  readonly steps: string[]       // 따라야 할 절차
  readonly doneWhen: string[]    // 무엇이 통과되면 완성인가 (검증)
}

const task: TaskSpec = {
  goal: "강의 제목과 요약을 검색하는 기능",
  materials: ["src/content/curriculum.ts", "기존 검색 UI 스타일"],
  steps: ["데이터 구조 확인", "검색 로직 작성", "빈 결과 화면 처리"],
  doneWhen: ["npm run verify 통과", "모바일 화면 확인"],
}
```

## AI 시대에서의 의미

바이브코딩에서 실력 차이는 프롬프트 문장력보다 시스템을 축적하는 습관에서 벌어집니다. 요청 한 번을 잘하는 사람은 그 순간만 좋은 결과를 얻지만, 재료와 절차와 검증을 파일로 쌓는 사람은 다음 요청부터 점점 적게 말하고 점점 좋은 결과를 얻습니다. 이번 모듈의 나머지 강의는 이 다섯 부품을 하나씩 만드는 방법을 다룹니다.

## 자주 헷갈리는 것

프롬프트 엔지니어링과 시스템 설계는 대립하지 않습니다. 좋은 프롬프트는 시스템의 부품이지 대체재가 아닙니다. 프롬프트 공식 가이드조차 "성공 기준을 먼저 정의하고 검증 방법을 갖추라"고 시작합니다.

Workflow와 Agent도 자주 섞입니다. 경로를 사람이 미리 정하면 Workflow, AI가 스스로 정하면 Agent입니다.

마지막으로 "시스템 = 복잡한 것"이라는 오해가 있습니다. 공식 권고는 정반대로, 가장 단순한 방법에서 시작해 필요할 때만 복잡성을 높이라는 것입니다.

## 실무에서 쓰는 방식

실무에서는 단일 요청 최적화로 충분한 일에 에이전트 시스템을 만들지 않습니다. Anthropic 가이드도 "단일 LLM 호출 최적화만으로 충분한 경우가 많다"고 말합니다.

대신 반복되는 신호를 관찰합니다. 같은 설명을 세 번째 붙여넣고 있다면 재료 파일로, 같은 절차를 반복하고 있다면 Skill로, 같은 실수를 반복해서 잡고 있다면 검증 단계로 승격시킵니다. 지금 보고 있는 이 사이트도 강의 생산을 리서치, 집필, 검증, 반영 단계로 나눈 파이프라인으로 만들어지고 있습니다.

## 공부 체크리스트

- 일회성 프롬프트 방식의 한계 두 가지를 예를 들어 설명한다.
- AI 시스템의 다섯 구성요소(재료, 도구 연결, 절차, 흐름, 검증)를 말한다.
- Workflow와 Agent의 차이를 한 문장으로 구분한다.
- "단순하게 시작하라"는 권고가 왜 시스템 설계와 모순되지 않는지 설명한다.
