## 오늘 배울 것

오늘은 Context Engineering이 무엇인지, 왜 단순한 프롬프트 작성보다 넓은 개념인지 배웁니다.

핵심은 AI에게 더 많은 자료를 넣는 법이 아닙니다. AI가 매 순간 판단에 쓸 목표, 제약, 파일, 로그, 도구 결과를 어떻게 선별하고 유지할지 배우는 강의입니다.

## 한 줄 정의

Context Engineering은 모델 추론 시점에 들어갈 정보 묶음을 설계·선별·유지하는 작업입니다.

여기서 컨텍스트는 AI가 답을 만들 때 함께 받는 토큰 묶음입니다. 시스템 지시, 대화 이력, 도구 정의, 도구 결과, 외부 데이터가 모두 컨텍스트가 될 수 있습니다.

## 쉬운 비유

회의를 잘하려면 참석자에게 모든 회사 문서를 던져주는 것이 아니라, 오늘 안건과 필요한 자료만 정리해서 줍니다.

Context Engineering도 같습니다. AI에게 모든 파일과 로그를 한꺼번에 주면 안전해 보이지만, 실제로는 중요한 신호가 묻힙니다. 좋은 회의 자료처럼 목표, 배경, 제약, 판단 기준만 선명하게 남겨야 합니다.

다만 회의 자료와 다른 점도 있습니다. AI의 컨텍스트 창은 유한한 작업 메모리라서, 긴 작업을 반복할수록 오래된 대화와 도구 결과가 창을 차지합니다. 그래서 한 번 정리하는 일이 아니라 매 턴 다시 정리하는 일이 됩니다.

## 왜 생겼는가

Anthropic은 2025년 9월 29일 Context Engineering을 Prompt Engineering의 자연스러운 확장으로 설명했습니다. Prompt Engineering이 지시문을 잘 쓰는 일에 가깝다면, Context Engineering은 추론 시점에 들어가는 전체 정보 상태를 관리하는 일입니다.

이 개념은 장기 실행 에이전트 때문에 중요해졌습니다. 에이전트는 한 번 답하고 끝나지 않고, 도구를 호출하고 결과를 받아 다시 판단합니다. 이 과정에서 시스템 지시, 메시지, 도구 결과, 파일 내용이 계속 누적되기 때문에 단일 프롬프트만 잘 써서는 안정적인 결과를 만들기 어렵습니다.

## 어떤 문제를 해결하는가

첫 번째 문제는 컨텍스트가 유한하다는 점입니다. Claude 문서는 컨텍스트 창을 모델이 응답을 만들 때 참조할 수 있는 작업 메모리로 설명합니다. 이 창에는 시스템 프롬프트, 메시지, 문서, 도구 정의, 도구 결과가 함께 들어갑니다.

두 번째 문제는 정보가 많을수록 항상 좋은 것이 아니라는 점입니다. Anthropic은 토큰 수가 늘어날수록 정확도와 회상이 떨어지는 현상을 context rot으로 설명합니다. 그래서 Context Engineering은 "많이 넣기"가 아니라 "필요한 것을 남기기"의 문제를 해결합니다.

## 핵심 개념

첫째, 컨텍스트는 모델이 샘플링할 때 포함되는 토큰 집합입니다. 토큰은 AI가 처리하는 글자 조각 단위입니다. 우리가 파일, 대화, 규칙을 많이 넣을수록 이 토큰 예산을 사용합니다.

둘째, 시스템 프롬프트는 원하는 행동을 분명히 제시해야 합니다. 하지만 복잡하고 깨지기 쉬운 조건문 목록이나 모호한 일반론만 쌓으면 오히려 행동 기준이 흐려질 수 있습니다.

셋째, 도구 정의도 컨텍스트입니다. 도구는 에이전트와 정보·행동 공간 사이의 계약이므로, 어떤 도구를 언제 써야 하는지 명확해야 합니다. 겹치는 도구가 많으면 AI가 어느 도구를 쓸지 헷갈립니다.

넷째, 예시는 예외를 끝없이 나열하는 방식보다 대표 행동 패턴을 보여주는 방식으로 골라야 합니다. 예시는 AI가 따라 할 기준이 되므로, 적은 수라도 신호가 분명해야 합니다.

다섯째, 긴 세션에서는 compaction, context editing, 상태 산출물이 필요합니다. compaction은 긴 대화를 핵심 상태로 압축하는 일입니다. 상태 산출물은 현재 목표, 수정 파일, 테스트 결과처럼 다음 턴에 복구해야 할 정보를 작게 남기는 방식입니다.

## 실제 예시

장기 리팩터링 세션을 생각해봅시다. 처음에는 "결제 모듈을 정리해 주세요"라고 말할 수 있습니다. 하지만 작업이 길어지면 수정한 파일, 실패한 테스트, 남은 위험, 사용자 제약이 계속 쌓입니다.

Context Engineering 방식으로는 이 정보를 작은 상태 문서로 유지합니다. 오래된 로그 전문은 계속 넣지 않고 요약합니다. 현재 목표와 다음 행동만 남기면 AI가 다음 턴에서 다시 방향을 잡을 수 있습니다.

## 코드 예시

아래 코드는 AI에게 보낼 컨텍스트를 작은 패킷으로 정리하는 예시입니다.

```ts
type ContextPacket = {
  goal: string
  constraints: string[]
  evidence: Array<{ claim: string; sourceUrl: string }>
  nextAction: string
}

const packet: ContextPacket = {
  goal: "검색 UI의 빈 결과 상태를 점검합니다",
  constraints: ["기존 디자인 패턴 유지", "모바일 화면에서 줄바꿈 확인"],
  evidence: [{ claim: "검색 대상은 강의 제목과 요약입니다", sourceUrl: "KB" }],
  nextAction: "관련 컴포넌트와 테스트 결과만 컨텍스트에 넣습니다",
}

console.log(`${packet.goal} -> ${packet.nextAction}`)
```

## AI 시대에서의 의미

바이브코딩에서 Context Engineering은 "AI에게 더 길게 설명하기"가 아닙니다. 목표, 제약, 파일, 로그, 검증 기준, 도구 결과를 매 작업 턴에 맞게 정리하는 일입니다.

큰 로그나 파일 전체를 계속 넣으면 컨텍스트가 빠르게 커집니다. 그래서 좋은 작업자는 AI에게 모든 것을 기억시키려 하기보다, 회복 가능한 상태와 체크리스트를 남겨 다음 턴의 판단 재료를 작게 만듭니다.

## 자주 헷갈리는 것

Prompt Engineering과 Context Engineering은 같은 말이 아닙니다. Prompt Engineering은 지시 작성에 초점이 있고, Context Engineering은 추론 시점의 전체 정보 상태를 다룹니다.

컨텍스트는 길수록 좋은 것도 아닙니다. 더 큰 컨텍스트가 자동으로 더 나은 결과를 뜻하지 않으며, 토큰이 늘어나면 정확도와 회상이 떨어질 수 있습니다.

도구를 많이 붙이면 좋은 것도 아닙니다. 도구 정의도 컨텍스트를 차지하므로, 현재 작업에 필요한 도구만 명확하게 노출해야 합니다.

## 실무에서 쓰는 방식

실무에서는 작업 시작 전에 목표, 제약, 근거, 다음 행동을 분리합니다. 진행 중에는 오래된 로그를 요약하고, 실패한 테스트와 남은 위험처럼 다음 판단에 필요한 정보만 남깁니다.

도구가 많은 에이전트에서는 모든 도구를 한 번에 넣지 않습니다. 현재 작업에 필요한 도구만 노출하고, 도구 설명은 겹치지 않게 씁니다. RAG 기반 교재 사이트라면 검색 결과를 그대로 붙이지 않고 출처, 핵심 주장, 사용할 섹션을 나누어 전달합니다.

## 공부 체크리스트

- Context Engineering을 "추론 시점 정보 상태 관리"라고 설명할 수 있다.
- 컨텍스트가 길수록 항상 좋은 것이 아닌 이유를 말할 수 있다.
- 시스템 프롬프트, 도구 정의, 대화 이력이 모두 컨텍스트를 소비한다는 점을 설명할 수 있다.
- 긴 AI 작업에서 compaction과 상태 산출물이 필요한 이유를 예로 들 수 있다.
