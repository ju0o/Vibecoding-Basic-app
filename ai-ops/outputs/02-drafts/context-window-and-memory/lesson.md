## 오늘 배울 것

오늘은 컨텍스트 윈도와 메모리 관리를 배웁니다. 컨텍스트 윈도는 AI가 답을 만들 때 참고할 수 있는 작업 메모리이고, 이 창에는 시스템 지시, 메시지, 문서, 도구 정의, 도구 결과가 함께 들어갑니다.

핵심은 “많이 넣으면 안전하다”가 아닙니다. 긴 작업에서 무엇을 남기고, 무엇을 요약하고, 다음 턴에 어떤 상태를 전달할지 정하는 법을 배웁니다.

## 한 줄 정의

컨텍스트 윈도는 모델이 응답을 만들 때 참조할 수 있는 유한한 작업 메모리입니다.

메모리 관리는 그 창 안에 목표, 제약, 근거, 도구 결과를 너무 크게 쌓지 않고 계속 회복 가능한 상태로 정리하는 일입니다. 이 관리는 Context Engineering의 핵심 실무가 됩니다.

## 쉬운 비유

작업 책상을 떠올려보세요. 책상 위에는 오늘 처리할 문서, 메모, 도구만 올라와 있어야 합니다. 모든 서류철을 다 펼쳐 놓으면 자료가 많아진 것처럼 보이지만, 정작 필요한 종이를 찾기 어려워집니다.

컨텍스트 윈도도 비슷합니다. AI가 볼 수 있는 책상은 넓이가 정해져 있습니다. 오래된 대화, 실패 로그, 도구 결과가 계속 쌓이면 중요한 지시와 근거가 묻힐 수 있습니다. 다만 실제 책상과 달리, AI의 책상은 토큰이라는 글자 조각 단위로 채워진다는 점이 다릅니다.

## 왜 생겼는가

Context Engineering은 장기 실행 에이전트가 등장하면서 중요해졌습니다. 에이전트는 한 번 답하고 끝나는 것이 아니라, 도구를 호출하고 결과를 받아 다시 판단합니다. 이때 시스템 지시, 메시지, 도구 결과, 외부 데이터가 계속 컨텍스트에 누적됩니다.

Anthropic은 Context Engineering을 Prompt Engineering의 자연스러운 확장으로 설명합니다. 프롬프트 문장만 잘 쓰는 것으로는 긴 작업의 정보 상태를 안정적으로 유지하기 어렵기 때문입니다.

## 어떤 문제를 해결하는가

첫 번째 문제는 컨텍스트 창이 유한하다는 점입니다. Claude 문서는 컨텍스트 창을 모델이 응답을 만들 때 참조할 수 있는 작업 메모리로 설명합니다. 이 창에는 시스템 프롬프트, 메시지, 이미지, 문서, 도구 정의, 도구 결과가 모두 들어갈 수 있습니다.

두 번째 문제는 context rot입니다. Anthropic은 토큰 수가 늘어날수록 정확도와 회상이 떨어질 수 있다고 설명합니다. 따라서 긴 대화를 계속 붙이는 방식은 안전장치가 아니라, 중요한 신호를 흐리게 만드는 원인이 될 수 있습니다.

## 핵심 개념

첫째, 컨텍스트는 모델이 샘플링할 때 포함되는 토큰 집합입니다. 토큰은 AI가 처리하는 글자 조각 단위입니다. 시스템 지시, 이전 메시지, 파일 내용, 도구 결과가 모두 이 예산을 사용합니다.

둘째, 도구 정의도 컨텍스트를 차지합니다. Claude Agent SDK 문서는 도구 정의, 대화 이력, 도구 입력과 출력, 스킬 설명이 컨텍스트를 소비한다고 설명합니다. 그래서 도구를 많이 붙이는 것만으로 좋은 에이전트가 되는 것은 아닙니다.

셋째, context rot은 “컨텍스트가 길수록 좋다”는 오해를 깨뜨립니다. 많은 정보가 들어가면 모델이 더 많이 볼 수는 있지만, 중요한 내용을 더 잘 떠올린다는 뜻은 아닙니다.

넷째, compaction은 긴 대화와 결과를 핵심 상태로 압축하는 방법입니다. 오래된 로그 전문을 계속 남기기보다 현재 목표, 확인된 근거, 실패한 시도, 다음 행동을 짧게 남깁니다.

다섯째, 상태 산출물은 다음 턴에서 회복해야 할 작업 상태입니다. 예를 들어 현재 목표, 수정한 파일, 테스트 결과, 남은 위험을 별도 상태로 남기면 긴 세션에서도 방향을 잃기 어렵습니다.

여섯째, context editing은 컨텍스트 안에서 어떤 내용을 유지하고 어떤 내용을 줄일지 조정하는 일입니다. KB는 긴 세션에서 compaction, context editing, 상태 산출물이 필요하다고 설명합니다. 즉 메모리 관리는 저장이 아니라 편집에 가깝습니다.

## 실제 예시

버그 수정 세션을 생각해봅시다. 처음에는 오류 로그 한 개만 보고 시작합니다. 하지만 작업이 길어지면 읽은 파일, 실행한 테스트, 실패한 수정, 새로 발견한 제약이 계속 생깁니다.

이때 모든 로그를 다시 붙이면 컨텍스트가 커집니다. 대신 “현재 목표는 검색 오류 수정, 확인한 원인은 빈 결과 처리 누락, 실패한 시도는 API 수정, 다음 행동은 UI 빈 상태 테스트”처럼 상태를 요약하면 다음 판단에 필요한 정보만 남습니다.

또 다른 예시는 도구가 많은 에이전트입니다. 지금 필요한 일이 파일 읽기라면 모든 외부 서비스 도구를 함께 노출할 필요가 없습니다. 도구 설명 자체도 컨텍스트를 차지하므로, 현재 작업과 직접 관련 있는 도구만 남기는 편이 신호를 더 선명하게 만듭니다.

## 코드 예시

아래 코드는 긴 작업의 컨텍스트를 작은 상태로 압축하는 예시입니다.

```ts
type WorkMemory = {
  goal: string
  confirmed: string[]
  failedAttempts: string[]
  nextAction: string
}

const memory: WorkMemory = {
  goal: "검색 빈 결과 화면을 안정화합니다",
  confirmed: ["검색 결과가 없을 때 빈 배열이 반환됩니다"],
  failedAttempts: ["API 응답 구조를 바꿨지만 UI 문제는 남았습니다"],
  nextAction: "UI 컴포넌트의 빈 상태 분기를 확인합니다",
}

console.log(`${memory.goal}: ${memory.nextAction}`)
```

## AI 시대에서의 의미

바이브코딩에서 컨텍스트 윈도 관리는 AI에게 더 길게 말하는 기술이 아닙니다. AI가 지금 판단해야 하는 목표와 근거를 작게 유지하는 기술입니다.

긴 리팩터링, 테스트 수정, 문서 작성에서는 대화가 빠르게 길어집니다. 좋은 작업자는 AI에게 모든 것을 다시 읽히려 하지 않고, 회복 가능한 상태와 체크리스트를 남겨 다음 턴의 판단 비용을 줄입니다.

## 자주 헷갈리는 것

컨텍스트 창은 영구 기억이 아닙니다. 모델이 현재 응답을 만들 때 참조하는 작업 메모리에 가깝습니다.

컨텍스트를 크게 쓰는 것이 항상 품질을 높이지도 않습니다. KB는 context rot을 설명하며, 토큰이 늘수록 정확도와 회상이 떨어질 수 있다고 말합니다.

메모리 관리는 대화 전체를 보존하는 일이 아닙니다. 필요한 신호를 남기고 오래된 내용은 요약하는 일입니다.

## 실무에서 쓰는 방식

실무에서는 긴 세션마다 작은 상태 문서를 유지합니다. 현재 목표, 제약, 확인된 근거, 실패한 시도, 다음 행동을 적고 오래된 로그는 요약합니다.

도구가 많은 에이전트에서는 현재 작업에 필요한 도구만 노출합니다. 도구 정의와 도구 결과도 컨텍스트를 차지하므로, 작업과 무관한 도구 설명을 계속 넣지 않는 것이 좋습니다.

RAG 기반 교재 사이트에서도 같은 원리가 적용됩니다. 검색 결과를 그대로 붙이는 대신 출처, 핵심 주장, 사용할 섹션을 분리해 전달하면 모델이 판단해야 할 재료가 작고 명확해집니다.

## 공부 체크리스트

- 컨텍스트 윈도를 유한한 작업 메모리라고 설명할 수 있다.
- 시스템 프롬프트, 메시지, 문서, 도구 결과가 모두 컨텍스트를 차지한다는 점을 말할 수 있다.
- context rot 때문에 많은 정보가 항상 좋은 것은 아니라고 설명할 수 있다.
- compaction과 상태 산출물이 긴 AI 작업에 필요한 이유를 예로 들 수 있다.
