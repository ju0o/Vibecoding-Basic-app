## 1. 제품 배경

### 1.1 현재 (코드에서 확인된 사실)

`AI_VIBE_CODING_MASTER`는 비개발자를 대상으로 AI·바이브코딩의 **원리**를 가르치는 정적 교재 사이트다.

| 축 | 현재 |
|---|---|
| 성격 | 단방향 교재. 저자가 쓰고 학습자가 읽는다. |
| 규모 | 52개 라우트, 13모듈 커리큘럼, 용어사전, Atlas 개념 지식베이스, 실습·평가 자료 |
| 기술 | Next.js 16 App Router + `output: "export"` 정적 내보내기 → Firebase Hosting (`ju0o-ec967`) |
| 상태 저장 | 전부 브라우저 localStorage (진행률·체크리스트·북마크·Atlas 진행률) |
| 검색 | 빌드타임 생성 정적 인덱스, 클라이언트 스코어링 |
| 백엔드 | **없음.** Firebase는 Hosting만 사용. 인증·DB·Storage·Functions 전부 미도입 |
| 사용자 | 익명. 계정 개념이 존재하지 않음 |
| 콘텐츠 생산 | 저자 1인 + ai-ops 파이프라인. 학습자는 기여 경로가 없음 |

### 1.2 문제 정의

현재 구조에서 확인되는 구조적 한계 4가지:

| # | 문제 | 근거 |
|---|---|---|
| P-1 | **학습이 개인 기기에 갇힌다** | 진행률·북마크가 localStorage 전용이므로 기기를 바꾸면 소실되고, 학습 이력이 사용자에게 귀속되지 않는다 |
| P-2 | **지식이 한 방향으로만 흐른다** | 학습자가 겪은 오류·해결·산출물·도구 후기가 사이트에 축적되지 않는다. 같은 문제를 각자 혼자 푼다 |
| P-3 | **콘텐츠 생산이 저자 1인에 병목된다** | 강의·용어·Atlas 전부 레포지토리 커밋으로만 갱신된다. AI 도구 생태계의 변화 속도를 1인이 따라갈 수 없다 |
| P-4 | **학습자 사이에 연결이 없다** | 구피티 오프라인 모임, 프로젝트 협업, 질문·답변이 사이트 밖(카톡·디스코드 등)에서 흩어진다 |

### 1.3 그런데 지금 잘 되고 있는 것

전환에서 **훼손하면 안 되는 것**을 먼저 못박는다.

- 검증된 출처 기반 서술과 인용 정책 (`/verification`, `scripts/scan-citations.mjs`, ai-ops 파이프라인)
- 원리 중심·설명 가능성 중심의 교육 톤
- 정적 사이트의 속도·안정성·거의 0에 가까운 운영 비용
- 52개 라우트의 SEO 자산과 URL 안정성

## 2. 제품 비전

> **AI와 바이브코딩을 배우고, 찾고, 공유하고, 함께 만드는 지식 커뮤니티**

한 문장으로 다시 쓰면:

> **검증된 공식 교재를 중심(core)에 두고, 그 주위에 학습자의 실전 경험이 쌓이며, 좋은 경험이 다시 교재로 승격되는 순환 구조.**

이 비전에서 가장 중요한 단어는 **"중심"**이다. 커뮤니티는 교재를 대체하지 않고 교재를 **둘러싼다.**

## 5. 핵심 사용자 시나리오

### S-1. 막힌 입문자가 답을 얻는다
비회원 A가 검색으로 `/learn/vibe-coding-foundation/errors-to-ai` 유입 → 강의 하단 "이 강의 관련 커뮤니티 글"에서 같은 오류를 겪은 글 발견 → 해결 → 자기도 질문하려고 가입 → 승인 대기 → 승인 후 질문 작성 → 24시간 내 댓글 도착 → 알림 확인.

### S-2. 학습자가 만든 것을 공유한다
회원 B가 첫 결과물 완성 → `오늘 만든 것`에 스크린샷과 함께 글 작성 → 좋아요·댓글 → 다른 회원이 프로젝트 모집 글로 연결 제안.

### S-3. 노하우가 교재로 승격된다
회원 C가 프롬프트 템플릿 모음을 교육자료로 등록 → `pending_review` → 운영자 검토 → `community` 게시 → 좋아요 누적 + 신고 0 → 운영자가 `official` 승격(저자 동의 확인) → 이후 레포지토리 강의에 반영, 기여자 표기.

### S-4. 운영자가 하루 10분으로 운영한다
운영자가 `/admin` 접속 → 승인 대기 3명 확인·승인 → 검토 대기 자료 2건 처리 → 신고 1건 확인 후 게시글 숨김 → 모든 조치가 `adminLogs`에 자동 기록.

### S-5. 오프라인 모임이 사이트로 모인다
운영자가 `구피티 모임`에 공지 → 회원들이 댓글로 참석 표명 → 모임 후 참석자가 후기 글 작성 → 다음 모임 공지에서 후기 링크.

### S-6. 잘못된 정보가 걸러진다
회원이 오래된 도구 후기를 발견 → 신고(`wrong_info`) → 운영자가 검토 → 원저자에게 `needs_revision` 통보 → 수정 또는 `archived`.

## 6. 제품 원칙 (충돌 시 판단 기준)

### 원칙 1 — 공식 지식층은 커뮤니티와 같은 취급을 받지 않는다
기존 강의·용어·Atlas·커리큘럼·실습·평가는 **레포지토리 관리 콘텐츠**다. 회원이 직접 편집할 수 없고, 변경 경로는 git 커밋 + 기존 ai-ops 파이프라인뿐이다. 회원은 **제안**만 할 수 있다.
→ 상세: [07 콘텐츠 거버넌스](./07-CONTENT-GOVERNANCE-SSOT.md) 3절

### 원칙 2 — 읽기는 열고, 쓰기는 승인한다
비회원과 승인 대기자도 공개 콘텐츠를 전부 읽을 수 있다. 쓰기 활동만 관리자 승인 이후 열린다. 이 비대칭이 SEO 자산과 커뮤니티 품질을 동시에 지킨다.

### 원칙 3 — UI 숨김은 보안이 아니다
모든 권한은 **Firestore Security Rules 또는 Cloud Functions에서 강제**된다. 클라이언트 가드는 사용성을 위한 것일 뿐 방어선이 아니다. 정적 export 사이트이므로 클라이언트 코드는 전부 공개물이라는 전제로 설계한다.
→ 상세: [06 보안·운영](./06-SECURITY-AND-MODERATION-SSOT.md)

### 원칙 4 — 승격은 있고 자동 승격은 없다
회원 자료는 절대 자동으로 공식 자료가 되지 않는다. 좋아요가 아무리 많아도 사람의 판단이 개입한다.

### 원칙 5 — 운영 부하를 설계 제약으로 취급한다
운영자가 1인이라는 사실은 제약이 아니라 요구사항이다. 관리자 화면은 "목록 → 한 번의 클릭 → 로그 자동 기록"으로 끝나야 한다. 검토가 필요한 흐름을 늘릴 때마다 운영 부하를 함께 계산한다.

### 원칙 6 — 기존 것을 부수지 않는다
`next.config.ts`의 `output: "export"`, 52개 라우트 경로, 기존 테스트, localStorage 진행률은 V1에서 **변경하지 않는다.** 커뮤니티는 추가되는 층이지 대체하는 층이 아니다.

### 원칙 7 — 출처와 검증 문화를 커뮤니티로 확장한다
이 교재의 정체성은 "검증된 출처"다. 회원 자료에도 출처 표기 규칙, AI 생성물 표기 의무, 인용 길이 제한을 적용한다.
